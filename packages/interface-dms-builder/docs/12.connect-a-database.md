## Overview

A connect flow, such as dms-assistant's **Start from an existing database**, drives these operations. They are served wherever the builder is, in development or under `builder.enabled`, and `CheckDatabaseConnection` answers in development only.

| Operation | Answers |
| --- | --- |
| `ListDatabaseConnections()` | Each catalog connection as `{ id, engine?, version?, database?, role?, error? }`: what its provider's `Info()` answers, or why it did not. |
| `CheckDatabaseConnection({ engine, url })` | `{ reachable, latencyMs?, user?, canRead, canWrite, reason? }`. See [Check a connection before writing it](#check-a-connection-before-writing-it). |
| `GetDatabaseProject()` | `{ modules, self, ownDatabase?, databasePins, dmsDatabase?, interfaceDatabase?, drivers }`. See [What connecting a database writes](#what-connecting-a-database-writes). |
| `ConfigureProject(steps, { variables })` | As `ConfigureProject`, with the variables' development values written to `.env` first. See [Development values](#development-values). |
| `RepairDatabaseConnections({ dryRun? })` | The configuration change, or a success with no file when nothing is missing. See [Repair a connection made before](#repair-a-connection-made-before). |
| `GetDatabaseConnection(connection)` | `{ wiring, details? }`: the driver, the tables modules and the variables wired for the connection, and its URL's parts without the password. `not_found` when no module declares it. |
| `SetDatabaseConnectionUrl(connection, url)` | `{ variable }`, the variable the URL was written to. A URL with no password keeps the current one. |
| `RemoveDatabaseConnection(connection, { dryRun? })` | The configuration change. See [Remove a connection](./11.external-databases.md#remove-a-connection). |
| `GetLatestAnalysis(connection)` | The connection's running analysis, or else the last to finish. `not_found` when none ran since the start. |
| `SampleDatabaseRows(connection, { relation, columns?, limit })` | The rows the provider's `SampleRows` answers. `not_found` for an unknown connection, and `invalid_config` with the provider's message when it refuses. |

## Check a connection before writing it

`CheckDatabaseConnection` tests a database before anything is written to `antelope.config.ts` or `.env`. The driver module is not configured at that point, so the builder opens the database itself with the engine's client library: `pg`, `mysql2`, `mongodb` or `rethinkdb-ts`. They are optional peer dependencies of `@antelopejs/dms`, required only when their engine is checked, first from the DMS and then from the project. When neither installs the client, the answer is `reachable: false` with a `reason` such as `Install pg to connect a PostgreSQL database.`

`DATABASE_ENGINE_SCHEMES` lists the engines the check takes, each with the URL schemes it accepts, such as `["postgres:", "postgresql:"]` for `postgres`. A form that offers engines can compare its own list with it.

Outside development the call fails with `unsupported` and opens nothing, since it connects to a host the caller names. An `engine` other than `postgres`, `mysql`, `mongodb` or `rethinkdb`, or a `url` whose scheme is not that engine's, fails with `invalid_config`, naming the fields and never their values.

The answer reads as follows:

- `reachable` is `true` when a server answered, even to refuse the sign-in. `latencyMs` is the round trip of the first query of the signed-in account, and `user` is the account the server reports.
- `canWrite` is `true` when the account may insert, update or delete in any relation it can see, as the catalog of the engine's driver decides. `canRead` is `true` when it may read any of them, or when it sees none. A MongoDB server without access control gives full privileges, whatever the database holds.
- `reason` is a short sentence for the person who connects, present when the database is unreachable, refuses the sign-in or cannot be read. It never holds the URL, the password or a query a driver echoes in its message.

`mysql` checks MySQL and MariaDB alike, with `mysql://` URLs, and reads the account's privileges as `@antelopejs/mysql` does: a grant on some columns of a relation only does not make it readable. A MySQL, MariaDB or RethinkDB URL with no database after the port is answered once the account has signed in, with `reachable: true`, `user`, no access and a `reason` saying the URL names no database.

The check ends within three times the connect timeout of five seconds, and closes every connection it opened, whether the database answers or the deadline passes first. It never waits for a server to close its end before it answers, and it shuts a socket still open a quarter of a second after its goodbye. For RethinkDB it deletes a key no row has to learn whether the account may write, so it changes no row.

## What connecting a database writes

A connect flow plans one `ConfigureProject` batch from `GetDatabaseProject()`. Its answer names `self`, the DMS's id in `antelope.config.ts`, `ownDatabase`, the project's default `interface-database` provider, `databasePins`, the modules to pin to it, and `dmsDatabase`, the id of the `dms-database` entry. `ownDatabase` and `dmsDatabase` are absent when the project has no such database or module. `interfaceDatabase` is the version of `@antelopejs/interface-database` core resolves for the project, and `drivers` gives each engine's driver package with a range of only its releases built for that version, such as `>=0.2.5 <0.4.0` for `@antelopejs/postgres` on 0.3.4. A range never reaches a release built for another line of the interface, which the project could not start with. An engine with no driver built for that version is absent from `drivers`.

`GetDatabaseProject` fails with `invalid_config` when the configuration does not say plainly which database is the default, or when a module that imports `interface-database` without providing it, or `dms-database` itself, is written as a version string or with a spread or a member under a computed name, so the builder cannot write its pin. An entry with a spread that pins `interface-database` in an `importOverrides` written after its last spread counts as pinned, since a later key wins.

The batch writes these steps in order:

1. `AddModule` for the engine's driver, at the package and range `drivers` gives, with its URL read from a variable.
2. `CreateLocalModule` for the module that holds the tables, pinned to the driver.
3. `ConfigureModule` on `self`, declaring the catalog connection under the connection's id.
4. `ConfigureModule` on `dms-database`, when the project has it and an own database. For a connection `erp` served by the driver `builder-db-erp` over a project whose own database is `mongodb`, the entry then reads:

   ```typescript
   const modules = {
     "dms-database": {
       importOverrides: [
         { interface: "@antelopejs/interface-database", source: "mongodb" },
         { interface: "@antelopejs/interface-database", source: "builder-db-erp", id: "erp" },
         { interface: "@antelopejs/interface-database-catalog", source: "builder-db-erp", id: "erp" },
       ],
       config: { externalConnections: { erp: { access: "read" } } },
     },
   };
   ```

   The first `interface-database` entry without an id is the binding a plain import reaches, so the own database comes first. The connection keeps one id on both interfaces and in `externalConnections`.
5. One `ConfigureModule` for each module in `databasePins`. Once a second `interface-database` provider exists, core refuses to start a module that imports `interface-database` without a pin, so each one that does not provide it gets a pin to the own database.

`ConfigureModule` writes an override without an id ahead of the first named connection of its interface, and merges a nested `config` object key by key, so the connections already registered with `dms-database` stay. It replaces a scalar or an array held where it writes an object. It refuses the step, naming the module and the key path, where that value is an object with a spread, a variable or a call, or where the object it writes into holds a member under a computed name, a method or an accessor, since that member may be the key it writes.

## Development values

`ConfigureProject(steps, { variables: [{ name, value }] })` writes each variable's development value into the project's `.env`, once a dry run has accepted the steps, then writes the configuration. Each variable must be one the steps map in their `env`. When `.env` refuses one, nothing is written, and when the configuration then fails, `.env` goes back to what it held. `.env` must be ignored by git. With `dryRun`, the variables are not written.

## Repair a connection made before

A project connected before the steps above has the catalog connection and nothing `dms-database` reads. `RepairDatabaseConnections()` adds what is missing for every catalog connection declared on the DMS's entry. It writes the `dms-database` overrides and the pins of step 5, and never `access`, so a value set in the `dms-database` console is kept. With `{ dryRun: true }` it answers the changes without writing them. It refuses as `GetDatabaseProject` does.

A configuration that already holds everything answers `{ ok: true, data: { files: [] }, changes: [] }` and is not written, so a second call changes nothing.
