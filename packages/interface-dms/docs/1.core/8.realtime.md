# Realtime

## Overview

Realtime works on topics. A topic is a plain string a page declares interest in, and any backend code can publish a message on it. `RegisterPageTopic` binds a topic to a page id; `PublishMessage` sends an event on that topic to every client currently subscribed to it. `SubscribeMessage` is the read half: it lets backend code receive what is published, instead of only feeding the dashboard's own streams.

Everything on this page lives in `@antelopejs/interface-dms/realtime`.

## How a Page Ends Up Subscribed

Subscription is derived, not requested by the publisher:

1. A page — or a component on it — calls `RegisterPageTopic(pageId, topic)` at registration time. `pageId` is the page's `fullId` ([Pages and Modules](/docs/interfaces/core/pages-and-modules)), not its slug.
2. A client opens a realtime session and reports which page it is on. The backend checks that the user may access that page, then subscribes the session to every topic registered for that page id, and drops the topics that are no longer wanted.
3. `PublishMessage(topic, type)` delivers to the sessions currently subscribed to `topic` — with a `tenantId`, only to those of that tenant (see [Tenant-scoped messages](#tenant-scoped-messages)).

So a publisher never addresses a page or a user. It addresses a topic, and the page-topic registry decides who is listening.

Registering the same topic for the same page twice is harmless — a page's topics are a set.

A binding belongs to the module that registered it: it is removed when that module is unloaded, and it survives a reload of the DMS module, which gets every binding back from the core. Registering from `onCreated`, as below, makes the module whose page it is that owner.

## Register a Topic for a Page

The typical caller is a component builder's `onCreated` callback. It receives the page the component was declared on, typed `CreatedPage` (its `target` and its `pageInfo.fullId` and `fullSlug`); at run time that is the page's `PageMetadata` ([Components](/docs/interfaces/core/components)):

```typescript
import { ComponentBuilder } from "@antelopejs/interface-dms/component";
import { RegisterPageTopic } from "@antelopejs/interface-dms/realtime";

export const STOCK_TOPIC = "catalog:stock";

export function StockCounter(options: { fetchUrl: string }) {
  return new ComponentBuilder<{ fetchUrl: string }>("acme-stock-counter")
    .options(options)
    .onCreated((page) => {
      const pageInfo = page.pageInfo;
      if (!pageInfo) return;
      RegisterPageTopic(pageInfo.fullId, STOCK_TOPIC);
    });
}
```

Registering from `onCreated` is what makes the binding follow the component: whichever page the component is placed on gets the topic. The chart builders of the [Base](/docs/interfaces/base/introduction) domain do exactly this — a chart declaring `realtimeTopic` registers each of its topics on the page it is placed on.

To bind a topic to a page you know statically, call `RegisterPageTopic` with that page's `fullId` directly.

```typescript fragment
RegisterPageTopic(pageId: string, topic: string): void
```

## Publish a Message

```typescript fragment
import { Controller, Post } from "@antelopejs/interface-api";
import { PublishMessage } from "@antelopejs/interface-dms/realtime";
import { STOCK_TOPIC } from "../components/stock-counter";

export class StockController extends Controller("/api/stock") {
  @Post("/restock")
  async restock(): Promise<{ ok: boolean }> {
    await applyRestock();
    await PublishMessage(STOCK_TOPIC, "stock.updated", {
      payload: { warehouse: "eu-west" },
      actorId: "system",
    });
    return { ok: true };
  }
}
```

```typescript fragment
PublishMessage(
  topic: string,
  type: string,
  options?: PublishMessageOptions,
): Promise<void>
```

| Parameter | Description |
| --------- | ----------- |
| `topic` | The topic to publish on. Subscribers are the sessions on a page that registered this topic. |
| `type` | The event type carried with the message, for subscribers that distinguish several kinds of event on one topic. |
| `options` | Optional payload, actor and tenant. |

### `PublishMessageOptions`

| Option | Type | Description |
| ------ | ---- | ----------- |
| `payload` | `Record<string, unknown>` | Data carried with the event. |
| `actorId` | `string` | Identifies who caused the event, so a client can ignore an event it triggered itself. |
| `tenantId` | `string` | The tenant the event is about: only the sessions of that tenant receive it. Omitted, the message is global and reaches every tenant. |

`PublishMessage` resolves once the message has been handed to the broker. It does not report how many sessions received it, and publishing on a topic no page registered is not an error — it simply reaches nobody.

### Tenant-scoped messages

Page topics are shared by every tenant: a page registers the same topic whichever workspace views it. A message published without a `tenantId` therefore reaches the sessions of **every** workspace on that page — each one refetches, and a paused live page counts the message in its "N new" banner. Publish a workspace's data with the tenant it belongs to:

```typescript fragment
import { getRequestTenantId } from "@antelopejs/interface-dms/request-tenant";

await PublishMessage(CAMPAIGN_TOPIC, "campaign.sent", {
  payload: { count: sent.length },
  tenantId: getRequestTenantId(ctx), // or the tenant a job runs for
});
```

A session is bound to the tenant of the request that opened it, and receives the messages of that tenant plus the global ones. When the browser switches workspace (or account), the client opens a new session in the new one, and the server ends a session whose page requests come from a workspace or account other than its own, so the previous workspace's messages stop with it. A session on the connection a browser's tabs share is ended alone: the other tabs' sessions on it stay. Keep messages without a tenant for what is the same for every workspace: a platform-wide setting, a catalogue shared by all tenants.

A session on a platform page (a page of a module, which only the platform owner opens) receives the messages of **every** tenant on that page's topics, whichever workspace the owner has open: such a page lists the data of all of them.

The table views of the [Base](/docs/interfaces/base/tables#realtime) domain publish their row changes and presence for the writer's tenant, or for every tenant when their rows live in the shared schema. Messages to one user (notifications) and the menu invalidations already name their audience in the topic.

## Subscribe from the Backend

`SubscribeMessage` receives every message published on a topic, whichever instance and whichever tenant published it (a handler serving one tenant filters on `message.tenantId` itself): the subscription rides the same broker as `PublishMessage`, so what one instance publishes reaches subscribers on every other.

```typescript fragment
import { SubscribeMessage } from "@antelopejs/interface-dms/realtime";
import { STOCK_TOPIC } from "../components/stock-counter";

const unsubscribe = SubscribeMessage(STOCK_TOPIC, (message) => {
  if (message.type !== "stock.updated") return;
  const warehouse = message.payload?.warehouse;
  if (typeof warehouse === "string") {
    void refreshWarehouseCache(warehouse);
  }
});
```

```typescript fragment
function SubscribeMessage(
  topic: string,
  handler: RealtimeMessageHandler,
): UnsubscribeMessage;

type RealtimeMessageHandler = (message: RealtimeMessage) => void;
type UnsubscribeMessage = () => void;
```

### `RealtimeMessage`

| Field | Type | Description |
| ----- | ---- | ----------- |
| `topic` | `string` | Topic the message was published on. |
| `type` | `string` | Event type given to `PublishMessage`. |
| `payload` | `Record<string, unknown>` | Data carried with the event, when the publisher sent any. |
| `actorId` | `string` | Who caused the event, when the publisher named an actor. |
| `tenantId` | `string` | The tenant the message was published for; absent on a global message. |
| `ts` | `number` | Publication timestamp. |

Paired with `PublishMessage`, this turns the DMS's broker into one a module can use for realtime channels of its own — its own endpoint subscribes here and the DMS carries the messages — instead of bringing a second broker to do the same job.

Three properties to design around:

- **Handlers must not throw.** They are called on the delivering instance's event loop, and nothing catches for you.
- **Delivery is fire-and-forget.** There is no replay: a message published while nobody was subscribed is gone. Do not use a topic as a queue.
- **Unsubscribing is automatic** when the registering module is unloaded. The returned `UnsubscribeMessage` is for ending a subscription earlier than that; calling it twice is a no-op.
