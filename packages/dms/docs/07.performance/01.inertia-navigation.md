# Inertia navigation performance gate

Run the browser gate against a built DMS frontend and its backend. The browser profile must already have an authenticated DMS session; an auth redirect is not a valid navigation scenario.

```bash
pnpm performance:inertia-navigation
```

The default scenario navigates from `/form/form-simple` to `/form/form-advanced` on `http://127.0.0.1:3001` and performs seven full source-page resets followed by an Inertia navigation. Override both values when the deployment uses another origin or when measuring another stable route pair:

```bash
DMS_PERF_SOURCE_URL=http://127.0.0.1:3001/dashboard \
DMS_PERF_TARGET_SELECTOR='a[href="/settings"]' \
DMS_PERF_BROWSER_STATE=/tmp/dms-auth-state.json \
DMS_PERF_OUTPUT=.amp/in/artifacts/inertia-navigation.json \
pnpm performance:inertia-navigation
```

Create the optional auth state once with `agent-browser state save /tmp/dms-auth-state.json` after signing in. The output records only that a state was provided, never its path or contents.

The runner uses the installed `agent-browser` Chromium tooling and listens for `inertia:finish`, including the next animation frame in the timing. Each run starts a HAR immediately before a direct click, without intentionally triggering hover prefetch. Only requests carrying the `X-Inertia` request header contribute to deterministic network budgets.

## Budgets

| Metric | Budget | Purpose |
| --- | ---: | --- |
| Median Inertia response payload | 75,000 bytes | Prevent oversized page props |
| Median Inertia request count | 3 | Prevent navigation request waterfalls while allowing redirects/retries |
| Median click-to-post-render duration | 1,500 ms | Actionable local/CI regression threshold with headroom for shared runners |

Seven samples and the median limit host jitter without putting flaky wall-clock assertions in unit tests. Payload and request count remain the primary deterministic gates. The JSON output contains the exact scenario, budgets, every raw sample, medians, pass/fail result, and any setup error. Keep the output as a CI artifact when investigating a miss.

A network miss usually indicates duplicated Inertia visits or excessive shared/page props. A timing-only miss should be reproduced before changing code, then diagnosed with a browser trace; do not loosen the deterministic budgets to hide it.
