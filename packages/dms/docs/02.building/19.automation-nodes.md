When [`@antelopejs/dms-automation`](/docs/modules/automation/introduction) is loaded, the DMS registers its own nodes in the procedure builder: the triggers below, which fire on its events, and the actions further down. Every input of an action is a port. Set it in the inspector, or wire it from a trigger's output or a data node.

## Triggers

Every trigger fires on the instance that made the change (`replicated`). A change made on another instance fires there. Each output carries `at`, the ISO date of the event, and every trigger that can fire twice for one event carries a `deliveryId`: wire it into an `idempotencyKey` input so a replay acts once.

| Trigger                    | Fires when                                                                                     | Settings                                                    | Outputs, besides `at`                                                                                                                                                                                 |
| -------------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dms.member-added`         | A user becomes a member of a workspace                                                         | `includeAutomationWrites`                                   | `tenantId`, `userId`, `isTenantOwner`, `deliveryId`, `originProcedureId`, `originRunId`                                                                                                                                                   |
| `dms.member-removed`       | Members are removed from a workspace                                                           | `includeAutomationWrites`                                   | `tenantId`, `userIds`, `originProcedureId`, `originRunId`                                                                                                                                             |
| `dms.member-roles-changed` | A member's roles, or their owner flag, change                                                  | `tenantId`, `includeOwnership` (`true`), `includeAutomationWrites` | `tenantId`, `userId`, `roleIds`, `previousRoleIds`, `addedRoleIds`, `removedRoleIds`, `isTenantOwner`, `previousIsTenantOwner`, `origin`, `actorId`, `deliveryId`, `originProcedureId`, `originRunId` |
| `dms.invite-created`       | An invitation is created                                                                       | `includeAutomationWrites`                                   | `tenantId`, `inviteId`, `email`, `asTenantOwner`, `roleIds`, `deliveryId`, `originProcedureId`, `originRunId`                                                                                                                             |
| `dms.invite-resolved`      | An invitation is accepted, cancelled, expired, replaced or resent                              | `reasons`, `tenantId`, `includeAutomationWrites`            | `tenantId`, `inviteId`, `email`, `reason`, `deliveryId`, `originProcedureId`, `originRunId`                                                                                                           |
| `dms.user-registered`      | A user completes signup                                                                        | none                                                        | `tenantId`, `userId`, `email`, `name`                                                                                                                                                                 |
| `dms.user-deleted`         | A user account is deleted, after the DMS removed what it keeps about them                      | none                                                        | `userId`, `email`, `tenantIds`, `reason` (`self`), `deliveryId`. No `tenantId`: the event belongs to no workspace                                                                                     |
| `dms.tenant-created`       | A workspace is provisioned                                                                     | none                                                        | `tenantId`, `name`, `userId`, `isDefault`, `deliveryId`                                                                                                                                               |
| `dms.tenant-deleted`       | A workspace is deleted                                                                         | none                                                        | `tenantId`, `name`, `ownerUserId`, `ownerUserIds`, `ownerEmail`, `operationId`, `deliveryId`                                                                                                          |
| `dms.record-created`, `dms.record-updated`, `dms.record-deleted` | Rows of a TableView-backed table are written through its routes | `location`, `tenantId`                                    | `tenantId`, `location`, `ids`, `deliveryId`, `actorId`, `actorName`                                                                                                                                   |

A `tenantId` setting fires the trigger for that workspace only. Left empty, it fires for every workspace.

### Record triggers

`location` is the data controller location, such as `/api/tables/leads`, matched exactly. The `tenantId` output is the workspace the write was made in. It is absent for a table of the schema every workspace shares (`CORE_SCHEMA_NAME`), and such a write never matches a `tenantId` setting. Each write has its own `deliveryId`.

### `dms.invite-resolved`

`reason` is `accepted`, `cancelled`, `replaced`, `expired` or `resent`. `resent` and `replaced` reissue the invitation rather than end it. Accepting it ends it too, and fires `dms.member-added` as well. `reasons` keeps only the listed ones; left empty, every reason fires. `deliveryId` is the resolution's identity, the same when a resumed resolution fires again. The payloads other modules attached to the invitation are not part of the output.

### `dms.member-roles-changed`

One event per member per write, carrying both a roles change and an owner flag change made together. `origin` names where the change was made: `member-edit` (the members table), `ownership` (the owner action of the members page), `role-deleted` (a role deleted with its holders moved), or `automation` (`dms.set-member-roles`). `actorId` is the signed-in user who made it, absent for `automation`. With `includeOwnership` off, a change of the owner flag alone does not fire.

A member's roles changed elsewhere do not fire it: an existing member re-granted through an invitation, or a membership written by another module.

### `dms.user-deleted`

Fires once per deletion. `userId` no longer exists when the run starts, so `dms.get-user` answers `found: false`. The run trace records `email`, the address of the deleted account.

### `dms.tenant-created`

Fires while the workspace is provisioned, from `Hook.TENANT_BEING_PROVISIONED`, after the provisioning handlers the modules registered at start. `userId` is the account the workspace is provisioned for, absent for the `default` workspace and for a workspace created for an invited owner. The `default` workspace's provisioning is retried after a failed attempt, so it can fire again with the same `deliveryId`, `tenant-created:<tenantId>`. A workspace whose provisioning fails afterwards is followed by `dms.tenant-deleted`; pair the two by `tenantId`.

### `dms.tenant-deleted`

Fires once the DMS deleted the workspace's members, invitations, roles and exports. `name` and the owners, oldest first, are read just before that cleanup; `ownerEmail` is the address of `ownerUserId`, and the run trace records it. `deliveryId` is the deletion's `operationId`, or `tenant-deleted:<tenantId>` when the deleting module passes none. A deletion that resumes after the cleanup fires again with the same `deliveryId` and no owners. Only a module that deletes workspaces, such as `dms-saas`, fires it.

### Changes made by procedures

A trigger that a procedure's own write can fire ignores those writes unless its `includeAutomationWrites` setting is on: `dms.member-added` and `dms.invite-created` (from `dms.invite-user`), `dms.member-removed` (from `dms.remove-member`), `dms.member-roles-changed` (from `dms.set-member-roles`) and `dms.invite-resolved` (from `dms.cancel-invite`, and from `dms.invite-user` when it replaces an invitation). A procedure therefore never triggers itself by default.

To react to members or invitations that `dms.invite-user` makes in another procedure, turn on the `includeAutomationWrites` setting of the **Member added** or **Invite created** trigger. With the setting on, the event carries the `originProcedureId` and `originRunId` of the procedure that made the change, so a graph can skip its own writes with an `if` node.

A circuit breaker stops loops that slip through, such as two procedures answering each other: past 5 procedure-made events for the same subject (a member, an invitation, a set of removed members) within 60 seconds, the DMS drops the next ones and logs a warning. Counts are per instance; the write and the trigger it fires run on the instance that ran the action.

## Actions

### `dms.send-notification`

Sends an in-app notification under the `AutomationSubject`, built as the [`Notification()` builder](/docs/building/backend-services#notifications) builds it.

| Input            | Type                                            | Notes                                                                                                                                   |
| ---------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `title`          | string, required                                | Literal text, or a `$` translation key resolved in each recipient's language                                                            |
| `description`    | string                                          | Same as `title`. Empty by default                                                                                                       |
| `params`         | object                                          | Interpolation params of both texts. Strings and numbers are kept, booleans read as their text, and nested values are dropped with a warning |
| `tone`           | `neutral` `primary` `success` `warning` `error` | Icon well colour. Unset reads `primary` while unread                                                                                    |
| `icon`, `linkTo` | string                                          | `i-ph-bell` by default, and the page the notification opens                                                                             |
| `userId`         | string                                          | One recipient, such as a trigger's `userId`                                                                                             |
| `userIds`        | string[]                                        | Recipients, combined with `userId`                                                                                                      |
| `roleIds`        | string[]                                        | Every member holding one of the roles                                                                                                   |
| `tenantId`       | string                                          | Restricts `roleIds` to that tenant's members (`toRoles(roleIds, { tenantId })`). Empty means the default tenant                         |
| `idempotencyKey` | string                                          | Stable event key, such as a trigger's `deliveryId`. A replay of the same event reaches each recipient once                              |

At least one of `userId`, `userIds` or `roleIds` is required. Otherwise the run fails with `dms.send-notification requires at least one of userId / userIds / roleIds`.

A procedure that welcomes each new member, with its texts in the project's locales, wires a **Member added** trigger (`dms.member-added`) to a **Send notification** node set as follows:

| Port             | Value                                                                                     |
| ---------------- | ----------------------------------------------------------------------------------------- |
| `userId`         | wired from the trigger's `userId`                                                         |
| `title`          | `$my_app.automation.welcome.title`                                                        |
| `description`    | `$my_app.automation.welcome.body`                                                         |
| `params`         | `{ "team": "Support" }`, set in the inspector or wired from a node that outputs an object |
| `tone`           | `success`                                                                                 |
| `linkTo`         | `/getting-started`                                                                        |
| `idempotencyKey` | wired from the trigger's `deliveryId`                                                     |

The keys live in the project's locale files like any other ([Localization](/docs/building/localization)):

```json [frontend-vue/i18n/locales/my-app-en-GB.json]
{
  "my_app": {
    "automation": {
      "welcome": {
        "title": "Welcome aboard",
        "body": "The {team} team is here to help."
      }
    }
  }
}
```

A notification node set up with a literal title and description, before these inputs existed, keeps working unchanged.

### `dms.send-email`

Sends an email through the project's `interface-email` provider ([Email templates and rendering](/docs/building/backend-services#email-templates-and-rendering)).

| Input      | Type             | Notes                                                                                        |
| ---------- | ---------------- | -------------------------------------------------------------------------------------------- |
| `to`       | string, required | Recipient address                                                                            |
| `subject`  | string, required | Subject line, sent as given                                                                  |
| `html`     | string           | The body, written out                                                                        |
| `template` | string           | Name of a template registered with `RegisterHtmlTemplate`, rendered instead of `html`        |
| `props`    | object           | Props the template is rendered with                                                          |
| `language` | string           | Language the template is rendered in. The recipient's own when the address belongs to a user |

One of `html` or `template` is required. A `template` that no module registered fails the run instead of sending an empty email. The output holds `success`, and `messageId` or `error`.

### `dms.invite-user`

Invites an address to a tenant, as the members page does. An existing user becomes a member directly. Anyone else receives an invitation, and its email unless `sendEmail` is `false`. An address that is already a member is left unchanged. The `dms.member-added` or `dms.invite-created` event it causes reaches only triggers whose `includeAutomationWrites` setting is on (see [Changes made by procedures](#changes-made-by-procedures)).

| Input                   | Type             | Notes                                                                            |
| ----------------------- | ---------------- | -------------------------------------------------------------------------------- |
| `email`                 | string, required | Address to invite                                                                |
| `tenantId`              | string           | Tenant to invite into. See [the `tenantId` input](#the-tenantid-input)            |
| `roleIds`               | string[]         | Roles of the new member                                                          |
| `asTenantOwner`         | boolean          | `false` by default                                                               |
| `sendEmail`             | boolean          | `true` by default                                                                |
| `language`              | string           | Language of the invitation email and of the account it leads to. `en` when empty |
| `firstname`, `lastname` | string           | The invitee's names, stored with the invitation and used in its greeting         |
| `inviterName`           | string           | Who the invitation email says it comes from                                      |

The output `kind` is `added`, `invited` or `already-member`, with the `userId` or the `inviteId`.

### `dms.get-user`

Reads a user by `userId` or by `email` (any letter case; `userId` wins when both are set), and their membership in `tenantId`. It reads every user, member of the workspace or not, so a procedure can reach a former member.

| Output                                                       | Notes                                                       |
| ------------------------------------------------------------ | ----------------------------------------------------------- |
| `found`                                                      | `false` when no user matches; the other outputs are then absent |
| `userId`, `email`, `name`, `language`, `timeZone`            | The user's profile                                          |
| `isValidated`, `isPlatformOwner`, `createdAt`, `lastActiveAt` | Account state                                               |
| `isMember`, `isTenantOwner`, `roleIds`                       | Membership in `tenantId`; `roleIds` is empty for a non-member |

It outputs these fields only: never the password, keys or two-factor data the user row holds. The run trace records the email and name.

### `dms.list-members`

Lists the members of `tenantId`, oldest first, `limit` at a time (50 by default, at most 200) from `offset`. `roleIds` keeps the members holding any of the roles, and `ownersOnly` the owners. The output `members` holds each member's `userId`, `email`, `name`, `language`, `roleIds`, `isTenantOwner` and `joinedAt`, with `total` across all pages and `hasMore`. An unknown `tenantId` fails the run. The run trace records the members' emails and names.

### `dms.get-tenant`

Reads a workspace: `name`, `isDefault`, `createdAt`, `updatedAt`, `memberCount`, its owners (`ownerUserIds`, oldest first, and `ownerUserId`), `closed` (deletion has started: member changes are refused) and `provisioningPending` (the `default` workspace's provisioning must be retried). An unknown or deleted workspace answers `found: false`, so a procedure fired by `dms.tenant-deleted` can branch. Plan and billing data of `dms-saas` are read with its own actions.

### `dms.set-member-roles`

Sets a member's roles and, optionally, their owner flag, with the checks of the members page: the workspace must accept member changes, `Hook.MEMBER_BEING_CHANGED` handlers (such as `dms-saas` seat limits) can refuse, the last owner cannot be demoted, and on the `default` workspace the platform owner flag follows the owner flag.

| Input           | Type             | Notes                                                                                          |
| --------------- | ---------------- | ---------------------------------------------------------------------------------------------- |
| `userId`        | string, required | The member, as triggers output it                                                              |
| `tenantId`      | string           | See [the `tenantId` input](#the-tenantid-input)                                                 |
| `roleIds`       | string[]         | Roles of the workspace. Unknown ids fail the run. Unset: roles unchanged                        |
| `mode`          | string           | `replace` (default) sets exactly `roleIds`, `add` and `remove` change the stored roles          |
| `isTenantOwner` | boolean          | Unset: owner flag unchanged                                                                    |

The output holds `changed`, `userId`, `roleIds`, `previousRoleIds`, `isTenantOwner` and `previousIsTenantOwner`. A user who is not a member fails the run. The member's menu refreshes; no in-app notification is sent, so add a `dms.send-notification` node to tell them. A change fires `dms.member-roles-changed` with `origin: automation` (see [Changes made by procedures](#changes-made-by-procedures)).

### `dms.cancel-invite`

Cancels a pending invitation of `tenantId`, as the Revoke action of the invitations page does. `inviteId` comes from `dms.invite-created`. The output `status` is `cancelled`, `already-resolved` (another decision ended it, named in `reason`; the run does not fail) or `not-found`, with `cancelled` and the invitee's `email`. A repeated call on a cancelled invitation finishes its cancellation and answers `cancelled` again.

### `dms.remove-member`

Removes `userId` from `tenantId` with the checks of the members page: the workspace and, outside SaaS mode, the platform keep an owner, a removed platform owner loses the flag, and `Hook.MEMBER_REMOVED` runs while the membership still exists. The output holds `removed` (`false` when the user was not a member, without failing), `userId` and `wasTenantOwner`. Unlike a removal on the members page, it notifies no owner, fires no `dms.record-deleted` and refreshes no open members table.

## The `tenantId` input

An action has no tenant of its own. The execution context carries none, whoever fires the procedure. A node that acts on tenant data therefore takes a `tenantId` input, which a procedure wires from its trigger. The member, invite and registration triggers output the `tenantId` of their event.

Left empty, a tenant-scoped node acts on the default tenant (`DEFAULT_TENANT_ID`, `"default"`, from `@antelopejs/interface-dms/constants`). A single-tenant project has only that tenant. `dms.invite-user` invites there, and `dms.send-notification` matches its `roleIds` there. In a multi-tenant project, wire the trigger's `tenantId` into every node that takes one. A `tenantId` naming no workspace fails `dms.list-members`, `dms.set-member-roles`, `dms.cancel-invite` and `dms.remove-member`; `dms.get-user` then reads no membership, and `dms.get-tenant` answers `found: false`.

## Test runs

The reads (`dms.get-user`, `dms.list-members`, `dms.get-tenant`) change nothing, so a test run executes them. The other actions declare `dryRun`. A **Test run** in the builder checks their input as a real run would, then sends, creates and changes nothing.

| Action                  | In a test run                                                                                                         | Output                                                                       |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `dms.send-email`        | Refuses a missing body or an unregistered template. Renders and sends nothing                                         | `{ success: true }`                                                          |
| `dms.send-notification` | Refuses a missing recipient, an unknown tone or bad params. Notifies nobody                                           | `{ ok: true }`                                                               |
| `dms.invite-user`       | Looks the address up in the tenant. Creates no user, member or invite, and sends no email                             | `already-member` or `added` with the user's id, else `invited` with no `inviteId` |
| `dms.set-member-roles`  | Refuses a non-member, an unknown role, demoting the last owner and a workspace being deleted. Runs no `Hook.MEMBER_BEING_CHANGED` handler, so a seat limit on an owner change shows only in a real run | The result, with `changed` |
| `dms.cancel-invite`     | Looks the invitation and its decision up. Cancels nothing | The status a real run would answer |
| `dms.remove-member`     | Refuses removing the last owner of the workspace or the platform, and a workspace being deleted. Runs no hook | `removed` and `wasTenantOwner` |

## Texts in the builder

The builder shows a node's `name` and `description`, and each schema property's `title` and `description`, through `processI18n`. Each one can be a [`$` key](/docs/building/localization) instead of literal text. The DMS nodes carry keys only, under `dms.automation.*` of the `dms-core` locales (`en` and `fr`):

- `triggers.<trigger>` and `actions.<action>` hold a node's name, its description, and its per-node field descriptions.
- `fields.<property>` holds the field labels that its nodes share.

A module that registers nodes of its own does the same under its namespace:

```ts fragment [src/automation/my-action.ts]
export const myAction: ActionType = {
  id: "my_app.archive",
  name: "$my_app.automation.archive.name",
  description: "$my_app.automation.archive.description",
  inputSchema: {
    type: "object",
    properties: {
      reason: { type: "string", title: "$my_app.automation.fields.reason" },
    },
  },
  // ...
};
```

The builder names an untitled property by its key in words. The canvas labels a port by its key, whatever its title.
