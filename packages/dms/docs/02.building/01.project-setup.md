To start a new application from the starter template, follow [Quickstart](/docs/getting-started/quickstart). This page describes the project layout, the module configuration and the lifecycle you work with when you adapt a template or add the DMS to an existing AntelopeJS application. Your application owns its pages, data and business logic. The DMS provides the dashboard, authentication and the component system.

::note
To package a reusable extension that other projects install, see [Distributable module](/docs/building/distributable-module). It uses the same page and component APIs. Only the packaging differs.
::

## Project layout

A typical project:

```bash [my-app/]
my-app/
  antelope.config.ts        # the project: which modules to load (the DMS included) and their config
  package.json              # deps: @antelopejs/dms, @antelopejs/dms-frontend and the stack
  src/
    index.ts                # your project's module: construct/start/stop lifecycle, AddFrontendModule
    frontend-module.ts      # optional: frontendModule(config), declared as dmsFrontend in package.json
    pages/                  # @RegisterPage classes                         → Pages & components
    data-api/               # DataControllers (TableViews attach on pages)  → Data controller
    data-types/             # custom DataTypes                              → Data types
    permissions/            # RegisterPermission                            → Auth & permissions
    db/                     # @RegisterTable models and schema
    routes/                 # @Controller HTTP routes                       → Pages & components
    services/               # your business logic
  frontend-vue/             # optional: your own frontend layer (custom Vue) → Frontend layer
```

## Load the DMS and the stack in `antelope.config.ts`

The config declares which modules to load and the configuration of each. Your own code loads as a module with a `local` source (`source.type: "local"`). The module key (`local` below) is only a name, so pick any. The [template's complete configuration](https://github.com/AntelopeJS/template-dms-demo/blob/main/antelope.config.ts) holds the current package ranges and infrastructure. The example below shows only the local module entry to merge into that configuration. It does not run on its own.

```ts [antelope.config.ts]
import { defineConfig } from "@antelopejs/interface-core/config";

export default defineConfig({
  name: "my-app",
  modules: {
    local: {
      source: {
        type: "local",
        path: ".",
        watchDir: ["src"],
        installCommand: ["pnpm install", "pnpm build"],
        reloadCommand: "pnpm exec tsc",
      },
      config: {
        /* your project's Config, passed to construct(config) in src/index.ts */
      },
    },

  },
});
```

The modules the DMS relies on:

- An HTTP server implementing `@antelopejs/interface-api`, such as `@antelopejs/api`, and a database implementing the 0.4 line of `@antelopejs/interface-database`, such as `@antelopejs/mongodb`. Wire each in `modules`.
- An `@antelopejs/interface-email` implementation, such as `@antelopejs/nodemailer`, for invites, email validation and password resets. File fields store through an `@antelopejs/interface-file-storage` implementation, such as `@antelopejs/file-storage-local`.
- The template and the playground also load `@antelopejs/auth-jwt`.
- Redis is optional for a single development instance.
- Table decorators come from the `@antelopejs/interface-database-decorators` library, which needs no module of its own.

The DMS keys you set most often are `apiBaseUrl`, `clientBaseUrl` and `auth.jwtSecret`, the secret that signs the DMS's session tokens. Set a strong `auth.jwtSecret` in production. [Configuration](/docs/building/configuration) lists every key and default, with the `auth`, `htmlRender` and `realtime` blocks.

The DMS registers its base dashboard layer itself: the shell, the login screens and the component vocabulary that render standard pages. Any other frontend module is included by the `dmsFrontend` declaration in its `package.json`, in development and in a production build, and registered with the backend by its `AddFrontendModule` call, not by config ([Frontend layer](/docs/building/frontend-layer#how-module-config-reaches-vue)). A project that only declares pages needs no frontend module of its own.

## The project's lifecycle in `src/index.ts`

A project is itself a module. The lifecycle functions (`construct`, `start` and the others) belong to the framework and are covered in [Creating a module](https://antelopejs.com/docs/module-development/creating-a-module). The side-effect imports run your `@RegisterPage`, `@RegisterDataType` and other decorators, and `construct(config)` receives the `config` of the `local` module.

```ts fragment [src/index.ts]
import "./pages"; // @RegisterPage
import "./db"; // models and schema
import "./data-api"; // DataControllers
import "./routes"; // @Controller

export interface Config {
  /* whatever you put under modules.local.config */
}
let globalConfig: Config = {
  /* defaults */
};
export function getConfig(): Config {
  return globalConfig;
}

export function construct(config: Config): void {
  globalConfig = config;
}
```

A custom frontend module is optional. Write a `frontendModule` function, pass its result to `AddFrontendModule` from the lifecycle, and declare it as `dmsFrontend` in the project's `package.json`. That declaration is how `ajs dms dev`, `ajs dms build` and `ajs dms start` find it ([Frontend layer](/docs/building/frontend-layer#how-module-config-reaches-vue)).

## What you register

Once the project is wired, you build the dashboard with the same APIs as the rest of these docs. None of them is specific to a project.

| You want to                                | Use                                                                               | Doc                                                                                    |
| ------------------------------------------ | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Add a dashboard screen                     | `@RegisterPage` and `PageController`, attached to `pagesCategory` or a `Category` | [Pages & components](/docs/building/pages-and-components)                              |
| Show a table with create, edit and delete  | `DataController` with `TableViewRoutes` and `TableView`                           | [Data controller](/docs/components/data-controller), [Tables](/docs/components/tables) |
| Add a custom field or column type          | `@RegisterDataType` extending `DataType`                                          | [Data types](/docs/components/data-types)                                              |
| Add custom actions and reactivity between components | `.action()`, `.watch()`, `ActionTarget`                                 | [Actions & reactivity](/docs/building/actions-and-reactivity)                          |
| Gate pages and routes, define permissions  | `interface-dms/auth` and `interface-dms/guards` decorators, `RegisterPermission`  | [Auth & permissions](/docs/auth-and-tenancy/auth-and-permissions)                      |
| Use hooks, notifications and HTML rendering | `interface-dms/hooks`, `interface-dms/notifications`, `interface-dms/html-render` | [Backend services](/docs/building/backend-services)                                    |
| Write custom Vue in your dashboard         | your `frontend-vue/`                                                              | [Frontend layer](/docs/building/frontend-layer)                                        |

## Running

A project runs as two processes that work together. [Architecture](/docs/getting-started/architecture) and [Frontend layer](/docs/building/frontend-layer) describe them in full.

- The backend runs with `ajs project dev -w`, which watches the sources. Most projects start their infrastructure (MongoDB, Redis) in Docker first, for example with a `dev` script of `docker-compose up -d && ajs project dev --inspect -w`.
- The frontend runs with the Vue loader, `ajs dms dev`. It finds the backend from the enclosing project's `.antelope/dev.json`, so `-b <apiBaseUrl>` is optional ([Frontend CLI](/docs/building/frontend-cli)). Projects usually expose it as a `frontend:dev` pnpm script.

In production you build both processes once and start them from their build output, with production secrets and Redis. [Deployment](/docs/building/deployment) covers the build commands, the startup order and the production checklist.
