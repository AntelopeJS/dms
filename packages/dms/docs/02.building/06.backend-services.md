Beyond pages and auth, the DMS exposes cross-cutting services that any module can use. [Automation nodes](/docs/building/automation-nodes) lists the nodes the DMS adds to the `dms-automation` procedure builder.

## Lifecycle hooks

Hooks let a module react to platform events, and contribute to some of them. Register a handler with `RegisterHook(hook, handler)`.

- TypeScript checks the handler's signature against the hook. `HookHandler<H>` types the arguments and the result from the hook, so a mismatch is a compile error, not a runtime one.
- At runtime `RegisterHook` adds the callback to the hook's list and does no validation.
- The registration belongs to your module and is released with it, including when it reloads in development. You have nothing to unregister in `destroy()`.

```ts [src/index.ts]
import { Hook, RegisterHook } from "@antelopejs/interface-dms/hooks";

RegisterHook(Hook.DATABASE_INITIALIZED, async () => {
  // setup once the DB schema is ready, safe to run again
});

RegisterHook(Hook.MEMBER_ADDED, async (payload) => {
  // payload = { tenantId, userId, isTenantOwner, deliveryId? }, the user who joined a tenant
});

RegisterHook(Hook.TENANT_DATA_EXPORT, async (tenantId: string) => {
  return { moduleId: "my-module", data: { tenantId } };
});
```

The first two handlers are where your module's work goes. A hook whose result is `undefined` is an event. Its dispatchers discard what handlers return, so an event handler may return any value or promise. The export example contributes only tenant metadata. Replace `data` with your module's export payload.

`RegisterHook(hook, handler, { moduleId })` sets the module id a handler is known by. Without it, the runtime infers the id from the call site. The id namespaces the module's entries in a [tenant export archive](#tenant-data-export-archive). It does not change when the registration is released.

The `Hook` enum:

| Hook                                                         | Fires                                                             |
| ------------------------------------------------------------ | ----------------------------------------------------------------- |
| `DATABASE_INITIALIZED`                                       | On every DMS start, once the database schema is ready. A handler registered afterwards runs at once (see the note below). |
| `TENANT_BEING_PROVISIONED`                                   | A tenant is being created: the `default` tenant on its first start, or a SaaS workspace at signup. Write its default data here (see the note below). |
| `TENANT_DELETED`                                             | A tenant was deleted. Clean up per-tenant data.                   |
| `TENANT_DATA_EXPORT`                                         | A tenant requests an export of their data, in SaaS mode (see the note below). |
| `INVITE_BEING_CREATED`, `INVITE_CREATED`, `INVITE_DELETED`   | Invite lifecycle.                                                 |
| `MEMBER_BEING_ADDED`, `MEMBER_ADDED`, `MEMBER_REMOVED`       | Tenant membership lifecycle.                                      |
| `MEMBER_BEING_CHANGED`                                       | Before every membership write that `changeTenantMembers` makes, once per change: an addition, a removal, a role change or an ownership change. A handler that throws refuses the write. |
| `USER_REGISTERED`                                            | A user completed registration. The payload is `{ tenantId, userId, email, name }`. |
| `USER_DELETED`                                               | A user was deleted, after the DMS removed its rows. Today the only path is deleting one's own account. The payload is `{ userId, email, tenantIds, reason }`. `tenantIds` lists the workspaces the user was a member of and left before the deletion. `reason` is `"self"` (`UserDeletionReason`). Delete the per-user rows your module keeps. A failing handler is logged and does not bring the account back. |

`UnregisterHook(hook, handler)` removes a handler, for a module that stops listening while it stays loaded.

- The `*_BEING_*` variants fire _before_ the action commits, so use them to veto or prepare. The past-tense variants fire _after_.
- Each hook has its own payload shape, type-checked against the hook. `MEMBER_ADDED` and `MEMBER_BEING_ADDED` carry `{ tenantId, userId, isTenantOwner, deliveryId? }` for the single member added. `MEMBER_REMOVED` carries `{ tenantId, userIds }`, an array, because one removal can cover several members.
- Rely on the handler's inferred parameter type instead of assuming one shape for every hook.

::note
`DATABASE_INITIALIZED` works like an already-resolved promise. A module loaded or reloaded after the DMS started still gets its handler run, at once and in the background. A failure there is logged and does not break the module's `construct()`. A handler can therefore run several times in one process: on every DMS start, and again each time its module reloads. Make it safe to replay against a live database. Create what is missing instead of inserting unconditionally, and never send mail or charge from it without recording that it already happened.
::

::note
`TENANT_BEING_PROVISIONED` fires once per tenant, when the tenant is created. For the `default` tenant, it fires once every module has started, on the replica that holds the provisioning lease, and its payload has no `userId`. If an attempt fails or its process dies, the next start or another replica runs the `default` tenant's handlers again, so a handler skips what it already wrote. For a workspace, the SaaS signup flow fires it. Write a tenant's default data there, once. Do not write it from `start()` or `DATABASE_INITIALIZED`, and never again on a later start, because from then on it belongs to the tenant.

Handlers run in series and are awaited, and one that throws aborts the provisioning. A module can therefore write its own signup data, carried in an opaque `extras` object the DMS never reads, and know that no workspace is provisioned without it. The converse does not hold. There is no shared transaction, so rows a handler already committed survive a later failure. Key them on `tenantId` and keep the write idempotent. Emitters fire the hook through `ProvisionTenant` (`@antelopejs/interface-dms/tenant-provisioning`), which registers the tenant's schema instance before any handler runs.
::

::note
The **`dms-saas`** module drives `TENANT_DATA_EXPORT` ([SaaS mode](/docs/auth-and-tenancy/saas-mode)). When a tenant requests an export of their data, every registered handler adds to the archive being assembled. Register a handler to include your module's tenant data in that export. Without `dms-saas`, nothing invokes this hook. See [Tenant data export archive](#tenant-data-export-archive) for the full contract, including large files.
::

## Notifications

Build a notification with the chainable `Notification()` builder. `.build()` returns a `SendableNotification`, which you send with its own `to*` and `broadcast` methods. `icon`, `title`, `description` and `subject` are required, and `.build()` throws `Notification is missing required fields: ...` without them.

```ts fragment [src/services/notifications.ts]
import { Notification, GeneralSubject } from "@antelopejs/interface-dms/notifications";

const n = Notification()
  .icon("i-ph-bell")
  .title("$my_app.notifications.welcome.title") // $ key or literal
  .description("$my_app.notifications.welcome.body")
  .params({ teamName: "Acme" }) // i18n interpolation params for title and description
  .subject(GeneralSubject)
  .linkTo("/dashboard")
  .build(); // SendableNotification

await n.toUser(userId); // optional 2nd arg: { idempotencyKey, dedupe }
await n.toUsers([a, b]); // optional 2nd arg: { readScope, idempotencyKey, dedupe }
await n.toRoles([roleId]); // optional 2nd arg: { tenantId, readScope, idempotencyKey, dedupe }
await n.broadcast(); // optional arg: { readScope, idempotencyKey, dedupe }
```

`.tone(tone)` colours the icon well the notification is listed with: `neutral`, `primary`, `success`, `warning` or `error`.

Notifications are organized by **category**, then **subject**. Users toggle the subjects they receive from their notification settings, and a send to a user who disabled the subject is skipped without an error. The built-in subjects are `GeneralSubject`, `SecuritySubject`, `AccountSubject`, `CollaborationSubject` and `AutomationSubject`, under `SystemCategory`.

Register your own with the public `NotificationCategory(id, opts)` and `NotificationSubject(id, opts)` functions, then pass your subject to `.subject(...)`. A category or subject can set `togglePermission: "forbidden"` so users cannot turn it off. `GeneralSubject` does.

Three delivery details:

- **`readScope`** is `"individual"` by default, which gives each recipient their own read state. `"shared"` groups the copies, so one recipient reading it marks it read for everyone. Use it for "someone should handle this" alerts.
- **Deduplication.** A notification identical to one the same recipient received less than 10 seconds before is not stored again. Identical means the same title, description, params, link, category, subject, tone and icon. `dedupe: false` stores every send. A send with an `idempotencyKey` is stored once per key either way.
- Delivery is **live**. Each stored notification is also published on the recipient's realtime stream, so badges and previews update without a refresh ([Realtime and notifications](/docs/frontend-composables/realtime-and-notifications)).

### Module update notifications in development

When the project runs in development mode (`ajs project dev`), the DMS checks the npm registry for updates to the project's **package-sourced AntelopeJS modules**. At startup and then every hour, it compares each module's configured version range with the latest published version.

It broadcasts a notification under the development-only `updates` subject (`SystemCategory`) that lists the modules whose latest version falls **outside** their configured range. An update inside the range installs itself on the next boot, so the notification lists only the updates that need an `antelope.config.ts` edit or `ajs project modules update`. The DMS notifies the same set of outdated modules once. Registry failures are silent, and nothing runs in production.

## Realtime

Backend code pushes live updates to the dashboard by publishing to **named topics**. A topic is **bound to a page**. Subscribing to the page activates its topics, and messages reach the browser over each user's single SSE stream.

Register a topic for a page, then publish when data changes:

```ts fragment [src/routes/stats.ts]
import { RegisterPageTopic, PublishMessage } from "@antelopejs/interface-dms/realtime";

RegisterPageTopic("stats", "stats:live"); // bind topic to page "stats"

// later, when data changes:
await PublishMessage("stats:live", "stats.update", { payload: { total } });
```

`PublishMessage(topic, type, options?)` takes an optional `payload`, `actorId` and `tenantId`.

- Set `actorId` to the acting user's id, so their own client can skip echoing the change back to them.
- Set `tenantId` to the workspace the data belongs to: `getRequestTenantId(ctx)`, or the tenant a job runs for. Without it the message is global and wakes the page in every workspace. See [tenant-scoped messages](/docs/interfaces/core/realtime#tenant-scoped-messages).

On the **frontend**, components subscribe with `useRealtimeTopic` or the page-scoped realtime API. See [Realtime and notifications](/docs/frontend-composables/realtime-and-notifications) for the consuming API.

Backend code can also read the stream back. `SubscribeMessage(topic, handler)` delivers every message published on `topic`, whichever instance published it, because the subscription uses the same broker as `PublishMessage`:

```ts [src/routes/my-stream.ts]
import { SubscribeMessage } from "@antelopejs/interface-dms/realtime";

const unsubscribe = SubscribeMessage("stats:live", (message) => {
  // message: { topic, type, payload?, actorId?, tenantId?, ts }, from every tenant
});
```

A module that serves realtime channels of its own, such as an SSE endpoint it exposes itself, subscribes here. The DMS broker then carries the messages across instances, and the module runs no second broker for the same job.

- Handlers run on the delivering instance's event loop and must not throw.
- Delivery is fire-and-forget. There is no replay, and a message published while nobody was subscribed is gone.
- The returned function ends the subscription, and calling it twice does nothing. The DMS removes a module's subscriptions when the module unloads.

Some builders wire this for you. A chart with a `realtimeTopic` registers the topic on its page and refetches on publish ([Charts and widgets](/docs/components/charts-and-widgets)). A `TableView` publishes row mutations (`created`, `updated`, `deleted`) and edit **presence** on its own topics, unless you opt out with `realtime: false` ([Tables](/docs/components/tables)).

::note
Topics are page-bound. A message published to a topic that no page registered reaches no subscriber. The transport driver, Redis or in-memory, comes from the `realtime.driver` config. The in-memory driver does not cross instances ([Configuration](/docs/building/configuration#realtime-transport-driver-in-realtime)).
::

## Extension and hook delivery

An invite extension's fields also appear in the edit form of a **pending** invitation, prefilled with the stored payload. An admin can change it until the invitee accepts. The DMS validates the edited slice against the same `schema` and stores it in place of the old one, and `onAccept` later receives it as if it had been typed at invite time.

`onUpdate(payload, previous, context)` runs after the DMS stores a changed payload, for an extension that derives something before acceptance. Its failures are logged, not raised. Set `editable: false` to show the fields read-only there. An invitation that already has a terminal decision refuses the edit with a 409.

Durable invite callbacks receive an optional `deliveryId`, stable across retries and concurrent calls. The runtime delivers and cleans up durable invitations with retries. An invalid stored payload, an unavailable captured extension, or a callback failure keeps the decision for a retry. Successful callbacks can run again when a later callback fails. Each extension must make its own effects idempotent, using the identity and its domain's atomic constraints. An id alone does not deduplicate an email, a payment or an arbitrary callback.

`ExecuteHooks` awaits handlers in order and propagates errors. `CollectHooks` logs and skips errors, and is not a strict delivery API. `TENANT_DELETED` accepts `(tenantId, context?: TenantDeletionContext)`, with `context.operationId` supplied by the deleting module. Deletion handlers can repeat and must use that identity for effects that are not idempotent. Do not record success before an external send. Retries are at-least-once unless the provider enforces the same idempotency key, so a lost acknowledgement can duplicate a send.

Automation events such as `MEMBER_ADDED` and `INVITE_CREATED` stay **best-effort**. Events can repeat or be lost. An optional `deliveryId` does not guarantee deduplication or a successful run of a procedure.

### Tenant deletion closes producer admission first

Call `closeTenantLifecycleAdmission(tenantId)` before deletion hooks or a provisioning rollback, and stop the destructive flow if it rejects. Write membership and invitation rows only through `changeTenantMembers(tenantId, plan)` from `@antelopejs/interface-dms/tenant-members`, and await their effects. The [tenant lifecycle reference](/docs/interfaces/core/tenancy#tenant-lifecycle-admission) defines the signatures, the failure and retry semantics, and the safety rows a deletion must preserve. When closure keeps rejecting because a release failed, [unblock the deletion](/docs/interfaces/core/tenancy#unblocking-a-deletion) with the ids the error and the log line name.

## The export-job engine

The asynchronous export behind a `TableView`'s Export button ([Tables](/docs/components/tables/live-pages#export-jobs)) is a **reusable engine**. A module can run its own long exports through it and get the same job rows, progress tracking, storage upload, ownership checks, and sweeping of stale files:

```ts fragment [src/routes/report-export.ts]
import { runExportJob } from "@antelopejs/interface-dms/base/export-jobs";

// start: creates a job row, processes in the background, returns the ticket
const ticket = await runExportJob({
  ctx,
  user,
  scope: "acme-report", // namespaces the job for the access checks
  filename: "monthly-report", // base name, the engine adds the timestamp and extension when serving
  extension: "csv",
  contentType: "text/csv",
  generate: async ({ localPath, reportProgress, signal }) => {
    // write the file to localPath, calling reportProgress as you go
    // (clamped to 0-99, the engine sets 100 on completion);
    // signal aborts when the job exceeds maxExecutionTimeMs (default 10 min)
  },
});
// ticket: { jobId, extension, filename }
```

`generate` receives the `jobId` and `tenantId`, a `localPath`, the job `context`, a `reportProgress` callback, and an abort `signal`. It writes the file to `localPath`. The engine uploads the file to file storage and marks the job completed, or failed if `generate` throws or times out.

Expose three routes: the start route, one that calls `getExportJobStatus` (polled), and one that calls `downloadExportJob` (streams the file, then cleans up). Point an [`exportJob` action target](/docs/building/actions-and-reactivity#action-targets) or the frontend [`useExportJob`](/docs/frontend-composables/ui-toolkit#async-export-progress-useexportjob) runner at them.

A job belongs to the user and the tenant that requested it. The status and download functions check that, and an optional `isOwnedBy` adds your own access check, on the job's `context` read back through the `contextSchema` you pass with it. An hourly built-in cron sweeps files older than 24 hours. The exporter registry ships **CSV**. The delivery registry ships **download** and **email**.

By default the engine drops a job and its stored file once the user downloads it. Pass `retainUntilExpiry: true` to keep both until the sweep expires them. Set it whenever you deliver a link or list a history, because both outlive the first download. `listExportJobs` returns the caller's own jobs, most recent first, filtered by `scope` and capped by `limit` when you pass them:

```ts fragment
import { listExportJobs } from "@antelopejs/interface-dms/base/export-jobs";

const jobs = await listExportJobs(ctx, user, { scope: "acme-report" });
// jobs: [{ jobId, scope, status, progress, filename, createdAt, expiresAt, result, ... }]
```

`generate` may return an `ExportJobResultSummary` (`{ partial, failures }`). The engine stores it on the job, and `getExportJobStatus` and `listExportJobs` return it, so an incomplete export never looks complete.

Email delivery (`delivery: "email"`) sends the requesting user the `EmailExportReady` template once the job completes. The email holds a link built from `deliveryPath` and the job id, the expiry, and the failed parts when the export is partial. `deliveryPath` is a client-side path, and this delivery requires it. Delivery failures are logged and never fail a job that otherwise completed.

## Tenant data export archive

A `TENANT_DATA_EXPORT` contributor receives the tenant id, the archive being assembled, and an abort signal:

```ts fragment [src/index.ts]
import {
  Hook,
  RegisterTenantDataExportContributor,
} from "@antelopejs/interface-dms/hooks";

RegisterTenantDataExportContributor(
  "my-module",
  async (tenantId, archive, signal) => {
    await archive.addJson("config.json", await readConfig(tenantId));
    await archive.addFile("report.pdf", localReportPath);
    await archive.addStream("volumes/data.tar", await openRemoteDump(signal));

    return { moduleId: "my-module", data: { summary } }; // optional
  },
);
```

- **The implementation namespaces paths** under `modules/<moduleId>/`, so contributors cannot collide. It tells colliding module ids apart.
- **Await every `add*` call.** Contributors run one after another, and each call resolves only once the archiver has consumed the entry. That passes back-pressure to the producer and keeps memory flat at any volume. Use `addStream` for a dump that must never be held in memory.
- **A returned contribution stays valid.** The archive writes it to `modules/<moduleId>.json`, so a handler that ignores the archive and signal arguments keeps working unchanged.
- **A failing contributor does not fail the export.** Its error is recorded in `manifest.json`, and the archive is delivered as **partial**. The job's result summary carries the failure, so a history table and the delivered email can say so. An aborted signal cancels the whole export.

The resulting ZIP holds `manifest.json` (tenant id, timestamp, `partial`, and one report per contributor), one `modules/<moduleId>.json` per JSON contribution, and the large entries each contributor streamed in.

The module that owns the export request runs it as a job:

```ts fragment [src/routes/data-export.ts]
import { startTenantExportJob } from "@antelopejs/interface-dms/base";

const ticket = await startTenantExportJob({
  ctx,
  user,
  scope: "tenant-data-export",
  filename: `workspace-export-${tenantId}`,
  delivery: "email",
  deliveryPath: "/settings/tenant/data-export",
});
```

`startTenantExportJob` runs `buildTenantExportArchive` through the export-job engine with the ZIP content type and `retainUntilExpiry`. Call `buildTenantExportArchive({ tenantId, localPath, signal, reportProgress })` directly only to assemble an archive outside a job.

## Email templates and rendering

Register named HTML templates and render them on the backend, for emails and static HTML:

```ts [src/emails/welcome-email.ts]
import {
  RegisterHtmlTemplate,
  GenerateHtml,
  GetHtmlTemplate,
} from "@antelopejs/interface-dms/html-render";

// Register a named template; the type param types its props and you get a typed ref back.
const welcomeEmail = RegisterHtmlTemplate<{ userName: string }>("welcome-email");

// Render it with props (pass the ref, not the name).
const html = await GenerateHtml(welcomeEmail, { userName: "Jane" });
```

`GetHtmlTemplate(name)` and `GetAllHtmlTemplates()` read the registry. Rendering happens on the **frontend**. `GenerateHtml` posts to the configured `htmlRender.renderEndpoint` with a short-lived service token ([Configuration](/docs/building/configuration#template-rendering-in-htmlrender)), and the Inertia and Vue app renders the named email component.

**Sending** the rendered HTML is a separate concern. The DMS sends mail through the standard AntelopeJS `interface-email` `Send` function, so your `antelope.config.ts` must load a module that implements it, such as `@antelopejs/nodemailer` with your SMTP settings.
