Production runs the same two processes as development, the backend and the `ajs dms` frontend ([Architecture](/docs/getting-started/architecture)). Each one is built once and launched from its build output instead of the dev tooling. The steps below are the production-specific ones. The pages linked from each section own the details.

## Build and run the backend

Build the project once, then launch it from the build output:

```bash [Terminal]
ajs project build
ajs project start
```

`ajs project start` launches from the build artifact and skips the module download and the development CLI. `ajs project dev` runs the project in development mode, even without `--watch`. `ajs project run` is the same command under its old name. Do not use either one as a production launcher.

Use production values in your `antelope.config.ts`: real secrets (see the [production checklist](#production-checklist)), Redis for realtime, durable file storage and your SMTP settings. [Configuration](/docs/building/configuration) lists every key and default.

## Build and run the frontend

Build the frontend from the **project itself**, with no backend running. `ajs dms build` evaluates `antelope.config.ts` for the environment and takes each installed module's frontend from `node_modules/<module>/frontend-vue/`. A module declares its frontend as `dmsFrontend` in its `package.json`. The build holds no secret.

```bash [Terminal]
ajs dms build -e production          # in the project, next to antelope.config.ts
export DMS_BOOTSTRAP_SECRET=…        # same value as the backend's frontend.bootstrapSecret
ajs dms start -b https://api.example.com -p 3001
```

`ajs dms start` computes each module's public options again from the project's configuration and the current environment variables. The module's `dmsFrontend` function computes them, the same one the backend calls. A change to a deployment variable therefore needs no rebuild. The variables the options read (`DMS_API_PUBLIC_BASE_URL`, `DMS_CLIENT_BASE_URL`, a Stripe publishable key…) must hold the same values for the frontend server and for the backend.

Build and deploy both processes from the same commit. Once ready, the frontend server reports each module's version to the backend, and the backend logs a warning on any difference.

`start` does not discover the backend by itself. Pass `-b` or set `DMS_API_BASE_URL`. The [Frontend CLI reference](/docs/frontend/cli/overview) lists the flags and the workspace behavior.

::tip
The [Frontend](/docs/frontend) section covers the frontend server's own deployment: the reverse proxy, public endpoints, caching and scaling. This page keeps what a DMS project adds on top, which is how the two processes start and the secrets they share.
::

Set `DMS_SESSION_SECRET` to a stable secret of at least 32 characters on every frontend instance. `start` refuses a missing or shorter value, because it signs sessions with it.

Keep the complete generated build, including `dist/server/locales/`. The email renderer reads its merged translation catalogs from these JSON files, so a copy of the email JavaScript files alone breaks localized rendering.

Only `start` needs `DMS_BOOTSTRAP_SECRET`. It presents the secret when it reports what it serves. The server reads its private options (`DMS_HTML_RENDER_SECRET`, `DMS_OAUTH_RELAY_SECRET`) from its environment at start, never at build.

Pass the bootstrap secret through the environment rather than `--bootstrap-secret`. `ajs dms` trims surrounding whitespace, so a trailing newline from a file is harmless. A value that still holds a space, a line break, a control character or a non-ASCII character cannot travel in an HTTP header, and `ajs dms` refuses it with "The bootstrap credential cannot travel in an HTTP header".

## Start the two processes

The two processes start in any order. The frontend asks the backend nothing to build or to start. Until the backend is up, the frontend answers a page with the backend's own error.

Rebuild the frontend whenever the layer set changes: you add or remove a module that calls `AddFrontendModule`, or you change a layer's code. Backend-only changes (pages, components, data) need no frontend rebuild, because pages are data the frontend draws.

## Production checklist

The defaults are development values. Set each of these before going live:

| Key                                                   | Default   | Production requirement                                                                     |
| ----------------------------------------------------- | --------- | ------------------------------------------------------------------------------------------ |
| `auth.jwtSecret` (DMS config)                         | `""`      | A strong random value. It signs every session token. The DMS refuses to start in production when it is empty or `"dev"`. |
| `htmlRender.serviceSecret` (DMS config)               | `"dev"`   | A strong random value. It signs the backend's calls to the frontend's HTML renderer. The DMS refuses to start in production when it is empty or `"dev"`. |
| `frontend.bootstrapSecret` (DMS config)               | None      | A strong random value. Setting it gates the dev manifest and the frontend's ready report. Also set it as `DMS_BOOTSTRAP_SECRET` on the frontend server. |
| `secret` (the `@antelopejs/auth-jwt` module's config) | None      | A strong random value, independent of `auth.jwtSecret`.                                    |
| `apiBaseUrl`, `clientBaseUrl`                         | `http://127.0.0.1:5010`, `http://localhost:3001` | Your public backend and dashboard URLs. Generated links (invite emails, signup) use them, and modules read them through `GetApiBaseUrl()` and `GetClientBaseUrl()`. `clientBaseUrl` is required in production and must be an http(s) origin with no path. The DMS adds it to the api module's allowed CORS origins, next to the ones configured there. |
| `DMS_SETUP_TOKEN` (backend environment)               | Generated | A strong random value of at least 16 characters, when the platform must know the first owner's address in advance. Without it, the backend generates a token on its first start, stores it in the database, and logs the wizard's address at every start while no owner exists. Only the owner's registration needs it. See [The setup token](/docs/getting-started/built-in-dashboard#the-setup-token). |
| `htmlRender.renderEndpoint`                           | `http://localhost:3001/api/html/render` | The production frontend's `/api/html/render` URL, reachable from the backend. |

Serve the dashboard to browsers over **HTTPS and HTTP/2** (or HTTP/3), usually through a reverse proxy that terminates TLS. See [HTTP/2 and long-lived streams](#http2-and-long-lived-streams).

All of these keys live in the DMS `config` block, except the auth-jwt secret, which belongs to that module's own entry. [Configuration](/docs/building/configuration) documents each key. Transactional email also needs an `interface-email` implementation, usually `@antelopejs/nodemailer`, wired in the config. Without one, invites, validation and password resets fail ([Backend services](/docs/building/backend-services)).

## HTTP/2 and long-lived streams

Each signed-in browser keeps one realtime stream open to the origin it reaches the backend through, and all of its tabs share that stream ([Realtime & notifications](/docs/frontend-composables/realtime-and-notifications#one-connection-per-browser-a-session-per-tab)). When the frontend server proxies `/api`, that origin is the dashboard's own. Over HTTP/1.1, the stream holds one of the six connections a browser opens per host for as long as it lives. Set up the proxy as follows:

- **Serve the dashboard over HTTPS with HTTP/2** at the reverse proxy. HTTP/2 carries every request and stream on one connection, so the six-connection limit no longer applies. The proxy can keep talking HTTP/1.1 to the frontend server.
- **Serve it over HTTPS** in any case. The tabs share their stream through Web Locks, which browsers offer only in a secure context (HTTPS, or `localhost`). Over plain HTTP on another host name, each tab opens a stream of its own, and a few tabs use up the connections.
- **Let the stream through unbuffered.** The backend sends `X-Accel-Buffering: no` (for nginx) and a keepalive every 20 seconds. A proxy idle timeout shorter than 20 seconds drops the stream, and the browser then reopens it.
- **Forward the `x-realtime-connection` and `x-realtime-session` headers.** A tab names its connection in `x-realtime-connection` and its session in `x-realtime-session`. The dashboard's frontend server relays both by name to the backend. A proxy of your own between the browser and the backend must forward them too. Otherwise every session request answers `ok: false`, the browser keeps reopening its connection with a growing delay, and live pages fall back to polling.

## Multiple instances

More than one backend instance needs two things: Redis for realtime, and affinity on `/api/realtime/*`.

### Redis for realtime

The in-memory driver does not cross process boundaries. Events, presence and notification streams stay on one instance. Load `@antelopejs/redis`, and keep `realtime.driver` at `"auto"` or set it to `"redis"` ([Configuration](/docs/building/configuration#realtime-transport-driver-in-realtime)). With Redis, an event published on any instance reaches every browser, whichever instance holds its stream.

### Affinity on `/api/realtime/*`

Redis carries the events, not the connections. The registry of a browser's realtime connection, and of the sessions its tabs open on it, stays in the memory of the instance that serves the stream:

1. `GET /api/realtime/connection` opens the browser's SSE stream on one instance. That instance registers the connection and greets it with its id.
2. Each tab then sends `POST /api/realtime/session` with that id in `x-realtime-connection`. Only the instance that holds the stream knows the connection. Any other instance answers `ok: false`.
3. The tab's later requests (`/session/close`, `/subscribe/:pageId`, `/unsubscribe`, `/acquire`, `/release`) read the same registry.

All of a browser's realtime requests must therefore reach the instance that serves its stream. Without affinity, a session request lands on another instance and gets `ok: false`. The browser then reopens its connection with a growing delay, live pages fall back to polling, and presence keeps resetting.

Route `/api/realtime/*` with affinity at the balancer in front of the backend instances. Other `/api` routes need none.

- **Through the dashboard's frontend server** (the default, when it proxies `/api`), hash on the client address. The frontend server writes the browser's address in `X-Forwarded-For` on every backend request ([Routing and proxy](/docs/frontend/deployment/routing-and-proxy)), the same for the stream and for every session request of that browser. It never relays the browser's `Cookie` or `Authorization`, so a balancer cookie set on the backend side never comes back. Do not hash on `Authorization` either. The access token changes at each refresh, while the stream stays open.
- **Browsers that reach the backend directly** can use a balancer cookie instead, or the same hash on the client address.

With nginx:

```nginx
upstream dms_backend {
  server backend-1:5010;
  server backend-2:5010;
}

upstream dms_backend_realtime {
  hash $http_x_forwarded_for consistent;
  server backend-1:5010;
  server backend-2:5010;
}

server {
  location /api/realtime/ {
    proxy_pass http://dms_backend_realtime;
  }

  location / {
    proxy_pass http://dms_backend;
  }
}
```

On Kubernetes, a Service's `sessionAffinity: ClientIP` sees the frontend server's address, not the browser's. Every browser behind one frontend pod would land on one backend pod. Hash on `X-Forwarded-For` at the ingress or proxy in front of the backend instead. With ingress-nginx, put the `nginx.ingress.kubernetes.io/upstream-hash-by: "$http_x_forwarded_for"` annotation on an Ingress that serves only `/api/realtime`.

When a browser's address changes, or an instance goes away, its requests move to another instance. The session request then answers `ok: false`, and the browser reopens its connection there. The affinity only has to hold for as long as a stream lives.

::note
A single-instance deployment works without Redis. The DMS still uses Redis when it is present (`realtime.driver: "auto"`), so most production stacks include it from the start.
::
