The DMS module reads one config object, the `config` block you give `@antelopejs/dms` in your `antelope.config.ts` ([Project setup](/docs/building/project-setup)). This page lists every key and its default. Every key is optional, and a bare `config: {}` runs with the defaults.

::tip
On a first read, skim the example below and go on to [Pages & components](/docs/building/pages-and-components). Come back when you need a specific key.
::

```ts fragment [antelope.config.ts]
"@antelopejs/dms": {
  source: { /* … */ },
  config: {
    apiBaseUrl: "http://localhost:5010",
    clientBaseUrl: "http://localhost:3001",
    homepage: "/form/form-simple",
    meta: { title: "Acme Admin", description: "Internal operations dashboard" },
    auth: {
      jwtSecret: "…", // signs the DMS's session tokens: set a strong value in production
      mustValidateEmail: true,
    },
    realtime: { driver: "auto" },
    htmlRender: { renderEndpoint: "http://localhost:3001/api/html/render" },
  },
},
```

## Top-level options

| Key             | Type      | Default                 | Purpose                                                                                                                                        |
| --------------- | --------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `apiBaseUrl`    | `string`  | `http://127.0.0.1:5010` | Where the backend is reachable. The frontend's authenticated fetch is bound to it, and modules read it through `GetApiBaseUrl()` to build absolute links to backend routes. |
| `clientBaseUrl` | `string`  | `http://localhost:3001` in development, none in production | The dashboard's http(s) origin, without a path or parameters. Generated links use it (for example the signup link in invite emails), the DMS adds it to the api module's allowed CORS origins, and modules read it through `GetClientBaseUrl()`. Required in production: the DMS refuses to start without it, or with a value that is not an origin. |
| `homepage`      | `string`  | `/`                     | The route the dashboard opens on. The frontend reads it through `useHomepage()`. A user whose role cannot access it goes to the first page they can access. |
| `meta`          | `object`  | None                    | `{ title?, description? }`, the dashboard's document title and description. The DMS serves them through `/api/system-state`, and the SEO plugin applies them. |
| `auth`          | `object`  | See below               | Authentication settings.                                                                                                                       |
| `htmlRender`    | `object`  | See below               | HTML and email rendering.                                                                                                                      |
| `realtime`      | `object`  | `{ driver: "auto" }`    | The realtime transport.                                                                                                                        |
| `uploads`       | `object`  | See below               | Global limits on file uploads.                                                                                                                 |
| `frontend`      | `object`  | See below               | Who may fetch the frontend layers and their private options.                                                                                   |
| `store`         | `object`  | See below               | Where the module store reads its catalog.                                                                                                      |
| `docsPreview`   | `boolean` | `false`                 | Serves the hidden public `/dms-preview` page. Framework development mode (`GetRuntimeInfo().dev`) or `DMS_DOCS_PREVIEW=1` also serves it, even when this option is `false`. The DMS reads it once, at module construction. `NODE_ENV` does not select framework development mode. See [Block preview page](/docs/ai-and-claude-code/block-preview-page). |
| `provisioningLease` | `{ renewEveryMs, staleAfterMs, pollEveryMs }` | `{ 10000, 60000, 5000 }` | How replicas share the `default` tenant's first provisioning. The replica that holds the lease renews it every `renewEveryMs`. Another replica takes over once the holder has been silent for `staleAfterMs`, and a waiting replica checks every `pollEveryMs`. A longer `staleAfterMs` delays a takeover. A value close to `renewEveryMs` risks taking over from a holder that is only slow. |

### Public URLs in a module

A module that builds an absolute link asks the DMS for the origin instead of reading request headers, which a reverse proxy may not forward (`X-Forwarded-Host`):

```ts
import { GetApiBaseUrl } from "@antelopejs/interface-dms/api-base-url";
import { GetClientBaseUrl } from "@antelopejs/interface-dms/client-base-url";

const fileUrl = `${await GetApiBaseUrl()}/i18n/site/fr.json`; // a backend route
const pageUrl = `${await GetClientBaseUrl()}/modules/lang`; // a dashboard page
```

Each returns the configured value (`apiBaseUrl`, `clientBaseUrl`), or `undefined` when the configuration clears it. Under `ajs dms dev`, both follow the origins the dev server reports, as the frontend's URLs do.

### Upload limits

`uploads` sets the limits the presign endpoint applies to every upload, before the limits of the field itself ([File storage](/docs/components/file-storage)).

| Key                | Type       | Default  | Purpose |
| ------------------ | ---------- | -------- | ------- |
| `maxSize`          | `number`   | 100 MiB  | Largest upload in bytes. `0` or less removes the cap. |
| `allowedMimetypes` | `string[]` | `[]`     | Mimetypes accepted, matched exactly. Empty accepts every mimetype. Once set, a file whose mimetype is not listed is refused, a file of unknown extension (empty mimetype) included. |

## Tokens, validation and sanitization in `auth`

These settings drive the [built-in authentication](/docs/auth-and-tenancy/authentication) flow. Lifetimes are in milliseconds.

| Key                            | Type       | Default | Purpose                                                                                                                                                                                                 |
| ------------------------------ | ---------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jwtSecret`                    | `string`   | `""`    | The DMS's own signing secret for session tokens, mixed into each user's token secret. It is independent of the `@antelopejs/auth-jwt` module's `secret`. Required in production: the DMS refuses to start when it is empty or `"dev"`. |
| `accessTokenLifetime`          | `number`   | 1 hour  | How long an access token is valid. The frontend refreshes it without the user noticing.                                                                                                                  |
| `refreshTokenLifetime`         | `number`   | 30 days | How long a refresh token is valid. A refresh replaces a token older than 15 days with a new one.                                                                                                        |
| `emailValidationTokenLifetime` | `number`   | 1 day   | How long an email validation token stays usable.                                                                                                                                                        |
| `passwordRecoverTokenLifetime` | `number`   | 1 day   | How long a password reset code stays usable.                                                                                                                                                            |
| `mustValidateEmail`            | `boolean`  | `false` | When `true`, routes guarded by `@AuthUser` accept a user only once their email is validated. A signup through an invitation link counts as validated.                                                   |
| `userSensitiveKeys`            | `string[]` | `[]`    | Extra `User` fields to strip from API responses, on top of the built-in set (tokens, 2FA secrets and others). Dotted paths work.                                                                       |
| `oauth`                        | `object`   | None    | Login providers. See below.                                                                                                                                                                             |
| `trustedProxies`               | `number`   | `0`     | How many reverse proxies in front of the API append to `x-forwarded-for`. Picks the client address recorded on sessions, looked up for a sign-in's country, and returned to modules by `getClientIp`. See below. |
| `clientIpHeader`               | `string`   | None    | Header the hosting platform overwrites with the client's address (`X-Client-IP` on AntelopeJS Cloud). When set, it replaces `trustedProxies`. See below.                                                 |
| `signInCountry`                | `object`   | None    | Where the "New sign-in" alert reads a sign-in's country. See below.                                                                                                                                     |

### Client address behind proxies

Every session records the address it was opened from. The address appears under **Profile › Sessions**, and the sign-in country is looked up from it. `auth.trustedProxies` tells the API how many reverse proxies stand in front of it, each appending to `x-forwarded-for` the address it received the request from. The API walks back from its socket peer through that many entries, from the right, and records the one the outermost trusted proxy saw. The client wrote the entries further left, so the API never uses them. With the default `0`, the API records the socket peer and ignores the header. A chain shorter than configured yields its leftmost entry. Modules resolve a request's address the same way through `getClientIp` (`@antelopejs/interface-dms/client-ip`), so this one setting covers them too.

Count every hop between the browser and the API. Sign-in goes through the frontend server, which calls the API's `/api/auth/*` routes and sets `x-forwarded-for` to the client it resolved itself (from its own `DMS_TRUSTED_PROXY_HOPS`). The frontend server is therefore one hop, plus each proxy on its way to the API. A frontend server that reaches the API directly needs `1`. One that reaches it through its public URL, behind a CDN and an ingress, needs `3`. A value too low records a proxy's address. A value too high lets a client choose the recorded address.

### Client address from the platform

`auth.clientIpHeader` names a header the hosting platform writes on every request with the client's address. When it is set, the API takes the client address from that header for sessions, the sign-in throttle and `getClientIp`, and ignores `trustedProxies`. A request without that header, or with anything but one IP address in it, falls back to the socket peer, never to `x-forwarded-for`. The frontend server sets the same header on its backend requests when its `DMS_CLIENT_IP_HEADER` names it, so name the same header on both sides.

::warning
The header is trustworthy only because the platform controls who reaches the API. Its gateway overwrites the header on every public request, and only the frontend server can open a connection to the API. AntelopeJS Cloud guarantees both, with default-deny network policies that admit only the gateway and approved private callers, and sets the option itself through `DMS_CLIENT_IP_HEADER`. Do not set it on an API that any other caller can reach, since that caller would choose its own address.
::

### Country of a sign-in

A sign-in from a browser, system and device type the account never used raises a "New sign-in" notification. The country counts too. The same browser and system signing in from another country is a new sign-in, and the notification names the country, never the address. `auth.signInCountry` says where the country comes from:

| Option     | Type              | Default        | Description |
| ---------- | ----------------- | -------------- | ----------- |
| `header`   | `string \| false` | `CF-IPCountry` without a `database`, none with one | Header the reverse proxy fills with the client's ISO 3166-1 country code. Cloudflare sets `CF-IPCountry`. Name your proxy's header when it uses another one, or set `false` to read none. A named header wins over the database. |
| `database` | `string`          | None           | Path to a MaxMind-format country database (`.mmdb`) you supply, in which the API looks up the client address (see above) when the header gives nothing. |

The package ships no country database. Use either source:

- **A proxy header.** Behind Cloudflare, turn on IP Geolocation and keep the default. Another proxy names its own header in `header`. The proxy must overwrite it on every request. A forged one can show a wrong country, or leave the check to the device alone.
- **A database file.** Point `database` at a MaxMind-format country database, such as GeoLite2 Country or DB-IP IP to Country Lite. The API then reads a header only when `header` names one. Its license is yours to honour, attribution included. An unreadable file logs a warning.

Without a country, the notification still goes out, and the device alone decides.

Behind the frontend server, the header reaches the API only when the frontend server relays it. The frontend server relays the header its `DMS_COUNTRY_HEADER` variable names (`CF-IPCountry` by default) when `DMS_TRUSTED_PROXY_HOPS` is above `0`. Name the same header on both sides.

## Login providers in `auth.oauth`

Each built-in provider (`github`, `google`) adds a "Continue with …" button to the login and signup screens. A provider stays disabled and hidden until the instance supplies both credentials, so the whole block is opt-in.

```ts fragment [antelope.config.ts]
auth: {
  jwtSecret: "…",
  oauth: {
    providers: {
      github: { clientId: process.env.GITHUB_CLIENT_ID, clientSecret: process.env.GITHUB_CLIENT_SECRET },
    },
    allowAccountCreation: true,
  },
},
```

| Key                    | Type      | Default          | Purpose                                                                                                                                                              |
| ---------------------- | --------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `providers`            | `object`  | `{}`             | `{ github?, google? }`, each `{ clientId, clientSecret, scopes? }`. Keep credentials in environment variables, never in a committed config.                         |
| `allowAccountCreation` | `boolean` | `false`          | Whether an unknown provider identity may create an account without an invitation. Turning it on makes every provider account a way to sign up.                       |
| `linkByVerifiedEmail`  | `boolean` | `true`           | Whether a provider identity binds to the existing account holding the same email. Turn it off to require linking from a signed-in session.                          |
| `callbackBaseUrl`      | `string`  | `clientBaseUrl`  | Public origin the provider redirects back to. Set it when the origin the browser sees differs from the configured one.                                              |

Register `<callbackBaseUrl>/auth/oauth/<provider>/callback` as the authorization callback URL in the provider's application settings.

The frontend server limits the OAuth routes the browser calls to 10 flows per minute per client. Each route has its own budget of 10, so a full flow spends one start and one callback. The frontend server identifies a client from its own `DMS_TRUSTED_PROXY_HOPS` environment variable, the number of proxies in front of it. The default `0` uses the socket address only, since any caller can write `x-forwarded-for`. Behind a shared proxy, clients then share one budget until you set the variable. The limit matters most with `allowAccountCreation` on, where an unthrottled flow would create accounts at will.

[Login providers](/docs/auth-and-tenancy/login-providers#which-account-a-provider-identity-resolves-to) lists which account a provider identity resolves to, when an invitation creates one, and the code each refusal answers.

## Template rendering in `htmlRender`

The backend renders HTML templates (transactional emails, static HTML) by calling the frontend's render endpoint with a short-lived service token. See [Backend services](/docs/building/backend-services#email-templates-and-rendering).

| Key                    | Type     | Default                                 | Purpose                                                               |
| ---------------------- | -------- | --------------------------------------- | --------------------------------------------------------------------- |
| `renderEndpoint`       | `string` | `http://localhost:3001/api/html/render` | The frontend route that renders a named template to HTML.             |
| `serviceSecret`        | `string` | `"dev"`                                 | Shared secret that signs the service token. Required in production: the DMS refuses to start when it is empty or `"dev"`. |
| `serviceTokenLifetime` | `number` | 5 minutes                               | How long each render service token is valid, in milliseconds. The frontend render server rejects a token valid for more than 5 minutes. |

## Realtime transport driver in `realtime`

The realtime layer carries SSE topics, presence and notification streams ([Backend services](/docs/building/backend-services#realtime)). `realtime.driver` picks its broker:

| Value      | Behavior                                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------- |
| `"auto"`   | The default. Uses Redis when an `@antelopejs/interface-redis` implementation is loaded, memory otherwise. |
| `"redis"`  | Always uses Redis pub/sub. Required when more than one backend instance runs.                            |
| `"memory"` | Stays in the process.                                                                                     |

::warning
The memory driver serves a single instance. Events, presence and notification streams do not cross process boundaries. As soon as you deploy more than one backend instance, run Redis with `driver: "auto"` or `"redis"`, and route `/api/realtime/*` with affinity ([Deployment](/docs/building/deployment#affinity-on-apirealtime)).
::

## The frontend server in `frontend`

The project itself builds and starts a production frontend. `ajs dms build` and `ajs dms start` evaluate `antelope.config.ts` and call each module's frontend function (the `dmsFrontend` entry of its `package.json`), which the backend calls too. The backend serves only two routes to the frontend tool:

| Route | Use |
| --- | --- |
| `GET /dms/frontend` | The manifest `ajs dms dev` follows: the modules, their layer paths and options. |
| `POST /dms/frontend/ready` | A frontend server reports the modules it serves and their package versions. The backend warns when one differs from what it runs. |

### Renderer selection

Pass `renderer` and `rendererVersion` together on the manifest route. Versions match by major version.

- An unsupported selection returns `404`.
- An incomplete or invalid selection returns `400`.
- Without either parameter, the route selects the `vue` renderer, version 3.

The manifest's top-level `version` is the frontend protocol version, not a renderer or package version. Adapters fail closed when they receive a version they do not implement.

### Bootstrap protection

The manifest carries data no browser and no stranger should see: each module's `privateOptions` (`oauth.relaySecret`, `htmlRender.serviceSecret`) and the paths of its sources.

`bootstrapSecret` is the credential `ajs dms` presents to reach these routes, and setting it closes them. An instance that configures one answers `401 error.frontend.bootstrap_required` to every caller that does not present it.

| Key                | Type                  | Default  | Purpose                                                                                                                                                                       |
| ------------------ | --------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bootstrapSecret`  | `string`              | None     | Shared secret between this instance and its frontend server. Configuring it gates both routes. Set a strong value in production.                                             |
| `requireBootstrap` | `"warn" \| "enforce"` | `"warn"` | Read only when no `bootstrapSecret` is configured. `"warn"` serves an unauthenticated caller a manifest stripped of every private option, and logs once. `"enforce"` answers `401`, which closes the routes to everyone, since no caller has a credential to present. |

```ts fragment
config: {
  frontend: {
    bootstrapSecret: process.env.DMS_BOOTSTRAP_SECRET,
  },
},
```

Set the same value as `DMS_BOOTSTRAP_SECRET` on the frontend server. The DMS does not derive it from `auth.jwtSecret`. The value lives on another host, so it must not be a function of the secret that signs session tokens, and rotating it must not sign every user out.

::warning
`requireBootstrap` cannot open a gated instance again. The presence of the credential decides on its own. To leave the routes open, leave `bootstrapSecret` unset.
::

### Development credentials

In development nothing needs configuring. The instance generates a credential for each boot and publishes it to the project's `.antelope/dms-dev.json`, readable by its owner only and stamped with the process id. `ajs dms dev` and `ajs dms prepare` find it by walking up from the working directory.

The file outlives the instance that wrote it, because deleting it on shutdown could race the credential a replacement backend has just published. Once the process named in a leftover file is gone, the tools ignore the file.

## The module store in `store`

The Modules page installs, updates, pauses and removes the official AntelopeJS modules on a running platform ([Built-in dashboard](/docs/getting-started/built-in-dashboard#the-modules-page-and-the-store)). What it installs goes into `antelope.config.ts`, like a module added with `ajs project modules add`, so every environment loads it.

Owners change modules from the store in development only. In production a new module also needs a frontend rebuild, so the store lists modules read-only and the platform loads what `antelope.config.ts` declares.

| Key          | Type     | Default | Purpose                                                                                                                                                              |
| ------------ | -------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `catalogUrl` | `string` | None    | A remote catalog, shaped like the bundled `data/module-store/catalog.json` and read every hour. The store uses the bundled catalog when this is unset or the URL cannot be read. |

The store writes one entry per module, under the package name:

```ts fragment
modules: {
  "@antelopejs/dms-lang": {
    source: {
      type: "package",
      package: "@antelopejs/dms-lang",
      version: "^0.1.1",
    },
    optional: true,
  },
},
```

The store edits only that entry, through the core. The rest of the file (comments, expressions, other modules) stays as it is. The running project does not restart for the write, since the store has already loaded, stopped or reloaded the module itself. A paused module keeps its entry with `disabled: true`. Uninstalling removes the entry, and the module's data stays where it was.

- **Which entries.** The store manages the entries that install a catalog module from npm, whatever their key, so you can update or pause a module first added by hand from the Modules page. It leaves alone an entry that loads a module from a local folder or git. It recognizes the working copy by the package name in its `package.json`, shows the module as active with that version, and offers no action on it. Installing the same module from npm next to it is refused.
- **Versions.** The store writes a caret range on the latest release. Releases within the range load at the next start. The page offers an update when the latest release falls outside the range, and the update moves the range. The store refuses a release whose `@antelopejs/interface-dms` range the installed DMS does not satisfy, as the runtime would.
- **Starts never blocked.** With `optional: true`, the core loads the module once the others have started, and runs on without it when it fails to download, construct or start. The page then shows it as not running, with an **Apply** action.
- **The frontend loader.** A frontend layer may declare the `@antelopejs/dms-frontend` range it accepts (`engines["@antelopejs/dms-frontend"]` in its `frontend-vue/package.json`, read from the published archive). The store refuses a release whose range excludes the running `@antelopejs/dms-frontend`, as `ajs dms dev` would. The tile names the range, the `pnpm add -D @antelopejs/dms-frontend@<version>` command that would satisfy it, and the installed layers that version would refuse. The store never changes `@antelopejs/dms-frontend` itself. The running version is the one the frontend server reports when it becomes ready, or else the one installed in the project.
- **Interfaces.** A release may depend on an interface no running module implements, such as `@antelopejs/interface-redis` with no Redis module. At install, the store then asks which npm package implements it. It offers the modules the [interfaces registry](https://github.com/AntelopeJS/interfaces) lists for that interface, as `ajs project modules install` does, or any other npm package (never a git or local source), with the JSON config of its entry. The store installs that module first, under its own entry, and undoes the whole install when either fails. A module that other running modules need for such an interface cannot be paused or removed until they are.

The store needs a core that implements the module declaration functions of `@antelopejs/interface-core/modules` (`ListModuleDeclarations`, `SaveModuleDeclaration`, `RemoveModuleDeclaration`), retires the generation `LoadModule` replaces, and refuses a module whose interfaces nothing implements. It also needs a configuration whose default export is an object, plain or through `defineConfig`. Otherwise the store stays read-only and says why.
