Every UI string in the DMS can be a **`$`-prefixed i18n key** instead of literal text. This page covers how the DMS resolves keys, how namespaces divide them, and how locale files ship.

## The `$` key convention

A label that starts with `$` is an i18n key. Anything else is literal text. The `$` is a marker that the frontend reads at runtime, so the key in the JSON file does **not** include it.

```ts fragment [page metadata]
displayName: "$page.tasks.title"; // resolves to t("page.tasks.title")
displayName: "Tasks"; // literal, passes through unchanged
```

Backend page, permission and data type metadata all follow this convention. The frontend resolves a key through `useTranslation().processI18n`, which strips the `$` and calls the `t()` function of Vue I18n.

## Namespaces

Every namespace maps to a top-level object in the locale JSON, without the `$`. Two rules keep layers apart:

- **The base layers own the shared namespaces**, such as `$dms.*`, `$common.*`, `$page.*`, `$menu.*` and `$error.*`. Locales merge across layers, so you can add a key under one of these. Do it on purpose, never by accident.
- **Your module or project takes a namespace of its own.** The maintained modules use `dms_<name>`, as in `$dms_automation.title`. A project does the same, as in `$my_app.report.perm.regenerate`.

Error keys live in the shared `error.*` namespace. [Error feedback](/docs/frontend-composables/ui-toolkit#error-feedback-useapierror) shows how backend messages reach it.

## Ship your locales

Put one JSON file per language under `i18n/locales/` in your frontend module. The loader discovers the files, so nothing declares them. The language code comes from the **file name**, which ends in `<ll>-<CC>.json`, either alone or after a `-`. `my-app-en-GB.json` adds to `en`, and `my-app-fr-FR.json` adds to `fr`. The loader skips a file whose name does not match, without a warning.

At build time the loader merges the files that share a language code across modules. Every module adds to the same language this way, and one namespace can receive keys from several modules. A language other than `en` falls back to the `en` catalog for the keys it lacks. The DMS base module ships `en` and `fr`. Your module joins them when it ships files for the same codes.

```json [frontend-vue/i18n/locales/my-app-en-GB.json]
{
  "my_app": {
    "report": {
      "title": "Reports",
      "perm": { "regenerate": "Regenerate the report" }
    }
  }
}
```

Reference a key as `"$my_app.report.title"` in backend metadata, or as `t("my_app.report.title")` in a Vue template. When a key must exist in several files, one per language, search for a neighbouring key to find them all.

### Special characters

A locale value is a vue-i18n message, not plain text. `{` and `}` open and close a placeholder, `@` starts a linked message (`@:other.key`), and `|` separates plural forms. A raw `@` or an unmatched brace breaks the compilation of the message. A raw `|` turns the message into a plural without a warning. Write such a character as a literal interpolation, with the character quoted inside braces:

| Character | Write    | Example                                 |
| --------- | -------- | --------------------------------------- |
| `@`       | `{'@'}`  | `"Write to support{'@'}example.com"`    |
| `{`       | `{'{'}`  | `"Use {'{'}name{'}'} as a placeholder"` |
| `}`       | `{'}'}`  | (as above)                              |
| `\|`      | `{'\|'}` | `"Monthly {'\|'} Yearly"`               |

A `$` inside a value renders as written. The escaping applies to locale values only. The values a placeholder receives (`params`) are not compiled, so an email address passed as a param needs no escaping. A message that does not compile fails where the page shows it.

## Composed texts

Send a text that names values, such as an amount, a date or a count, as a **composed text** instead of formatting it on the server. A composed text is `{ key, params }`: the key of the message and the raw values. The browser writes it in the reader's language, time zone and clock. The display blocks, the layout banners and your own components accept it (see [Composed texts](/docs/components/block-fundamentals#composed-texts)):

```ts fragment
{ key: "saas.banner.retry", params: { date: { type: "date", value: invoice.retryAt, format: "day" } } }
// "saas.banner.retry": "Payment failed, retry {date}" renders "Payment failed, retry Oct 10"
```

The message is an ordinary entry of your locale files. `params` fill its `{name}` placeholders, and a `count` parameter picks the plural form (`"no seat | {count} seat | {count} seats"`).

## The language of a request

The interface language and the profile's language are the same setting. A signed-in user's dashboard opens in the language stored on their profile (`users.language`). Every language switcher stores the new choice on the profile as it switches the screen: the user menu, the command palette, and the footer of the sign-in pages. A visitor's choice lives in a cookie until they sign in.

A route that words a text for the screen reads the language of the request, not the profile. Every request a block makes carries the interface language in the `x-content-language` header. That is the language the reader sees at that moment.

```ts fragment [src/pages/sales.ts]
@Get("summary")
summary(@Parameter("x-content-language", "header") language: string) {
  return { title: language === "fr" ? "Ventes" : "Sales" };
}
```

A route that sends no worded text at all is simpler. The browser writes a `$` key or a [composed text](#composed-texts) in the language on screen, and the route answers the same JSON whatever the reader's language. Keep `users.language` for what reaches the user outside a page, such as the mails the server sends.

## Dates and times

On **Settings › Language & region**, each user picks a time zone, a first day of the week, a clock (12-hour or 24-hour), and a date format (numeric `01/10/2026` or written `1 Oct 2026`). Each one defaults to automatic: the browser's time zone, and the week and clock of the interface language. The DMS stores them on the user row (`timeZone`, `weekStart`, `timeFormat` and `dateFormat`, all optional). They travel with the session user, so the server-rendered page already uses them.

In a component, format through `useRegionalFormat()` (see [Page context](/docs/frontend-composables/page-context#useregionalformat)). It returns the shared formatters already bound to the interface language and the user's preferences. The interface language is the bare tag (`en`), which `Intl` writes in US conventions, as the DMS's own blocks do. `useRegionalFormat({ locale: "format" })` writes in the locale of the DMS's texts instead (`formatLocale`, which is `en-GB` or `fr-FR`).

```ts fragment [a module's component]
const { formatDateTime, formatPrice, dateTimeFormat } = useRegionalFormat();

const createdAt = computed(() => formatDateTime(props.row.createdAt));
const total = computed(() => formatPrice(props.row.total));
const day = computed(() =>
  dateTimeFormat({ weekday: "long", day: "numeric", month: "long" }).format(
    new Date(props.row.dueAt),
  ),
);
```

The shared formatters apply the preferences for you. They are `formatDate`, `formatTime`, `formatDateTime` and `formatRelativeTime` from `dms-core/app/utils/formatter`. The `date` and `relative_date` table data types use them, and so do notification and activity times, the members' "Last active", and the calendars of date pickers and the period selector.

Outside a component, such as in a plugin or a plain function, call the formatters directly and pass the locale. Without one, they write `en-US`. Use them instead of a bare `Intl.DateTimeFormat`. For a custom format, use `regionalDateTimeFormat(locale, options)` from `dms-core/app/utils/regional`, which takes the `Intl` options and adds the user's preferences.

Options you pass win. The formatter keeps a `timeZone`, `hour12` or `hourCycle` you pass, and the date format rewrites only full dates (day, month and year). For a calendar day computed in the browser, pass `{ keepLocalZone: true }` so the value does not move to another zone. A server render writes dates in the browser's own zone, which the browser keeps in its `dms-time-zone` cookie, so the HTML shows the dates the browser shows. The user's chosen zone still comes first.

A screen that needs the values themselves, such as a calendar's `weekStartsOn` or the zone to show next to a time, reads them from `useUserRegionalPreferences()` (see [Page context](/docs/frontend-composables/page-context#useuserregionalpreferences)).

Amounts keep the currency of their data. The DMS has no display-currency preference, because it cannot convert an amount into another currency.
