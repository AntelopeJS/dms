# Upgrading to DMS 0.9

DMS 0.9 ships with `@antelopejs/dms-frontend` 0.6 and `@antelopejs/interface-dms` 0.7, in one coordinated release: nothing of the previous releases is kept for compatibility. A module upgrades its frontend range, its backend routes and its reads together. The renderer's own changes are listed in its changelog (v0.6.0, "Migration for module authors"); this page covers what the DMS adds on top.

## The loader range

A frontend module's `package.json` declares the new loader range:

```json [frontend-vue/package.json]
{
  "engines": {
    "@antelopejs/dms-frontend": ">=0.6.0 <0.7.0"
  }
}
```

## Backend routes the browser reaches

The frontend server proxies only the backend prefixes declared to it and answers every other path with a page; a write to a page path is a `404`. The DMS declares `/api/**` and `/dms/**` in its own `dms.server.ts`.

- **Page controller routes moved under `/dms/pages`.** A route a `PageController` or `RootPageController` declares sat at the page's own path (`/settings/user/security/sessions`), which is now the page. It is served at `/dms/pages<slug><route>`: build the URL with `pageRoutePath(slug, route)`, from `@antelopejs/interface-dms/page` on the backend and auto-imported in a layer (`#dms-core/app/utils/pageRoutes`). A page's `layoutUrl` follows (`/dms/pages<slug>/pagelayout`). A `fetchUrl`, `submitUrl`, `url` or `confirm.from` naming a page route changes the same way.
- **A plain `Controller` your frontend calls** belongs under `/api/<module>/`. A prefix outside `/api/**` and `/dms/**` (media, a webhook) is declared in `AddFrontendModule`:

  ```ts
  await AddFrontendModule({
    // …
    backendProxies: [{ path: "/media/**", auth: "none" }],
  });
  ```

  `auth: "session"` (the default) adds the session's token server-side; `"none"` sends no session. A frontend module can declare one in its `dms.server.ts` instead, with `server.registerBackendProxy(pattern, options)`.

## Reading data: `useApiData`

- **Every read a component renders goes through `useApiData`**: a page's data in the server render, a dialog's or a drawer's with `immediate: false` and `execute()` once it opens, polling with `refreshInterval`. `$authFetch` is for writes. `useAuthFetch().useFetchAuth`, the former name of `useApiData`, is gone.
- **Drop the `refresh()` calls made after a write.** `refreshPageBlocks()` and the events of the page's realtime topics read every `useApiData` of the page again. A read that refreshes on triggers of its own (`usePageLiveRefresh`) opts out with `refreshOnPageRefresh: false`, or it is read twice.
- **Drop any reset of `status` meant to force a read on mount** (`status.value = "idle"`): data read before shows at once and is read again on each mount.
- **Keys are scoped per account and workspace** by the DMS: drop the account or tenant id you added to a key to keep sessions apart, and anything that cleared the cache on a switch.
- **`data` is a shallow ref.** Replace the value instead of changing it in place (`data.value.rows.push(row)` no longer updates the view), or pass `deep: true`.
- **A call without a key renders its default on the server.** Give every server-rendered `useDmsAsyncData` a key.
- **A reactive request that fails no longer shows the previous request's data**: it belonged to another record. A failed read of the same request still keeps the last data.
- The result's type is exported: `ApiDataResult<T>`.
- **Polling stops through its interval.** `refreshInterval` may be a ref or a getter; `0` or `null` stops it until it has a value again (an install check, a job that finished). A `useApiData` called from a plugin, outside any component, polls for as long as the application runs: a status or a sidecar check needs no component of its own.
- **"Load more" lists use `useApiPagedData`.** `useApiPagedData(key, ({ $authFetch, cursor, signal }) => …, { nextCursor, initialCursor })` keeps every page under one key: the server renders the first page, `loadMore()` appends the next one (`pages`, `hasMore`, `loadingMore`), and the page's refreshes read every loaded page again. Put the folder or the filters in the key.
- **`refreshPageBlocks()` returns a promise** that resolves once the page's `useApiData` reads are read again: await it where a write must see the fresh data before going on.
- **`useApiData(url, { key })`** takes a ref or a getter for `key` too.
- **A test that looks for a response's entry** computes its key with `dmsRequestKey(url, { query, body })` from `#dms/frontend-module` instead of hashing the request itself; the DMS's scope (`<scope>|`) prefixes it in the runtime's map.

See [Auth requests & permissions](/docs/frontend-composables/authenticated-requests) for the patterns (chained reads, an editable draft, readers and writers).

## The site layout

The site layout (`shared`, `/dms/sitelayout`, `useSiteLayout().siteLayout`) is a cached Inertia prop, and its format changed:

- **Categories are listed once.** `siteLayout.categories` holds every category, keyed by **full id** (it was keyed by slug, navigable categories only). Pages, categories and tree nodes name their category with `categoryId` instead of carrying a `category` object. A category with `urlTransparent` answers at its parent's slug.
- **Navigation badges left the menu.** The counts published with `navBadge` are served with each page visit, as the page's `navBadges` (`{ badge, tone? }` by page full id), and drawn by the DMS's navigation. The menu keeps a page's static `badge` only; `badgeTone` is no longer served on menu entries.
- **Menu resyncs are per member.** An access change (a role's permissions, a member's roles or ownership, a removal) publishes `menu-changed` on the topic of each member it changes, `menu:member:<tenant>:<user>`, not on the workspace's. `NotifyMenuChanged(tenantId)` still reaches the whole workspace.

## Server routes and cookies

- The DMS serves the session, sign-in, OAuth and e-mail render routes from its `dms.server.ts`; the renderer has none of its own. The DMS API serves the API tester.
- `dms_*` sealed cookies belong to the DMS; another module's sealed cookies are stored as `<module id>.<name>`.
- The manifest's private secrets win over `DMS_OAUTH_RELAY_SECRET` / `DMS_HTML_RENDER_SECRET`, which are the fallback for a frontend built without them.

## Renamed renderer helpers

`getDmsComponent` is `resolveDmsComponent`, and `prefetchComponents` is `preloadDmsComponents`. `useDmsLazyAsyncData` is gone: pass `lazy: true` to `useApiData` (or `useDmsAsyncData`).

Every generic runtime API carries `Dms`, with no alias left: `useUserSession` is `useDmsUserSession`, `useError` is `useDmsError`, `clearError` is `clearDmsError`, `createError` is `createDmsError`, `showError` is `showDmsError`, `abortNavigation` is `abortDmsNavigation`, `preloadComponents` is `preloadDmsComponents`, and `app.config.ts` calls `defineDmsAppConfig`. Rename the auto-imported calls too: the old names are no longer declared.

## Removed import paths

The former paths kept for compatibility are gone: import `usePageRecordLabel` from `#dms-core/app/composables/page/usePageRecordLabel` and `useControlError` from `#dms-ui/app/composables/form/useControlError` (or rely on their auto-imports).
