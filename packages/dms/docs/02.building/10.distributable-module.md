Most DMS work is a **project** that loads the DMS and registers its own pages ([Project setup](/docs/building/project-setup)). The rarer case is a **distributable extension module** that other projects install, the way the official `dms-*` modules ship. Pages, components, DataTypes, auth and the lifecycle work the same as in a project (the Building and Frontend sections). A module differs only in how it is packaged and loaded:

- A consumer installs it and adds it to their `antelope.config.ts` as a `package` or `git` module. A project wires its own code as the `local` module instead.
- It may define **its own AntelopeJS interface** so other modules can extend it. Many distributable modules publish no interface at all.

A DMS module is an ordinary AntelopeJS module. It depends on `@antelopejs/dms`, registers a module and its pages when it loads, and ships a Vue frontend module for any custom frontend.

## Lay out the module directory

The maintained modules use variations of the layout below. Adapt it to your module.

```bash [<module-name>/]
<module-name>/
  src/
    index.ts                        # entry: construct/start/stop/destroy + RegisterModule + AddFrontendModule
    db/                             # schema, models, tables (if it owns data)
    pages/                          # @RegisterPage, @RegisterPageExtension      → see Pages & components
    routes/                         # HTTP controllers feeding components         → see Pages & components
    services/  utils/  types/       # internal logic and constants
  frontend-vue/                     # the module's Vue frontend module            → see Frontend layer
    dms.frontend.ts                 # entry: registers pages, components, plugins, the stylesheet
    app/{components,composables,types}/
    i18n/locales/*.json
  package.json
  tsconfig.json
```

## Write the lifecycle entry (`src/index.ts`)

The entry file has two jobs.

Its **side-effect imports** run your decorators: `@RegisterPage`, `@RegisterPageExtension`, `@RegisterDataType` and the DataControllers, as in a project. A module that only extends another module's pages ([Extending another module's page](/docs/building/pages-and-components#extending-another-modules-page)) still needs those imports. The injection happens when the decorator runs, and it applies whenever the target page registers, before or after.

Its **lifecycle exports** place each registration at the right moment. `construct`, `start`, `stop` and `destroy` are a framework concept ([Creating a module](https://antelopejs.com/docs/module-development/creating-a-module)).

- **`construct(config)`** receives the consumer's config and attaches the frontend module with `AddFrontendModule`. Wire an interface implementation (`ImplementInterface`) here too. A module with a frontend also declares it as `dmsFrontend` in its `package.json` ([The module manifest](#the-module-manifest-antelopejs-in-packagejson)). Without that declaration, the frontend leaves the module out, in development and in production.
- **`start()`** begins runtime work. Provision the database schema (`RegisterSchema`), fill caches and schedule cron jobs here.
- **`stop()`** and **`destroy()`** release those resources.

`RegisterModule` is the exception. It runs at **import time**, at the top level of the file.

```ts fragment [src/index.ts]
import { resolve } from "node:path";
import "./db"; // side-effect imports: decorators register on import
import "./pages";
import { RegisterSchema } from "@antelopejs/interface-database-decorators";
import { AddFrontendModule, RegisterModule } from "@antelopejs/interface-dms/page";

export interface Config {
  /* whatever the consumer passes under this module's config */
}
let config: Config;

export const myModule = RegisterModule({
  id: "<name>", // pages attach with module: "<name>"
  title: "$your_module.title", // i18n key, see Localization
  description: "$your_module.description",
  icon: "i-ph-cube",
});

export async function construct(cfg: Config): Promise<void> {
  config = cfg;
  await AddFrontendModule({
    name: "my-module",
    sourcePath: resolve(__dirname, "../frontend-vue"),
    renderer: { name: "vue", version: "3" },
  });
}

export async function start(): Promise<void> {
  await RegisterSchema("<module-name>"); // provision the schema once the database is up
}

export function stop(): void {
  /* stop cron, deactivate subscriptions */
}
```

### Register the dashboard entry with `RegisterModule`

`RegisterModule(opts)` registers a top-level module in the dashboard navigation and returns a `CategoryInfo`, the module root. Call it at the top level of a file, usually `src/index.ts`. It must run before the module's pages register, because a page that names an unknown module throws. A second call with the same `id` throws `Module "<id>" is already registered.`. [Module navigation and access](#module-navigation-and-access) covers how pages attach, their URLs and the access model.

```ts [src/index.ts]
import { RegisterModule } from "@antelopejs/interface-dms/page";

export const demoModule = RegisterModule({
  id: "demo", // pages attach with module: "demo"
  title: "Demo Module", // use a "$dms_demo.title" i18n key in real modules
  description: "A demo module to showcase the module system",
  icon: "i-ph-cube",
  // landingPage: "<page-id>",         // page shown when entering the module
  defaultCategory: {
    // groups the module's loose pages under a heading
    displayName: "Demo Pages",
    icon: "i-ph-files",
    order: 0,
  },
});
```

`defaultCategory` also takes a `urlSlug`, which defaults to `pages`. Without a `displayName`, the heading reads the generic "Pages" label.

## Module navigation and access

A module ships its own **separate sidebar**. [Navigation](/docs/building/navigation) covers the dashboard tree it sits in. A page joins the module by setting **`module: "<id>"`**. Its `category` decides where it lands inside the module:

- With a `category`, the page lands under that category. The category must descend from the module root that `RegisterModule` returns, so nest your categories under it.
- Without a `category`, the page lands under the module's `defaultCategory`, or under a generic "Pages" heading when the module declares none.

Registration enforces three rules, and each one throws:

- A page's `category` must descend from its module's root.
- A module page cannot use the Settings category. A module declares its settings pages inside its own sidebar.
- The module must already exist. A page that names an unknown module throws.

Module pages resolve at **`/modules/<moduleId>/<urlSlug>`**. Entering the module opens its `landingPage` when that page exists, and otherwise the first page in menu order. The DMS does not remember where the user was in the module. An empty module resolves to `/modules/<moduleId>`.

The DMS serves the module's own address, **`/modules/<moduleId>`**, as a redirect to that landing page. When the caller may not open `landingPage`, the redirect goes to the first page they may open. The redirect keeps the query and the hash the address was opened with, so `/modules/api?live=0` opens the landing page paused. A server render answers with a redirect. In the browser (a typed URL, a return from sign-in, the module's breadcrumb), the navigation goes straight to the landing page, so the module's address never enters the history. A module needs no hidden page of its own at that address.

::warning
A hand-written link or `router.push({ path })` to a module page **must** include the `/modules/<moduleId>` prefix. Without it, the frontend catch-all answers 404, even with a clean backend build. Read `fullSlug` from the page or site layout instead of hardcoding paths.
::

Access is **owner-only by design**. The Modules group, and every page and category inside it, is visible to the **platform owner** alone, the user flagged `owner` ([Auth & permissions](/docs/auth-and-tenancy/auth-and-permissions)). On a SaaS deployment the platform owner is you, the maker. Your customers are tenant owners ([SaaS mode](/docs/auth-and-tenancy/saas-mode#the-two-roles)). Page and component permission ids still exist, prefixed **`modules.<moduleId>.…`**, but they are **module-scoped**:

- They never appear in the grantable Roles tree.
- Permission checks deny them to any non-owner, whatever the stored role grants say.
- Per-page permissions have no effect inside the module. The owner sees everything.

Design module pages as owner and admin areas.

On the frontend, `useCurrentModule()` returns the module that owns the current route ([Page context](/docs/frontend-composables/page-context)).

## The module manifest (`antelopeJs` in `package.json`)

The AntelopeJS core reads a module's manifest from the `antelopeJs` key of its `package.json`. Two fields matter for packaging:

```json [package.json]
{
  "name": "@acme/dms-invoices",
  "antelopeJs": {
    "baseUrl": "dist",
    "implements": ["@acme/interface-dms-invoices"]
  }
}
```

- **`baseUrl`** points at the compiled output the core loads.
- **`implements`** lists every interface package this module provides at runtime. There is no `imports` counterpart. What a module consumes is its ordinary `dependencies`.

A module with a frontend adds a top-level **`dmsFrontend`** next to `main`. It names the compiled file that exports the module's `frontendModule(config, { dev })`, the function whose result the backend passes to `AddFrontendModule`. `ajs dms dev`, `ajs dms build` and `ajs dms start` read the project, and include a module's frontend through this declaration alone ([Frontend layer](/docs/building/frontend-layer#how-module-config-reaches-vue)):

```json [package.json]
{
  "main": "dist/index.js",
  "dmsFrontend": "dist/frontend-module.js"
}
```

At startup the core walks the `dependencies` of each loaded module and decides which ones are interface dependencies. It skips a dependency that is itself a module in the project, or that a loaded module lists in `implements`. It counts a remaining dependency as an interface when the resolved package has an `antelopeJs` key and its `implements` is empty, missing, or lists only the package's own name. Every interface dependency must be implemented by a loaded module, or the boot fails with:

```text
Unresolved interface dependencies:
  - <module> requires <package>

Run 'ajs project modules install' to resolve missing dependencies.
```

An interface package whose manifest sets `standalone: true` is the exception. The core stubs it instead of failing the boot.

A runtime package that implements other interfaces is never taken for an interface, so consumers may list it in `dependencies` and import from it. `@antelopejs/dms` lists `["@antelopejs/interface-dms"]` alone in `implements`, and exports only its root entry. Extensions name their target page by id ([Extending another module's page](/docs/building/pages-and-components#extending-another-modules-page)) and import nothing but the interface package.

## Expose an interface (optional)

A module can define **its own AntelopeJS interface** so other modules extend it. Authoring, implementing and wiring interfaces is framework territory. [Interfaces](https://antelopejs.com/docs/concepts/interfaces) and [Exporting interfaces](https://antelopejs.com/docs/module-development/exporting-interfaces) are the reference. On the packaging side, declare each interface as an explicit `exports` subpath of your `package.json` so consumers can import it.
