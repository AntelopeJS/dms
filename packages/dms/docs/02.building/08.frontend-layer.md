Most admin screens need no frontend code. The backend describes them, and the Inertia and Vue frontend renders them ([Architecture](/docs/getting-started/architecture)). A **frontend module** is optional. Add one when a screen needs a **custom component** the standard builders do not cover, or to **override** a component the DMS already ships. "Layer" is the older name for the same unit, and the loader calls it a frontend module.

That code lives in `frontend-vue/`. A `frontendModule` function describes it: the backend passes the function's result to `AddFrontendModule`, and the package declares the function as `dmsFrontend` ([How module config reaches Vue](#how-module-config-reaches-vue)). The frontend loader that `ajs dms` runs serves it ([Frontend CLI](/docs/building/frontend-cli)). This page covers what a dashboard project writes in that module, and how the loader turns it into rendered pages.

For a concrete result, see the [custom retention input](/docs/components/forms/custom-inputs#custom-input-in-a-real-form). Its Vue component adjusts a value, displays a validation error and asks for confirmation, while the DMS form still owns saving.

::note
The [Frontend](/docs/frontend) section holds the loader's own reference. It covers every file a frontend module may ship (`dms.server.ts`, `dms.frontend.build.ts`, server routes, route rules), the server rendering model, and the deployment of the frontend server.
::

## Layout

A frontend module is a plain npm package with one required file, `dms.frontend.ts`, at its root. The loader discovers a few other files and directories by convention:

```bash [frontend-vue/]
frontend-vue/
  package.json                   # "type": "module", "main": "./dms.frontend.ts", engines
  dms.frontend.ts                # the entry: registers everything explicitly
  app/
    app.config.ts                # discovered by convention, see Theming and branding
    components/                  # Vue SFCs, registered by name from the entry
    composables/                 # useXxx composables, auto-imported when declared, see Auto-imports
    plugins/                     # defineDmsPlugin setups, registered from the entry
    utils/                       # helpers
    config/
      shortcuts-registry.ts      # discovered by convention, see UI toolkit
  i18n/
    locales/<module>-<ll>-<CC>.json   # discovered by convention, see Localization
  public/                        # static files, discovered by convention
```

The loader finds five things on its own: `dms.frontend.ts`, `app/app.config.ts` (see [Theming and branding](/docs/extending-the-dashboard/theming-and-branding)), `app/config/shortcuts-registry.ts`, `i18n/locales/*.json` and `public/`. Everything else reaches the dashboard because the entry registers it: components, plugins and middleware. A module has no `nuxt.config.ts` and no `extends` chain. [Auto-imports](#auto-imports) covers which directories are auto-imported.

::note
A large module may split the convention-discovered directories into sub-roots under `layers/<name>/`. The DMS itself is organised this way (`dms-core`, `dms-ui`, `dms-auth`, and others). The split is all or nothing. Once `layers/` exists, the loader scans the sub-roots and stops scanning the module root. `dms.frontend.ts` stays at the module root either way. A module's own `layers/<name>/` also becomes the `#<name>/*` import alias.
::

## The module entry

`dms.frontend.ts` default-exports a `DmsFrontendModule`. It is an object with one `setup(sdk)` method and an optional `componentPrefix` (see [Component naming](#component-naming)). The loader awaits `setup` once per module, in priority order, while the app boots.

```ts fragment [frontend-vue/dms.frontend.ts]
import { type Component, defineAsyncComponent } from "vue";
import type { DmsFrontendModule } from "#dms/frontend-module";
import ratingDataType from "./app/plugins/rating-data-type.client";

interface VueModule {
  default: Component;
}

// Every component is addressed by name from the backend, so registering the
// whole directory keeps the two sides in sync without a manual list.
const components = import.meta.glob<VueModule>("./app/components/**/*.vue");

const frontendModule: DmsFrontendModule = {
  // Put in front of every name registered below: GraphCanvas.vue registers
  // as YourModuleGraphCanvas.
  componentPrefix: "YourModule",
  setup(sdk) {
    for (const [path, loader] of Object.entries(components).sort()) {
      const name = path.split("/").at(-1)!.replace(/\.vue$/, "");
      sdk.registerComponent(
        name,
        defineAsyncComponent(async () => (await loader()).default),
      );
    }
    // Client-only: the display it registers carries callables, which the SSR
    // payload strips.
    sdk.registerPlugin(ratingDataType, { clientOnly: true });
  },
};

export default frontendModule;
```

The `sdk` handed to `setup` is the module's whole contract with the dashboard:

| Member | What it does |
| ------ | ------------ |
| `options` | The module's public options, as `{ public }`. See [How module config reaches Vue](#how-module-config-reaches-vue). |
| `registerComponent(name, component, options?)` | Makes a component resolvable by the name the backend puts in a serialized tree, behind the module's `componentPrefix`. `{ prefix: false }` registers the name as given (see [Overriding an existing component](#overriding-an-existing-component)). |
| `registerPage(name, component, preload?)` | Registers a full Inertia page component. |
| `registerDynamicPage(name, component, preload?)` | Registers a renderer for a backend-described page kind. |
| `registerLayout(name, component, preload?)` | Registers a page layout. |
| `registerErrorPage(component, preload?)` | Replaces the error page. |
| `registerPlugin(setup, { clientOnly?, enforce? })` | Runs a `defineDmsPlugin` setup at boot, on the client only when `clientOnly` is set. `enforce` is `"pre"`, `"default"` or `"post"`, as in Nuxt. |
| `registerMiddleware(name, handler, { global?, parallel? })` | Adds navigation middleware, named or global. A `parallel` middleware runs at the same time as the parallel middlewares next to it. |
| `registerAccessRedirect(code, path)` | Sends a page visit that the backend refuses with a typed 403 whose body is `code` to `path`, instead of the error page. |
| `provide(key, value)` | Provides a value to the whole Vue app. |
| `use(plugin)` | Installs a Vue plugin. |

Every registration under a name or key is **first write wins**. A name already taken by an earlier module stays with that module. Priority matters for that reason (see [Overriding an existing component](#overriding-an-existing-component)).

## Imports from the module runtime

Everything the dashboard exposes to a module comes from the `#dms/frontend-module` alias, which the generated workspace maps to its own runtime. Import from it explicitly.

```ts fragment [frontend-vue/app/components/ExampleView.vue]
import {
  DmsLink,
  useDmsAsyncData,
  useDmsRoute,
  useDmsRouter,
  useDmsRuntimeConfig,
} from "#dms/frontend-module";
```

The alias also carries `defineDmsPlugin`, `defineDmsMiddleware`, `useDmsFetch`, `useDmsData`, `useDmsState`, `useDmsCookie`, `useI18n`, `useHead`, `useSeoMeta`, `navigateDms`, `resolveDmsComponent` and the `Dms*` types the registrations take. A module reaches the composables in [Frontend composables](/docs/frontend-composables/overview) the same way.

State lives in composables. The dashboard has no global store, neither Vuex nor Pinia. Follow the existing modules' `useXxx` composables instead of adding a store.

## Auto-imports

An auto-imported export is available to the whole application, in scripts and templates, without an `import`. Auto-imports are opt-in. A module declares its auto-imported directories in an optional `dms.frontend.build.ts`, next to `dms.frontend.ts`:

```ts fragment [frontend-vue/dms.frontend.build.ts]
import { defineDmsFrontendBuild } from "#dms/frontend-build";

export default defineDmsFrontendBuild((build) => {
  build.registerAutoImports(["app/composables", "app/utils", "app/types"]);
});
```

- Each entry is a directory relative to the module root, and may hold glob patterns, such as `layers/*/app/composables` for a module split into layers. Every export of the files under it is auto-imported.
- A module without the file has nothing auto-imported.
- `app/build/` is never auto-imported. The loader leaves it out of a broader entry. An entry that names it, or a directory outside the module, is ignored with a warning when Vite starts. Import `app/build/` code by path.
- The file runs in Node.js when Vite starts (`ajs dms dev`, `ajs dms build`), not in the application. It may import `#dms/frontend-build` and Node.js built-ins, never the application's own code. Vite restarts when it changes.
- `build.registerVitePlugins(() => [...])` adds Vite plugins to the build, after the renderer's own plugins. The function is synchronous.

### What the DMS layer exposes

In each of the DMS's own layers (`dms-core`, `dms-ui`, `dms-layout`, and others), the `components/`, `composables/`, `utils/` and `types/` folders under `app/` are the public API. Their components are global, their exports are auto-imported, and a module may rely on them.

`app/build/` holds the DMS's internals. Nothing under it is a contract, and its exports are not auto-imported, because the DMS's `dms.frontend.build.ts` declares the public folders only. Its components are registered like the others, under the `Dms` prefix, so the DMS's backend pages can name them. That does not make them API. A module that renders or imports one depends on internals that change without notice.

The DMS's composables take the plain `use<Thing>` name, with no `Dms` prefix: `useSiteLayout`, `useModal`, `useDevReload`. The `Dms` prefix belongs to the `#dms/frontend-module` runtime. The runtime puts it on every generic API it defines (`useDmsFetch`, `useDmsRoute`, `useDmsState`, `useDmsUserSession`, `useDmsError`, `defineDmsAppConfig`). Only the upstream APIs it re-exports unchanged keep their names (`useHead`, `useSeoMeta`, `useI18n`, `$fetch`).

### Linting auto-imported names

ESLint's `no-undef` reports an auto-imported name as undefined unless the config declares it. Two packages publish the names as flat-config globals:

- `@antelopejs/dms/eslint-globals` covers every export of the DMS layer's `composables/`, `utils/` and `types/` folders (`useAuthFetch`, `useApiData`, `useSidePanel`, …).
- `@antelopejs/dms-frontend/eslint-globals` covers the renderer's own auto-imports: Vue, `#dms/frontend-module` and Nuxt UI's composables.

```js [frontend-vue/eslint.config.mjs]
import dmsGlobals from "@antelopejs/dms/eslint-globals";
import rendererGlobals from "@antelopejs/dms-frontend/eslint-globals";

export default [
  {
    languageOptions: {
      globals: { ...rendererGlobals, ...dmsGlobals },
      parserOptions: { lib: ["esnext", "dom", "dom.iterable"] },
    },
    rules: { "no-undef": "error" },
  },
];
```

Names your own module auto-imports are not in either object. Declare them in the same `globals`.

`parserOptions.lib` names the TypeScript libs your code compiles with, so that `@typescript-eslint/parser` declares their types (`RequestInit`, `ParentNode`, …) and `no-undef` accepts them.

## Component naming

A component's name is the module's `componentPrefix` followed by the string you pass to `sdk.registerComponent`. The backend puts that full name in a `CustomComponent(...)` call or in a data type's input declaration. With `componentPrefix: "YourModule"`, `registerComponent("GraphCanvas", ...)` registers `YourModuleGraphCanvas`, and the backend sends `CustomComponent("YourModuleGraphCanvas")`. The DMS's own prefix is `Dms`. A module without a `componentPrefix` registers names as given.

Lookups are **normalized**. The registry strips a leading `lazy` and every non-alphanumeric character, then lowercases the rest, so `YourModuleGraphCanvas` and `your-module-graph-canvas` resolve to the same component. A leading `Dms` is kept, because it is the DMS's prefix. `DmsTable` and another module's `Table` are two components.

- Pick a prefix of your own, so your names never collide with another module's. When two modules still register the same full name, the module of higher priority keeps it. The browser console then warns, naming both modules.
- A component the registry cannot find renders a bare `<div>`, because the tree resolver falls back to `"div"` instead of failing. When a pane comes up empty with no console error, check the name first and the component second.

## Overriding an existing component

Modules **compose**. The registrations of every loaded module coexist, and adding a module adds components. Replacing a component the DMS ships is a deliberate and heavy change. For logos, colours and design tokens, use [Theming and branding](/docs/extending-the-dashboard/theming-and-branding) instead.

A real override needs two conditions:

1. **Register the same full name, without your prefix.** `sdk.registerComponent("DmsFoo", MyFoo, { prefix: false })` replaces the DMS's `DmsFoo`, and the console does not report it as a collision. A different name produces a _different_ component, not an override.
2. **Give your module a higher `priority`.** The loader materializes modules in descending priority order and sets them up in that order, and the first registration of a name wins. The base module sits at `priority: 0`, so use `priority: 1` to take a name from it. Modules of equal priority keep the order the loader reads them in. Give them distinct priorities instead of relying on that order.

After you change a module's priority, regenerate the frontend workspace.

## How module config reaches Vue

A module describes its frontend once, in a function of its configuration. The function names the module, points at its source directory, declares the renderer it targets, and carries its options. It reads nothing but its arguments, so both the backend and the frontend loader can call it. The file exports it as `frontendModule`, typed `FrontendModuleFunction` from `@antelopejs/interface-dms/page`:

```ts fragment [src/frontend-module.ts]
import { resolve } from "node:path";
import type { FrontendModuleFunction } from "@antelopejs/interface-dms/page";
import type { Config } from "./config";

export const frontendModule: FrontendModuleFunction<Config> = (config) => ({
  name: "@antelopejs/my-module",
  sourcePath: resolve(__dirname, "../frontend-vue"),
  renderer: { name: "vue", version: "3" },
  configKey: "myModule",
  priority: 1,
  options: { readOnly: config.readOnly ?? false }, // public, read as runtimeConfig.public.myModule
  privateOptions: { apiKey: "" }, // named here, valued by the backend
});
```

The backend registers the function's result with the private values ([Project setup](/docs/building/project-setup)), and the package names the compiled file as `dmsFrontend`:

```ts fragment [src/index.ts]
export async function start() {
  const { dev } = await GetRuntimeInfo();
  const registration = frontendModule(getConfig(), { dev });
  if (!registration) return;
  await AddFrontendModule({
    ...registration,
    privateOptions: { apiKey: getConfig().apiKey },
  });
}
```

```json [package.json]
{
  "main": "dist/index.js",
  "dmsFrontend": "dist/frontend-module.js"
}
```

The frontend loader reads the declaration. `ajs dms dev`, `ajs dms build` and `ajs dms start` evaluate `antelope.config.ts` and call the `dmsFrontend` function of each module the project loads, with that module's configuration. Under `ajs dms dev`, the context says `dev: true`. `ajs dms build` and `ajs dms start` ask no backend. Under `ajs dms dev`, the backend's registration supplies what only the running backend holds: the private values, the development origins, and the set of modules that `dev` follows to rebuild when the module store changes it.

A package that ships `frontend-vue/` without the declaration is left out of every frontend, development included. `build` warns that it left the module out, and `dev` warns that the backend registers a module the project does not serve. Keep the file free of runtime imports, such as API decorators and interface calls, because the frontend loader loads it on its own.

::note
`renderer` decides which frontend loads the module. The backend groups modules by renderer name and major version, and the `GET /dms/frontend` manifest serves one renderer at a time, `vue` 3 when the caller names none. A renderer with no module answers `error.frontend_renderer_not_found`. `{ name: "vue", version: "3" }` is the only pair the shipped loader asks for.
::

`options` are public. The loader merges them into the frontend runtime config, under `configKey` when one is given, and hands the same object to your entry as `sdk.options.public`:

```ts fragment [frontend-vue]
const { readOnly } = useDmsRuntimeConfig().public.myModule;
```

`privateOptions` are secrets. The Vue renderer does not pass them to a frontend module. A build keeps their shape only, with every string emptied. `ajs dms start` fills them from its own environment: `DMS_HTML_RENDER_SECRET`, `DMS_OAUTH_RELAY_SECRET`, and `DMS_PRIVATE_OPTIONS` (JSON keyed by module id) for any other module. `ajs dms dev` reads them from the local backend's manifest, and writes its manifest cache with mode `0600` for that reason.

::warning
The backend serves the manifest behind the [`frontend.bootstrapSecret`](/docs/building/configuration#bootstrap-protection) gate. A backend that configures a secret refuses a caller that does not present it. A backend that configures none serves the manifest to anyone, stripped of every private option, and logs a warning. Set `frontend.requireBootstrap: "enforce"` to refuse those callers too. A private option can therefore be missing from `runtimeConfig[configKey]`, in development and in a production server started without its variable. Read it defensively, or state the requirement in your module's setup docs. A module's source directory reaches whoever builds the frontend, so keep secrets out of the files under `sourcePath`.
::

## Declaring the loader releases a module supports

`renderer` names a framework, not a release of the loader that builds it. In `{ name: "vue", version: "3" }`, `version` is the framework's major version, and it means the same thing under every `@antelopejs/dms-frontend` release. A module declares the loader releases it runs on in its own `package.json`, the way a package declares the Node.js versions it supports:

```json [frontend-vue/package.json]
{
  "name": "@acme/dms-billing-frontend-vue",
  "type": "module",
  "main": "./dms.frontend.ts",
  "engines": {
    "@antelopejs/dms-frontend": "<the loader releases you check the module against>"
  }
}
```

The loader reads `engines["@antelopejs/dms-frontend"]` before it generates the workspace, in `dev`, `build`, `prepare` and `verify-source`. When its own release falls outside the range, it stops with `These frontend modules do not run on @antelopejs/dms-frontend <release>` and lists each module with its range. It does not fail later on an API that a release removed or does not have yet. A module that declares no range still loads, with a one-time warning.

Start the range at the lowest release the module is checked against, and cap it below the next breaking release. While the loader is 0.x, that is the next minor release. When a new loader release ships, check the module against it, then widen the range in a release of the module. A range open up to `<1.0.0` admits the release that removes something the module calls.

## Localization

A module adds translations as JSON files under `i18n/locales/`. The loader discovers them without any declaration. The language code comes from the **file name**, which ends in `<ll>-<CC>.json` (`marketing-en-GB.json` adds to `en`). Files that share a language code merge across modules at build time. Every module adds to the same language this way, and one namespace can receive keys from several modules. See [Localization](/docs/building/localization).

## How a backend-described page renders

One dynamic page component renders every backend-defined page:

1. The backend serves the page's route metadata and its serialized component tree.
2. The renderer maps each node's `componentName` to a real component with `resolveDmsComponent(name) || "div"`. It recurses through the node's children and carries each child's `slot` and `colSpan`.
3. The renderer draws the resolved tree one top-level node at a time, and wires page realtime, permission refresh and page setup functions alongside it.

A backend edit therefore changes the UI. The page is **data** the frontend draws, not a compiled Vue route.

## The materialized workspace is a physical copy

The **`ajs dms` CLI** materializes every resolved module as physical files, not the backend. `ajs dms build` and `ajs dms start` use `<project>/.dms-frontend`, or the `--workspace` directory. Other workspaces live under `~/.antelopejs/dms-frontend/<sha256(workspaceKey)>/`. The workspace key is the canonical backend URL, or `project:<absolute project path>` when `dev` discovers the backend on its own.

Each module lands in `frontend-modules/<safeName>/` inside the workspace. The `safeName` is the module's package name with a leading `@` removed and every `/` replaced by `__`, so `@antelopejs/my-module` becomes `antelopejs__my-module`. Each copy is a pnpm workspace package of the generated workspace, and the dev server serves **those copies**, not your module's `frontend-vue/` source.

The module's `.gitignore` filters the copy, so `node_modules`, build output and caches stay out of it. Nothing is symlinked, even in dev. pnpm resolves workspace packages through their real path, and a symlink would install the module's transitive dependencies back into your source tree.

In dev, `ajs dms dev` runs file watchers that resync source edits into the materialized copy. Adds, changes and deletes mirror as they happen, not only on restart. A `.vue` or composable edit therefore reaches the dashboard on its own. If a reload still does not show the change, suspect a stale copy.

The resync applies to **every** resolved frontend module, not only the ones you develop locally. The `dmsFrontend` declaration of each module the project loads is what includes it.

## Read the registered frontend modules from the backend

A backend module can list the registered frontend modules with `GetFrontendModules()` from `@antelopejs/interface-dms/page`. Each entry holds the name, source directory and public options, never the private ones. The list changes as modules register or are taken down. Modules start in parallel, so a module that reads the list in its own `start()` may run before another registers. Register a handler on `FrontendModulesChanged` first, read the list once, and read it again in the handler:

```ts fragment
import { FrontendModulesChanged, GetFrontendModules } from "@antelopejs/interface-dms/page";

FrontendModulesChanged.register(() => void refresh());
await refresh(); // reads GetFrontendModules()
```
