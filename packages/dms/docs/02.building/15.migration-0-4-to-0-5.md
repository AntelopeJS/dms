# Migrate from 0.4 to 0.5

These changes tighten permission checks, open the settings root to every member and harden the account-security flows. Most projects only need the checklist; each section shows the code before and after.

## Checklist

| Area | What to do | Section |
| --- | --- | --- |
| Permissions | Store every ancestor id with a granted permission, in role fixtures and external resolvers | [Permission ancestors](#a-permission-counts-only-with-its-ancestors) |
| Settings | Nothing for the settings root; set `memberAccess` on a page filed under a page that relied on inheriting it | [Settings root](#the-settings-root-opens-to-every-member) |
| Account security | Update clients and end-to-end tests that drive 2FA, password reset, email change or sign-out | [Account security](#account-security) |
| New optional fields | Nothing to do | [New fields](#new-optional-fields) |

## A permission counts only with its ancestors

`HasPermission` now counts a permission a role holds only when every ancestor id is held too. An ancestor that is not a registered permission, or that every member holds (`defaultGranted`, such as `settings` or the `memberAccess` pages), counts as held. The wildcard `*`, module scopes and `defaultGranted` leaves work as before.

Roles saved through the DMS (the roles editor, `/settings/workspace/roles/*` and `/api/tables/roles`) are completed with their ancestor ids on save, so nothing changes for them. A role written another way, a test fixture, or an external resolver such as a plan definition, lists the whole chain:

```ts
// Before: the delete action alone let the action through
permissions: ["library.table-view.table-view-archive.table.delete"];

// After: the page, its table and their categories come with it
permissions: [
  "library",
  "library.table-view",
  "library.table-view.table-view-archive",
  "library.table-view.table-view-archive.table",
  "library.table-view.table-view-archive.table.delete",
];
```

See [Auth & permissions](/docs/auth-and-tenancy/auth-and-permissions).

## The settings root opens to every member

`settingsCategory` is `memberAccess`: `/settings` opens to every signed-in member and lists only the settings they can open, and the roles editor no longer offers a "Settings" node (the workspace settings show at its top level).

A page no longer passes `memberAccess` on to the pages filed under it; only a `Category` does. A page that relied on inheriting it from a parent page declares it itself:

```ts
// Before: opened to every member through the page it is filed under
export class MyPrefsPage extends PageController("my-prefs", { displayName: "My preferences", category: AccountPage }) {}

// After
export class MyPrefsPage extends PageController("my-prefs", {
  displayName: "My preferences",
  category: AccountPage,
  memberAccess: true,
}) {}
```

## Account security

These flows changed for every user; update a client or an end-to-end test that drives them:

- **Email 2FA setup:** `POST /settings/user/security/two-factor/enable-email` still takes `{ currentPassword }` but only sends a code to the account email. `POST /settings/user/security/two-factor/confirm-email { code }` turns the method on.
- **2FA step:** `POST /api/auth/verify-2fa` accepts at most 5 codes per challenge, then answers 429 `error.too_many_2fa_attempts`: sign in with the password again. An account takes at most 10 wrong codes within an hour across its challenges, then every code answers 429 `error.too_many_2fa_attempts_account` until the window passes, even after a new sign-in. A challenge opens one session, then answers 401 `error.2fa_challenge_used`. The two-factor token carries a random `jti`, so two sign-ins get two challenges. An authenticator code is accepted once.
- **Stored 2FA email code:** `User.twoFactorEmailCode` holds a SHA-256 hash of `[userId, code]`, no longer the code. A module that writes it must store the hash.
- **Password reset:** the code is matched in any case, is withdrawn after 5 wrong tries, and a reset signs out every session.
- **Email change:** the code is withdrawn after 5 wrong tries (429 `error.email_change_too_many_attempts`), and the one-code-a-minute limit survives a cancel.
- **Sign-out:** an access token stops working as soon as its session is signed out or deleted, instead of at its expiry.
- **Invitations:** `POST /api/auth/validate-invite-token { token, email }` tells a revoked, replaced, expired or used link apart. Signing up through an invitation always marks the email verified, with no validation round even under `auth.mustValidateEmail`.
- **Deprecated `skipEmailValidation`:** on `UserInvite`, `InviteUserToTenantOptions` and `CreateUserInviteTokenOptions` (now optional there), it is still accepted but has no effect, and will be removed in a future breaking release; stop passing it. The Members invite form and the invitation edit form no longer offer it, and the invite form no longer asks for a name or a single address because of it.

## New optional fields

Additive, nothing to migrate:

- `User.twoFactorTotpLastStep`: the last accepted authenticator time step.
- `InviteResolution.inviteToken` and `InviteResolutionsModel.getForToken(token)`.
- `PageLayout.allComponentsHidden`: set when a page declares blocks and the caller may see none.
