The 0.5 release line tightens permission checks, opens the settings root to every member and hardens the account-security flows. Most projects need only the checklist. Each section shows the code before and after.

## Checklist

| Area | What to do | Section |
| --- | --- | --- |
| Permissions | Store every ancestor id with a granted permission, in role fixtures and external resolvers | [Permission ancestors](#a-permission-counts-only-with-its-ancestors) |
| Settings | Nothing for the settings root. Set `memberAccess: true` on a page that relied on inheriting the root's access | [Settings root](#the-settings-root-opens-to-every-member) |
| Account security | Update clients and end-to-end tests that drive 2FA, password reset, email change or sign-out | [Account security](#account-security) |
| Notification counts | Replace `unseenCount` and `markAllSeen` with `unreadCount`, and drop calls to `/unseen-count` and `/seen` | [Notification counts](#the-bell-counts-unread-notifications) |
| New optional fields | Nothing to do | [New fields](#new-optional-fields) |

## A permission counts only with its ancestors

`HasPermission` counts a permission a role holds only when every ancestor id is held too. An ancestor that is not a registered permission, or that every member holds (`defaultGranted`, such as `settings` or the `memberAccess` pages), counts as held. The wildcard `*`, module scopes and `defaultGranted` leaves work as before.

The DMS completes a role with its ancestor ids when it saves the role through the roles editor, `/settings/workspace/roles/*` or `/api/tables/roles`, so nothing changes for those roles. A role written another way, a test fixture, or an external resolver such as a plan definition lists the whole chain:

```ts fragment
// Before: the delete action alone let the action through
permissions: ["library.table-view.table-view-archive.table.delete"];

// After: the page, its table and their categories come with it
permissions: [
  "library",
  "library.table-view",
  "library.table-view.table-view-archive",
  "library.table-view.table-view-archive.table",
  "library.table-view.table-view-archive.table.delete",
];
```

See [Auth & permissions](/docs/auth-and-tenancy/auth-and-permissions).

## The settings root opens to every member

`settingsCategory` is `memberAccess: "self"`. `/settings` opens to every signed-in member and lists only the settings they can open. The roles editor no longer offers a "Settings" node, and the workspace settings show at its top level. `"self"` opens the overview alone, so a page declared under `settingsCategory` still needs its own permission.

`memberAccess: true` passes on to what is declared under the entry, and `"self"` does not. A page that relied on inheriting the settings root's access declares `memberAccess: true` itself, or sits in a category of its own flagged `true` ([Personal settings](/docs/building/settings-pages#personal-settings)):

```ts fragment
// Before: opened to every member through the page it is filed under
export class MyPrefsPage extends PageController("my-prefs", { displayName: "My preferences", category: AccountPage }) {}

// After
export class MyPrefsPage extends PageController("my-prefs", {
  displayName: "My preferences",
  category: AccountPage,
  memberAccess: true,
}) {}
```

## Account security

These flows changed for every user. Update a client or an end-to-end test that drives them:

- **Email 2FA setup.** `POST /settings/user/security/two-factor/enable-email` still takes `{ currentPassword }` but only sends a code to the account email. `POST /settings/user/security/two-factor/confirm-email { code }` turns the method on.
- **2FA step.** `POST /api/auth/verify-2fa` accepts at most 5 codes per challenge, then answers 429 `error.too_many_2fa_attempts`. The user signs in with the password again. An account takes at most 10 wrong codes within an hour across its challenges, then every code answers 429 `error.too_many_2fa_attempts_account` until the window passes, even after a new sign-in. A challenge opens one session, then answers 401 `error.2fa_challenge_used`. The two-factor token carries a random `jti`, so two sign-ins get two challenges. An authenticator code is accepted once. Every bad two-factor token (not a JWT, unknown user, bad signature, expired, wrong purpose) answers the same 401 `error.invalid_2fa_token` on `verify-2fa` and `request-2fa-email`, instead of `Invalid 2FA token`, `Invalid user` or the token library's message (`jwt expired`, `invalid signature`). A missing token answers 400 `error.invalid_2fa_token`.
- **Current password.** The forms that ask for it again (email change, password change, adding a 2FA method, account deletion) share 10 tries per account within 15 minutes. Past that, they answer 429 `error.too_many_current_password_attempts`, even to the right password. The right password clears the count.
- **Stored 2FA email code.** `User.twoFactorEmailCode` holds a SHA-256 hash of `[userId, code]`, no longer the code. A module that writes it must store the hash.
- **Password reset.** The code is matched in any case and is withdrawn after 5 wrong tries. A reset signs out every session.
- **Email change.** The code is withdrawn after 5 wrong tries (429 `error.email_change_too_many_attempts`). The limit of one code a minute survives a cancel and is checked before the current password, so a second request within the minute answers 429 `error.rate_limited` even with a wrong password.
- **Sign-out.** An access token stops working as soon as its session is signed out or deleted, instead of at its expiry.
- **Invitations.** `POST /api/auth/validate-invite-token { token, email }` tells a revoked, replaced, expired or used link apart. Signing up through an invitation always marks the email verified, with no validation round even under `auth.mustValidateEmail`.
- **Removed `skipEmailValidation`.** It is gone from `UserInvite`, `InviteUserToTenantOptions` and `CreateUserInviteTokenOptions`, and an invite signup always validates the address. Stop passing it (TypeScript refuses it). The Members invite form and the invitation edit form no longer offer it.

## The bell counts unread notifications

The header bell and the Notifications menu badge show the same count. Both show the unread notifications, drawn in the tone of the most important one. The "unseen since the bell was last opened" count is gone:

- `useNotifications()` no longer returns `unseenCount`, `markAllSeen` or `handleRemoteSeen`. Read `unreadCount` and the new `unreadTone`.
- `GET /settings/user/notifications/unseen-count` and `PUT /settings/user/notifications/seen` are removed, `/counts` no longer returns `unseen` (it returns `unreadTone`), and the `notification:seen` realtime event is no longer published.
- A nav badge may carry a tone. `navBadge({ count })` can return `{ count, tone }`, and a table tab takes `navBadge: { tone }`. Several badges on one page add up in the strongest tone. See [Navigation badges](/docs/interfaces/core/components#navigation-badges).

## New optional fields

These fields are additive, with nothing to migrate:

- `User.twoFactorTotpLastStep`: the last accepted authenticator time step.
- `InviteResolution.inviteToken` and `InviteResolutionsModel.getForToken(token)`.
- `PageLayout.allComponentsHidden`: set when a page declares blocks and the caller may see none.
