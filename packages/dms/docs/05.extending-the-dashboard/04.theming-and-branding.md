The dashboard's look comes from **app config** and **CSS design tokens**. Your frontend layer overrides both, and no DMS component has to be copied. The sections below go from the change you make most often to the least: the logo, the footer, the colors, the deeper tokens, then the user settings your own components should follow.

Everything here lives in a [frontend layer](/docs/building/frontend-layer). The loader merges the `app/app.config.ts` of every layer into `useDmsAppConfig()` before any module's `setup` runs, gives the same config to the email renderer, and applies an edit in development without a restart. Your layer entry, `dms.frontend.ts`, does not import that file. If an override does not take effect, give your layer a **higher** `priority` on `AddFrontendModule` than the DMS layer, such as `1` against the DMS at `0`, the same way as for a [component override](/docs/building/frontend-layer#overriding-an-existing-component).

A branded layer changes what the dashboard shows and nothing else. With your logo, a `violet` primary, and a serif font, the **Appearance** settings page keeps its layout and its text, which still names the DMS. Only the logo, the control colors, and the typeface change. Logo and token overrides never rewrite application copy.

## Replace the logo

The shell reads its logos from `appConfig.branding.logo`. There is one slot per place a logo is drawn, and each slot has a light and a dark file. Override the slots in your layer's `app/app.config.ts` and ship the files in your layer's `public/` directory:

```ts fragment [frontend-vue/app/app.config.ts]
export default defineDmsAppConfig({
  branding: {
    logo: {
      alt: "Helio",
      default: {
        light: "/branding/logo-light.svg",
        dark: "/branding/logo-dark.svg",
      },
      collapsed: {
        light: "/branding/icon.svg",
        dark: "/branding/icon.svg",
      },
      email: {
        light: "/branding/logo-email.png",
        dark: "/branding/logo-email-dark.png",
      },
      favicon: {
        light: "/branding/favicon.svg",
        dark: "/branding/favicon-dark.svg",
      },
    },
  },
});
```

| Slot        | Where it is drawn                                     | What picks light or dark                      |
| ----------- | ----------------------------------------------------- | --------------------------------------------- |
| `default`   | The expanded sidebar and the auth pages               | The dashboard's color mode                    |
| `collapsed` | The icon-only sidebar                                 | The dashboard's color mode                    |
| `email`     | The header of the emails, in place of `default.light` | The mail client's dark mode, where it has one |
| `favicon`   | The browser tab                                       | The operating system's color scheme           |

A slot you leave out keeps the DMS logo. A file you leave out keeps the DMS file too, so give both `light` and `dark` for each slot you override. When the sidebar collapses, it draws the `collapsed` slot instead of shrinking the `default` wordmark.

Set `alt` to your application's name. A screen reader announces it for the logo, and it stays `Antelope DMS` until you set it.

**Email.** Use a PNG or a JPEG, because Gmail and Outlook refuse SVG. The built-in emails leave out a logo that a mail client cannot load, an SVG or a path without a public `clientBaseUrl` ([Built-in emails](/docs/interfaces/html-render/built-in-emails#logo)), rather than draw a broken image. The `dark` file goes, through a `<picture>` source, to the clients that follow the reader's dark mode. The other clients draw `light`. Without an `email` slot, the emails use `default.light`, and the default DMS logo is an SVG, so the built-in emails then have no logo. For a rendered email of your own, see [A rendered custom digest](/docs/interfaces/html-render/introduction#a-rendered-custom-digest).

**Favicon.** `light` and `dark` follow the operating system's `prefers-color-scheme`, not the dashboard's color mode, because the browser draws the tab outside the page. When the two files differ, the DMS writes one `<link rel="icon">` per scheme with a `media` query. Give the same file to both for a single icon. The `type` of each link comes from the file extension (`.svg`, `.png`, `.ico`, or `.webp`). The DMS default is its collapsed icon.

The document title and description are not app config. They come from the `meta` block of the DMS backend config ([Configuration](/docs/building/configuration)).

### Read the DMS defaults

Whatever a layer sets, `appConfig.branding.defaults` keeps the DMS's own logos and palettes, for a tool that previews a return to the DMS look:

```ts fragment [what the base layer ships]
branding: {
  defaults: {
    logo: { default, collapsed, favicon }, // the AntelopeJS logos, no email logo
    colors: { primary: "dms", secondary: "violet", neutral: "neutral", success: "emerald", warning: "amber", error: "red", info: "cyan" },
  },
}
```

Read it through `useDmsAppConfig().branding.defaults`. It is not a setting. A layer overrides `branding.logo` and `ui.colors`, never `branding.defaults`.

## Footer

The footer of the public and auth pages reads `appConfig.branding.footer`. Each key is optional, and a key you leave out keeps its default:

```ts fragment [frontend-vue/app/app.config.ts]
export default defineDmsAppConfig({
  branding: {
    footer: {
      copyright: "Acme", // shown as "© Acme"; a `$`-prefixed i18n key works, `false` drops it
      localeSwitcher: true, // the language picker
    },
  },
});
```

The defaults are `copyright: "Antelope"` and `localeSwitcher: true`. The links of the row come from a registry. Add, replace, or remove them with `registerFooterLink` and `unregisterFooterLink` ([Dashboard chrome](/docs/extending-the-dashboard/dashboard-chrome#footer-links)).

The footer also shows a static **Star** link to the AntelopeJS DMS repository on GitHub. It has no star count and sends no request to the GitHub API.

## Change the colors

The dashboard uses Nuxt UI's semantic color tokens. The base layer maps them in its `app.config.ts`:

```ts fragment [what the base layer ships]
ui: {
  colors: {
    primary: "dms",       // the DMS cyan, a custom palette
    secondary: "violet",  // the assistant's accent
    neutral: "neutral",
    success: "emerald",
    warning: "amber",
    error: "red",
    info: "cyan",
  },
}
```

To rebrand, point `primary`, or any other semantic token, at another palette in your own `app.config.ts`. A stock Tailwind palette name works as is:

```ts fragment [frontend-vue/app/app.config.ts]
export default defineDmsAppConfig({
  ui: { colors: { primary: "violet" } },
});
```

For a brand-exact palette, declare its 11 shade variables as ordinary CSS properties in a stylesheet of your layer, then name the palette. Nuxt UI resolves the names at runtime, so the stylesheet needs no Tailwind compilation of its own:

```css [frontend-vue/app/assets/css/theme.css]
:root {
  --color-acme-50: #f2f8ff;
  /* … --color-acme-100 through --color-acme-900 … */
  --color-acme-950: #0a1a2e;
}
```

```ts fragment [frontend-vue/app/app.config.ts]
export default defineDmsAppConfig({
  ui: { colors: { primary: "acme" } },
});
```

Import the stylesheet from your layer entry, `dms.frontend.ts`, with `import "./app/assets/css/theme.css";`, as the DMS layer does with its own. If the palette belongs to a stylesheet that Tailwind processes and you also want utilities such as `bg-acme-600`, declare it with `@theme static` instead.

Charts, badges, buttons, and the other components take their colors from these tokens, and the chart renderer reads the live theme. One palette change restyles the charts and the chrome together. The DMS accent follows `primary` as well. `--dms-accent`, the solid fill with its hover and text colors, the tints, the lines, the focus ring, and the glows all derive from the palette's shades (`--ui-color-primary-*`).

## Override the design tokens

Beyond the palette, four mechanisms give finer control. All of them are standard Nuxt UI and Tailwind mechanisms.

**Component theme slots.** The `ui` app-config key also holds per-component overrides (`ui.card.slots` and `ui.navigationMenu`, for example). Use one to restyle a component family everywhere. To see what the DMS already overrides, read the base layer's `app.config.ts`.

**CSS variables.** The base layer's stylesheet defines the surfaces as CSS variables, each with a dark-mode value:

- `--ui-bg*` for the canvas and the raised surfaces, `--ui-border*` for the hairlines, and `--ui-text*` for the text tiers.
- `--ui-radius` for corner rounding. `--dms-radius-tab-list`, `--dms-radius-tab`, and `--dms-radius-tab-badge` for pill tabs derive from it.
- `--dms-surface-card` and `--dms-radius-card` for card frames.
- `--dms-bg-sidebar` and `--dms-bg-field` for the sidebar and the form fields.
- `--dms-canvas-glow` for the background image behind the page: a glow of the primary color in dark mode, `none` in light mode.
- `--dms-accent-fill`, `--dms-accent-fill-hover`, and `--dms-accent-on-fill` for solid primary buttons. `--ui-primary` is the accent for text and icons.
- The shadow tokens.

The DMS declares its values in the `dms` cascade layer. Your unlayered declarations override them whatever the stylesheet order, with no doubled selectors and no `!important`. The glow and live-edit highlights follow `--dms-accent`, which is primary shade 500 in light mode and 400 in dark mode.

Scope each override to its mode. The `.dark` class sits on the same `<html>` element as `:root`, so an unlayered `:root` block also applies to the dark page. Because it is outside the `dms` layer, it beats the DMS's own `.dark` values, and a light surface color declared there shows in dark mode too. Declare light values under `:root:not(.dark)` and dark ones under `.dark`. Keep `:root` for the tokens that do not change with the mode, such as the font, the radius, or a palette's shades:

```css [frontend-vue/app/assets/css/theme.css]
:root {
  --font-sans: "Inter", sans-serif;
  --ui-radius: 0.5rem;
}
:root:not(.dark) {
  --ui-bg-muted: #f6f5fb;
  --dms-surface-card: #ffffff;
}
.dark {
  --ui-bg-muted: #0c0b12;
  --dms-surface-card: #181525;
}
```

The order independence holds for token declarations, not for competing component rules. If your stylesheet declares the Tailwind cascade layers before it imports the DMS stylesheet, keep the DMS order with `@layer theme, base, dms, components, utilities;`. Put utility and component customizations in their matching layers.

**Fonts.** The DMS self-hosts Geist and Geist Mono and wires them through `--font-sans` and `--font-mono`, plus Tailwind's `--default-font-family`. To change the typeface everywhere, declare your own `@font-face` and reassign those variables.

**Icons.** The shell's icons resolve through `ui.icons` in app config, which the base layer maps to Phosphor. To use another icon set, remap them there.

## Follow the interface scale

The whole interface scales from the root font size. The `data-scale` attribute on `<html>` switches between `small` (87.5%, a 14px root), `normal` (16px), and `large` (112.5%, an 18px root). Users pick a scale on the built-in **Appearance** settings page. Your code reads or sets it through the `useInterfaceScale()` cookie ref ([Page context](/docs/frontend-composables/page-context#useinterfacescale)).

The DMS sizes everything in `rem`, so your components scale with it when they do the same. Use `rem` and `em` units in your own CSS.

## Follow the color mode

Users pick light, dark, or system on the same **Appearance** page, or from the theme submenu of the user menu in the sidebar footer. The choice lives in the `dms-color-mode` cookie. An explicit `light` or `dark` class is already on `<html>` in the server-rendered page, and `system` follows the operating system and resolves in the browser before the first paint. Your code reads or sets the choice through the `useColorModePreference()` cookie ref ([Page context](/docs/frontend-composables/page-context#usecolormodepreference)).

Nuxt UI's color-mode components (`UColorModeSelect`, `UColorModeButton`, and the theme group of the dashboard search) stay in sync with it in both directions. Style dark mode with Tailwind's `dark:` variant, which keys on the `dark` class.

## Accessibility

The **Accessibility** block of the same **Appearance** page holds three options. Like the color mode and the scale, they are set per device. They live in the `dms-accessibility` cookie, which the server reads, so their classes are on `<html>` from the first paint. Your code reads or sets them through `useAccessibilityPreferences()` ([Page context](/docs/frontend-composables/page-context#useaccessibilitypreferences)).

| Option                 | Values                       | Class on `<html>`                                 | Effect                                                                                                                                                                                                                     |
| ---------------------- | ---------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reduce motion          | Automatic (default), On, Off | `dms-reduce-motion` (On), `dms-full-motion` (Off) | Animations and transitions last 0.01 ms and play once. Spinners (`animate-spin`) keep turning. Charts draw without animation. Automatic sets no class and follows the operating system's `prefers-reduced-motion`.       |
| Increase contrast      | On, Off                      | `dms-increase-contrast`                           | Darker `--ui-text*`, `--ui-border*`, and `--dms-*` line tokens in the light theme, lighter ones in the dark theme. Muted and dimmed text reach WCAG AA (4.5:1) on cards and the canvas, and field borders reach 3:1. |
| Always underline links | On, Off                      | `dms-underline-links`                             | Underlines content links: the `<a>` elements with the `hover:underline` class (`ULink`, table link cells, inline links) and anything with the `dms-text-link` class. Menu items, tabs, cards, and buttons stay as they are. |

There is no text-size option, because the interface scale already scales the text.

To keep your module in line with these options:

- Use Tailwind's `motion-safe:` and `motion-reduce:` variants for decorative motion. The DMS redefines them to follow the device setting first, and the system setting under Automatic.
- Before JavaScript-driven motion (a canvas, a chart library, a count-up), call `isReducedMotionActive()`, which is auto-imported, and skip the motion when it returns `true`. It reads the device setting and, under Automatic, the system's `prefers-reduced-motion`. It returns `false` on the server.
- Style secondary text and borders with the `text-muted`, `text-dimmed`, and `border-*` tokens instead of fixed colors, so the contrast option reaches them.
- Give a content link built on a bare `<DmsLink>` or `<a>` the `dms-text-link` class, so the underline option covers it.
