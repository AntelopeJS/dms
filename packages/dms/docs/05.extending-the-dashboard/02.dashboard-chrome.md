The **dashboard shell** is the UI around your page: navigation, header, search, footer, and optional panels. A [frontend layer](/docs/building/frontend-layer) adds an item by calling a register function from a plugin. The shell renders the item without changes to the DMS itself.

[Layout banners](#layout-banners) are the exception. A backend module registers them, because the server decides for each request whether a banner shows. App widgets, sidebar widgets, and app overlays are on their own page, [Widgets and overlays](/docs/extending-the-dashboard/widgets-and-overlays).

The frontend examples on this page call the layer's auto-imported functions, so they are shown without imports.

## Header actions

`registerHeaderAction` adds an icon-only button to the dashboard header, on the right of the navbar, before the quick actions and the notifications.

```ts fragment
registerHeaderAction(action: HeaderAction): void
useHeaderActions(): { actions: ComputedRef<HeaderAction[]> }
```

`HeaderAction` has these fields:

| Field         | Type            | Required | Notes                                                                                                   |
| ------------- | --------------- | -------- | ------------------------------------------------------------------------------------------------------- |
| `id`          | `string`        | yes      | Stable key. Registering the same `id` again replaces the entry.                                         |
| `icon`        | `string`        | yes      | Icon name, for example `i-ph-cloud-arrow-up-light`. The button shows no text.                           |
| `label`       | `string`        | yes      | Tooltip and `aria-label`. A `$`-prefixed value resolves as an i18n key.                                 |
| `onSelect`    | `() => void`    | one of   | Runs on click.                                                                                          |
| `sidePanelId` | `string`        | one of   | The [side panel](#side-panels-docked) the button opens and closes. Takes precedence over `onSelect`.    |
| `order`       | `number`        | no       | Sort key, ascending. Defaults to `100`.                                                                 |
| `isVisible`   | `() => boolean` | no       | Read reactively. Omit it to always show the button.                                                     |
| `isActive`    | `() => boolean` | no       | Makes the button a toggle and reports whether it is on. Derived from the side panel with `sidePanelId`. |

**Active state.** A toggle is an action with `isActive` or `sidePanelId`. While it is on, the button renders with `color="primary"` instead of the muted toolbar style, and `aria-pressed` is set. With `sidePanelId`, the DMS reads the state and runs the click through [`useSidePanel`](#side-panels-docked), so the module wires nothing.

**Where to register.** An action with a `sidePanelId` and no callables is plain data. Register it from an ordinary plugin, and the server renders the button and its state. An action with a callable (`onSelect`, `isVisible`, or `isActive`) goes in a `.client` plugin, because the SSR payload drops functions. The server never renders such a button. It joins the header after hydration. The header skips any entry left with neither a callable `onSelect` nor a `sidePanelId`, so a stray server-side registration hides the button instead of crashing.

**Where it renders.** `DashboardHeader.vue` renders each visible action in the navbar's `#right` slot as a `UButton` with `variant="ghost"`, sorted by `order`.

```ts fragment [app/plugins/header-action.client.ts]
export default defineDmsPlugin(() => {
  registerHeaderAction({
    id: "my-module:sync",
    icon: "i-ph-arrows-clockwise-light",
    label: "$my_module.sync",
    order: 50,
    onSelect: () => {
      syncMyModule();
    },
  });
});
```

For a button that toggles a side panel, see the [side panel example](#side-panels-docked).

## Layout banners

A layout banner is a global message stacked under the header navbar. A backend module registers it with `RegisterLayoutBanner` from `@antelopejs/interface-dms/layout-banners`. Its `visible` resolver runs on the server for each site layout request, so the banner is part of the server-rendered page and never appears after hydration.

`scope` picks the pages a banner shows on. The module area is everything under `/modules`: the modules page, the module store, and every module's own pages.

| `LayoutBannerScope` | Pages                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------- |
| `APP`               | The application's pages, outside the module area. The default.                              |
| `MODULES`           | The module area only.                                                                       |
| `EVERYWHERE`        | Every page. Use it for a workspace-wide state such as a past-due bill or a suspended workspace. |

This module shows a past-due banner to owners on every page:

```ts [src/banners.ts]
import {
  LayoutBannerScope,
  LayoutBannerVariant,
  RegisterLayoutBanner,
} from "@antelopejs/interface-dms/layout-banners";

declare function isPastDue(tenantId: string): Promise<boolean>;

RegisterLayoutBanner({
  key: "my-module:past-due",
  variant: LayoutBannerVariant.ERROR,
  scope: LayoutBannerScope.EVERYWHERE,
  text: "$my_module.banner.past_due",
  dismissible: true,
  order: 10,
  visible: async ({ tenantId, isOwner }) =>
    isOwner && (await isPastDue(tenantId)),
});
```

A banner shows either `text`, with optional link `actions`, or a `component`: the name of a global component from a frontend layer, with serializable `props`.

When the message names the state that makes the banner show, such as "Invoice INV-42 of €29.00 failed, retry Oct 10", register `resolve` instead of `visible`. For each request, `resolve` returns a [composed text](/docs/components/block-fundamentals#composed-texts) and link buttons, or `undefined` to hide the banner. The browser then writes the amount and the date in the reader's language, with no frontend component.

```ts [src/banners.ts]
import {
  LayoutBannerScope,
  LayoutBannerVariant,
  RegisterLayoutBanner,
} from "@antelopejs/interface-dms/layout-banners";

interface OpenInvoice {
  number: string;
  amountDue: number;
  currency: string;
  nextAttemptAt: string;
}

declare function openInvoice(tenantId: string): Promise<OpenInvoice | undefined>;

RegisterLayoutBanner({
  key: "my-module:past-due",
  variant: LayoutBannerVariant.ERROR,
  scope: LayoutBannerScope.EVERYWHERE,
  resolve: async ({ tenantId }) => {
    const invoice = await openInvoice(tenantId);
    if (!invoice) return undefined;
    return {
      text: {
        key: "my_module.banner.past_due",
        params: {
          invoice: invoice.number,
          amount: { type: "money", value: invoice.amountDue, currency: invoice.currency },
          date: { type: "date", value: invoice.nextAttemptAt, format: "day" },
        },
      },
      actions: [{ label: "$my_module.banner.pay", to: "/billing?pay=1" }],
    };
  },
});
```

A resolver that throws, or does not answer within two seconds, hides its banner for that request.

**Where it renders.** `DashboardBanners.vue` sits in the dashboard panel's header slot, right under `DashboardHeader.vue`, at full width. The DMS draws the variant's color and icon, a close button when `dismissible` is set, and the live-region role: `alert` for `error`, `status` for `info` and `warning`. A `component` banner mounts your global component as the content, with the banner's `props` bound to it.

**Scope.** The site layout carries every banner with its `scope`. `useLayoutBanners()` keeps the banners whose scope covers the current route, on the server-rendered page and again on each client-side navigation. Opening a module page removes the `APP` banners without a refetch, and leaving the module area brings them back.

**Dismissal.** A dismissible banner stays closed for the browser session. The dismissed keys live in the `dms-dismissed-banners` cookie, which the server-side render also reads, so a closed banner does not come back on the next page. The dismissal belongs to the browser, so the backend registration and its `visible` answer stay unchanged. Give a banner a new `key` to show it again to users who closed it.

**Height.** Banners stack in the panel's header, above the part of the panel that scrolls, so their height comes out of the page, not out of the window. A page that fills the panel ([`fillHeight`](/docs/interfaces/base/page-layouts#pages-that-fill-the-panel)) gets shorter by that much instead of scrolling, and grows back when the banner is dismissed. A page that sizes itself from the viewport with `calc(100vh - ...)` does not account for the banner and scrolls under it.

The [Layout Banners reference](/docs/interfaces/core/layout-banners) has every field, the resolver context, and how to refresh connected clients with `NotifyMenuChanged`.

## Command palette sources

`registerCommandPaletteSource` adds groups of commands to the Ctrl/Cmd+K palette (`UDashboardSearch`). Each source is a reactive builder of Nuxt UI `CommandPaletteGroup` arrays. The palette joins the groups of every registered source, in source `order`.

```ts fragment
registerCommandPaletteSource(source: CommandPaletteSource): void
unregisterCommandPaletteSource(id: string): void
useCommandPaletteGroups(): { groups: ComputedRef<CommandPaletteGroup[]> }
```

`CommandPaletteSource` has these fields:

| Field    | Type                          | Required | Notes                                                                                                                                  |
| -------- | ----------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `id`     | `string`                      | yes      | Stable key. Registering the same `id` again replaces the entry, and `unregisterCommandPaletteSource` targets it.                       |
| `order`  | `number`                      | no       | Position of this source's groups relative to other sources, ascending. Defaults to `100`. Sources with the same order keep registration order. |
| `groups` | `() => CommandPaletteGroup[]` | yes      | Builds the groups. The palette reads it inside a `computed`, so reactive state read here updates the palette. Return `[]` for nothing. |

Prefix your group ids with your source id. Group ids are global to the palette, and a collision merges the items of both groups under the first group's header without a warning. `order` applies to the empty-search view. While the user types, the palette orders groups by match relevance.

An item can also carry a `searchText` field, the value of the `COMMAND_PALETTE_SEARCH_TEXT_KEY` constant. The palette matches on it with a lower weight than `label` and `suffix`, and never renders it, so a match on it does not replace the breadcrumb shown. The built-in navigation source uses it to match page descriptions. Use it for keywords an item should answer to without displaying them.

**Where to register.** Register a source from a `.client` plugin. A source carries callables (`groups` and each item's `onSelect`), and the SSR payload drops functions. The palette skips any entry whose `groups` is not a function, so a stray server-side registration shows no commands instead of crashing. A source whose `groups` throws is skipped and logged, and the other sources still render.

**Where it renders.** `DashboardSearch.vue` passes the groups to `UDashboardSearch`, which opens from the sidebar search button or Ctrl/Cmd+K.

The DMS registers four sources. Pick an `order` between them to position your groups:

| Source                                 | Order | Groups                                                                                                                                                    |
| -------------------------------------- | ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Quick actions (`dms-quick-actions`)    | 10    | Backend-registered [quick actions](/docs/building/navigation#quick-actions-the-command-palette), one group per category. The server sends only the actions the caller can run. |
| Personal pages (`dms-personal-pages`)  | 20    | The user's favorite pages, and recently visited modules, which open at their last path.                                                                   |
| Navigation (`dms-navigation`)          | 40    | The whole navigation tree as breadcrumbed links, filtered by access. It holds more than the sidebar shows.                                                |
| Session (`dms-session`)                | 50    | Profile, settings, switch account, a language submenu, copy the current URL, and log out.                                                                 |

```ts fragment [app/plugins/command-palette-tasks.client.ts]
export default defineDmsPlugin(() => {
  const { tasks } = useMyTasks();

  const groups = computed(() => [
    {
      id: "my-module-tasks",
      label: "Tasks",
      items: tasks.value.map((task) => ({
        label: task.title,
        icon: "i-ph-check-square-light",
        to: `/modules/tasks/${task.id}`,
      })),
    },
  ]);

  registerCommandPaletteSource({
    id: "my-module:tasks",
    order: 30,
    groups: () => groups.value,
  });
});
```

The `order` of `30` places the tasks between personal pages and navigation. Build your groups in your own `computed`, as above, and return it from `groups`. The source then rebuilds its groups only when its own dependencies change. Labels from backend metadata can be `$`-prefixed i18n keys. `useI18n` is unavailable in a plugin, so resolve them with [`getAppTranslation().processI18n`](/docs/frontend-composables/utilities#usetranslation-the-prefix-convention).

## Command palette assistant

`registerCommandPaletteAssistant` gives the Ctrl/Cmd+K palette an assistant mode that your module provides. While an assistant is registered:

- **Tab** in the palette's input switches the dialog between search and assistant mode. Assistant mode uses the violet `secondary` color. The input's icon becomes your `icon`, the placeholder becomes your `placeholder`, the dialog's halo turns violet, and the footer's **Ask AI** button reads **Back to search**. A screen reader announces each switch. Shift+Tab still moves focus through the dialog.
- Every non-empty search ends with an item that reads `Ask the assistant "<query>"`, after the search results. When nothing matches, it is the only item and it is highlighted, so Enter asks the assistant.
- In assistant mode, an empty prompt lists your suggestions under **Try asking**. Once the user types, the prompt is the first item, so Enter sends it. The suggestions stay below it, reachable with the arrow keys.
- A submitted prompt mounts your `answerComponent` inside the palette, in a violet frame headed by your `label`. Editing the prompt removes the answer.

Without an assistant, the palette has no assistant mode. Tab moves focus and the palette adds no item.

```ts fragment
registerCommandPaletteAssistant(assistant: CommandPaletteAssistant): void
unregisterCommandPaletteAssistant(id: string): void
useCommandPaletteAssistant(): { assistant: ComputedRef<CommandPaletteAssistant | undefined> }
```

`CommandPaletteAssistant` has these fields:

| Field             | Type                                        | Required | Notes                                                                                                                       |
| ----------------- | ------------------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------- |
| `id`              | `string`                                    | yes      | Stable key. Registering the same `id` again replaces the entry, and `unregisterCommandPaletteAssistant` targets it.         |
| `label`           | `string`                                    | yes      | Name shown in the answer frame and as the header of the "Ask" items. A `$`-prefixed value resolves as an i18n key.          |
| `icon`            | `string`                                    | yes      | Icon of the assistant mode: the input's icon and the items' icon, for example `i-ph-sparkle`.                               |
| `placeholder`     | `string`                                    | no       | Input placeholder in assistant mode, `$`-prefixed for an i18n key. Defaults to "Ask anything about your workspace...".      |
| `suggestions`     | `() => CommandPaletteAssistantSuggestion[]` | yes      | Builds the suggestions shown while the prompt is empty. The palette reads it inside a `computed`, so reactive state updates them. |
| `answerComponent` | `string`                                    | yes      | Full registered name of the global component that answers a submitted prompt.                                               |

A suggestion is `{ label, prompt?, icon? }`. The palette shows `label`, `$`-prefixed for an i18n key. It submits `prompt`, which defaults to the resolved label. `icon` defaults to the assistant's icon.

The answer component receives `CommandPaletteAssistantAnswerProps`. The palette mounts a new instance for every submission:

| Prop     | Type         | Notes                                                                         |
| -------- | ------------ | ----------------------------------------------------------------------------- |
| `prompt` | `string`     | The submitted prompt, trimmed.                                                |
| `close`  | `() => void` | Closes the palette. Call it before an action that takes the user elsewhere.   |

The palette only frames the answer. The component decides what to do with the prompt: answer it inline and read-only, or hand it to your own interface with a button such as **Continue in the assistant**. Put actions on explicit buttons instead of running them on submit. A component whose `setup` awaits, with a top-level `await` in `<script setup>`, shows the palette's violet loading skeleton until it resolves. A component that renders at once draws its own progress, which suits an answer that streams in. If the async setup rejects, or no registered component has the name, the frame shows "The assistant could not answer" instead.

**Where to register.** Register an assistant from a `.client` plugin. `suggestions` is a function, which the SSR payload drops, and the palette ignores an entry without it. When several modules register an assistant, the palette uses the last one registered. Unregistering it gives the mode back to the previous one, or removes the mode.

**Where it renders.** `DashboardSearch.vue` renders the assistant in the same `UDashboardSearch` dialog as the sources. The suggestions and the prompt are palette groups, the answer is in the palette's empty slot, and the mode toggle is in its footer.

```ts fragment [app/plugins/command-palette-assistant.client.ts]
export default defineDmsPlugin(() => {
  registerCommandPaletteAssistant({
    id: "my-module:assistant",
    label: "$my_module.assistant.label",
    icon: "i-ph-sparkle",
    suggestions: () => [
      { label: "$my_module.assistant.suggestions.churn" },
      { label: "Late orders", prompt: "Which orders are late this week?" },
    ],
    answerComponent: "MyModulePaletteAnswer",
  });
});
```

`MyModulePaletteAnswer` is a global component from your layer. Its `setup` awaits the answer, so the palette shows its skeleton until the answer arrives:

```vue [app/components/MyModulePaletteAnswer.vue]
<script setup lang="ts">
const props = defineProps<CommandPaletteAssistantAnswerProps>();
const router = useDmsRouter();

const answer = await askMyModule(props.prompt);

function openConversation(): void {
  props.close();
  void router.push(`/modules/my-module/chat?q=${encodeURIComponent(props.prompt)}`);
}
</script>

<template>
  <p>{{ answer.text }}</p>
  <UButton class="mt-3" size="sm" color="secondary" @click="openConversation">
    Continue in the assistant
  </UButton>
</template>
```

The playground registers a demo assistant whose answer repeats the prompt after a short delay, in `playground/frontend-vue/app/plugins/command-palette-assistant-demo.client.ts`.

## Side panels (docked)

`registerSidePanel` docks one of your components on the right of the dashboard, next to the page: an assistant, an inspector, or a chat. From the `lg` breakpoint, the page shrinks to make room, and a resize handle on the panel's inner edge sets its width. Below `lg`, the same panel slides over the page as a sheet above a backdrop.

The DMS owns the panel's state. The registration is plain data, and `useSidePanel(id)` opens and closes the panel from anywhere: a header action, a command, or the panel's own close button.

To open a table row in a side panel, you register nothing. A row action with a `sidePanel` target uses the same panel, with a header the DMS draws: the title, the row's position, previous and next buttons, and a close button. See [Row drawers](/docs/components/tables/row-drawers#side-panel).

```ts fragment
registerSidePanel(panel: SidePanel): void
unregisterSidePanel(id: string): void
useSidePanel(id: string): {
  isOpen: Readonly<Ref<boolean>>;
  open: () => void;
  close: () => void;
  toggle: () => void;
}
useAppSidePanels(): { panels: Readonly<Ref<SidePanel[]>> }
```

`SidePanel` has these fields:

| Field          | Type     | Required | Notes                                                                                                                         |
| -------------- | -------- | -------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `id`           | `string` | yes      | Stable key. Registering the same `id` again replaces the entry, `unregisterSidePanel(id)` removes it, and `useSidePanel(id)` targets it. |
| `component`    | `string` | yes      | Name of the global component rendered inside the panel. It fills the panel's height and scrolls its own content.              |
| `ariaLabel`    | `string` | no       | Accessible name of the panel's `<aside>` landmark. A `$`-prefixed value resolves as an i18n key.                              |
| `defaultWidth` | `number` | no       | Width in px before the user resizes the panel. Defaults to `440`.                                                             |
| `minWidth`     | `number` | no       | Narrowest width in px the handle allows. Defaults to `320`.                                                                   |
| `maxWidth`     | `number` | no       | Widest width in px the handle allows. Defaults to `720`. The docked panel also never takes more than 60% of the viewport.      |

**Where to register.** Register a panel from an ordinary plugin. Every field is serializable, so the server registers the panel too, and a panel left open renders open in the server HTML.

**Where it renders.** The DMS renders the open panel once for the whole app, in `SidePanelHost.vue`, which it registers as an [app overlay](/docs/extending-the-dashboard/widgets-and-overlays#app-overlays-free) outside the routed layouts. The panel is `position: fixed` on the right. From `lg`, each dashboard frame keeps the panel's width free on its right through the `--dms-side-panel-width` CSS variable, so the page shrinks next to it. The panel shows for a signed-in user on pages with the dashboard shell. A page without the shell, such as onboarding or an error page, hides the panel and keeps it mounted.

- **One panel at a time.** Opening a panel closes the one that was open. `close()` acts only on its own panel, so closing a panel that is not open does nothing.
- **State.** The `dms-side-panel` cookie stores which panel is open and the width each panel was given. The server reads it, so a reload renders the open panel docked at its width, with no layout shift.
- **Width.** The user drags the handle, or focuses it and presses the arrow keys: `←` widens, `→` narrows, and `Home` and `End` jump to the bounds. A double click resets the width to `defaultWidth`. The page follows the handle while it moves, and the width is stored when the drag ends.
- **Navigation.** The panel renders outside the layouts, so its component stays mounted across every navigation, including between the default and settings layouts.
- **Focus.** Opened as a sheet, the panel takes focus unless its component already did, and on close, focus returns to where it was. A backdrop click or Escape closes the sheet. Docked, Escape is left to your component.

This plugin registers a panel and a header button that toggles it. The DMS shows the button as active while the panel is open:

```ts fragment [app/plugins/assistant-panel.ts]
export default defineDmsPlugin(() => {
  registerSidePanel({
    id: "my-module:assistant",
    component: "MyModuleAssistantPanel",
    ariaLabel: "$my_module.assistant.label",
    defaultWidth: 440,
  });

  registerHeaderAction({
    id: "my-module:assistant",
    icon: "i-ph-sparkle-light",
    label: "$my_module.assistant.toggle",
    sidePanelId: "my-module:assistant",
  });
});
```

`MyModuleAssistantPanel` is a global component from your layer:

```vue [app/components/MyModuleAssistantPanel.vue]
<script setup lang="ts">
const { close } = useSidePanel("my-module:assistant");
</script>

<template>
  <div class="flex h-full flex-col">
    <header class="flex items-center justify-between p-4">
      <h2>Assistant</h2>
      <UButton icon="i-ph-x-light" variant="ghost" @click="close" />
    </header>
  </div>
</template>
```

## Footer links

`registerFooterLink` adds a link to the footer's link row, next to the copyright and the language picker.

The row starts with two Antelope links, `dms:documentation` and `dms:website`, at orders 10 and 20. Register an entry under one of these ids to replace it, or remove it with `unregisterFooterLink(id)`. URL targets (`https://...`) open in a new tab.

The footer also always shows a **Star** link to the AntelopeJS DMS repository on GitHub, outside this registry. It shows no star count and sends no request to the GitHub API.

The rest of the footer comes from `appConfig.branding.footer`: the name after the `©` and the language picker. See [Theming and branding](/docs/extending-the-dashboard/theming-and-branding#footer).

```ts fragment
registerFooterLink(link: FooterLink): void
unregisterFooterLink(id: string): void
useFooterLinks(): { links: ComputedRef<FooterLink[]> }
```

`FooterLink` has these fields, all required:

| Field   | Type     | Notes                                                       |
| ------- | -------- | ----------------------------------------------------------- |
| `id`    | `string` | Stable key. Registering the same `id` again replaces the entry. |
| `label` | `string` | An i18n key. The footer renders it through `t()`.           |
| `to`    | `string` | Route or URL of the link target.                            |
| `order` | `number` | Sort key, ascending. There is no default.                   |

**Where to register.** Register links from an ordinary plugin. The entry is plain data and SSR-safe. The registry is a module-level `ref`, so it does not need the frontend context, but a plugin keeps the layer's wiring in one place.

**Where it renders.** `Footer.vue` renders a link per entry, sorted by `order`, with the label resolved by `t(link.label)`.

This plugin adds a link and removes the Antelope website link. The documentation link stays:

```ts fragment [app/plugins/footer-links.ts]
export default defineDmsPlugin(() => {
  registerFooterLink({
    id: "my-module:docs",
    label: "footer.docs",
    to: "/docs",
    order: 200,
  });
  unregisterFooterLink("dms:website");
});
```

## Auth links

`registerAuthLink` adds a link below an auth page's form, for example an extra link under the login form. Auth links are page-scoped. Each entry names the page it belongs to, and each page reads only its own links.

```ts fragment
registerAuthLink(link: AuthLink): void
useAuthLinks(page: string): { links: ComputedRef<AuthLink[]> }
```

`AuthLink` has these fields, all required:

| Field   | Type     | Notes                                                                                                         |
| ------- | -------- | ------------------------------------------------------------------------------------------------------------- |
| `id`    | `string` | Stable key. Registering the same `id` again replaces the entry.                                               |
| `page`  | `string` | The auth page the link belongs to. It must match the key the page passes to `useAuthLinks`.                   |
| `label` | `string` | An i18n key, resolved through `$t()`.                                                                         |
| `to`    | `string` | Route or URL of the link target.                                                                              |
| `order` | `number` | Sort key, ascending. There is no default.                                                                     |

**Where to register.** Register links from an ordinary plugin. The entry is plain data and SSR-safe, and the registry is a module-level `ref`.

**Where it renders.** The login page is the auth page that reads the registry, with `useAuthLinks("login")`. When it has links, it renders them under the submit button as a centered column, sorted by `order`, each label resolved through `$t()`.

```ts fragment [app/plugins/auth-links.ts]
export default defineDmsPlugin(() => {
  registerAuthLink({
    id: "my-module:sso",
    page: "login",
    label: "auth.sso_hint",
    to: "/auth/sso",
    order: 100,
  });
});
```
