Three registries mount a global component of your [frontend layer](/docs/building/frontend-layer) in the dashboard shell. They differ in where the component lands and in who draws the chrome around it. A fourth, the [side panel](/docs/extending-the-dashboard/dashboard-chrome#side-panels-docked), docks a component next to the page.

| Registry                                                                        | Lands                                               | Chrome                                                                 |
| ------------------------------------------------------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------- |
| [App widget](#app-widgets-framed-dock)                                          | The dock in the bottom-left corner of the page      | The DMS draws an icon chip and the card that unfolds from it.          |
| [Sidebar widget](#sidebar-widgets-free)                                         | Above or below the sidebar's search button          | None. The component receives the sidebar's `collapsed` state.          |
| [App overlay](#app-overlays-free)                                               | Wherever the component positions itself             | None.                                                                  |
| [Side panel](/docs/extending-the-dashboard/dashboard-chrome#side-panels-docked) | A full-height column on the right, next to the page | The DMS draws the column, its resize handle, and the sheet below `lg`. |

[Sidebar entry locks](#sidebar-entry-locks) mount nothing: they close an entry of the sidebar menu and show why.

The examples on this page call the layer's auto-imported functions, so they are shown without imports.

## App widgets (framed dock)

`useAppWidgets().register(widget)` adds a framed widget to the dock in the bottom-left corner of the dashboard content panel. The DMS owns the presentation. Each widget is a low-opacity icon chip, stacked with the other widgets, and its `body` component unfolds into an animated card to the right of the chip on hover or keyboard focus. Your module only declares metadata.

```ts fragment
useAppWidgets(): {
  widgets: Readonly<Ref<AppWidget[]>>;
  register: (widget: AppWidget) => void;
  unregister: (id: string) => void;
}
```

`AppWidget` has these fields:

| Field           | Type     | Required | Notes                                                                                                                                           |
| --------------- | -------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`            | `string` | yes      | Stable key. Registering the same `id` again replaces the entry, and `unregister(id)` removes it.                                                |
| `icon`          | `string` | yes      | Icon name shown in the dock chip, for example `i-ph-git-branch-light`.                                                                          |
| `label`         | `string` | yes      | Chip tooltip and accessible name. A `$`-prefixed value resolves as an i18n key through `useTranslation().processI18n`.                          |
| `body`          | `string` | yes      | Name of the global component rendered inside the unfolded card.                                                                                 |
| `order`         | `number` | no       | Stack order, ascending from the bottom. Defaults to `0`. Widgets with the same order keep the order of their last registration.                 |
| `onSelectEvent` | `string` | no       | A `useDmsState` key. Each click on the chip adds one to the number stored there, starting from `0`. Watch it to open your own UI.               |
| `badge`         | `"dot"`  | no       | Draws an attention dot on the chip corner, and on the launcher when the dock folds. The chip's accessible name says the widget needs attention. |

**Where to register.** Register a widget from an ordinary plugin. Every field is a serializable string, so the plugin does not need `.client`. A widget decides its own visibility: call `register` when it has something to show, and `unregister(id)` when it does not.

**Where it renders.** `AppWidgetsDock.vue` is an absolute stack in the bottom-left corner of the dashboard content panel, in the panel's footer slot, so it does not scroll with the page. A chip lights up on hover or focus, and the `body` card slides out to the right while the other chips stay in place. The dock shows from the `sm` breakpoint only. Below `xl`, two or more widgets fold behind a single launcher chip, which unfolds the stack on hover or focus.

```ts fragment [app/plugins/app-widget.ts]
export default defineDmsPlugin(() => {
  useAppWidgets().register({
    id: "my-module:status",
    icon: "i-ph-pulse-light",
    label: "$my_module.widget.label",
    body: "MyModuleStatusCard",
    order: 10,
  });
});
```

`MyModuleStatusCard` is a global component from your layer.

**Click and attention.** A widget with `onSelectEvent` is clickable. Hover and focus still unfold `body`, so the card stays a status preview and the click opens the full UI. The click is plain data: the dock writes a counter into DMS state under the key you name, and your module watches that state. `badge: "dot"` stays until you register the widget again without it.

```ts fragment [app/plugins/assistant-widget.ts]
const SELECTED = "my-module:assistant-selected";

export default defineDmsPlugin(() => {
  const { register } = useAppWidgets();
  register({
    id: "my-module:assistant",
    icon: "i-ph-sparkle",
    label: "$my_module.assistant.label",
    body: "MyModuleAssistantStatus",
    onSelectEvent: SELECTED,
    badge: "dot",
  });

  watch(
    useDmsState<number>(SELECTED, () => 0),
    () => openAssistantPopup(),
  );
});
```

`openAssistantPopup` stands for whatever your module opens.

## Sidebar widgets (free)

`useSidebarWidgets().register(widget)` mounts a free component in the sidebar. The DMS adds no chrome. The component renders as it is, stacked with the other sidebar widgets, and scrolls with the sidebar content. `position` sets where the widget lands, and `module` sets when it renders.

```ts fragment
useSidebarWidgets(): {
  widgets: Readonly<Ref<SidebarWidget[]>>;
  register: (widget: SidebarWidget) => void;
  unregister: (id: string) => void;
}
```

`SidebarWidget` has these fields:

| Field       | Type                    | Required | Notes                                                                                                                                                                                   |
| ----------- | ----------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`        | `string`                | yes      | Stable key. Registering the same `id` again replaces the entry, and `unregister(id)` removes it.                                                                                        |
| `component` | `string`                | yes      | Name of the global component to mount. It receives a `collapsed: boolean` prop with the sidebar's state.                                                                                |
| `position`  | `SidebarWidgetPosition` | no       | `SidebarWidgetPosition.ABOVE_SEARCH_BAR` or `SidebarWidgetPosition.BELOW_SEARCH_BAR`. Defaults to `BELOW_SEARCH_BAR` for a widget with a `module`, and to `ABOVE_SEARCH_BAR` otherwise. |
| `order`     | `number`                | no       | Stack order, ascending from the top, among the widgets at the same `position`. Defaults to `0`.                                                                                         |
| `module`    | `string`                | no       | When set, the widget renders only inside that module (`/modules/<id>/**`). Omit it to render only in the global sidebar, outside every module.                                          |

`order` cannot interleave widgets at different positions, because they render at different places. Ties keep the widget's current index in the registry, which is not the time it was registered. Registering an existing id again keeps its index, even when the new `order` moves it into another tie group. Calling `unregister` and then `register` moves it to the end. Give tied widgets distinct `order` values when the stack has to be deterministic.

Import `SidebarWidgetPosition`, `useSidebarWidgets`, and their types and helpers from `#dms-layout/app/composables/useSidebarWidgets`. `resolveSidebarWidgetPosition(widget)` returns the position a widget renders at, with the defaults applied. `isSidebarWidgetVisible(widget, currentModuleId)` returns whether the widget renders while the user browses that module.

**Where to register.** Register a widget from an ordinary plugin. Every field is serializable, so the widget renders during SSR. The `module` field scopes a widget to a module. Any other visibility condition is the widget's own: render nothing when there is nothing to show, or call `unregister(id)`.

**Where it renders.** `DashboardSidebar.vue` renders each widget in the sidebar's content area, at the widget's `position`:

- `ABOVE_SEARCH_BAR` is at the top, below the logo and above the search button.
- `BELOW_SEARCH_BAR` is under the search button. Inside a module, it is also under the module title card, so a module widget reads as part of the module.

**When it renders.** `module` controls visibility, whatever the `position`. A global widget, with no `module`, renders only outside modules. A module-scoped widget renders only inside its own module. A widget out of scope stays registered and is not mounted, so registering it once at startup is enough. Widgets from different layers share one stack per position, so the layers agree on `order` values to keep the stack predictable.

Widgets keep rendering when the sidebar collapses to the icon rail. Each one receives `collapsed` and can switch to an icon-only variant. A widget that ignores the prop still renders, so it must at least not overflow the rail.

```ts fragment [app/plugins/sidebar-widget.ts]
export default defineDmsPlugin(() => {
  useSidebarWidgets().register({
    id: "my-module:announcement",
    component: "MyModuleAnnouncement",
    position: SidebarWidgetPosition.ABOVE_SEARCH_BAR,
    module: "my-module",
    order: 10,
  });
});
```

`MyModuleAnnouncement` is a global component from your layer. It hides its text when the sidebar collapses:

```vue [app/components/MyModuleAnnouncement.vue]
<script setup lang="ts">
defineProps<{ collapsed?: boolean }>();
</script>

<template>
  <div
    class="rounded-md border border-default px-3 py-2"
    :class="{ 'px-0 text-center': collapsed }"
  >
    <UIcon name="i-ph-megaphone" />
    <span v-if="!collapsed">New release available!</span>
  </div>
</template>
```

## Sidebar entry locks

`useMenuLocks().lock({ fullId, reason })` keeps a page or category in the sidebar but closes it. Use it for a page your module registers and cannot serve in the current setup, so the user sees that it exists and why it is closed.

```ts fragment
useMenuLocks(): {
  locks: Readonly<Ref<MenuLock[]>>;
  lock: (menuLock: MenuLock) => void;
  unlock: (fullId: string) => void;
}
```

`MenuLock` has these fields, all required:

| Field    | Type     | Notes                                                                                                            |
| -------- | -------- | ---------------------------------------------------------------------------------------------------------------- |
| `fullId` | `string` | The `fullId` of the page or category, as registered. Locking it again replaces its reason.                       |
| `reason` | `string` | The entry's tooltip. A `$`-prefixed value resolves as an i18n key through `useTranslation().processI18n`.        |

Both calls are idempotent. `lock` with the reason an entry already has changes nothing, and `unlock` of an entry that is not locked does nothing, so a plugin or a component can call either every time it runs. Import `useMenuLocks` and `MenuLock` from `#dms-layout/app/composables/useMenuLocks`.

**Where to register.** Lock from an ordinary plugin when the condition is known at startup. Plugins run before the sidebar renders on the server and in the browser, so the lock is in the first paint. A lock a page component sets is not: the sidebar renders before the page, so the entry turns locked once the browser renders. Use a component only for a condition that changes at runtime.

**Where it renders.** `NavigationMenu.vue` draws a locked entry in every sidebar menu: the page tree, the favorites, the footer entries, and the collapsed icon rail. The entry is muted and hatched, with a lock icon in place of its badge or status dot, and `reason` as its tooltip. It has no link. Locking a category locks every page under it: a collapsible category hides its children, and the pages a `label` category lists after it are drawn locked with the category's reason. A lock only changes the menu: it does not guard the route, so the page still answers a direct URL.

```ts fragment [app/plugins/menu-locks.ts]
export default defineDmsPlugin(() => {
  useMenuLocks().lock({
    fullId: "modules.my-module.diagram",
    reason: "$my_module.locked.external_database",
  });
});
```

## App overlays (free)

`useAppOverlay().register(name)` registers a global component by name. The component renders on every page with no chrome and positions itself, usually with `position: fixed`. Use it for a floating action button, a status bubble, or anything the framed dock does not fit. The component lives outside the routed page, so it stays mounted across navigation.

```ts fragment
useAppOverlay(): {
  overlays: Readonly<Ref<string[]>>;
  register: (name: string) => void;
  unregister: (name: string) => void;
}
```

`register` takes one argument, `name`: the name of a global component to mount. The component must be available globally, as the layer's auto-imported components are. Registering the same name twice has no effect.

**Where to register.** Register an overlay from an ordinary plugin. The payload is a string, so it is SSR-safe.

**Where it renders.** The app mounts each registered name with `<component :is>`, inside `UApp` and outside the routed page. The overlay is app-wide and persistent, and it controls its own placement. The DMS registers its own [side panel](/docs/extending-the-dashboard/dashboard-chrome#side-panels-docked) host the same way.

This plugin shows a floating support bubble on every page, not only on your module's pages:

```ts fragment [app/plugins/support-bubble.ts]
export default defineDmsPlugin(() => {
  useAppOverlay().register("MyModuleSupportBubble");
});
```
