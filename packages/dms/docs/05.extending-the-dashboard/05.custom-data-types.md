The built-in catalog ([Data types](/docs/components/data-types)) covers most fields, and a custom data type covers the rest. A custom type has two halves joined by one `id`:

- The **backend** declares the type: its validation, its compare modes, and the **names** of its input and filter widgets. It holds no Vue and refers to components by name only.
- The **frontend**, a plugin in your [frontend layer](/docs/building/frontend-layer), renders a stored value in table cells and read views.

The two halves share no code. Use the same `id` on both sides, and the DMS connects them. The per-field `options` object travels from the backend to every frontend hook.

## Declare the type on the backend

Subclass `DataType`, decorate the class with `@RegisterDataType("<id>")`, and import the file once in your module. The decorator registers the type when the file loads. The constructor passes three values to `super(...)`: the compare modes the type offers, its default mode, and the per-field `options`. The class then implements two members:

- `getValidation()` returns the Zod schema that validates a value before it is saved.
- `defaultInputComponent()` returns the input widget, built with a `FormComponents` helper (`InputText`, `InputNumber`, or `InputCheckbox`, for example). Each helper returns a `componentName` string and its options, never a Vue component.

The form input and the filter inputs both come from `defaultInputComponent()`. Override the public `inputComponent()` or `filterComponents()` only when forms and filters need different widgets.

Two more hooks refine the behavior. `filter()` decides how a filter value matches a row under a compare mode. `decorateField()` adds extra decorators to each field of the type, and the relation types use it. `filterComponents()` also gives a specific compare mode its own widget.

## Render the type on the frontend

From a plugin in your layer, register the same `id` with `useDataTypes().registerDataType({...})`. The last registration of an `id` wins. Every field besides `id` is optional, and all of them concern **reading** values:

| Field               | Purpose                                                                                                                                                                                                                                  |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `formatter`         | A map of `(value, locale, options?, row?) => string \| VNode` functions, keyed by compare mode, with a required `default`. `default` renders table cells, and the per-mode entries format filter chips. Two more keys exist: `cell`, a shorter grid rendering, and `empty`, drawn for a null value instead of the fallback. `row` is the listed row in a table and is absent elsewhere. |
| `displayComponent`  | A read-only Vue component for the form's read view. It receives `modelValue` and wins over `formatter` there. Any component works. Wrap a heavy one in `defineAsyncComponent` to keep its code out of the startup bundle. |
| `beforeStateMapper` | `(value, options?) => value` reshapes the server value before the form state is seeded. It must be idempotent, because a form reset applies it again to values that may already be mapped. The built-in `relation` type uses it to turn populated objects back into bare ids. |
| `isSameValue`       | `(left, right, options?) => boolean` tells whether two values of the type are the same. An edit form sends only the fields whose value differs from the loaded one, and compares them with this function. Without it, values compare deeply. The built-in `relation` type compares the referenced ids, so a populated row and the id the picker holds match, and the picks of a multiple relation compare as a set. |
| `filterEditorValue` | `(text, mode) => value` gives the value a filter chip's editor holds for a filter that a view or a tab declared as text, under a compare mode. The built-in number types read `"0"` as `0`, and the `date` type splits an `is_between` value into its two days. Without it, the editor reads the text as is. The filter keeps its text, so the query does not change. |
| `selectSource`      | `(options) => { searchUrl, keyMapping? } \| undefined` is for a type whose value holds ids of rows that another table serves. It returns the `select` route those rows are read from, given the options of the type's control. A filter chip and a read-only list name the ids through it, and ask the route for those rows alone with `?ids=`. The built-in `relation` and `cascader_relation` types return their picker's `searchUrl` and `keyMapping`. An id that the route does not return reads "Not found". A table cell, a card, and a kanban card do not use it, because the route that lists them joins the related rows (`Foreign`). |

::warning
The frontend registration has no `inputComponent` or `filterComponents`. The backend decides the input and filter widgets and sends them as `componentName` strings. The frontend half owns read rendering only.
::

`formatter` receives the options of the field's input component as its `options` argument, both in table cells and in the form read view. A formatter can rely on them, for example the labels and tones of a status or the items of a select.

A formatter runs wherever a value is drawn: a cell, a card field, a group header, a footer summary, or a filter chip. It often runs with no component setup active, so it must not call a composable. `useI18n()` throws there with "Must be called at the top of a `setup` function", and the page shows the error page. Write the formatter's texts through `getAppTranslation()`:

- `processI18n("$my.key")` for a `$`-prefixed label.
- `processApiMessage(message)` for a server message.
- `t("my.key", { count }, count)` for a plain key, plural count included.

A `ComposedText` goes through `getAppComposedText().processText(text)`. Each call reads the active locale, so the text follows a language switch.

## Cell data types

A frontend data type can draw cells without being a column's type. A column names it with a `display`, a class registered under the type's id with `@RegisterDisplay("<module>:<id>")` ([Cell displays](/docs/components/tables/cell-displays)), and keeps its own `type` for forms and filters. The formatter then receives, as `options`:

- The display's options.
- `typeOptions`, the options of the column's own type, such as a select's items.
- `columnType`, the id of the column's own type, to write the value as the column would.

The formatter also receives the row.

The DMS registers the frontend types behind its own `DefaultDisplays` classes under these ids: `identity`, `two_line`, `pills`, `relative_date`, `indicator`, `status_pill`, `progress`, `sparkline`, `duration`, `bytes`, `string`, and `mono`. [Cell displays](/docs/components/tables/cell-displays#built-in-displays) lists their options.

## Example: a rating type

This example adds a star rating from 0 to 5. The backend declares the type and reuses the built-in numeric input. The frontend draws filled stars in table cells and in the form's read view. A value of 4 shows four filled stars and one empty star.

On the backend, declare the type, its validation, and its input widget:

```ts [src/data-types/rating-type.ts]
import { z } from "zod";
import { FormComponents } from "@antelopejs/interface-dms/base/form";
import {
  DataType,
  DefaultDataCompareTypes,
  RegisterDataType,
} from "@antelopejs/interface-dms/base/data-types";

@RegisterDataType("rating")
export class RatingType extends DataType {
  constructor(public readonly options: { max?: number } = { max: 5 }) {
    super(
      [DefaultDataCompareTypes.Is, DefaultDataCompareTypes.IsNot],
      DefaultDataCompareTypes.Is,
      options,
    );
  }

  protected defaultInputComponent() {
    const component = FormComponents.InputNumber({
      min: 0,
      max: this.options.max ?? 5,
      step: 1,
    });
    component.options = { ...component.options, ...this.options };
    return component;
  }

  getValidation() {
    return z
      .number()
      .min(0)
      .max(this.options.max ?? 5);
  }
}
```

`defaultInputComponent()` copies the type's options onto the input's options, because the frontend reads `max` from there. Import the file once, then use the type like a built-in one: `type: new RatingType({ max: 5 })` on a `Form` field ([Forms](/docs/components/forms)) or a `TableView` column ([Tables](/docs/components/tables)). If the type's options carry `$`-prefixed labels, add the matching i18n keys to every locale file ([Localization](/docs/building/localization)).

On the frontend, register the same `id` with a star formatter and an async display component:

```ts fragment [app/plugins/register-rating.ts]
import { defineAsyncComponent, h } from "vue";
import UIcon from "@nuxt/ui/runtime/vue/components/Icon.vue";

export default defineDmsPlugin(() => {
  const { registerDataType } = useDataTypes();

  registerDataType({
    id: "rating", // must equal @RegisterDataType("rating")
    formatter: {
      default: (value, _locale, options) => {
        const max =
          typeof options === "object" &&
          options !== null &&
          "max" in options &&
          typeof options.max === "number"
            ? options.max
            : 5;
        const filled = Math.round(Number(value) || 0);
        return h(
          "span",
          { class: "inline-flex items-center gap-0.5" },
          Array.from({ length: max }, (_, i) =>
            h(UIcon, {
              name: i < filled ? "i-ph-star-fill" : "i-ph-star",
              class: "size-4",
            }),
          ),
        );
      },
    },
    displayComponent: defineAsyncComponent(() => import("../components/DisplayRating.vue")),
  });
});
```

Import `UIcon` from Nuxt UI's Vue entry, `@nuxt/ui/runtime/vue/components/Icon.vue`, as the DMS does. The Nuxt component entry imports Nuxt runtime dependencies that a DMS frontend does not have.

The display component receives `modelValue`, and the field's options as separate props, `max` included:

```vue [app/components/DisplayRating.vue]
<script setup lang="ts">
import { computed } from "vue";
import UIcon from "@nuxt/ui/runtime/vue/components/Icon.vue";

interface Props {
  modelValue?: number | null;
  max?: number;
}

const props = withDefaults(defineProps<Props>(), { max: 5 });
const filled = computed(() => Math.round(Number(props.modelValue) || 0));
</script>

<template>
  <span v-if="modelValue == null" class="text-dimmed">—</span>
  <span
    v-else
    class="inline-flex min-h-9 items-center gap-0.5"
    role="img"
    :aria-label="`${filled} out of ${max} stars`"
  >
    <UIcon
      v-for="i in max"
      :key="i"
      :name="i <= filled ? 'i-ph-star-fill' : 'i-ph-star'"
      class="size-4"
      aria-hidden="true"
    />
  </span>
</template>
```

The read view uses this component instead of the formatter, and table cells still use the formatter. Both round the value the same way. A missing value shows a dash, and zero shows five empty stars.

The frontend names no input or filter component. Those come from the backend's `defaultInputComponent()` and resolve by name.
