---
title: "TableView displays"
description: The registry and the backend options behind an alternate TableView body, such as a board, cards or a calendar, that keeps the table's search, filters, sort, tabs, pagination, selection and row actions.
mode: reference
---

A `TableView` runs one shared list query, and its toolbar drives it: search, filters, sort, tabs, pagination, selection and row actions ([Tables](/docs/components/tables)). The body only paints the result. A **display** replaces that body. The grid is the default display, the DMS ships `kanban`, `cards` and `grouped` as built-in alternatives, and a display of your own, such as a calendar or a gallery, keeps the whole toolbar.

A display is two declarations that share an `id`:

- A **frontend registration** gives the label, the icon, the body component and the availability rule. A plugin in your [frontend layer](/docs/building/frontend-layer) makes it.
- A **backend offer** in the table view's options lists the display, picks the default, and declares how the display reads its data and which toolbar controls it keeps.

## Display registration

`registerTableViewDisplay` adds a display to the registry. Call it once, from a plugin, with an id of the form `<module>:<id>` (`"saas:plan-cards"`, `"automation:timeline"`). The built-in ids `table`, `kanban`, `cards` and `grouped` are reserved. `registerTableViewDisplay` throws for a reserved id, for an id without its module prefix, and for an id that another registration already claimed.

```ts fragment [app/plugins/my-display.ts]
import MyDisplay from "../components/MyDisplay.vue";

export default defineDmsPlugin(() => {
  registerTableViewDisplay({
    id: "crm:deal-board",
    label: "Board",
    icon: "i-ph-cards",
    order: 30,
    component: MyDisplay,
  });
});
```

A `TableViewDisplay` has these fields:

| Field          | Type                         | Notes                                                                                                                         |
| -------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `id`           | `string`                     | `<module>:<id>`. Matches `displays[].id`, `defaultDisplay` and the saved user preference.                                    |
| `label`        | `string`                     | An i18n key or a literal label, shown in the view switcher.                                                                   |
| `icon`         | `string`                     | The icon shown in the view switcher.                                                                                          |
| `component?`   | `Component \| ComponentInfo` | The body renderer: a component, or a `ComponentInfo` resolved by name. Left out, the table view renders its own grid.        |
| `order?`       | `number`                     | The position in the switcher, lower first. Defaults to `100`.                                                                 |
| `isAvailable?` | `(ctx) => boolean`           | Hides the display from a table it cannot render. `ctx` is `{ columns, options? }`. The kanban uses it to require a column to group on. |

Register from a universal plugin, not a `.client` one. The registry holds callables, so the server never serializes it: the plugin rebuilds it on the server and again in the browser. The server render then draws the view switcher, and hydration finds it in place. A display registered from a `.client` plugin works too, but it joins the switcher only after hydration, and the toolbar shifts.

## The display context

The body component receives one prop, `context`, a `TableViewDisplayContext`. A display that paints `items` keeps search, filters, sort and pagination, because they all feed the shared query.

```ts fragment [app/components/MyDisplay.vue]
import type { TableViewDisplayContext } from "#dms-ui/app/composables/table-view/types";

const props = defineProps<{ context: TableViewDisplayContext }>();
```

| Field                      | Type                          | Purpose                                                                                                                                                                  |
| -------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `items`                    | `T[]`                         | The current page of rows from the shared list query. Under `loadMore` or `infinite` pagination, every row loaded so far. Empty for a self-managed display.               |
| `columns`                  | `TableViewColumn[]`           | The full column metadata: types, labels and accessor keys.                                                                                                              |
| `loading`                  | `boolean`                     | The shared query is in flight, for its first read or for any later read.                                                                                                |
| `firstPageLoading`         | `boolean`                     | No answer has arrived yet. Draw a skeleton, not the empty state. A later read keeps the rows, or the empty state, on screen, and a skeleton in their place flashes.     |
| `selection`                | `TableViewDisplaySelection`   | `{ ids, isSelected(id), toggle(id, value?), toggleAll(value?), clear() }`. The grid and the display share one selection state.                                         |
| `pagination`               | `TableViewDisplayPagination`  | `{ pageIndex, pageSize, total, setPage(i), setPageSize(n), mode, hasMore, loadMore() }`. A change re-runs the shared query. `mode` is the table's [pagination](/docs/components/tables/pagination) mode. Under `loadMore` and `infinite`, call `loadMore()` while `hasMore` is true. |
| `actions`                  | `TableViewDisplayActions<T>`  | The `canAdd`, `canEdit`, `canDelete` and `canDetails` flags, the per-row `canEditRow(item)` and `canDeleteRow(item)`, and the handlers `add`, `edit`, `delete(ids, rows?)`, `duplicate(id)`, `details`, `open(item)`, `custom(action, item)` and `customFor(item)`. Pass `rows` to `delete` so the confirmation can name the rows the display draws. `customFor(item)` lists the custom row actions the item offers. |
| `presenceByRow`            | `TableViewPresenceMap`        | Realtime presence keyed by row id, for an "X is editing this" marker.                                                                                                   |
| `rowIdKey`                 | `string`                      | The field used as the row id.                                                                                                                                           |
| `labelKey?`                | `string`                      | The field used as an item's title, when the table view sets one.                                                                                                        |
| `location`                 | `string`                      | The data API location, for a self-managed display that fetches its own rows.                                                                                           |
| `query`                    | `Record<string, unknown>`     | The active filters, search and sort, without limit or offset, for a self-managed display.                                                                              |
| `componentId?`, `pageId?`  | `string`                      | Stable identifiers, for example for a fetch key per instance.                                                                                                           |
| `options?`                 | `Record<string, unknown>`     | The options the backend declares for this display on this table.                                                                                                        |
| `refresh()`                | `() => Promise<void> \| void` | Reads the table view again: the shared list, the tab counts and the active display.                                                                                    |
| `setShownRows?(rows)`      | `(rows: T[]) => void`         | For a self-managed display: hands over the rows shown, in reading order, so a row opened from the display steps through them in its drawer.                            |
| `reorder?`                 | `TableViewDisplayReorder`     | Rows ordered by hand (backend `reorder`): `{ enabled, move(from, to) }`, with indexes into `items`. Set on the grid and the `cards` display, for a caller who may edit. `enabled` is off while a search, a filter or a tab narrows the rows (see [Rows ordered by hand](/docs/components/tables/reorder)). |
| `table?`                   | `Table<T>`                    | The TanStack table instance, present when the display renders inside the table body slot. For advanced displays.                                                        |

`actions.canEditRow(item)` and `actions.canDeleteRow(item)` evaluate the conditional rules, so a display can show an edit or delete control on one item and hide it on another. `actions.customFor(item)` does the same for the custom row actions. It lists the actions whose `rule` accepts the item, in their declared order, so a card that draws its own menu offers what the grid's menu offers. Give an action an `id` to find it among them, for example to place "Stop selling" on a button of its own.

::note{title="Self-managed displays"}
Most displays read `items`. A **self-managed** display (`selfManagedData: true` in the backend options) skips the shared list query: `items` arrives empty, and the display fetches its rows from `context.location` with `context.query`. Expose a `refresh()` method on the component. The table view calls it on a realtime update. Call `context.setShownRows(rows)` each time the rows shown change, in the order the user reads them. A row opened from the display then steps through those rows in its drawer or side panel ("3 of 12", previous and next, J and K). Without the call, the row opens without steps. The built-in kanban is self-managed and hands its cards column by column, top to bottom in each column.
::

## The backend offer

A registered display shows nowhere until a table view offers it. A table view without `displays` offers the `table` display alone. A table view with `displays` offers the displays it lists, so list `{ id: "table" }` to keep the grid. The `kanban` and `grouped` options also add their display after the list when the list does not place it. `defaultDisplay` picks the display shown when the user has no saved preference. It defaults to the first display offered.

```ts [src/pages/deals.ts]
import { CustomComponent } from "@antelopejs/interface-dms/base/custom";
import { DefaultDataTypes } from "@antelopejs/interface-dms/base/data-types";
import { TableView } from "@antelopejs/interface-dms/base/table-view";

TableView.fromSource({
  fetchUrl: "/api/deals",
  caption: "Deals",
  labelKey: "name",
  columns: {
    name: { name: "Name", type: new DefaultDataTypes.StringType() },
    stage: { name: "Stage", type: new DefaultDataTypes.StringType() },
  },
  displays: [
    { id: "crm:deal-board", component: CustomComponent("MyDisplay") },
    { id: "table" },
  ],
  defaultDisplay: "crm:deal-board",
});
```

Each entry is a `TableViewDisplayOption`. The table view throws for an id that is neither a built-in id nor `<module>:<id>`, for a built-in id given a `component` of its own, and for a `defaultDisplay` it does not offer.

| Field              | Type                           | Notes                                                                                                                                          |
| ------------------ | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`               | `string`                       | A built-in display id (`"cards"`), or a module display's `<module>:<id>`.                                                                       |
| `options?`         | `Record<string, unknown>`      | Options for this table, passed to the body as `context.options`.                                                                               |
| `component?`       | `Component`                    | A component reference that survives serialization (`CustomComponent("...")`). Set it so the body renders during the server render.          |
| `selfManagedData?` | `boolean`                      | `true` skips the shared list query for this display.                                                                                           |
| `capabilities?`    | `TableViewDisplayCapabilities` | The toolbar controls shown while this display is active. A capability turned off also stops its saved state from narrowing the shared query.  |

These are the capabilities and their defaults:

| Capability         | Default | Controls                                                     |
| ------------------ | ------- | ------------------------------------------------------------ |
| `columnManagement` | `false` | Column visibility, pinning, size and order                   |
| `filters`          | `true`  | The filters row and the filter trigger                       |
| `search`           | `true`  | The search box                                               |
| `sorting`          | `true`  | The sort menu                                                |
| `tabs`             | `true`  | The filter tabs                                              |
| `header`           | `true`  | The table's own chrome around the display: caption, toolbar, tabs, filters row and bulk bar. A display that draws a complete interface of its own turns it off. |

A table with `reorder` turns `sorting` off on every display.

`selfManagedData` and `capabilities` live in the backend options, not in the client registry, because the server renders first. `selfManagedData` decides whether the server runs the shared list query, and `capabilities` decides which toolbar controls it renders. A decision made in the browser would differ from the server render and break hydration. For the same reason, reference the body component in `displays[].component`, so it renders on the server.

The switcher lists the displays found in all three of these: the client registry, the ids the backend offers, and the displays whose `isAvailable` accepts the table. The active display comes from the user's saved preference, with two guards:

- A saved id the table no longer offers falls back to `table` when the table offers it, and to `defaultDisplay` otherwise.
- After mount, an active display that the switcher does not list, and that the backend gives no `component`, falls back the same way.

When the default display turns its `header` off, the table opens on it whatever the saved preference.

## Built-in displays

The DMS registers four displays:

- **`table`** (`order: 10`) is the grid. It has no `component`, which tells the table view to render its own body. Its defaults turn `columnManagement` on.
- **`grouped`** (`order: 15`) is the grid with its rows under a header per group, set by the table view's `grouped` option. Like the grid, it has no `component`. Its defaults turn `columnManagement` on and `sorting` off, because the rows are sorted on the grouped column.
- **`kanban`** (`order: 20`) needs a column to group on: a single-select column, a boolean column or a status column. Its defaults set `selfManagedData: true` and `tabs: false`.
- **`cards`** (`order: 30`) draws a grid of cards over the shared list query, from the table view's `card` option, like the kanban's cards (see [Cards](/docs/components/tables/cards)).

An entry for a built-in display merges its own fields over these defaults, key by key. Overriding one kanban capability keeps the others.

## Example: a cards display

This custom card display is three files: the client registration, the body component and the backend offer. The playground's **Cards (Custom Display)** page runs it.

The plugin registers the display in your frontend layer:

```ts fragment [frontend-vue/app/plugins/table-view-cards-display.ts]
import { defineAsyncComponent } from "vue";

const TaskCardsDisplay = defineAsyncComponent(
  () => import("../components/TaskCardsDisplay.vue"),
);

export default defineDmsPlugin(() => {
  registerTableViewDisplay({
    id: "playground:task-cards",
    label: "Cards",
    icon: "i-ph-cards",
    order: 30,
    component: TaskCardsDisplay,
  });
});
```

The body component paints `context.items`, and sends selection, actions and pagination back through the context:

```vue [frontend-vue/app/components/TaskCardsDisplay.vue]
<script setup lang="ts">
import type { TableViewDisplayContext } from "#dms-ui/app/composables/table-view/types";

const props = defineProps<{ context: TableViewDisplayContext }>();

const rowId = (item: Record<string, unknown>): string => String(item[props.context.rowIdKey] ?? "");

const title = (item: Record<string, unknown>): string => {
  const value = props.context.labelKey ? item[props.context.labelKey] : undefined;
  return value != null && value !== "" ? String(value) : rowId(item);
};

const currentPage = computed({
  get: () => props.context.pagination.pageIndex + 1,
  set: (page: number) => props.context.pagination.setPage(page - 1),
});
</script>

<template>
  <div v-if="context.firstPageLoading" class="grid gap-3 sm:grid-cols-2 lg:grid-cols-3">
    <USkeleton v-for="n in 6" :key="n" class="h-32 w-full" />
  </div>

  <div v-else-if="context.items.length === 0" class="py-10 text-center text-sm">No items</div>

  <div v-else class="grid gap-3 sm:grid-cols-2 lg:grid-cols-3">
    <div
      v-for="item in context.items"
      :key="rowId(item)"
      class="rounded-lg border p-4"
      :class="{ 'cursor-pointer': context.actions.canEdit }"
      @click="context.actions.canEdit && context.actions.edit(item)"
    >
      <div class="flex items-center gap-2">
        <UCheckbox
          :model-value="context.selection.isSelected(rowId(item))"
          @click.stop
          @update:model-value="(v) => context.selection.toggle(rowId(item), !!v)"
        />
        <p class="truncate text-sm font-semibold">{{ title(item) }}</p>
        <UButton
          v-if="context.actions.canDelete"
          icon="i-ph-trash"
          color="error"
          variant="ghost"
          size="xs"
          @click.stop="context.actions.delete([rowId(item)], [item])"
        />
      </div>
    </div>
  </div>

  <UPagination
    v-model:page="currentPage"
    :total="context.pagination.total"
    :items-per-page="context.pagination.pageSize"
  />
</template>
```

The page controller offers the display, with a component reference the server can render:

```ts fragment [src/pages/tasks-cards.ts]
static table = TableView(taskDataAPI, {
  caption: "Tasks (cards)",
  labelKey: "name",
  rowActions: {
    add: true,
    edit: { isVisible: true },
    delete: { isVisible: true },
    details: true,
    duplicate: true,
    hasSelection: true,
  },
  displays: [
    { id: "table" },
    { id: "playground:task-cards", component: CustomComponent("TaskCardsDisplay") },
  ],
  defaultDisplay: "playground:task-cards",
});
```

When the user types in the search box or changes a filter, the shared query runs again and `items` changes under the cards, with no code in the display. To react to those changes elsewhere on the page, listen to the table view's [component events](/docs/extending-the-dashboard/component-events).
