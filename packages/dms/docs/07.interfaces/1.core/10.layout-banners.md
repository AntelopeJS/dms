# Layout Banners

## Overview

A layout banner is a global message the backend adds under the dashboard header: a colored strip carrying a line of text or a component of your frontend layer. It renders on every page of the dashboard layout — tenant pages and the module back-office pages under `/modules` alike — and banners stack by `order`.

Whether a banner shows is decided per request, on the server, while the site layout is built. The answer is part of the server-rendered page, so a banner never flashes in or out after hydration.

Everything lives in `@antelopejs/interface-dms/layout-banners`.

## Register a Banner

`RegisterLayoutBanner(info)` registers the banner and returns a function removing it. Register at import time, next to the state the banner reports on; the registration is dropped automatically when your module stops.

```typescript
import {
  LayoutBannerVariant,
  RegisterLayoutBanner,
} from "@antelopejs/interface-dms/layout-banners";
import { isMaintenanceScheduled } from "./maintenance";

RegisterLayoutBanner({
  key: "my-app:maintenance",
  variant: LayoutBannerVariant.WARNING,
  text: "$my_app.banners.maintenance",
  order: 10,
  dismissible: true,
  visible: async ({ tenantId }) => isMaintenanceScheduled(tenantId),
});
```

A banner can mount a global component of your [frontend layer](/docs/building/frontend-layer) instead of a text. The DMS still draws the chrome around it — color, icon, close button and ARIA role — and passes `props` to the component:

```typescript
RegisterLayoutBanner({
  key: "my-app:trial",
  variant: LayoutBannerVariant.INFO,
  component: "MyAppTrialBanner",
  props: { upgradeUrl: "/settings/billing" },
  visible: ({ isOwner }) => isOwner,
});
```

Re-registering a `key` replaces the banner.

## `LayoutBannerInfo`

| Field | Type | Description |
| ----- | ---- | ----------- |
| `key` | `string` | Unique across the deployment. Required. Also what a dismissal remembers: give a banner a new key when it must show again to users who dismissed it. |
| `variant` | `LayoutBannerVariant` | `"info"`, `"warning"` or `"error"`. Required. Picks the color, the default icon and the ARIA role. |
| `text` | `string` | The message. A `$`-prefixed value resolves as an i18n key. Exclusive with `component`; one of the two is required. |
| `component` | `string` | Name of a global component rendered as the banner's content. Exclusive with `text`. |
| `props` | `Record<string, unknown>` | Props passed to `component`. Must be serializable. |
| `order` | `number` | Stack order, ascending from the top. Defaults to `0`; ties keep the registration order. |
| `icon` | `string` | Leading icon. Defaults to one matching the variant. |
| `dismissible` | `boolean` | Whether the user can close the banner. Defaults to `false`. |
| `visible` | `LayoutBannerVisibility` | Decides per request whether the banner shows. Absent means always. |

## Visibility

`visible(context)` returns a boolean, or a promise of one. It runs server-side for every site layout request, all resolvers together, so the request waits for the slowest one rather than for their sum. A resolver that throws, does not answer within two seconds, or returns anything but `true` hides its banner for that request; the other banners are unaffected.

### `LayoutBannerContext`

| Field | Type | Description |
| ----- | ---- | ----------- |
| `user` | `User \| undefined` | The caller; `undefined` for an unauthenticated request. |
| `tenantId` | `string` | The tenant the site layout is built for. |
| `permissions` | `Set<string>` | The caller's effective permissions in the tenant. |
| `isOwner` | `boolean` | Whether the caller holds the wildcard permission. |
| `isTenantAccessDenied` | `boolean` | Whether a [tenant access gate](./5.tenancy.md) currently refuses the caller. |

Unlike product surfaces, a banner reads the permissions a denying access gate would hide: telling a suspended or past-due workspace why is exactly what a banner is for. Check `isTenantAccessDenied` when the two situations call for different banners.

The resolvers run whenever a client fetches its site layout — on a full page load and after a menu invalidation. When the state a resolver reads changes, call `NotifyMenuChanged(tenantId)` from `@antelopejs/interface-dms/page` so the connected clients of that tenant re-fetch it and the banner appears or goes without a reload.

## Rendering

Banners render under the header of the dashboard layout, full width, in `order`. Each one is its own live region: `error` banners carry `role="alert"`, `info` and `warning` banners `role="status"`.

A dismissible banner shows a close button. The dismissal lasts for the browser session and is kept in the `dms-dismissed-banners` cookie, which the server reads too, so a dismissed banner is already absent from the server-rendered page. A banner that is not dismissible ignores any dismissal recorded under its key.
