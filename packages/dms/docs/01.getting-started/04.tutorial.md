In this tutorial, we add a purchasing section to Helio, the solar installer of the demo template. Helio buys its panels and inverters from suppliers, so we build a **Suppliers** table, a **Purchase orders** table linked to it, a dashboard that counts the orders placed in a period, and a role that may create orders but not delete them. We write backend TypeScript only. There is no Vue file in this tutorial.

You need the project from the [Quickstart](/docs/getting-started/quickstart), with its backend and dashboard running. Add the new files next to the template's own files.

## What we build

A purchase order goes through three layers. The model stores it, the data controller describes its fields and routes, and a `TableView` page lists it and opens its edit form:

```text [From data to screen]
┌─────────────────┐     ┌─────────────────┐     ┌───────────────────┐
│ Supplier and    │────▶│ DataController  │────▶│ TableView page    │
│ PurchaseOrder   │     │ fields + routes │     │ list + edit form  │
└─────────────────┘     └─────────────────┘     └───────────────────┘
```

These are the files we add under `src/`:

```bash [src/]
src/
  db/purchasing.ts               # two tables and their models
  data-api/purchasing.ts         # two data controllers: fields and CRUD routes
  pages/purchasing.ts            # a Purchasing category, two table pages, a dashboard
  routes/purchasing-stats.ts     # the route behind the dashboard's KPI card
```

:::steps{level="3"}

### Declare the tables and models

Tables, models, and the `@Field` and `@Relation` decorators come from AntelopeJS. The framework's [Database guide](https://antelopejs.com/docs/guides/database) explains them. Create `src/db/purchasing.ts`:

```ts [src/db/purchasing.ts]
import {
  BasicDataModel,
  CreationTime,
  Field,
  Index,
  RegisterTable,
  Relation,
  Table,
  UpdateTime,
} from "@antelopejs/interface-database-decorators";

export const PURCHASING_SCHEMA = "purchasing";

@RegisterTable("purchasing_suppliers", PURCHASING_SCHEMA)
export class Supplier extends Table {
  @Field("string") declare _id: string;
  @Field("string") declare name: string;
  @Field("string") declare email: string;
  @CreationTime() @Index() @Field("date") declare createdAt: Date;
  @UpdateTime() @Index() @Field("date") declare updatedAt: Date;
}
export class SupplierModel extends BasicDataModel(Supplier, "purchasing_suppliers") {}

@RegisterTable("purchasing_orders", PURCHASING_SCHEMA)
export class PurchaseOrder extends Table {
  @Field("string") declare _id: string;
  @Field("string") declare reference: string;
  @Index() @Field("string") declare status: "ordered" | "received";
  @Field("string") @Relation({ to: () => Supplier }) declare supplierId?: string;
  @CreationTime() @Index() @Field("date") declare createdAt: Date;
  @UpdateTime() @Index() @Field("date") declare updatedAt: Date;
}
export class PurchaseOrderModel extends BasicDataModel(PurchaseOrder, "purchasing_orders") {}
```

`PurchaseOrder.supplierId` carries `@Relation({ to: () => Supplier })`, so the schema itself records the link between the two tables. `@CreationTime()` and `@UpdateTime()` stamp the dates on insert and update.

`PURCHASING_SCHEMA` is a schema of our own. The second argument of `@RegisterTable` files each table under it, and the entry file provisions it once the pages exist. The section stays shared by every tenant. To keep one copy of the data per tenant, use the tenant schema and scoped models instead ([Multi-tenant data](/docs/auth-and-tenancy/multi-tenant)).

### Describe the data with data controllers

A data controller declares once what each field is and which operations exist. The table pages and their forms read everything from it ([Data controller](/docs/components/data-controller)). The `DataController` factory and the field decorators come from the AntelopeJS Data API ([Data API guide](https://antelopejs.com/docs/guides/data-api)). The DMS adds the `@Column` and `@Searchable` metadata and the `TableViewRoutes` sets, which generate the routes a table needs and gate each route with its own permission. Create `src/data-api/purchasing.ts`:

```ts fragment [src/data-api/purchasing.ts]
import { Controller } from "@antelopejs/interface-api";
import { DataController, RegisterDataController } from "@antelopejs/interface-data-api";
import {
  Access,
  AccessMode,
  Listable,
  Mandatory,
  ModelReference,
  Sortable,
} from "@antelopejs/interface-data-api/metadata";
import { Model } from "@antelopejs/interface-database-decorators";
import { DefaultDataTypes } from "@antelopejs/interface-dms/base/data-types";
import { Searchable } from "@antelopejs/interface-dms/base/searchable";
import { Column, Select, TableViewRoutes } from "@antelopejs/interface-dms/base/table-view";
import {
  PurchaseOrder,
  PurchaseOrderModel,
  Supplier,
  SupplierModel,
} from "../db/purchasing";

@RegisterDataController()
export class supplierDataAPI extends DataController(
  Supplier,
  TableViewRoutes.All,
  Controller("/api/purchasing/suppliers"),
) {
  @ModelReference()
  @Model(SupplierModel)
  declare model: SupplierModel;

  @Select()
  @Listable()
  @Access(AccessMode.ReadOnly)
  declare _id: string;

  @Searchable()
  @Select()
  @Listable()
  @Sortable()
  @Column({ name: "Name", type: new DefaultDataTypes.StringType(), filterable: true })
  @Mandatory("new", "edit")
  @Access(AccessMode.ReadWrite)
  declare name: string;

  @Listable()
  @Column({ name: "Email", type: new DefaultDataTypes.EmailType() })
  @Mandatory("new", "edit")
  @Access(AccessMode.ReadWrite)
  declare email: string;
}

@RegisterDataController()
export class purchaseOrderDataAPI extends DataController(
  PurchaseOrder,
  TableViewRoutes.All,
  Controller("/api/purchasing/orders"),
) {
  @ModelReference()
  @Model(PurchaseOrderModel)
  declare model: PurchaseOrderModel;

  @Listable()
  @Access(AccessMode.ReadOnly)
  declare _id: string;

  @Searchable()
  @Listable()
  @Sortable()
  @Column({ name: "Reference", type: new DefaultDataTypes.StringType(), filterable: true })
  @Mandatory("new", "edit")
  @Access(AccessMode.ReadWrite)
  declare reference: string;

  @Listable()
  @Column({
    name: "Status",
    type: new DefaultDataTypes.SelectType({
      items: [
        { value: "ordered", label: "Ordered" },
        { value: "received", label: "Received" },
      ],
    }),
    filterable: true,
    defaultValue: "ordered",
  })
  @Mandatory("new", "edit")
  @Access(AccessMode.ReadWrite)
  declare status: string;

  @Listable()
  @Column({
    name: "Supplier",
    type: new DefaultDataTypes.RelationType({
      dataApiController: supplierDataAPI,
      keyMapping: { label: "name", value: "_id" },
    }),
  })
  @Mandatory("new", "edit")
  @Access(AccessMode.ReadWrite)
  declare supplierId: string;
}
```

The `RelationType` column is the UI side of the relation that the schema declared. The purchase order form gets a supplier picker, which the supplier controller's `select` route serves. The list shows the supplier's `name` instead of an id. The supplier controller has a `new` route, so the picker also offers an inline form to add a supplier to users who hold that permission.

`@Select()` marks the fields that the `select` route returns. Only the target of a relation needs it: `_id` is the picker's value and `name` its label. No relation points at purchase orders, so their controller marks no field with `@Select()`.

### Register the pages

A page puts a screen in the sidebar. The `purchasing` category groups our pages under `pagesCategory`, the sidebar's root **Pages** section. Each `TableView` points at its data controller, and the columns and forms come from the controller's decorators. The first argument of `PageController` is the page id. The permission ids in the last step start from it. Create `src/pages/purchasing.ts`:

```ts fragment [src/pages/purchasing.ts]
import { TableView } from "@antelopejs/interface-dms/base/table-view";
import {
  Category,
  PageController,
  RegisterPage,
  pagesCategory,
} from "@antelopejs/interface-dms/page";
import { purchaseOrderDataAPI, supplierDataAPI } from "../data-api/purchasing";

export const purchasing = Category("purchasing", {
  displayName: "Purchasing",
  icon: "i-ph-package",
  category: pagesCategory,
});

@RegisterPage()
export class SuppliersPage extends PageController("suppliers", {
  displayName: "Suppliers",
  icon: "i-ph-factory",
  category: purchasing,
  urlSlug: "suppliers",
}) {
  static table = TableView(supplierDataAPI, {
    caption: "Suppliers",
    labelKey: "name",
    formContainer: { type: "drawer" },
    rowActions: { add: true, edit: true, delete: true, hasSelection: true },
  });
}

@RegisterPage()
export class PurchaseOrdersPage extends PageController("purchase-orders", {
  displayName: "Purchase orders",
  icon: "i-ph-receipt",
  category: purchasing,
  urlSlug: "orders",
}) {
  static table = TableView(purchaseOrderDataAPI, {
    caption: "Purchase orders",
    labelKey: "reference",
    formContainer: { type: "drawer" },
    rowActions: { add: true, edit: true, delete: true, hasSelection: true },
    tabs: [
      {
        id: "ordered",
        label: "Ordered",
        filter: { accessorKey: "status", value: "ordered", mode: "is" },
      },
      {
        id: "received",
        label: "Received",
        filter: { accessorKey: "status", value: "received", mode: "is" },
      },
    ],
  });
}
```

`labelKey` names the field that identifies a row in a container title, so the drawer of an order shows its reference instead of an id. `hasSelection` turns on row selection.

Now wire the entry file. Open the template's `src/index.ts` and add these imports next to its other imports. The side-effect imports run the decorators, so the tables, controllers, and pages register when the module loads:

```ts fragment [src/index.ts]
import "./db/purchasing";
import "./data-api/purchasing";
import "./pages/purchasing";
import { PURCHASING_SCHEMA } from "./db/purchasing";
```

The template already provisions its own schema in a `Hook.DATABASE_INITIALIZED` hook inside `construct()`. That hook runs once the database is ready. Add our schema to it:

```ts fragment [src/index.ts, inside construct()]
RegisterHook(Hook.DATABASE_INITIALIZED, async () => {
  await RegisterSchema(DEMO_SCHEMA_NAME);
  await RegisterSchema(PURCHASING_SCHEMA);
  startServiceSimulator();
  return undefined;
});
```

Stop `pnpm dev`, start it again, and reload the dashboard.

The sidebar now shows a **Purchasing** group under **Pages**, with **Purchase orders** and **Suppliers**. Try it:

1. In **Suppliers**, select **New entry**. Enter `Sunline Panels` and `orders@sunline.example`, then select **Create**.
2. In **Purchase orders**, select **New entry** and create an order with the reference `PO-1001`, the status **Ordered**, and **Sunline Panels** in the supplier picker.
3. Add a second order, `PO-1002`, with the status **Received**.

The table shows both orders, with **Sunline Panels** in the **Supplier** column. The **Ordered** tab shows `PO-1001` only, and the **Received** tab shows `PO-1002` only. Search, column filters, and the drawer forms all work without a line of Vue.

### Add a dashboard

A dashboard is a page made of widgets. A `PeriodSelector` publishes a date range. A `KpiCard` that names the selector in `periodScope` fetches its value again each time the range changes ([Charts & widgets](/docs/components/charts-and-widgets)).

First, add the KPI route. It receives the selector's range as the `from` and `to` query parameters and answers with the `value` and `delta` that a `KpiCard` reads. The route checks the dashboard page's permission, because hiding a widget does not protect its route. Write `src/routes/purchasing-stats.ts`:

```ts fragment [src/routes/purchasing-stats.ts]
import { Controller, Get, Parameter } from "@antelopejs/interface-api";
import { Model } from "@antelopejs/interface-database-decorators";
import type { User } from "@antelopejs/interface-dms/auth/db";
import { AuthUserWithPermission } from "@antelopejs/interface-dms/guards";
import { PurchaseOrder, PurchaseOrderModel } from "../db/purchasing";
import { PurchasingDashboardPage } from "../pages/purchasing";

export class PurchasingStatsController extends Controller("/api/purchasing/stats") {
  @Model(PurchaseOrderModel)
  declare orders: PurchaseOrderModel;

  @Get("orders-placed")
  async ordersPlaced(
    @AuthUserWithPermission(PurchasingDashboardPage) _user: User,
    @Parameter("from", "query") from?: string,
    @Parameter("to", "query") to?: string,
  ) {
    const start = from ? new Date(from) : new Date(0);
    const end = to ? new Date(to) : new Date();
    const span = end.getTime() - start.getTime();
    const previousStart = new Date(start.getTime() - span);

    const all = await this.orders.getAll();
    const placedIn = (order: PurchaseOrder, a: Date, b: Date) =>
      order.createdAt >= a && order.createdAt <= b;
    const value = all.filter((order) => placedIn(order, start, end)).length;
    const previousValue = all.filter((order) => placedIn(order, previousStart, start)).length;
    const delta = previousValue === 0 ? 0 : ((value - previousValue) / previousValue) * 100;

    return { value, delta };
  }
}
```

`getAll()` reads every order, which is fine for a tutorial. A real dashboard asks the database for the count of one range.

Then add the dashboard page at the end of `src/pages/purchasing.ts`. It has a period selector, one live KPI card, and a chart with fixed sample values:

```ts fragment [src/pages/purchasing.ts, at the end]
import { ChartColumn } from "@antelopejs/interface-dms/base/chart";
import { Grid, GridRow } from "@antelopejs/interface-dms/base/grid";
import { KpiCard } from "@antelopejs/interface-dms/base/kpi-card";
import { PeriodSelector } from "@antelopejs/interface-dms/base/period-selector";

@RegisterPage()
export class PurchasingDashboardPage extends PageController("purchasing-dashboard", {
  displayName: "Dashboard",
  icon: "i-ph-chart-line-up",
  category: purchasing,
  urlSlug: "dashboard",
  order: 0,
}) {
  static period = PeriodSelector({ id: "purchasing", defaultPreset: "last-30-days" });

  static widgets = Grid({ gap: "1rem" }).child(
    "row",
    GridRow()
      .child(
        "ordersPlaced",
        KpiCard({
          title: "Orders placed",
          fetchUrl: "/api/purchasing/stats/orders-placed",
          periodScope: "purchasing",
        }),
      )
      .child(
        "panels",
        ChartColumn({
          title: "Panels delivered (sample data)",
          height: "260px",
          staticDataset: [
            { name: "Panels", data: [120, 190, 80, 240, 150].map((y, i) => ({ x: `W${i + 1}`, y })) },
          ],
        }),
      ),
  );
}
```

Add the route file to the imports of `src/index.ts`:

```ts fragment [src/index.ts]
import "./routes/purchasing-stats";
```

Restart `pnpm dev` and reload the dashboard. Open **Purchasing** > **Dashboard**. **Orders placed** shows `2`, the two orders we saved, for the default range of the last 30 days. Select another range, such as **Last 7 days**. The KPI card fetches its value again, and the chart stays the same, because `staticDataset` holds fixed values. To feed the chart from a route, replace `staticDataset` with a `fetchUrl` and a `periodScope`, as on the KPI card.

### Gate it with a role

Every page, table, and table action we registered already has a permission. A permission id starts with the page's path in the sidebar, then the component and the action, such as `pages.purchasing.purchase-orders.table.delete`. We declare nothing more.

::important
An invitation is an email, so the project must load an `interface-email` module. The demo template loads `@antelopejs/nodemailer` with `ethereal: true` in development, which sends every email to a disposable test inbox ([Optional dependencies](/docs/getting-started/installation#add-optional-dependencies)).
::

1. Open the **Roles** settings page and create a role named `Buyer`.
2. In its permission tree, open **Purchasing** and grant the **Purchase orders** page with `list`, `add`, and `edit`, but not `delete`.
3. Invite a user from the **Members** settings page with the `Buyer` role ([Built-in authentication](/docs/auth-and-tenancy/authentication)), then sign in as that user.

The row menu of **Purchase orders** has no **Delete** entry for this user. The delete route refuses the request too, because the same permission gates the menu entry and the route. [Auth & permissions](/docs/auth-and-tenancy/auth-and-permissions) explains how the ids are built, the decorators, and permissions you declare yourself.

:::
