The backend describes the UI, and a shared frontend renders it. That choice shapes the rest of the DMS. It runs as two processes, and every page follows the same path from your code to the screen.

## Why the backend describes the UI

Most admin frameworks build screens on the frontend and call an API for data. The AntelopeJS DMS does the opposite.

The backend declares both the screen and its data sources, as serializable data. A shared frontend reads that description and renders it. Adding an admin page is a backend-only change in almost every case.

You get three things from this design:

1. **One frontend for every module.** Every module's UI uses the same blocks, so a single Inertia and Vue app renders all of them. A module with no custom Vue component needs no frontend code of its own. A module that ships a frontend layer is built into that one app, so adding one means rebuilding it.
2. **The backend stays the source of truth.** Components receive the URLs they fetch from and submit to. The data and the permissions live with the backend code that defines the page.
3. **Pages are plain values.** A page is a class, its components are static fields, and modules add pages. You factor and reuse them like any TypeScript value.

## Two processes

At runtime, the DMS runs as two processes.

**The backend is your project.** It loads the DMS runtime (`@antelopejs/dms`) next to your own modules. Your pages and routes import DMS contracts from `@antelopejs/interface-dms/<subpath>`, for example `@antelopejs/interface-dms/page`. Do not import them from the runtime package's old `interfaces/*` paths.

**The frontend is shared.** `@antelopejs/dms-frontend` is a generic Inertia and Vue loader. Every DMS project runs the same one, and none of it lives in your repository. At startup, it asks the backend for its Vue frontend modules: the built-in dashboard layer and every module registered with `AddFrontendModule`. Then one catch-all route renders the component tree that the backend returns for each page.

Because of that startup call, the backend starts first, and the frontend starts once the backend answers. A standard page needs no per-page Vue file. Your project can still include a [frontend layer](/docs/building/frontend-layer) for custom components, translations, or branding, as the demo template does.

Commands, ports, and how `ajs dms` discovers the backend are operational details, covered in [Project setup](/docs/building/project-setup#running) and the [Frontend CLI reference](/docs/frontend/cli/overview).

## How a page reaches the screen

A single request flows from your backend page class through the frontend renderer and back to a controller route:

```text [Request flow]
@RegisterPage class            (your backend code)
  static form = Form({...})     ── builder produces a serializable component description
        │
        ▼
RegisterPage decorator          ── records the page in the page registry at import time
        │
        ▼
GET /dms/pages<page>/pagelayout ── frontend fetches the page's component tree from the backend
        │
        ▼
catch-all route                 ── the built-in dashboard layer recursively renders the tree
                                   with the component vocabulary
        │
        ▼
component fetches its data      ── Form/TableView/Chart call their fetchUrl / submitUrl …
        │                          (routes declared on the page class or in src/routes/)
        ▼
controller route handler        ── returns JSON; auth enforced by the route's decorators
```

The builder output is data, not a live component. `Form({...})` renders nothing. It returns a description that the frontend knows how to draw. That is why a backend edit changes the UI, and why you rarely touch Vue.

## How it sits on AntelopeJS

The DMS does not replace AntelopeJS. It is built on it:

- The DMS and every module are **AntelopeJS modules** loaded by the core.
- Everything the DMS exposes, and everything a module exposes, is an **AntelopeJS interface** consumed as a package subpath.

A question about interfaces, the CLI, or module wiring in general belongs to the AntelopeJS documentation. A question about pages, components, data types, auth, or the DMS services belongs here.
