# DMS Base Documentation

## Overview

The `dms-base` interface is the component vocabulary of the DMS: forms, tables, charts and cards, layout containers, trees, the data types behind every field, and the shared prop types they all draw from.

Every component here is a builder. `Form({...})`, `TableView(controller, {...})` and `ChartLine({...})` do not render anything — they return a `ComponentBuilder` from the `dms` interface, which is a serializable description of a component: its name, its options, and its children. You assign that description to a static field of a page class, and the frontend reads the page's tree and draws it. The options you set are therefore data, and the components that need data are given a `fetchUrl` and a `submitUrl` pointing back at routes you declare on the same page or on a data controller.

Two consequences shape the whole interface. First, a component's contract is its props interface: what you can express is exactly what the props allow, which is why this reference documents them field by field. Second, anything the frontend must receive has to survive serialization, so a builder that accepts a nested `Component` — a modal target, a kanban card, a chart inside a card — stores its serialized form instead.

The DMS documentation carries task-shaped chapters on the same components, organised around what you are building. This folder is the contract behind them: the exact symbol names, option fields and return types.

## Key Features

- **Builders that produce data** — Every component function returns a `ComponentBuilder`, so a page's UI is a plain value you can factor, reuse and compose with `.child()`.
- **Forms from typed fields** — A field names a `DataType`, and the type supplies both the input component and the Zod schema; `Form` compiles the field list into one schema and ships its JSON Schema form with the component.
- **Tables from data controllers** — `TableView` reads a controller's data-api metadata and its `@Column` declarations to build the columns, the `new` / `edit` / `view` forms, and the permission-carrying actions in one call.
- **Server-enforced row rules and guards** — Row-action rules are a small algebra evaluated on both sides, and guards run inside the mutating routes, so what the row menu offers is what the server accepts.
- **A chart and widget set with a shared period scope** — Twelve chart types plus KPI, chart and top-list cards; one `PeriodSelector` id ties them to the same range and comparison.
- **Layout without a frontend build** — Grids, stacks, tabs and page layouts arrange components, and `CustomComponent` names a Vue component when the vocabulary runs out.
- **An extensible data-type registry** — `@RegisterDataType` and `@RegisterDataCompareMode` add your own types and filter operators to the catalogue the forms, columns and filters draw from.
- **Shared prop vocabulary** — Colours, sizes, HTTP methods, action targets, readonly behaviour and watch actions are declared once in `types` and reused by every component.

## Dependencies

This interface relies on the following AntelopeJS packages:

- [@antelopejs/interface-api](https://github.com/AntelopeJS/interface-api) - Request context, controller metadata and route parameters.
- [@antelopejs/interface-api-util](https://github.com/AntelopeJS/interface-api-util) - `assert` for failing a route with an HTTP status.
- [@antelopejs/interface-core](https://github.com/AntelopeJS/interface-core) - Metadata storage, decorator factories, interface functions and logging.
- [@antelopejs/interface-data-api](https://github.com/AntelopeJS/interface-data-api) - Data controllers, default routes, list parameters and field metadata.
- [@antelopejs/interface-database](https://github.com/AntelopeJS/interface-database) - The value proxies compare modes build their filters from.
- [@antelopejs/interface-database-decorators](https://github.com/AntelopeJS/interface-database-decorators) - Models and the localization modifier.
- [@antelopejs/interface-file-storage](https://github.com/AntelopeJS/interface-file-storage) - Upload constraints, staged-key promotion and file deletion behind the file and image types.
- [zod](https://www.npmjs.com/package/zod) and [zod-to-json-schema](https://www.npmjs.com/package/zod-to-json-schema) - Field validation schemas and their JSON Schema form.

It also builds on sibling interfaces of the same package: `dms/component` for `Component` and `ComponentBuilder`, `dms/page` for the page a component is registered on, `dms/permissions` for the action permissions a table view declares, and `dms-auth` for the authenticated user its routes receive.

## Quick Start

A page declaring one component. The `Form` builder describes the fields; the two routes on the same class serve and accept the values. Define the backing model first; `SettingsModel` is application code, not a DMS export.

```typescript [db.ts]
import {
  BasicDataModel,
  Field,
  RegisterTable,
  Table,
} from "@antelopejs/interface-database-decorators";

export const SETTINGS_SCHEMA = "example_settings";
export const SETTINGS_ROW_ID = "module";

@RegisterTable("settings", SETTINGS_SCHEMA)
export class Settings extends Table {
  @Field("string") declare _id: string;
  @Field("boolean") declare enabled: boolean;
  @Field("number") declare retentionDays: number;
}

export class SettingsModel extends BasicDataModel(Settings, "settings") {}
```

The page edits one module-wide record, so restrict it to platform owners. It returns defaults before the first save and upserts only `SETTINGS_ROW_ID`, rather than updating every row in the table.

```typescript [settings-page.ts]
import { Get, JSONBody, Post } from "@antelopejs/interface-api";
import { assert } from "@antelopejs/interface-api-util";
import { GetModel } from "@antelopejs/interface-database-decorators";
import {
  PageController,
  pagesCategory,
  RegisterPage,
} from "@antelopejs/interface-dms/page";
import { DefaultDataTypes } from "@antelopejs/interface-dms/base/data-types";
import { Form, formSchema } from "@antelopejs/interface-dms/base/form";
import { DefaultLayout } from "@antelopejs/interface-dms/base/layouts";
import { HttpMethod } from "@antelopejs/interface-dms/base/types";
import { AuthOwnerOnly } from "@antelopejs/interface-dms/auth";
import { SettingsModel, SETTINGS_ROW_ID } from "./db";

@RegisterPage()
@AuthOwnerOnly()
export class SettingsPage extends PageController(
  "settings",
  {
    urlSlug: "settings",
    displayName: "Settings",
    description: "Module configuration",
    icon: "i-ph-gear",
    category: pagesCategory,
  },
  DefaultLayout(),
) {
  static form = Form({
    title: "Settings",
    fetchUrl: "/settings/",
    submitUrl: "/settings/",
    submitUrlMethod: HttpMethod.post,
    fields: [
      {
        id: "enabled",
        label: "Enabled",
        type: new DefaultDataTypes.BooleanType(),
      },
      {
        id: "retentionDays",
        label: "Retention (days)",
        type: new DefaultDataTypes.NumberType({ min: 0 }),
        required: true,
      },
    ],
  });

  settingsModel = GetModel(SettingsModel);

  @Get("/")
  async read() {
    return await this.settingsModel.get(SETTINGS_ROW_ID)
      ?? { enabled: false, retentionDays: 0 };
  }

  @Post("/")
  async write(@JSONBody() body: unknown) {
    const result = formSchema(SettingsPage.form).safeParse(body);
    assert(result.success, 400, "Invalid settings");
    await this.settingsModel.table.insert({
      _id: SETTINGS_ROW_ID,
      enabled: result.data.enabled ?? false,
      retentionDays: result.data.retentionDays,
    }, { conflict: "update" });
  }
}
```

Import the page and provision the schema from your module's entry file. Merge this into an existing `start()` if your module already has one:

```typescript [index.ts]
import "./settings-page";
import { RegisterSchema } from "@antelopejs/interface-database-decorators";
import { SETTINGS_SCHEMA } from "./db";

export async function start(): Promise<void> {
  await RegisterSchema(SETTINGS_SCHEMA);
}
```

The page registers itself at import time, and its routes are mounted under the page's slug — which is why the form fetches from and submits to `/settings/`. `Form` serializes the field descriptions and JSON Schema for the frontend; the custom write route must still validate the request on the server, as the `formSchema` call does here. For per-tenant settings, use a tenant-scoped schema and model instead of this module-wide record.
