These composables tell a layer's Vue where it sits in the dashboard: the navigation tree, the current module, and whether the viewer owns the tenant. Others keep per-user preferences. The ones that hold state keep it in shared state, so every component sees the same values, server render included.

## Layout and module context

The dashboard loads its navigation and module map into shared state. These composables expose that state and derive the current position from the route.

### `useSiteLayout()`

`useSiteLayout` returns the dashboard's loaded structure as shared refs. Layer code reads them, most often `modules`, `isOwner` and `quickActions`:

| Ref | Type | Holds |
| --- | --- | --- |
| `siteLayout` | `SiteLayout \| undefined` | Pages by slug, categories by full id. |
| `siteLayoutTree` | `SiteLayoutTree \| undefined` | The nested navigation tree, with children and order. |
| `quickActions` | `QuickActionsPayload \| undefined` | `{ categories, actions }` for the command palette. |
| `modules` | `Record<string, ModuleInfo & { hasAccess: boolean }> \| undefined` | Every registered module, by id. |
| `isOwner` | `boolean` | The viewer owns the current tenant. |
| `pageLayouts` | `Record<string, PageLayout>` | The component layout of each page, by slug. |
| `isLoading` | `boolean` | A load is in flight. |
| `loadingError` | `string \| null` | The last load's error message. |

`siteLayout.categories` lists every category once, by `fullId`. A page or a category names its category by `categoryId`. A category declared with `urlSlug: "/"` adds no URL segment. It is a section heading, marked `urlTransparent`, and no URL resolves to it. The menu carries no counted badges. Each page visit brings them (`navBadges`), and the navigation draws them.

```ts fragment [app/components/MyWidget.vue]
const { modules, isOwner, quickActions } = useSiteLayout();
const myModule = computed(() => modules.value?.["my-module"]);
```

The composable also returns loader and route-matching methods: `loadSiteLayout`, `loadPageLayout`, `refresh`, `resync`, `refreshIfStale`, `findMatchingRoute`, `findMatchingRouteOrCategory` and the development-only `probeAndCommitRoute`. The page renderer, the middleware and the development reload plugin call them. Layer code reads the refs and leaves the methods alone.

A page the backend describes brings the site layout with its props. A custom page, which only a frontend layer knows, does not. On such a page the dashboard frame loads the layout with the page through `useRenderedSiteLayout()`, so the server renders the menu there too.

### `useCurrentModule()`

`useCurrentModule()` returns `ComputedRef<{ id, info } | null>`, the module that owns the current route. It takes the id from a `/modules/<id>/...` path and looks it up in `modules`. `info` is the module's `ModuleInfo & { hasAccess }` entry. It is `null` outside a module page, and for an id `modules` does not hold.

```ts fragment
const current = useCurrentModule();
```

### `useIsOwner()`

`useIsOwner()` returns `ComputedRef<boolean>`, `true` only when the viewer owns the tenant. It reads `useSiteLayout().isOwner`. Use it to show owner-only UI. See [Auth and permissions](/docs/auth-and-tenancy/auth-and-permissions).

### `useModulesListing()`

`useModulesListing()` returns `{ modules, isLoading, loadingError, loadModulesListing, refresh }`, the module catalog of the **Modules** page. It is a `useApiData` read of `/dms/modules-listing`, made only for a platform owner. A server render shows it and hands it to the browser.

- `modules` is a `ModuleCatalogEntry[]`, `undefined` until loaded. Each entry is a module's info with its `landingSlug`, and the `status` and `readout` lines its catalog hooks reported.
- `loadModulesListing()` waits for the read.
- `refresh()` reads again and keeps the current list on screen meanwhile.
- `loadingError` is a `ModulesListingError`, `{ kind: "forbidden" | "failed", status? }`. `forbidden` means the server answered `403`. `failed` covers every other failure, with the HTTP status when the server answered. `modules` is then `undefined`. Nothing is thrown.

### `useModuleHistory()`

`useModuleHistory()` returns `{ record(moduleId, path), getLast(moduleId), entries }`. It remembers the last path visited inside each module, for the **Modules** page's recently used order and the command palette's recent modules group. It never decides where entering a module lands. A module tile, a breadcrumb, a recent module in the command palette and the module's own address all open its landing page.

The history is kept in the `dms-module-history` cookie for a year, with the twelve most recent modules, so the server renders the same order as the browser. `getLast` returns the stored path or `null`. `entries` is a computed list of `ModuleHistoryEntry`, `{ moduleId, path, visitedAt }`, from the oldest visit to the newest. `visitedAt` is the last visit in epoch milliseconds, `0` when unknown. Recording a known module moves it to the end.

```ts fragment
const history = useModuleHistory();
history.record("crm", "/modules/crm/contacts/42");
const back = history.getLast("crm");
const recent = history.entries.value;
```

### `useQuickActions()`

`useQuickActions()` returns `{ categoryGroups }`, a `ComputedRef<QuickActionCategoryGroup[]>` of the current user's quick actions from `useSiteLayout().quickActions`. The actions are grouped by category, and both levels are sorted by `order`. The server sends only actions the user can run, so there is no access flag to filter on. The header popover and the command palette both read it, and so should your code, instead of grouping the raw payload again.

The same file exports `dispatchQuickActionTarget(target)`, which runs a quick action in the browser. `navigate`, `openForm` and `button` route to the action's page. `openForm` and `button` carry the intent in the query, and the table view reads it when it mounts to open its creation form or press the named custom button. `event` dispatches a window `CustomEvent` in place.

```ts fragment
const { categoryGroups } = useQuickActions();
dispatchQuickActionTarget(action.target);
```

### `usePageRecordLabel()`

`usePageRecordLabel()` returns `{ label, setLabel }`, the label of the record a page is about. The page header ends its breadcrumb with it ("Tasks › Fix the login page"). A [`Form`](/docs/components/forms) with `labelKey` sets it once it loads its record. A module's own component on a record page sets it the same way, and any component may read it.

```ts fragment [app/components/RouteHeader.vue]
const route = useDmsRoute();
const { label, setLabel } = usePageRecordLabel();

watch(openedRoute, (name) => setLabel(route.path, name), { immediate: true });
```

| Member | Type | Contract |
| --- | --- | --- |
| `label` | `ComputedRef<string \| undefined>` | The label set for the page on screen, `undefined` when none was set. |
| `setLabel` | `(path: string, value: string \| undefined) => void` | Names the record of the page at `path` (`useDmsRoute().path` for the current page). `undefined` or `""` clears it. |

The label is stored with the path it was set for, so it never outlives its page. On another page, `label` reads `undefined` until that page sets one. A page has one label, and the last component to set it wins.

### `usePageToolbarSize()`

`usePageToolbarSize()` returns `{ size, heightClass }` for the [`PageToolbar`](/docs/components/layout-and-containers/page-toolbar) a component sits in. A leading block of a module's own, such as a scope chip or a picker, uses it to stand as tall as the live toggle and the period beside it.

```vue [app/components/ScopeChip.vue]
<script setup lang="ts">
const { heightClass } = usePageToolbarSize();
</script>

<template>
  <span class="inline-flex items-center rounded-md border px-2" :class="heightClass">
    All sites
  </span>
</template>
```

| Member | Type | Contract |
| --- | --- | --- |
| `size` | `ComputedRef<"xs" \| "sm" \| "md">` | The toolbar's `size`. `sm` outside a toolbar. |
| `heightClass` | `ComputedRef<string>` | The height of every control of the toolbar at that size: `h-6`, `h-7` or `h-8`. |

## Waiting for a backend change

### `useDevReload()`

A module that writes to the backend, such as a no-code builder that creates a page or an AI chatbox that edits one, makes the backend module reload in development. The module registers its pages again one at a time, so for a moment the site layout may not serve the page the user is on, or the one you are about to open. The core handles it. It reads the layout again, commits it only once the route resolves in it, and holds back the 404 the renderer would raise. The current page stays mounted, and the new layout applies in place.

`useDevReload()` gives access to that mechanism. Do not poll the site layout yourself, because a second loop races the core's and reads the layout for nothing.

```ts fragment
const { awaitRoute } = useDevReload();

await createPage(path);
await awaitRoute(path);
await navigateDms(path);
```

| Member | Type | Contract |
| --- | --- | --- |
| `reloading` | `Readonly<Ref<boolean>>` | A reload is in flight. It is internal state. Never render it or gate UI on it, because a reload must stay invisible. |
| `settled()` | `() => Promise<void>` | Resolves once no refresh is in flight. Await it before you read layout state that must be current. |
| `awaitRoute(path, options?)` | `(string, { timeoutMs?: number }) => Promise<boolean>` | Resolves `true` once the committed site layout serves `path`, `false` on timeout. `timeoutMs` defaults to `15000`. |

`awaitRoute` returns at once when the layout already serves `path`. Otherwise it joins the refresh the core is running, and starts one only if none is running. However many modules ask at once, one loop reads the layout.

`false` is a timeout, not an error. The page may still arrive a moment later. If navigating anyway is the right fallback, do it, and the renderer resolves the route again once the layout arrives.

The reload signal exists only in development. It travels on the browser's realtime connection once the user is signed in, and on a reload stream that signed-out tabs share. In production, `awaitRoute` never reads the layout. It resolves `true` when the route is known, and otherwise watches the committed layout for up to 2 seconds before it answers. The same call works in both builds.

## Page setup functions (`setupId`)

A backend page can name a setup function in its `setupId` option ([Pages and components](/docs/building/pages-and-components#page-setup-and-validation)). The renderer looks the id up in the function registry and runs the function when the page mounts. Your layer registers the function once, from a plugin:

```ts fragment [app/plugins/page-setups.client.ts]
export default defineDmsPlugin(() => {
  const { registerFunction } = useDefinedFunctions();

  registerFunction("app.pages.DashboardSetup", (context: PageSetupContext) => {
    const off = context.on("form", FormEvents.FIELD_CHANGE, (data) => {
      context.emit("chart", "app.chart.Highlight", data);
    });
    return () => off();
  });
});
```

`PageSetupContext` carries `pageInfo`, the resolved page, `permissions`, the viewer's set, and `on` and `emit`, a page-scoped view of the [component events](/docs/extending-the-dashboard/component-events). `on` returns an unsubscribe function. The setup function may return a cleanup callback, or a promise of one, which the renderer calls when the page unmounts.

Use a setup function when a page needs components to work together but no custom rendering. The page stays fully described by the backend.

### `siblingComponentId(componentId, key)`, the block next to yours

A custom block that follows another block of its page, such as a live preview of the form beside it, needs that block's component id, the one its [component events](/docs/extending-the-dashboard/component-events) carry. `siblingComponentId` returns the id of the block `key` declared under the same parent as the block `componentId`. It works for top-level blocks and for blocks inside a `Grid` or a `GridRow`.

```ts fragment [a preview beside a form]
const props = defineProps<{ componentId: string }>();
const formId = siblingComponentId(props.componentId, "form");

function onFieldChange(event: Event) {
  if (!(event instanceof CustomEvent)) return;
  const { component, data } = event.detail ?? {};
  if (component !== formId) return;
  // data.formValues holds the form's values as typed
}
onMounted(() => window.addEventListener(FormEvents.FIELD_CHANGE, onFieldChange));
onBeforeUnmount(() =>
  window.removeEventListener(FormEvents.FIELD_CHANGE, onFieldChange),
);
```

Call it instead of building the id yourself. The renderer owns the format of a nested block's id.

## User preferences

The composables in this section keep per-user settings in cookies, so they survive reloads and the server render reads them. `useUserRegionalPreferences` is the exception, because it reads the user's record.

### `usePreferences()`

`usePreferences` is a key and value store in the `dms-preferences` cookie, kept a year, addressed by dotted paths. It returns:

| Member | Purpose |
| --- | --- |
| `preferences` | A read-only snapshot of the whole tree. |
| `getPreference(keyPath, default?)` | Reads a nested value, or `default`. |
| `setPreference(keyPath, value)` | Writes a value and creates the objects on its path. |
| `updatePreference(keyPath, partial)` | Merges `partial` into an object value, one level deep. |
| `removePreference(keyPath)` | Deletes a key. |
| `clearAllPreferences()` | Resets the tree to `{}` and drops the table views' browser-only state. |

```ts fragment
const { getPreference, setPreference } = usePreferences();
setPreference("my-module.listSort", { field: "name", desc: false });
const sort = getPreference("my-module.listSort", {
  field: "createdAt",
  desc: true,
});
```

The tree is stored as base64url JSON, so the server render reads the same preferences as the browser. The browser sends the cookie with every request, so its size is capped at `MAX_PREFERENCES_COOKIE_BYTES`, 3 KB for name and value together. Past the cap, the table view states written least recently (the entries under `tables`) are dropped until the tree fits, then the remembered periods (`periods`). A write that still does not fit is refused, with a warning in development, and the stored preferences stay as they were. Nothing outside `tables` and `periods` is ever dropped. Keep a module's own preferences small and under a key of its own. Bulky state that a server render does not need belongs in `localStorage`.

A table view keeps its state in two places:

- The cookie holds what the server render needs to list and draw the right rows: the sort, the column filters, the page and page size, the active tab, the display, the open view and the hidden columns. Each table has one entry, `tables.<id>`, where `<id>` is an 8-character hash of the component id and the page id. A value equal to the table's default is not written, and the values are compact (a sort is `"-name"`, a hidden column `"-email"`). A sorted table costs about 35 bytes, and a sorted, filtered, paged table with two hidden columns about 110, so the cookie holds more than 20 tables.
- `localStorage` (`dms-table-preferences:v1:<id>`) holds what only the browser draws: the column order and widths, the density, whether the filters row is open, the kanban and grouped group-by, and the user's saved views. The server and the hydrating browser render the defaults, and the stored values apply once the table is mounted.

These entries are internal. Read and write a table's state through the table view, not through `tables.*` paths.

### `useInterfaceScale()`

`useInterfaceScale()` returns the UI density as a writable cookie ref, `Ref<InterfaceScale>`. The cookie is `dms-interface-scale`, the values are `"small" | "normal" | "large"`, and the default is `"normal"`. Assign `.value` to change it.

### `useColorModePreference()`

`useColorModePreference()` returns the color mode as a writable cookie ref, `Ref<ColorModePreference>`. The cookie is `dms-color-mode`, the values are `"light" | "dark" | "system"`, and the default is `"system"`. Assign `.value` to change it. Nuxt UI's color-mode components follow it, and a change made through them updates the cookie.

### `useAccessibilityPreferences()`

`useAccessibilityPreferences()` returns `{ preferences, reduceMotion, increaseContrast, underlineLinks }`, the accessibility options of the **Appearance** page, from the `dms-accessibility` cookie, kept a year. `preferences` is the complete object, read-only. The other three are writable refs:

- `reduceMotion` is `"auto" | "on" | "off"`, default `"auto"`, which follows `prefers-reduced-motion`.
- `increaseContrast` and `underlineLinks` are booleans, default `false`.

Assigning one rewrites the cookie and updates the classes on `<html>` ([Theming](/docs/extending-the-dashboard/theming-and-branding#accessibility)).

To decide whether to play JavaScript-driven motion, call `isReducedMotionActive()` instead of resolving `reduceMotion` yourself. It returns `true` when the device setting is On, or when it is Automatic and the system asks for reduced motion.

### `useUserRegionalPreferences()`

`useUserRegionalPreferences()` returns `{ preferences, detectedTimeZone, timeZone, weekStartsOn, timeFormat }`, the signed-in user's choices from **Settings › Language & region**. They are stored on the user, so they follow the user to every device.

- `preferences` holds what the user chose: `timeZone`, `weekStart`, `timeFormat` and `dateFormat`. An unset field is automatic.
- `detectedTimeZone` is the browser's zone.
- `timeZone`, `weekStartsOn` (0 is Sunday, 6 is Saturday) and `timeFormat` (`"h23" | "h12"`) are computed refs with the automatic values resolved: the browser's zone, and the language's first day and clock.

The shared date formatters already apply them ([Localization](/docs/building/localization#dates-and-times)). Read them for a component of your own, such as a calendar. `weekStartsOn` is a `number`, and `UCalendar` takes `0` to `6`, so the example looks the value up in a list of the seven days:

```vue
<script setup lang="ts">
import { useUserRegionalPreferences } from "#dms-core/app/composables/user/useUserRegionalPreferences";

const WEEK_DAYS = [0, 1, 2, 3, 4, 5, 6] as const;

const { weekStartsOn } = useUserRegionalPreferences();
const weekStart = computed(() => WEEK_DAYS[weekStartsOn.value] ?? 0);
</script>

<template>
  <UCalendar :week-starts-on="weekStart" />
</template>
```

### `useRegionalFormat()`

`useRegionalFormat(options?)` returns the shared formatters, bound to the interface language and the user's **Language & region** preferences (time zone, clock, date format). Each call reads the current language, so a value formatted in a `computed` follows a language switch.

| Member | Returns |
| --- | --- |
| `locale` | The interface language, such as `en` or `fr`. |
| `formatLocale` | The locale the DMS's texts are written in for that language: `en-GB` for `en`, `fr-FR` for `fr`. |
| `dateTimeFormat(options, settings?)` | An `Intl.DateTimeFormat` for a format the helpers do not cover. Pass `{ keepLocalZone: true }` as `settings` for a calendar day computed in the browser. |
| `formatDate`, `formatTime`, `formatDateTime` | The date, the time, or both, or `null` when the value is not a date. |
| `formatRelativeTime(date)` | "just now", "5 minutes ago", "yesterday at 14:05", then the date. |
| `formatNumber`, `formatPrice`, `formatPercentage` | A `string` for a `number`, and any other value as it is. `formatPrice` writes euros unless `options.currency` says otherwise. |

The formatters write in `locale` by default, as the DMS's own blocks do. A module whose screens follow the conventions of the DMS's texts (`en-GB` is a 24-hour clock with the day before the month) passes `{ locale: "format" }`, and every value, `dateTimeFormat` included, is written in `formatLocale`. Outside a component, `regionalFormatLocale(locale)` from `#dms-core/app/utils/regional` gives the same locale.

```vue
<script setup lang="ts">
interface OrderRow {
  createdAt: string;
  total: number;
}

const props = defineProps<{ row: OrderRow }>();
const { formatDateTime, formatPrice } = useRegionalFormat();
</script>

<template>
  <span>{{ formatDateTime(props.row.createdAt) }} · {{ formatPrice(props.row.total) }}</span>
</template>
```

### `useFavoritePages()`

`useFavoritePages` keeps the user's pinned pages in the `dms-favorite-pages` cookie and in shared state. A `FavoritePage` has the page's `id`, `path`, `title` and an optional `icon`. It returns:

| Member | Purpose |
| --- | --- |
| `favorites`, `sortedFavorites` | The list, and the list sorted by title. |
| `isFavorite(path)` | Whether the path is pinned. |
| `toggleFavorite(page)` | Pins or unpins the page and returns the new state. |
| `addFavorite(page)`, `removeFavorite(path)` | Pins or unpins explicitly. |
| `clearFavorites()` | Unpins every page. |
| `cleanupInvalidFavorites(isValidPath)` | Drops the entries whose path fails the predicate. |

```ts fragment
const { isFavorite, toggleFavorite } = useFavoritePages();
toggleFavorite({ id: "p1", path: route.path, title: "Contacts", icon: "i-ph-users" });
```

## App config and system

### `useHomepage()`

`useHomepage()` returns the dashboard's home path from the `homepage` config key ([Configuration](/docs/building/configuration)), or `"/"`. Use it for links back home instead of writing `/`.

### `useFirstAccessiblePagePath()`

`useFirstAccessiblePagePath()` returns the path of the first page the current user can access, in sidebar order, or `undefined` when the site layout is not loaded or no page is accessible. It looks inside categories the user cannot access, since they may hold pages the user can, but returns only navigable, visible pages the user can access. `settings` pages come last, and module pages are never returned, because modules have their own routing. The page renderer uses it to redirect a user whose role cannot access the configured homepage. `firstAccessiblePagePath(tree)` takes the layout tree directly, for code after an `await` where a composable cannot run.

### `useSystemState()`

`useSystemState()` returns the instance's system state, read with the page so the server render has it:

- `systemState` holds the `has_onboarded` flag and the dashboard `meta` (`title`, `description`) from the backend config.
- `metaTitle` and `metaDescription` are computed values for a page's `<head>`.
- `error` is the read's error, and `refresh()` reads again after a state change.
