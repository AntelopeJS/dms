# UI toolkit

Beyond the composables that talk to the backend, the base layers ship the building blocks your custom Vue assembles screens with. Using them keeps your screens visually and behaviorally consistent with the rest of the dashboard.

For the rendered results, see [row drawers](/docs/components/tables/row-drawers), [confirmation dialogs](/docs/components/tables/confirmations), and [form feedback](/docs/components/forms). This page explains how to open those same surfaces from your own Vue code.

## Programmatic containers — `useModal` / `useDrawer`

`useModal().open(options)` and `useDrawer().open(options)` mount a component inside a themed container and hand you a promise for its outcome. Use them when a flow needs a dialog you control from code — pick-a-record, a mini wizard, a confirmation with a form inside.

```ts
const modal = useModal();

const instance = modal.open({
  title: "Pick a template",
  description: "The report will be generated from it",
  component: MyTemplatePicker, // any component
  componentOptions: { category: "reports" }, // passed as props
});

const picked = await instance.result; // settles when the container closes
```

Both take the same `ContainerOptions`:

| Option                                         | Purpose                                                 |
| ---------------------------------------------- | ------------------------------------------------------- |
| `title` / `description?`                       | Header text.                                            |
| `component` / `componentOptions?`              | The body component and its props.                       |
| `headerComponent?` / `headerComponentOptions?` | Replace the default header.                             |
| `containerId?`                                 | Container identity; generated when omitted.             |
| `size?`                                        | `useModal` — `sm` … `5xl`, `full`. `useDrawer` — the width a `left` / `right` drawer opens at (a modal's width at that size; 600px without one). |
| `direction?`                                   | `useDrawer` only — `top` / `bottom` / `left` / `right`. |
| `sizeKey?`                                     | `useDrawer` only — the key the size the user gives the drawer is remembered under; `containerId` by default, else the body component's name (`name`, or a `<script setup>` component's file name). |
| `rowHeader?`                                   | `useDrawer` only — `{ title?, positionLabel?, navigation? }`: the DMS's row header in place of the title, as on a row action's drawer ([below](#a-drawer-on-a-row-of-your-own)). |

The returned `ContainerInstance` exposes `result`, which settles with the value the body component emits on `success` (or whatever you pass to `close(value)`), `close()`, which dismisses the container programmatically, and `patch(changes)`, which changes the open container in place: its `title` / `description`, its body's `componentOptions` and `componentKey` (a new key mounts the body anew), and on a drawer its `rowHeader`.

### A drawer on a row of your own

A module that opens a drawer on a row of a list it draws itself (a data browser, a key editor) gets the same header as a [row action's drawer](/docs/components/tables/row-drawers#detail-drawers) with `rowHeader`, without importing the layer's header component: the row's title, its position ("Key 4 of 12") and previous / next buttons next to the close button. **J** and **K** call the same steps while the drawer is open — do not bind them yourself. As the drawer steps, `patch` it with the new row: its `componentOptions` (and a `componentKey` to mount the body anew) and its `rowHeader`, which replaces the previous one.

| `rowHeader` field | Purpose |
| ----------------- | ------- |
| `title?`          | The row's title; the drawer's `title` without one. A long title wraps onto two lines. |
| `positionLabel?`  | An i18n key receiving `{index}` (from 1) and `{total}`, both grouped as the locale does; "4 of 12" without one. |
| `navigation?`     | A [`RowNavigation`](/docs/components/tables/row-drawers#the-components-props) — `{ index, total, hasPrev, hasNext, prev(), next() }`: the position, the buttons and J / K. No position nor buttons without one. |

```ts
const { open } = useDrawer();

function openKey(index: number) {
  const navigationAt = (at: number): RowNavigation => ({
    index: at,
    total: keys.value.length,
    hasPrev: at > 0,
    hasNext: at < keys.value.length - 1,
    prev: () => show(at - 1),
    next: () => show(at + 1),
  });
  const drawer = open({
    title: "Key",
    component: KeyEditor,
    componentOptions: { keyId: keys.value[index].id },
    rowHeader: { title: keys.value[index].path, positionLabel: "$lang.keys.position", navigation: navigationAt(index) },
  });
  function show(at: number) {
    drawer.patch({
      componentOptions: { keyId: keys.value[at].id },
      componentKey: keys.value[at].id,
      rowHeader: { title: keys.value[at].path, positionLabel: "$lang.keys.position", navigation: navigationAt(at) },
    });
  }
}
```

Every drawer is resizable from `lg`: a handle on its inner edge sets the width of a `left` / `right` drawer, the height of a `top` / `bottom` one. Drag it, or focus it and use the arrow keys (Home and End for the bounds); a double-click gives the drawer its default size back. A side drawer stays between 360px and 90% of the window, an edge drawer below 90% of its height (it keeps its natural height until resized). The size is remembered on the device (a cookie) per `sizeKey`, so the same drawer opens again at the size it was left at. Without one, the key is its `containerId`, else its component's name: a module's drawer keeps its size without passing anything. Pass `sizeKey` when one component opens drawers that should not share a size, when the `containerId` changes at every opening, or when the component is anonymous (a render function, a `defineAsyncComponent` wrapper), which otherwise forgets. Widths and heights are kept apart, so a side and a bottom drawer may share a key. From `lg` the handle replaces the drawer's own grip; below `lg` drawers keep their phone layout, grip included, and have no handle.

When a drawer or a modal closes, the page takes clicks again at once (the body's `pointer-events` is given back as the close starts, not once the panel is gone), its backdrop stops catching them and fades out in 100ms (immediately with reduced motion), while the panel still slides or scales out and focus returns to where it was: the user can click the next row or button straight away.

::note
These are the same containers a `TableView` ([Tables](/docs/components/tables)) opens for its `drawer` / `modal` form modes and that an [`ActionTarget`](/docs/building/actions-and-reactivity#action-targets) of type `drawer` / `modal` resolves to — one look everywhere.
::

## Confirmation — `useConfirm`

`useConfirm().confirm(options)` opens the standard confirm dialog and resolves to a boolean; dismissing the dialog counts as `false`.

```ts
const { confirm } = useConfirm();

async function remove() {
  const ok = await confirm({
    title: "Delete this report?",
    description: "This cannot be undone.",
    color: "error",
  });
  if (!ok) return;
  // proceed
}
```

`ConfirmOptions` is the backend `ConfirmDialog` with its texts resolved — `title`, `description?`, `confirmLabel?` / `cancelLabel?`, `color?`, `icon?`, `impact?`, `secondaryAction?` (`{ label, icon?, run }`: a button next to cancel and confirm, `run` awaited with the dialog left open, a rejection shown in its alert), `blocked?` (acknowledge only), `confirmText?` (type-to-confirm; `confirmTextCaseInsensitive: true` compares it ignoring case), `fields?` (filled in before confirming), `component?` — plus what only the browser gives: `body` (a render function), `validate`, `initialFocus` and `onConfirm(values)`, which runs the action from inside the dialog with the fields' values: a rejection stays on screen, under its field when the server names one.

### A dialog the server words — `useConfirmFrom`

A declarative action's `confirm: { from: url }` reads its dialog from a route ([Dialogs the server words](/docs/components/tables/confirmations#dialogs-the-server-words-from)). Code of your own asks the same dialog with `useConfirmFrom().confirmFrom(url, options?)`: the URL's `{{row.X}}` tokens are filled in with `params`, read with the user's session, its texts resolved with `params` and the dialog's own, then the standard dialog shown. It resolves like `confirm` — never `true` for a `blocked` dialog — and a failed read is an error toast resolving `false`.

```ts
const { confirmFrom } = useConfirmFrom();

async function remove(campaign: Campaign) {
  const ok = await confirmFrom("/api/campaigns/{{row.id}}/delete-confirm", {
    params: { id: campaign.id, name: campaign.name },
    fallback: { color: "error", icon: "i-ph-trash" },
    onConfirm: async (values) => {
      await $authFetch(`/api/campaigns/${campaign.id}`, { method: "DELETE", body: values });
    },
  });
  if (ok) refresh();
}
```

`ConfirmFromOptions`: `params?` (the URL's `{{row.X}}` tokens and the texts' fill-ins), `fallback?` (what the dialog leaves out: a colour, an icon, a label) and `onConfirm?` (the action run from inside the dialog with its fields' values, as for `confirm`).

A specialized variant, `usePresenceEditWarning().warnBeforeEdit(editors)`, shows the "someone is already editing this" dialog from a realtime presence list and resolves the same way — a `TableView` uses it before opening an edit form on a row someone else holds.

## Error feedback — `useApiError`

`useApiError(error, options?)` turns a failed backend call into the standard error toast: it extracts the message from the response body and runs it through i18n, falling back to a generic message when the error carries none.

```ts
try {
  await $authFetch("/api/report/regenerate", { method: "POST" });
} catch (error) {
  useApiError(error);
}
```

Success toasts are plain Nuxt UI — `useToast().add({ title: "Saved" })` — nothing DMS-specific.

## Async export progress — `useExportJob`

`useExportJob().runJob(options)` drives a backend [export job](/docs/building/backend-services#the-export-job-engine) from the client: it starts the job, polls its status into a progress toast, downloads the artifact when complete, and offers a retry on failure.

```ts
const { runJob } = useExportJob();

await runJob({
  startUrl: "/api/report/export/start",
  startQuery: { from: "2026-01-01" },
});
```

`RunExportJobOptions`:

| Option                        | Purpose                                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `startUrl`                    | Route that starts the job.                                                                       |
| `startMethod?`                | `GET` or `POST`.                                                                                 |
| `startQuery?` / `startBody?`  | Parameters for the start request.                                                                |
| `statusUrl?` / `downloadUrl?` | Functions of the returned ticket; default to `<startBase>/status/:jobId` and `/download/:jobId`. |
| `fallbackFilename?`           | Function of the ticket returning a filename. The `Content-Disposition` filename wins when present; defaults to `export-<jobId>.<extension ?? "bin">`. |
| `labels?`                     | Relabel the progress toast.                                                                      |
| `retryable?`                  | Offer a retry on failure.                                                                        |

The `exportJob` [action target](/docs/building/actions-and-reactivity#action-targets) is the declarative wrapper over this same runner.

## Page header actions — `usePageHeaderActions`

A Vue component of a page puts its own actions in the page header, next to the buttons the page layout serves (`DefaultLayout({ headerActions })`, [Layout](/docs/interfaces/base/layout#header-actions)): an action that runs in the browser — an export built client-side, a status pill — rather than one the server can describe. `usePageHeaderActions(render, options?)` takes a render function and shows what it returns once the page has set up; the actions go away when the component unmounts. Call it before the first `await` of the setup, so the server renders them with the page and they never pop in. Outside a layout that draws a page header, the call does nothing.

```vue [app/components/TranslationMatrix.vue]
<script setup lang="ts">
import { UButton } from "#components";
import { usePageHeaderActions } from "#dms-layout/app/composables/layout/usePageHeaderActions";

const { t } = useI18n();

usePageHeaderActions(
  () => h(UButton, { label: t("lang.export"), icon: "i-ph-download-simple", color: "neutral", variant: "outline", onClick: exportCsv }),
  { order: -1 },
);
</script>
```

| Option  | Type     | Default | Description |
| ------- | -------- | ------- | ----------- |
| `order` | `number` | `0`     | Place among the served buttons, each of which has an `order` of its own (`0` by default). The header sorts them together, smallest first; at an equal order the served buttons come first. Without it the actions follow every served button, as `-1` puts them before every served button left at `0`. |

One component of the page sets the actions: a second call replaces the first. Render several buttons from the one render function when the page needs several.

## Record card — `DmsRecordCard`

The v2 card of one record (a skill, a plan, a feature), for a table view's `card.component` or any grid of records: an icon well, a mono title and subtitle, a badge, a description, then tags, a mono note and buttons on a ruled footer.

```vue [app/components/FeatureCard.vue]
<DmsRecordCard
  icon="i-ph-table"
  :title="row.name"
  :subtitle="row.owner"
  :badge="{ label: 'Beta', tone: 'warning' }"
  :description="row.summary"
  :tags="[row.area]"
  :meta="`${row.votes} votes`"
  :actions="[{ label: 'Edit', icon: 'i-ph-pencil-simple', onClick: edit }]"
  :selected="selected"
  interactive
  @open="open()"
/>
```

`interactive` makes the whole card open the record (`open` on a click or Enter); its buttons act without opening it. `selected` rings it, `muted` dims it. Slots: `default` (between the description and the footer), `aside` (instead of the badge) and `actions` (instead of the buttons).

## Required-fields legend — `DmsFormRequiredLegend`

The line a stock `Form` and a confirm dialog with fields print under a form holding a required field: a red asterisk, then "Required fields" in the reader's language (`dms.form.required_legend`). A custom form of a module prints it the same way, so its required fields read like the dashboard's.

```vue [app/components/CampaignForm.vue]
<form @submit.prevent="save">
  <!-- fields marked with the same asterisk -->
  <DmsFormRequiredLegend v-if="hasRequiredFields" class="mt-4" />
</form>
```

It takes no props; a `class` lands on its paragraph.

## Code snippet — `DmsCodeSnippet`

Read-only code in the code editor's look, the component the [CodeBlock](/docs/components/display-blocks/code-block) draws: a head with the `title`, the language and a copy button, then the code highlighted in its language. Use it for a request body, a response, a generated snippet in a custom component — never a `<pre>` of your own.

```vue [app/components/RequestBody.vue]
<DmsCodeSnippet :code="body" language="json" title="Request body" max-height="20rem" />
<DmsCodeSnippet :code="curl" wrap="anywhere" />
```

| Prop        | Type                      | Default | Purpose                                                                                                   |
| ----------- | ------------------------- | ------- | --------------------------------------------------------------------------------------------------------- |
| `code`      | `string`                  | —       | The code, verbatim.                                                                                       |
| `language`  | `string`                  | —       | `json`, `javascript`, `typescript`, `html`, `sql`, `shell` or `text` (`js`, `ts`, `bash`, `sh`, `plain` read as theirs). |
| `title`     | `string`                  | —       | Shown in the head, as written.                                                                            |
| `copy`      | `boolean`                 | `true`  | A button copies the code.                                                                                 |
| `maxLines`  | `number`                  | —       | Lines shown before the code scrolls.                                                                      |
| `maxHeight` | `string`                  | —       | A CSS height the code scrolls past (`"20rem"`), when `maxLines` is not set.                               |
| `wrap`      | `boolean` · `"anywhere"`  | `false` | `true` wraps long lines between words; `"anywhere"` also breaks a word too long for the line (a URL, a token, minified JSON). |

Without a `title` and a `language` the snippet has no head: the copy button floats in the code's top corner, and the code keeps clear of it. Pass `language: "text"` to keep a head naming plain text.

## Scrolling to a block — `scrollToBlock`

`scrollToBlock(key, options?)` (auto-imported) brings a block of the current page into view and answers `true`, or `false` without scrolling when the block is not on screen. A block's **anchor** is the key path it is declared under: its static field's key for a top-level block, then each `.child()` key down to it. The anchors are stable — they are the page's own keys — so a custom component can name any block of its page:

```ts [src/pages/routes.ts]
static summary = StatGroup({ /* … */ });   // anchor "summary"
static tabs = Tab({ /* … */ })             // anchor "tabs"
  .child("statistics", Grid(), { slot: "statistics" }); // anchor "tabs.statistics"
```

```ts [app/components/RouteTree.vue]
function showStatistics(): void {
  if (!scrollToBlock("tabs.statistics", { behavior: "smooth" })) void navigateDms("?tab=statistics");
}
```

`options` are those of `Element.scrollIntoView` (`{ block: "start" }` by default); the block's first element is scrolled. A block in a closed tab, one the viewer may not see, or a key no block has answers `false`.

## Declaring keyboard shortcuts

Components define their shortcuts with Nuxt UI's `defineShortcuts` as usual; the DMS part is **declaring** them so they appear on the built-in **Shortcuts** settings page. The loader discovers one registry per module — `app/config/shortcuts-registry.ts`, found by convention, nothing to declare ([Frontend layer](/docs/building/frontend-layer#layout)) — and each registry default-exports the metadata:

```ts [frontend-vue/app/config/shortcuts-registry.ts]
import type { ComponentShortcuts } from "#dms-ui/app/types/shortcuts";

export default [
  {
    component: "ReportViewer",
    shortcuts: [
      { key: ["R"], descriptionKey: "$acme.shortcuts.refresh", component: "ReportViewer" },
    ],
  },
] satisfies ComponentShortcuts[];
```

`ShortcutMetadata` pairs the `key` combination (an array of keys) with the owning `component`, a `descriptionKey` — following the `$`-prefix i18n convention — and an optional `condition`. Every module's registry is aggregated at build time into the settings page, grouped by component.

### Search fields

"/" is taken by the navigation search: the settings menu's on every settings page. A custom page that adds a search of its own must not bind "/" too — two handlers on one key fight over the focus. Bind it to <kbd>Ctrl</kbd> <kbd>/</kbd> (<kbd>⌘</kbd> <kbd>/</kbd> on macOS) with the shared map, `buildPageSearchShortcuts` — auto-imported, or imported from `#dms-ui/app/composables/global/searchShortcuts` — which also covers layouts where "/" needs Shift (AZERTY), and show the same keys in the input's hint:

```vue
<script setup lang="ts">
import { buildPageSearchShortcuts } from "#dms-ui/app/composables/global/searchShortcuts";

const search = useTemplateRef<{ inputRef?: HTMLInputElement }>("search");
defineShortcuts(
  buildPageSearchShortcuts(() => search.value?.inputRef?.focus()),
);
</script>

<template>
  <UInput ref="search" v-model="query">
    <template #trailing>
      <UKbd value="meta" size="sm" />
      <UKbd value="/" size="sm" />
    </template>
  </UInput>
</template>
```

Like every `defineShortcuts` key, both are ignored while the focus is in an input, a textarea or a contenteditable, so typing "/" in a field never moves the focus. Both are already listed in the **Global** group of the Shortcuts page.
