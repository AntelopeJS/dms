description: The composables a layer's Vue uses to call the backend with the session, gate UI by permission, switch accounts and recover an expired session.

---

A layer's Vue uses these composables to call the DMS backend with the current session. Most custom components need three of them:

- `useApiData` loads the data a component displays, server render included.
- `useAuthFetch` returns `$authFetch`, for writes and for requests a click starts.
- `usePermissions` decides which actions the user sees. Backend routes still enforce access.

The permission ids come from the backend RBAC layer. [Auth and permissions](/docs/auth-and-tenancy/auth-and-permissions) shows where they are registered and how routes enforce them.

## `useApiData`, read what a component renders

`useApiData` is how a component loads the backend data it renders. It is the renderer's `useDmsFetch` and `useDmsAsyncData`, which follow Nuxt's `useFetch` and `useAsyncData`, with `$authFetch` as the fetch function. It has two forms:

```ts fragment
// One URL. The URL and `query`, `params`, `body` and `method` may be refs or
// getters: the data follows them.
const { data, status, error, refresh } = useApiData<Task[]>("/api/task", {
  query: () => ({ status: filter.value }),
  default: () => [],
});

// A URL that is null or undefined reads nothing until it has a value.
const { data: task } = useApiData<Task>(() =>
  taskId.value ? `/api/task/${taskId.value}` : null,
);

// Data made of several requests: a key, and a handler given `$authFetch`
// and the signal to pass on.
const { data: board } = useApiData("task-board", async ({ $authFetch, signal }) => {
  const [tasks, stats] = await Promise.all([
    $authFetch<Task[]>("/api/task", { signal }),
    $authFetch<TaskStats>("/api/task/stats", { signal }),
  ]);
  return { tasks, stats };
});
```

Its behaviour:

- A server render waits for the read and hands the result to the browser with the page, so the browser does not ask again. Awaiting the call is optional. Callers of the same request (method, URL, query and body) share one request.
- Data read before shows at once and is read again in the background each time a component showing it mounts, and each time a reactive request returns to it. The first mount after a server render does not read again.
- `refreshPageBlocks()` and each event of one of the page's realtime topics read again every `useApiData` the page shows. On a `live` page, the realtime events and `refreshLivePageBlocks()` go through the page's live gate. `refreshPageBlocks()` always reads, even while the page is paused. A form or a header button calls `refreshPageBlocks()` after it saves, so a write needs no `refresh()` of its own. Await it to continue once the reads are done. `refreshOnPageRefresh: false` opts a read out, for data with refresh triggers of its own (`usePageLiveRefresh`).
- The DMS keeps the data under a scope of the session's account and workspace. A switch of either drops the previous data, and a key never shows another account's data.
- `data` is a shallow ref. Replace the value (`data.value = { ...data.value, name }`) instead of changing it in place, or pass `deep: true`.
- Requests go through `$authFetch`, so they carry its headers and its session retry.

The options, beyond those of `useFetch` and `useAsyncData`:

| Option | Effect |
| --- | --- |
| `lazy: true` | A client navigation paints before the data arrives. The server still waits. |
| `server: false` | Only the browser reads, for data that depends on local storage or the window. |
| `immediate: false` | Waits for `execute()`. A dialog or a drawer reads what it shows once it opens. |
| `refreshInterval: ms` | Polls while a component shows the data and the tab is visible. A ref or a getter changes it. `0` or `null` stops it. Called from a plugin, it polls for as long as the application runs. |
| `refreshOnPageRefresh: false` | Leaves the read out of the page's refreshes. |
| `deep: true` | Makes `data` a deep ref. |
| `key` | Names the key of a URL read, for `useDmsData`. |

On a page declared with [`live`](/docs/building/pages-and-components#what-pause-freezes), a component's polling stops while the page is paused. On resume it reads once if a poll fell due meanwhile. A plugin's polling keeps running.

The result has `data`, `status`, `pending`, `error`, `key`, `placeholder`, `execute()`, `refresh()` and `clear()`. `clear()` resets the data to its `default`. A failure stays in `error`, with the backend's `statusCode` and `data`, until the next answer, and a failed refresh keeps the previous data. `transform(value, { key })` receives the key too. `placeholder` is true while a reactive request still shows the previous request's data.

Its type is `ApiDataResult<T>`, auto-imported like `UseApiDataOptions<T>`. A composable that shares a read declares it:

```ts fragment
export function useTask(id: MaybeRefOrGetter<string>): ApiDataResult<Task> {
  return useApiData<Task>(() => `/api/task/${toValue(id)}`);
}
```

`useApiPagedData(key, handler, { nextCursor })` reads a list page by page under one key, for a **Load more** button or an infinite list. The handler receives `$authFetch`, `cursor`, `index` and `signal`. `nextCursor(page, pages)` returns the next cursor, or `null` at the end, and `initialCursor` sets the first one. The server renders the first page. `loadMore()` appends the next one, and `pages`, `hasMore` and `loadingMore` follow it. A refresh reads every loaded page again. Put the folder or the filters in the key, because a new key starts from its first page.

A write, or a read a click starts (a dialog's confirmation, an export), is an `$authFetch` call. `useApiData` is for what a component renders.

### Three patterns

**Chained reads.** A read that needs another's answer keys on it. Its URL is `null` until the first one answers, so it reads nothing meanwhile, on the server and in the browser.

```ts fragment
const { data: project } = useApiData<Project>(() => `/api/project/${id.value}`);
const { data: owner } = useApiData<User>(() =>
  project.value ? `/api/user/${project.value.ownerId}` : null,
);
```

**An editable draft.** `data` is what the backend holds. The form edits a copy taken when an answer arrives, so a background read never overwrites what the user typed, and a save sends the copy.

```ts fragment
const { data } = useApiData<Settings>("/api/settings");
const draft = ref<Settings | null>(null);
watch(data, (value) => {
  if (value && !isDirty.value) draft.value = structuredClone(value);
}, { immediate: true });

async function save() {
  await $authFetch("/api/settings", { method: "PUT", body: draft.value });
  refreshPageBlocks();
}
```

**Readers and writers.** The components that show a record read it with `useApiData` and the same URL, so they share one request and one cache. The component that changes it writes with `$authFetch`, then calls `refreshPageBlocks()`, and every reader on the page reads again. No component calls another's `refresh()`. A composable that returns `useApiData` reads on the server too, so a button that only writes must not call it to reach a mutation. Give the writes a composable of their own.

::warning
Never call `$authFetch` in `setup` or in an immediate watcher to load data. The call runs on the server too, which neither waits for it nor hands its answer over, so the browser asks again. Read with `useApiData`, whose URL and query may be refs or getters.
::

### Update a read in place, `useDmsData`

`useDmsData(key)` is the runtime's equivalent of Nuxt's `useNuxtData`. It returns the `data` that a `useApiData` read holds under `key`, shared with every component that shows it. Assigning it updates them all without a new read. Changing it in place does too when the read is `deep: true`. Use it to put a write's answer in place (an optimistic update), or to apply what a realtime event says changed, even to a read the component does not show. It reads nothing itself, so a writer composable can use it.

- The handler form's key is its first argument. A URL read takes a `key` option: `useApiData("/api/task", { key: "tasks" })`.
- `data` is `undefined` until a component reads the key. It is also `undefined` after the browser lets the read go, and after the account or workspace changes. Of the reads no component shows, the browser keeps the 50 most recently shown. A read whose key moved (a ref or getter key) still shows the previous key's data. Assigning `undefined` data does nothing, and the next read loads it fresh.
- A read in flight writes its answer over the update. When that answer does not carry the new data, call the read's `refresh()` or `refreshPageBlocks()` once the write is done.

```ts fragment [app/composables/useTaskChanges.ts]
export const useTasks = () => useApiData<Task[]>("/api/task", { key: "tasks", default: () => [] });

export function useTaskChanges() {
  const { $authFetch } = useAuthFetch();
  const { data: tasks } = useDmsData<Task[]>("tasks");
  return {
    async rename(id: string, title: string) {
      const previous = tasks.value;
      if (previous) tasks.value = previous.map((task) => (task.id === id ? { ...task, title } : task));
      try {
        await $authFetch(`/api/task/${id}`, { method: "PATCH", body: { title } });
      } catch (error) {
        tasks.value = previous;
        throw error;
      }
    },
    async applyChange(id: string) {
      const task = await $authFetch<Task>(`/api/task/${id}`);
      tasks.value = tasks.value?.map((current) => (current.id === id ? task : current));
    },
  };
}
```

`rename` shows the new title at once and puts the old list back if the backend refuses. `applyChange` reads only the task a realtime event named, not the whole list.

## `useAuthFetch`, the authenticated fetch

`useAuthFetch()` returns `{ $authFetch }`. Use it for every backend request that is not a `useApiData` read:

```ts fragment
const { $authFetch } = useAuthFetch();

await $authFetch(`/api/task/${id}`, { method: "DELETE" });
```

`$authFetch` is a `$fetch.create` instance bound to the backend `baseURL` (`config.public.dms.baseURL`), with the call signature of `$fetch`. `$authFetch.raw(...)` retries like the call, `$authFetch.native` is the platform fetch, and `$authFetch.create(defaults)` returns a fetch with more defaults that retries too.

On a `401` while the user is signed in, `$authFetch` refreshes the session through `useSessionRecovery` and sends the request once more. A `401` on that second attempt, or while the user is signed out, makes it reconcile the session and send the user to `/auth` if they are still signed out.

### Headers it sets

| Header | Value | When |
| --- | --- | --- |
| `x-content-language` | The current i18n locale | On every request that does not set it |
| `x-realtime-session` | The active realtime session id | Once a realtime session is registered (see [Realtime and notifications](/docs/frontend-composables/realtime-and-notifications)) |

The browser never holds the access token. The frontend server proxies `/api/**` and `/dms/**` to the backend and adds `Authorization: Bearer` with the session's access token on the way.

## `usePermissions`, gate the interface

`usePermissions()` returns the current user's permission set from shared state, and the helpers that query it:

```ts fragment
const {
  permissions,
  isLoaded,
  loadPermissions,
  fetchPermissions,
  refreshIfStale,
  hasPermission,
  clear,
} = usePermissions();
```

| Member | Type | Purpose |
| --- | --- | --- |
| `permissions` | `ComputedRef<Set<string>>` | The loaded permission ids. |
| `isLoaded` | `ComputedRef<boolean>` | `true` once a load has filled the set. |
| `loadPermissions()` | `() => Promise<void>` | Loads the set unless it is loaded. Concurrent first loads share one request. |
| `fetchPermissions()` | `() => Promise<void>` | Reads `GET /dms/permissions` again into shared state. |
| `refreshIfStale()` | `() => Promise<void>` | Reads again only if the last load is older than 5 minutes. |
| `hasPermission(id)` | `(string) => boolean` | `true` when the set holds `id` or the `*` wildcard. |
| `clear()` | `() => void` | Empties the set. |

The set is async data under the `dms-permissions` key, loaded once and shared. Like every key, it belongs to the account and workspace, so switching either drops it. On a page that declares `auth`, the `auth` middleware loads the set during the server render and hands it to the browser with the page. Its 5-minute age counts from that load. Reading the set never loads it, so a component that shows it does not read it again on mount.

Call `loadPermissions()` when you only need the set. Call `fetchPermissions()` when the set changed on the backend. A failed refresh keeps the last set. Call `refreshIfStale()` on navigation to keep the set current without reading it on every render.

### `DmsPermissionGate`

Most layers use the `DmsPermissionGate` component instead of the composable. It renders its default slot only when the set is loaded and holds the `permission` id, and its `fallback` slot otherwise:

```vue
<template>
  <DmsPermissionGate permission="dms.task.write">
    <UButton @click="createTask">New task</UButton>
    <template #fallback>
      <p>You don't have access to create tasks.</p>
    </template>
  </DmsPermissionGate>
</template>
```

The `permission` is a backend permission id. Register and enforce the matching one on the server, as [Auth and permissions](/docs/auth-and-tenancy/auth-and-permissions) describes.

::warning
A permission gate hides actions. It does not protect them. The backend route still enforces the permission.
::

## `useMultiAccount`, the account switcher

`useMultiAccount()` manages the accounts this browser is signed in to, so the user can switch between them without signing in again:

```ts fragment
const {
  accounts,
  getActiveAccount,
  addCurrentAccount,
  removeAccount,
  syncActiveAccount,
  switchAccount,
  validateAllAccounts,
} = useMultiAccount();
```

`accounts` is a list kept in `localStorage` under the key `antelopejs-accounts`. Each entry is a `StoredAccount`:

```ts
interface StoredAccount {
  accountId: string;
  userId: string;
  email: string;
  name: string;
  lastUsed: Date;
  isExpired?: boolean;
}
```

The list holds no token. The frontend server keeps each account's refresh token in a sealed cookie of its own, keyed by `accountId`.

| Member | Purpose |
| --- | --- |
| `accounts` | The stored accounts, a ref backed by `localStorage`. |
| `getActiveAccount()` | A `StoredAccount` for the signed-in user, or `undefined`. |
| `addCurrentAccount()` | Adds the signed-in user to the list, or updates their entry. |
| `removeAccount(userId)` | Asks the frontend server to forget the account (`POST /auth/remove-account`), then drops it from the list. |
| `syncActiveAccount()` | Copies the session user's `name` and `email` onto their entry. |
| `switchAccount(userId)` | Signs in as a stored account. |
| `validateAllAccounts()` | Checks whether each other account can still sign in, and sets `isExpired`. |

`switchAccount` first stores the current account, so the user can switch back. It then sends `POST /auth/switch-account` with the entry's `accountId`. The frontend server refreshes that account's token with the backend and makes it the session. The browser then reads the session again, clears the permission set and reloads the site layout. Navigating after the switch is the caller's job. The accounts page navigates to the homepage. When the backend refuses the token (`400`, `401` or `403`), the entry is marked `isExpired` and the error is thrown again.

`validateAllAccounts` sends `POST /auth/validate-account` for each other account. The frontend server refreshes the token and keeps the new one when the backend rotated it. An answer of `null` means the backend could not tell, and leaves `isExpired` as it was. An expired account stays in the list, badged on `/auth/accounts`, until the user removes it.

::note
`/auth/switch-account`, `/auth/validate-account` and `/auth/remove-account` are routes of the frontend server, on the app's own origin. The composable calls them with `$fetch`, not `$authFetch`, which is for calls to the DMS backend.
::

## `useCurrentUser`, the reactive identity

`useCurrentUser()` returns `{ user, refresh }`. `user` is the shared session user that every view of the signed-in identity reads. `refresh()` reads the session again, then calls `syncActiveAccount()` so the stored account follows. A new name then shows everywhere without signing in again. The `profile-sync` plugin calls `refresh()` when the profile form or the language and region form saves.

## `useLogout`, the shared logout

`useLogout()` returns `{ logout }`, the logout behind the sidebar user menu and the command palette. `logout()` drops any **Preview as role** state, clears the session and removes the user from the stored accounts. It then routes to `/auth/accounts` when other accounts remain, and to `/auth` otherwise. It clears the session even when the user object has no `_id`. Call it instead of clearing the session and navigating yourself:

```ts fragment
const { logout } = useLogout();
await logout();
```

## `useSessionRecovery`, the shared refresh

`useSessionRecovery()` is the 401 recovery under `$authFetch` and the realtime stream. You rarely call it directly.

```ts fragment
const { loggedIn, refreshSession, reconcileSession, redirectToAuth } = useSessionRecovery();
```

- `refreshSession()` returns `Promise<boolean>`. It reads the session again and resolves `true` on success. Concurrent callers share one refresh in flight, so a `401` on an HTTP call and on the live connection at the same time cause one refresh. Two parallel refreshes with the same rotating token would invalidate each other and sign the user out.
- `reconcileSession()` refreshes only when the user is signed in.
- `redirectToAuth(redirect?)` navigates to `/auth` with a `redirect` query back to the current route. It does nothing on an `/auth` route.
