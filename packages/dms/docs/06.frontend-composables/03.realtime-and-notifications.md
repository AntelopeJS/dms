A signed-in user's browser holds one SSE stream to the backend (`GET /api/realtime/connection`). It carries every topic and is shared by all the browser's tabs. The engine joins it on sign-in and leaves it on sign-out. Anonymous visitors get no realtime traffic.

Your code never touches the stream. It subscribes to a named topic and gets a handler call for each event, plus a cached snapshot if it subscribes late. The backend binds topics to pages, so most layer code subscribes through the page's session. [Backend services](/docs/building/backend-services#realtime) shows how the backend registers and publishes topics.

### One connection per browser, a session per tab

Over HTTP/1.1 a browser opens at most six connections per host, and a stream holds one for as long as it lives. With a stream per tab, a few tabs would use them all, and pages, code chunks and writes would wait. So the tabs of one browser profile share one connection:

- One tab holds the stream, elected with a [Web Lock](https://developer.mozilla.org/docs/Web/API/Web_Locks_API) that the browser releases when the tab closes, crashes or is discarded. It relays what the stream carries to the other tabs over a `BroadcastChannel`.
- Each tab opens its own session on that connection (`POST /api/realtime/session`, with the connection in the `x-realtime-connection` header). Its page, its topics, its presence and its `sessionId` stay its own.
- A session belongs to the account and workspace its tab opened it in, and receives only that workspace's events. When the session's `accountId` or `activeTenantId` changes, the tab opens a new session on the same connection. When a tab's page requests come from another workspace than its session's, because another tab switched workspace, the server ends that session with a `session-ended` frame and the tab opens a new one. The other tabs keep theirs.
- When the holding tab goes, the next tab takes the lock and opens a new stream. Every tab then opens a new session on it, sets its page again and takes back its presence. When another tab goes, the holder ends that tab's session (`POST /api/realtime/session/close`) and its presence goes at once.
- When the backend answers a session request with `ok: false`, it does not know the connection the tab named. The tab asks the holder to open a new stream and opens its session on that one, with a growing delay between attempts.
- Tabs of different users never share a connection.
- In development the connection also carries the backend's reload signal, under the topic the session's greeting names in `devReloadTopic` (`dms:dev-reload`). Signed-out tabs and tabs whose session is reconnecting follow `GET /dms/dev/reload` instead, one stream shared the same way.

The frontend server's proxy relays the `x-realtime-connection` and `x-realtime-session` headers to the backend by name.

::warning
Web Locks need a secure context, HTTPS or `localhost`. Over plain HTTP on another host name, each tab holds a stream of its own, and six tabs over HTTP/1.1 hold all six connections. Every other request of those tabs then waits until one closes. Serve the dashboard over HTTPS, and over HTTP/2 or HTTP/3 in production, usually through a reverse proxy that terminates TLS. A stream is then one of many on a single connection. See [Deployment](/docs/building/deployment#http2-and-long-lived-streams).
::

## `useRealtimeTopic`, the simplest entry point

`useRealtimeTopic(topic, handler)` subscribes for the life of the calling component, and unsubscribes when its scope ends. The topic may be a ref or a getter. When it changes, the old subscription ends and a new one starts.

```ts fragment [app/components/StatsCard.vue]
import { useRealtimeTopic } from "#dms-core/app/composables/realtime/useRealtimeTopic";

useRealtimeTopic("stats:live", (event) => {
  refresh();
});
```

A falsy topic subscribes to nothing, so you can gate on a reactive value:

```ts fragment
const topic = computed(() => (rowId.value ? `presence:row:${rowId.value}` : undefined));
useRealtimeTopic(topic, onPresence);
```

## `usePageRealtime`, page-scoped

The backend activates a page's topics when a session subscribes to the page. `usePageRealtime(pageId)` watches `pageId` and calls `setPage` on the engine, which tells the backend which page the tab shows. It sets the page back to `null` when its scope ends. When several instances hold a page at once, the session follows the one that set its page last. A page remounted at the same path because its query changed may set up its new instance before or after the old one goes, and either order keeps the page's topics.

The catch-all page renderer (`[...slug].vue`) already calls `usePageRealtime` for the current page and provides it with `providePageRealtime`. A component inside a page subscribes to its topic with `useRealtimeTopic`, on the same session.

`usePageRealtime` returns a `PageRealtimeApi`: the engine's `subscribe`, the shared `sessionId`, the resolved `pageId` as a ref, and `pageTopics`, the page's realtime topics once the session is subscribed to it.

::tip
Use `useRealtimeTopic` in components. Call `usePageRealtime(pageId)` only when you render a page yourself.
::

## `usePageLive`, direct and pause

On a page declared with [`live`](/docs/building/live-pages), the built-in blocks refetch on their realtime events through the page's live valve. The valve is either in Direct, which the toggle labels **Live**, or paused. `usePageLive()` lets a module's own component follow the same state without reading the DOM. A component can stop a ticker while paused, show what was missed or offer its own switch. [Period filtering](/docs/extending-the-dashboard/period-filtering) shows the toggle next to the chart controls.

```ts fragment [app/components/LiveTraffic.vue]
const { isPaused, missedCount, lastUpdatedAt, pause, resume } = usePageLive();

watch(isPaused, (paused) => (paused ? stopTicker() : startTicker()));
```

| Field | Type | Meaning |
| --- | --- | --- |
| `isEnabled` | `ComputedRef<boolean>` | The page declares `live`. |
| `isLive` | `ComputedRef<boolean>` | The page's data follows its events: Direct, or a page without `live`. |
| `isPaused` | `ComputedRef<boolean>` | The page is paused, and its blocks request nothing on their events. |
| `pause`, `resume`, `toggle` | `() => void` | Switch the page. Resuming refetches once each block that missed an event, and lifts the current holds. |
| `lastUpdatedAt` | `ComputedRef<number \| null>` | When the page last read its data, in ms since the epoch. `null` without `live`. |
| `missedCount` | `ComputedRef<number>` | What the page missed since the pause, in published rows. `payload.ids` counts once per row, `payload.count` as that many, any other event as one. |
| `pauseReason` | `ComputedRef<PageLiveNote \| null>` | Why the page paused by itself: a hold's reason or a hidden tab. `null` while live or paused by the user. |
| `hold`, `release` | `(reason) => void`, `() => void` | Hold the page paused for a reason (a `$` i18n key or a `PageLiveNote`) until released or until the component goes. |
| `missedDetail`, `setMissedDetail` | `ComputedRef<PageLiveNote \| null>`, `(detail \| null) => void` | A breakdown of what was missed, shown after the count. Cleared on resume. |
| `isPolling` | `ComputedRef<boolean>` | The realtime stream is down and the page reads its blocks every `maxRate`. True from the first poll, not while the stream is still connecting. |

A `PageLiveNote` is `{ text, params?, tone? }`. `text` is an i18n key prefixed with `$`, translated with `params` and pluralised on `params.count`, or a plain text. `tone` is `neutral`, `warning` or `error`.

This component holds the page paused while the user types, and gives the toggle a breakdown of the missed events from the page's feed:

```ts fragment [app/components/RouteTester.vue]
const live = usePageLive();
const onFocus = () => live.hold("$api.live.typing_in_tester");
const onBlur = () => live.release();

let server5xx = 0;
useRealtimeTopic("api:requests", (event) => {
  if (!live.isPaused.value || !("payload" in event)) return;
  server5xx += Number(event.payload?.server5xx ?? 0);
  live.setMissedDetail({ text: "$api.live.in_5xx", params: { count: server5xx }, tone: "error" });
});
watch(live.isPaused, (paused) => !paused && (server5xx = 0));
```

On a page without `live`, `isEnabled` is false, the page reads as live, and `pause` and `resume` do nothing. The state belongs to the page on screen, so after a navigation a component reads the next page's state.

The server knows whether a page declares `live`, so `isEnabled` is right in a server render. The rest of the state starts in the browser. A server render reads the page as live, not polling, never read and with nothing missed. A component that hydrates that render reads the same until it is mounted, so its first render matches the server's HTML. A component mounted later, after a client navigation, reads the page's state at once.

A component that refreshes its own data on a topic uses [`usePageLiveRefresh`](#usepageliverefresh-refresh-like-a-built-in-block). A component that refreshes the whole page on its own clock calls `refreshLivePageBlocks()` from `#dms-ui/app/utils/blockRefresh`, not `refreshPageBlocks()`. The live one waits while the page is paused. The other is a user's request and always reads.

A component's `useApiData` polling (`refreshInterval`) stops while the page is paused and reads once on resume if a poll fell due meanwhile. `useApiData` reads the pause through `LIVE_PAUSE_SOURCE` from `#dms-core/app/composables/live/livePauseSource`, which the UI layer provides for the whole app. Without it, as in a test that mounts a component alone, a read polls as if live, and the test can provide its own `() => boolean`. [Live pages](/docs/building/live-pages#what-a-pause-freezes) lists what Pause freezes and what still reads.

## `usePageLiveRefresh`, refresh like a built-in block

`usePageLiveRefresh(refresh, options)` puts a module's own component through the same valve as a built-in block with a `realtimeTopic`. It follows the page's `maxRate`, and the slower `slowRateAfter` rate once the page's `PeriodSelector` shows a long period.

A `useApiData` read already follows the page's refreshes and the events of the page's topics. `usePageLiveRefresh` is for a topic of the component's own, or for an idle refresh. The read then sets `refreshOnPageRefresh: false`, because the page's refresh would read it a second time. The session subscribes only to the topics registered on the page, so bind a topic of the component's own to the page with `RegisterPageTopic(pageId, topic)` in the backend ([Backend services](/docs/building/backend-services#realtime)).

```ts fragment [app/components/HealthHero.vue]
const { data, refresh } = useApiData<Health>("/api/health", {
  refreshOnPageRefresh: false,
});

usePageLiveRefresh(() => void refresh(), {
  realtimeTopic: "api:requests",
  idleRefresh: 60,
});
```

When `refresh` runs:

- In Direct, on each event of `realtimeTopic` and on each `refreshLivePageBlocks()`, at most once per `maxRate`. The last event of a burst is never lost.
- While paused by the user, a hold or a hidden tab, never. The events count in the toggle's "N new", and one read catches up on resume.
- On `refreshPageBlocks()`, a user's action, at once, paused or not.
- On a page without `live`, on every event and every refresh of the page.

| Option | Type | Meaning |
| --- | --- | --- |
| `realtimeTopic` | `string \| string[]` | Topics whose events make the component read again. |
| `idleRefresh` | `number` | Seconds without a read after which the component reads again while the page is live, for data that changes with time alone. Nothing is read while paused. |

It returns `{ missed, trigger, refreshNow }`. `missed` counts the events the component missed while paused. `trigger()` asks for a read on the component's own clock, gated like an event. `refreshNow()` reads at once, as a user's action does. A component that must skip a read in some state returns early from `refresh`.

An event that names what changed can patch the read instead of reading it all again, through [`useDmsData(key)`](/docs/frontend-composables/authenticated-requests#update-a-read-in-place-usedmsdata).

## `useUserRealtime`, the engine

`useUserRealtime()` returns the app-wide engine that owns the stream:

```ts fragment
interface UserRealtimeApi {
  subscribe(topic: string, handler: RealtimeTopicHandler): () => void;
  setPage(pageId: string | null): Promise<void>;
  sessionId: Ref<string | undefined>;
  pageId: Ref<string | undefined>;
  menuTopics: Ref<string[]>;
  pageTopics: Ref<string[]>;
  devReloadTopic: Ref<string | undefined>;
}
```

- `subscribe(topic, handler)` registers `handler` for `topic` and returns an unsubscribe function. A topic may have several handlers.
- `setPage(pageId)` declares the page the tab shows (`POST /api/realtime/subscribe/<pageId>`), and `setPage(null)` clears it (`/api/realtime/unsubscribe`). `usePageRealtime` calls it for you.
- `sessionId` is the tab's realtime session id. `$authFetch` sends it as the `x-realtime-session` header, so the backend can tie your writes to your stream.
- `pageId` is the page the session is on.
- `menuTopics` are the menu topics the server subscribed the session to, announced in its greeting because their names hold the workspace.
- `pageTopics` are the realtime topics of the page the session is on.
- `devReloadTopic` is the topic of the development reload signal. It is unset in production and while no session is open.

Handlers receive one of two event shapes:

```ts
interface RealtimeEvent {
  topic: string;
  type: string;
  payload?: Record<string, unknown>;
  actorId?: string;
  ts: number;
}

interface RealtimeSnapshotEvent {
  topic: string;
  entries: Array<{
    topic: string;
    rowId: string;
    actor: { id: string; displayName?: string; avatarUrl?: string };
    sessionId: string;
    instanceId: string;
    since: number;
  }>;
}
```

A `RealtimeSnapshotEvent` carries `entries`, the presence state of who is on a row. A `RealtimeEvent` carries `type` and `payload`. Branch on the shape in your handler.

## Notifications

`useNotifications()` is the notification center's store, built on the engine. It returns shared state and two kinds of mutators. Server actions call the backend through `$authFetch`. Realtime reconcilers change local state from incoming events without reading the list again. A backend module sends a notification with the `Notification()` builder ([Backend services](/docs/building/backend-services#notifications)). The [bell](/docs/auth-and-tenancy/authentication#read-notifications) and the [notification preferences](/docs/auth-and-tenancy/authentication#notification-preferences) read this state.

```ts fragment
const { unreadCount, unreadTone, areCountsLoaded, unreadPreview, notifications, hasMore } =
  useNotifications();
```

| Field | Meaning |
| --- | --- |
| `unreadCount` | Unread notifications in the whole feed. The bell's badge, the Notifications entry of the navigation and the overview show it. |
| `unreadTone` | The tone of the most important unread notification, which the badge is drawn in. `undefined` when nothing is unread. |
| `areCountsLoaded` | Whether the counts were read once, with the page or by `fetchBellCounts`. Until then, `0` may be wrong. |
| `unreadPreview` | The short list of unread items for the dropdown. |
| `notifications` | The full list, page by page. |
| `hasMore` | Whether `fetchNotifications` has another page to read. |

The badge's tone is the most important unread one, in the order error, warning, primary, success, neutral. The server weighs it, and counts an untoned notification as `primary`, the colour the inbox gives it while unread. Opening the bell changes neither the count nor the tone. A notification leaves the count once it is opened or marked read.

Each item is a `UserNotification`:

```ts
type NotificationTone = "neutral" | "primary" | "success" | "warning" | "error";

interface UserNotification {
  _id: string;
  userId: string;
  icon: string;
  title: string;
  description: string;
  params: Record<string, string | number> | null;
  linkTo: string | null;
  isRead: boolean;
  categoryId: string;
  subjectId?: string;
  tone?: NotificationTone | null;
  createdAt: string;
  updatedAt: string;
}
```

### Server actions

These call the backend, then update local state:

- `fetchBellCounts()` reads `unreadCount` and `unreadTone` again. The dashboard frame reads them with the page through `useRenderedBellCounts()`, so a server render shows the badge and the browser starts from the same counts.
- `fetchUnreadPreview()` reads `unreadPreview` again.
- `fetchNotifications(reset = false)` appends the next page to `notifications`. Pass `true` to start again from the top.
- `markAsRead(id)` and `markAsUnread(id)` change `isRead` and take the counts the write answers.
- `deleteNotification(id)` removes the item and takes the counts the write answers.

Each write on the feed (`PUT mark-read/:id`, `mark-unread/:id`, `mark-all-read` and its undo, `DELETE delete/:id`) answers `counts`, the whole feed's counts after it, as `GET /counts` gives them. The badge takes them without asking again.

The inbox on the notifications page is not part of this store. It is a `TableView.fromSource` table over `pageRoutePath("/settings/user/notifications", "/inbox")`, drawn by the `dms:inbox` display. It lists the feed again after each of its own row actions, and whenever `unreadCount` or the newest notification changes.

```ts fragment [app/components/NotificationBell.vue]
const { unreadCount, unreadTone, areCountsLoaded, fetchBellCounts, fetchUnreadPreview } =
  useNotifications();

onMounted(async () => {
  if (!areCountsLoaded.value) await fetchBellCounts();
  await fetchUnreadPreview();
});
```

### How the SSE bridge keeps it live

A client plugin of the layout layer connects the engine to the store. While the user is signed in, it subscribes to the user's topic `notifications:user:<userId>` and sends each event to a reconciler by its `type`:

| Event `type` | Reconciler | Effect |
| --- | --- | --- |
| `notification:new` | `handleIncomingNotification` | Puts the item first, adds one to `unreadCount`, and keeps the stronger of `unreadTone` and the item's tone. |
| `notification:read` | `handleRemoteRead(ids, counts)` | Marks those ids read and takes the counts the event carries. |
| `notification:unread` | `handleRemoteUnread(ids, counts)` | Marks those ids unread and takes the counts the event carries. |
| `notification:all-read` | `handleRemoteAllRead(counts)` | Marks all read, empties the preview and takes the counts. |

The plugin is always mounted, so the badge and the dropdown follow reads made in other tabs and on other devices. A read, an unread or an all-read event carries the whole feed's counts after it (`payload.counts`), weighed by the server, tone included. A new notification is weighed in the browser, since it can only make the badge stronger. A tab's own write comes back as an event too, with the same counts, so taking them twice changes nothing. An event without counts makes the store read them with `fetchBellCounts`.
