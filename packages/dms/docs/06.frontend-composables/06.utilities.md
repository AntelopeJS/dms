## Translation

### `useTranslation` and the `$` prefix {#usetranslation-the-prefix-convention}

A screen the backend describes passes strings that are either a literal ("Save") or a translation key. The DMS tells them apart by a leading `$`. A value that starts with `$` is an i18n key, and any other value is shown as written. `processI18n` applies that rule:

```ts fragment [resolving a label]
const { processI18n } = useTranslation();

processI18n("Save"); // "Save", returned as written
processI18n("$actions.save"); // t("actions.save"), without the $
processI18n("$items.count", { n: 3 }); // params passed on to t()
```

A custom component can therefore take a user's label and a translation key through the same prop, and only the `$` ones are looked up. Define the matching keys in your layer's locale files ([Localization](/docs/building/localization)).

`useTranslation()` also returns `processApiMessage(message, params?)` for a message the API sends back. The API writes it as a bare key (`error.unauthorized`) or with the `$` prefix. When the key has no translation, a `$` message falls back to the bare key and any other message is shown as it came in.

`useI18n()` throws outside a component setup, such as in a DMS plugin, a data-type formatter or a render function. Use `getAppTranslation()` there. It returns the same `processI18n` and `processApiMessage`, plus the global composer's `t` for a key without `$`. Each call reads the active locale, so a text written in a `computed` follows a language switch. [Command palette sources](/docs/extending-the-dashboard/dashboard-chrome#command-palette-sources) translate backend display names this way:

```ts fragment [app/plugins/my-source.client.ts]
const { processI18n, t } = getAppTranslation();
processI18n("$actions.save"); // t("actions.save")
processI18n("Save"); // "Save"
t("commandPalette.groups.navigation");
```

### `useComposedText`, texts composed in the reader's language

A block text from the backend is a plain string or a [composed text](/docs/components/block-fundamentals#composed-texts), `{ key, params }` with raw amounts, dates and counts. `useComposedText()` returns `processText`, which writes any of them:

- A string goes through the `$` rule.
- A number is written for the active locale.
- A `ComposedText` is translated with each parameter formatted for the active locale and the user's regional preferences, and the plural form picked by its `count`.
- `null` and `undefined` give the empty string.

Each call reads the active locale, so in a `computed` the text follows a language switch.

```ts fragment [a custom cell or card]
const { processText } = useComposedText();

// props.row.statusDetail:
// { key: "saas.invoice.retry", params: { date: { type: "date", value: "2026-10-10", format: "day" } } }
const line = computed(() => processText(props.row.statusDetail));
processText("$actions.save"); // t("actions.save"), as processI18n
```

Outside a component setup, `getAppComposedText()` returns the same `processText`. `resolveComposedText(text, { translate, locale, now? })` does the work with a vue-i18n `t` that takes `(key, named, plural?)`, and `isComposedText(value)` tells a composed text from a string. The `dms-core` layer mirrors the types (`ComposedText`, `BlockText` and the parameter types).

### `useUniqueLocales`, for language switchers

`useI18n().locales` can list the same language code more than once. `useUniqueLocales()` returns `{ uniqueLocales }`, a `computed` list with one entry per `code`, where the first occurrence wins. Use it to fill a locale picker.

```ts fragment [locale picker]
const { uniqueLocales } = useUniqueLocales();
```

## Leave guard

### `useUnsavedChanges` and `useFormDirty`, guard a hand-built form

The generic `Form` already guards its unsaved changes ([Forms](/docs/components/forms#unsaved-changes)). A form you build yourself gets the same behaviour and the same warning dialog from two composables of the UI layer.

`useFormDirty(values, { initial? })` tracks whether the form is dirty. It returns `{ dirty, baseline, markClean }`:

- `dirty` is `true` while `values()` differs, deeply and by value, from the starting values. The starting values are a snapshot taken when you call it, or the `initial()` you keep yourself. Empty values (`undefined`, `null`, `""`, `[]`, `false`) count as equal.
- `baseline` is the snapshot, when there is no `initial`.
- `markClean(values?)` makes the current values, or the given ones, the new starting point, after a save.

`useUnsavedChanges({ dirty, containerId?, element? })` asks before the changes are lost. It returns `{ isDirty, confirmLeave }`. It asks when the user:

- Leaves the page through a link, the router, the browser's Back and Forward buttons, a reload or a closed tab.
- Closes the drawer or modal named by `containerId`.
- Switches away from the tab panel that holds `element`.

`confirmLeave()` asks before your own way out, such as a Cancel button or another entry picked in an editor, and resolves `true` to go ahead. It resolves `true` at once when there is nothing to lose. At most one dialog shows: a leave asked while it is open waits for the same answer. Discarding releases the form until it is clean again.

```ts fragment [hand-built form]
import { useFormDirty } from "#dms-ui/app/composables/unsaved-changes/useFormDirty";
import { useUnsavedChanges } from "#dms-ui/app/composables/unsaved-changes/useUnsavedChanges";

const name = ref(saved.value.name);
const { dirty } = useFormDirty(() => ({ name: name.value }), {
  initial: () => ({ name: saved.value.name }),
});
const { confirmLeave } = useUnsavedChanges({ dirty });

async function cancel() {
  if (await confirmLeave()) closePanel();
}
```

Show `DmsSaveBar` with `:dirty="dirty"` for the save bar. It takes no space while hidden, floats over the bottom of the page while the form is taller than the screen, and makes room under the last field when it shows there.

### `usePageLeaveGuard`, block navigation for another reason

`usePageLeaveGuard()` returns `{ registerGuard }`. Its guards belong to the current route, and the composable clears them when the component unmounts.

`registerGuard(callback)` returns an unregister function. The page's guards run in order when the router leaves the page. A callback that returns `false` or throws blocks the navigation, and any other value allows it. Callbacks may be async.

```ts fragment [unsaved form]
const { registerGuard } = usePageLeaveGuard();
const { confirm } = useConfirm();
const isDirty = ref(false);

onMounted(() => {
  registerGuard(async () => {
    if (!isDirty.value) return true;
    return confirm({
      title: "Unsaved changes",
      description: "Discard them and leave?",
    });
  });
});
```

The dialog comes from [`useConfirm`](/docs/frontend-composables/ui-toolkit#confirmation-useconfirm), so it matches the rest of the dashboard. Guards run only in the browser. During a server render, registering one does nothing.

### `useLeaveGuard`, guards by container

`usePageLeaveGuard` is built on `useLeaveGuard`, the registry of guards by container id. A drawer or a modal opened with `useDrawer` or `useModal` runs the guards of its `containerId` before it closes. Use `useLeaveGuard` to guard something other than the current page. It returns:

- `addGuard(containerId, callback)`, which returns an unregister function.
- `removeGuard(containerId, guardId)`, which removes one guard.
- `executeGuards(containerId)`, which returns `Promise<boolean>`. It runs the container's guards in the order they were added, and resolves `false` if one returns `false` or throws.
- `clearGuards(containerId)`, which removes every guard of a container.

You choose the `containerId` values and remove the guards yourself.

## Onboarding

### `useOnboarding`, read onboarding state

`useOnboarding()` is async and resolves to `{ hasOnboarded }`. The first call reads the state from the backend as async data under the `dms-onboarding` key, and later calls return the known value at once. A server render hands it to the browser with the page, so the browser does not ask again. A failed read throws.

```ts fragment [read state]
const { hasOnboarded } = await useOnboarding();
```

### `setOnboardingComplete`, release the guard without a reload

The backend sets the onboarding flag when the first admin registers, but the browser's cached value stays `false` until a reload. `setOnboardingComplete()` sets the cached value to `true`, so the onboarding middleware lets the user leave the wizard at once. Call it from the wizard's finish button.

```ts fragment [wizard finish]
async function finish() {
  await saveWizard();
  setOnboardingComplete();
  await navigateDms("/");
}
```

::note
A global route middleware sends users who have not onboarded to `/onboarding`, and sends onboarded users away from it. You configure nothing for it.
::

## Hydration

### `isDmsHydrating`, draw what the server drew

The browser takes over a page the server rendered: Vue hydrates the server's HTML, and every text, class and node must come out the same, or Vue warns `Hydration ... mismatch` and draws the page again. `isDmsHydrating()` tells whether the browser is hydrating now. It is true from the start of the application until the page has hydrated. It is false on the server, in a page the server did not render, and after a client navigation. It is not reactive, so read it once.

Use it for what the server and the browser cannot compute alike: a part drawn only in the browser, such as a canvas or an iframe preview, or a value only the browser has, such as local storage or the clock. While hydrating, a component draws the server's placeholder until it is mounted. After a client navigation it draws the real content from its first render, with no placeholder first:

```vue [app/components/SitePreview.vue]
<script setup lang="ts">
const isDrawn = ref(!import.meta.env.SSR && !isDmsHydrating());
onMounted(() => {
  isDrawn.value = true;
});
</script>
```

Data needs no check. Load it with [`useApiData`](/docs/frontend-composables/authenticated-requests), which a server render waits for and hands to the browser, without awaiting it in the setup.
