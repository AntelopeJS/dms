A reviewer pins a note on the viewer's canvas. A pin dropped on a block is a note on that block, and names it by the block's `id`, not by where the block is, so it still names that block after an insert, a move, a removal or a page rename, whether the editor, `mockup_patch_spec` or a whole-spec write made the change. A pin dropped outside every block is a note on the page as a whole. The DMS stores annotations in `mockups/<name>/annotations.json`:

```ts
interface StoredAnnotation {
  id: string;
  anchor: { block: string; steps: string[]; page?: string } | { page: string };
  offset: { x: number; y: number };
  text: string;
  status: "open" | "resolved";
  createdAt: string;
  resolvedAt?: string;
  version?: number;
  resolvedVersion?: number;
  state?: string;
}
// annotations.json: { "version": 3, "annotations": StoredAnnotation[] }

interface MockupAnnotation extends StoredAnnotation {
  page?: string;
  path?: string;
}
```

| Field | Meaning |
| ----- | ------- |
| `id` | A random, URL-safe id. |
| `anchor` | What the note is about. On a block, the one node whose `id` is `block`, then down through the one child whose `id` is each of `steps`: without `page`, `block` is a stamped `id`, looked up in the whole spec; with `page`, `block` is an `id` an author wrote, looked up on the page `page` only. On a page, `{ page }` alone: the page whose `id` is `page`. |
| `offset` | Where the pin sits on its block's box, or its page's, as fractions from 0 to 1 from the top left corner: `{ x: 1, y: 0 }` is the top right corner. The same fractions place the pin on every frame width. |
| `page` | The id of the page the block is on now, or the page a page note is on. Served, never stored. |
| `path` | The spec pointer of the block now, such as `/pages/0/tree/1/children/0`. Absent on a page note. Served, never stored. |
| `text` | 1 to 2,000 characters. |
| `createdAt` | ISO 8601. |
| `resolvedAt` | ISO 8601. Set while the annotation is resolved. |
| `version` | The `seq` of the [version of the mockup](/docs/ai-and-claude-code/mockups#version-history) that was newest when the note was pinned. Absent from a note written before versions, and from a note pinned on a mockup with no version yet. |
| `resolvedVersion` | The `seq` of the version that was newest when the note was resolved. Set while the note is resolved, with `resolvedAt`; a note reopened loses both. |
| `state` | The [named state](/docs/ai-and-claude-code/mockups#named-states) the sketch under the pin was drawn in when the note was pinned or last moved, such as `empty`. Absent when the sketch drew its own `html`, and on any other block. The note's card shows it. |

The API, the event stream and the MCP tools serve each note as `MockupAnnotation`: `page` and `path` are resolved against the current `spec.json` on every read, so they follow the block. Both are absent when the block or the page was removed, or when a block cannot be told apart because two blocks match its `anchor`. The note stays, and the viewer shows it in its tray of comments without a block. A note never moves to another block by itself. Put a block back with the same `id` and the note finds it again, or drag the pin onto a block.

`mockup_annotations` adds two fields to each note, read from the same `spec.json`, so the AI patches a commented block without reading the whole spec, and `mockup_read_spec` reads any other part of it by pointer:

| Field | Meaning |
| ----- | ------- |
| `pointer` | The spec pointer of what the note is on now, to use as is in `mockup_patch_spec`: its block, the same as `path`, or its page, such as `/pages/2`. Absent when the block or the page is gone. |
| `node` | The block the note is on, as `spec.json` holds it now. Absent on a page note, and when the block is gone. |

## Comments belong to versions

A note belongs to the version of the mockup it was pinned on: `version` is the `seq` that was newest at that moment, and `resolvedVersion` the one that was newest when the note was resolved. A note pinned on version 2 and resolved after the AI wrote version 3 has `version: 2` and `resolvedVersion: 3`: it was a comment about version 2 that version 3 answered. Resolving a resolved note keeps its first `resolvedVersion`. A note moved or edited keeps its `version`.

A write that folds into the newest version, as consecutive writes by one author do, keeps that `seq`, so a note pinned and resolved inside one fold has the same `version` and `resolvedVersion`. Write the spec first and resolve afterwards, as `mockup_resolve_annotation` asks, so `resolvedVersion` names the version that holds the fix.

The viewer shows the open notes on the current spec and nothing else. In **History** it shows, for each version, how many notes were pinned on it, and a version you preview shows the notes pinned on it, resolved ones included, placed where their blocks are in that version's spec. See [Version history](/docs/ai-and-claude-code/mockups#version-history).

A note written before versions has no stored `version`. It is served as pinned on the newest version, and the next change to that note stores the number it was served with. The file stays version 3: both fields are optional, so a file written before them reads as it is.

## The routes

The viewer reads and writes the notes through `/api/mockup/:name/annotations`, in development and for the platform owner only:

| Route | Body | Answers |
| ----- | ---- | ------- |
| `GET /annotations` | | `{ annotations }` |
| `POST /annotations` | `{ page, path?, offset, state?, text }` | The new note. Without `path`, a note on the page `page`. `state` is the state of the sketch drawn there. |
| `PATCH /annotations/:id` | `{ status?, text?, place? }` | The note. `place` is `{ page, path?, offset, state? }`: it moves the pin, anchored as a new note is, onto another block, onto its page, or to another spot of the same block, and replaces its `state`. |
| `DELETE /annotations/:id` | | `{ id }`. The note is gone for good. |

A body with any other key, an `offset` outside 0 to 1, a `state` that is not a state name or a `text` over 2,000 characters answers 400. A place where the spec has no such page or node answers 404, and so does an unknown note. A place on a block whose ids another block shares, or on a node of a spec that does not parse, answers 409 and changes nothing.

A node's `id` is unique only among its siblings, and copies keep it, so an `id` an author wrote does not name one block. Some ids also carry meaning: a block option child such as a `ChartCard`'s `chart` has the option's key. The DMS never renames an id. To anchor a note it walks up from the node to the nearest node that has no `id` or a stamped one:

- A node with no `id` gets a fresh one, `b-` and eight random characters, written to `spec.json`, and the note anchors there.
- A node with a stamped `id` anchors there. A stamped `id` names one block in the whole spec, so the note follows the block to another page and through a page rename.
- The `id` of each node the walk passes on the way is a step. A `chart` child anchors as the `id` of its card, then the step `chart`.
- When the node and every node above it have an `id` an author wrote, there is nothing to stamp. The note anchors on those ids and on the id of its page, and names the block whose root has that `id` on that page only. After that page is renamed or removed, or when two blocks of the page match, the note has no location.

The stamp sets the `id` and keeps the file's layout: a file on one line stays on one line, the indentation of the first indented line stays, and so do CRLF line endings and a final line ending. The rest is written as `JSON.stringify` writes it: keys keep their order, except that keys which are whole numbers move first in their object.

Keep a block's `id` when you move or rewrite it, in the editor and in a tool call: the `id` is what the notes on it hold on to. Give a copy a new `id`, or none: a spec in which two blocks have the same stamped `id` has an issue at the `id` of the second in document order, which names the first, so a write of it is refused. The editor's duplicate leaves out the stamped ids of the block it copies and of its children.

The DMS writes the file one change at a time and replaces it whole, through a temporary file and a rename, so concurrent annotations are all kept. A change that stamps an `id` takes the spec's write lock first, then the annotations file's, so it cannot interleave with another write of the spec. The module `src/mockup/annotations.ts` exports the same store as plain functions, `listAnnotations(name)`, `createAnnotation(name, draft)`, `updateAnnotation(name, id, patch)` and `deleteAnnotation(name, id)`, for a tool that runs in the backend. `createAnnotation` answers `{ kind: "created", annotation }` and `updateAnnotation` `{ kind: "updated", annotation }`, or why they changed nothing.

A version 2 file, written before pins, is still read: each of its notes sits at the top left corner of its block, `{ x: 0, y: 0 }`. The next change writes the file as version 3.

The history routes of the mockup serve the same notes by version: `GET /api/mockup/:name/history` counts them, and `GET /api/mockup/:name/history/:seq` lists the ones pinned on that version.

## In the editor

A file that only gained the `id` a new note stamped on a block is no other writer's change, also when it is the viewer's own write whose answer was lost: the viewer keeps its undo history and the edit it has not written yet, adds the `id` to them, and writes that edit over the file. It follows the block from step to step of the history, so an undo or a redo keeps the `id` on that block, and a step where the block does not exist, such as before it was inserted or after it was removed, gets no `id`.
