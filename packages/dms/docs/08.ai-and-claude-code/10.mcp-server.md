Under `ajs project dev`, `@antelopejs/dms` serves an MCP server. A coding agent you start in the project, such as Claude Code or Codex, reaches it through a stdio bridge. Claude Code launches the bridge from the project's `.mcp.json`, and Codex from the project's `.codex/config.toml`. The agent gets the builder tools, the database tools and the page tools of the dashboard assistant, with no other module installed. Nothing of the server loads in production.

## The agent entries

### Claude Code

Each start in development adds a `dms` server to the project's `.mcp.json`, and creates the file when there is none:

```json [.mcp.json]
{
  "mcpServers": {
    "dms": {
      "command": "node",
      "args": ["node_modules/.cache/dms/mcp-bridge.cjs"]
    }
  }
}
```

The DMS writes the entry only when it is missing. It keeps the other servers, never changes a `dms` entry you wrote, and leaves a `.mcp.json` that is not a JSON object of servers alone. The file is printed the way oxfmt and Prettier print it. It holds no machine path and no secret, so you can commit it.

Run `claude` in the project root and approve the `dms` server. The tools then read `mcp__dms__builder_catalog` and the like.

### Codex

Each start in development also adds a `dms` server to the project's `.codex/config.toml`, and creates the file when there is none:

```toml [.codex/config.toml]
[mcp_servers.dms]
command = "node"
args = ["-e", "require('.cache/dms/mcp-bridge.cjs')"]
```

Codex starts the server in the folder you run it from. Node finds the launcher in the nearest `node_modules`, so the entry works from any folder of the project.

The DMS appends the table only when no `dms` server is declared. It keeps the rest of the file as it is, comments included, and leaves a file that is not TOML, or that declares `mcp_servers` as an inline table, alone and logs why. The entry holds no machine path and no secret, so you can commit it.

Codex reads `.codex/config.toml` only in a project you trust. Run `codex` in the project and accept the trust prompt, then `codex mcp list` shows `dms`.

## How the bridge reaches the backend

The bridge is a stdio MCP server. It relays each JSON-RPC line to `POST /dms/mcp` on the backend and writes the answer back.

- Each start draws a new credential. The DMS writes it, with the route's URL, to `node_modules/.cache/dms/mcp.json`, with file mode `0600`. The launcher `mcp-bridge.cjs` sits beside it and loads the bridge of the installed `@antelopejs/dms`. Neither file is committed.
- The bridge reads that file for every message, so a restarted backend is reached without a reconnect.
- The route URL starts with `mcp.backendUrl`. Set it to the api module's same-host origin, `${@api.API_LOCAL_BASE_URL}`, as [Configuration](#configuration) shows. Without it, the bridge uses `apiBaseUrl` only when its host is loopback, such as the default `http://127.0.0.1:5010`. `apiBaseUrl` is the public backend URL, so a project that points it at a public host needs `mcp.backendUrl`.
- The credential never leaves the machine. When neither URL is loopback, the DMS writes no credential, no launcher, no `.mcp.json` entry and no `.codex/config.toml` entry, and logs one warning that names `mcp.backendUrl`. The bridge also refuses to send a request to a host that is not loopback, and answers an error that names `mcp.backendUrl`.
- The route answers only a caller on the backend's machine that came straight to it, holding the credential of this start. It refuses a request that carries a header a proxy adds: `X-Forwarded-For`, `Forwarded`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP`, `Via`, `True-Client-IP` or `CF-Connecting-IP`. The DMS frontend server adds `X-Forwarded-For` and `Forwarded` to every request it relays.
- The route reads up to 1 MiB per message and answers `413` past it.

When the backend is down, a call answers an error that says to start it with `ajs project dev`. The next call after the start works.

| `mockup_annotations`, `mockup_read_spec` | `read` |
| `mockup_write_spec`, `mockup_patch_spec`, `mockup_resolve_annotation`, `mockup_from_page`, `mockup_apply_to_page` | `builder` |

A `read` tool changes nothing in the project. A `builder` tool edits pages, resources, queries and the theme through the builder, which typechecks each edit before it writes it. A `project` tool changes the project past its sources: `antelope.config.ts`, what the dashboard may write to an external database, or the data of a deleted resource's table.

Some tools differ from the dashboard chat:

- `navigate_to_page` resolves a registered page and moves the open dashboard tab of each browser to it: the tab that holds the browser's realtime connection. It answers the page's dashboard URL, `<clientBaseUrl><path>`, and how many browsers moved, or the closest known routes when the path is not a page.
- `preview_blocks` renders nothing. It checks the block tree against the block types the DMS registers and the preview's limits, then answers what it checked. It refuses a sketch the mockup compiler refuses, by the same allowlist (see [Sketch check](/docs/ai-and-claude-code/sketch-check)).
- `page_verify` opens pages in a headless Chromium and answers a JSON report, so an agent proves a page works, not only that it builds. See [Verifying a page](#verifying-a-page).
- `typecheck` runs `tsc --noEmit` in the project root by default, or in a loaded module named by `target`.
- `builder_analyse_database` answers compactly, because a full proposal of a large database does not fit an AI client's context: per relation its screen, rows, and columns with types, relations and where each is used, then the relations excluded and the open questions. Its `detail` input names relations (`"schema.name"`) to answer in full, with each choice's rule and each column's profile.
- `mockup_from_page` turns an existing page into a [mockup](/docs/ai-and-claude-code/live-page-mockups#edit-a-live-page-as-a-mockup). The dashboard has no button for it: ask the AI. It answers an error unless the backend runs in development, where `/mockup` exists. Its spec page records the page in `livePage`: building the mockup updates that page and never creates another. With `into`, it converts the page into that existing mockup instead, at its real place among the mockup's pages; see [Convert a page into an existing mockup](/docs/ai-and-claude-code/live-page-mockups#convert-a-page-into-an-existing-mockup).
- `mockup_apply_to_page` builds such a spec page back into its live page in one write. See [Build it back into the page](/docs/ai-and-claude-code/live-page-mockups#build-it-back-into-the-page). It answers an error unless the backend runs in development.
- The `database_*` tools read every catalog connection the project declares for the DMS, each through its own provider. Pass a connection id from `database_connections` to the others. `database_project` answers what a `builder_configure_project` batch that connects a database needs, as `GetDatabaseProject` does: the module ids to write, the modules to pin, and the driver package and range of each engine the project can start. A driver answers its catalog in development only, so on a backend run with `ajs project start`, `database_connections` lists the connection with an `error` until the driver's entry sets `config.catalog.enabled`.

## Column presentation

A resource field's `@Column` takes the presentation a mockup column declares, so a mockup table is built with `builder` tools alone, in Safe mode too. `builder_add_field`, `builder_configure_field`, `builder_create_resource` and the `fields` of `builder_map_resources` take:

| Input | Written as |
| --- | --- |
| `display: { type, options? }` | `display: new DefaultDisplays.<Class>(options)`, with its import. `type` is a cell display the DMS draws: `identity`, `pills`, `relative_date`, `indicator`, `status_pill`, `two_line`, `progress`, `sparkline`, `duration`, `bytes`, `string` or `mono`. |
| `group` | `group`, the id of the form group the field joins. |
| `isVisible`, `size`, `cellWrap`, `description` | The `@Column` options of the same names. |

The builder checks a display's `options` against its class, with the schema the mockup compiler uses, and refuses an option the class does not take or a value of the wrong type with `invalid_config`, naming the option: `the two_line display refuses its options: options.subField: Expected string, received number`. `builder_map_resources` skips the relation instead and says why in a `relation_skipped` warning. `builder_configure_field` replaces an option sent and removes one sent as `null`. A relation mapped again keeps the presentation its controller holds for a field that leaves it out. On a mapped column, `display` is either a badge or a price, or a cell display drawn over a column written without either.

`builder_configure_column_groups { resource, groups }` writes the class's `@ColumnGroup(id, { label, description?, orientation?, order? })` decorators: a group sent replaces the one of its id, `null` removes it, and a group left out stays.

`builder_resource_structure` reads every option back on each field, and the groups as `columnGroups`.

## What the tools show of a connected database

The tools answer the shape of a connected database, never a value from its rows. See [Connected database values](/docs/ai-and-claude-code/connected-database-values).

## Sidebar sections

The sidebar groups pages two ways. A section is a header at the top of the sidebar, such as the built-in **Pages**, listing its pages under it. A category folds its pages away under one entry inside a section. A mockup's `categories` are sections.

- `builder_create_category` makes a category under its `parent`, **Pages** (ref `pages`) by default, and answers its ref, `pages.<name>`. With `section: true` it makes a section instead: a `RootCategory` beside **Pages**, whose ref is its name. A section takes no `parent`, and `pages`, `modules` and `settings` name built-in ones. Its `order` places it among **Pages** (1), **Modules** (2) and **Settings** (3).
- `builder_configure_category` with `section: true` turns a category directly under **Pages** into a section, and `section: false` turns a section back into a category under **Pages**. The pages in it keep their routes. Its ref changes, and the answer gives the new one. A category nested deeper is refused, since its routes would change.
- Pages go in a section as in a category: pass its ref as `builder_create_page`'s `category`, or a resource's `category` in `builder_map_resources`.
- `builder_list_pages` answers `{ pages, categories }`. Each category carries its ref, parent, title, icon and order, and a section also carries `section: true`. Each page, and the page of `builder_page_structure`, carries `section`: the ref of the section it shows under.
- `mockup_from_page` lists a page's section, other than **Pages**, as a category of the mockup and files the page under it. With `into`, it reuses the mockup's category of that section, by id or title, and places the page among the section's converted pages in the app's menu order.

## Mapping a database into menu sections

`builder_map_resources` writes one TableView page per relation, in the connection's category (`pages.<connection>`) unless the resource names another. Group the pages into sections by making the category first with `builder_create_category`, in the same `module` the tables are mapped into, then sending its id on each resource. Make it with `section: true` for a section of its own at the top of the sidebar, whose id is its name, such as `sales`:

```json
{
  "module": "shop-tables",
  "connection": "shop",
  "resources": [
    {
      "relation": "public.orders",
      "category": "pages.sales",
      "tableView": true,
      "writable": false,
      "fields": [{ "column": "reference" }, { "column": "total" }]
    }
  ]
}
```

- A new page is written inside the category. An id that is not a category, or a category another module declares, refuses that relation, naming it and the category, and writes none of its files. A module loads only its own sources, so a category made without the tables module's `module` cannot hold its pages.
- A relation mapped again updates its page where it is. The builder finds the page by the table it holds, the TableView named `table` bound to the relation's controller, not by its default route `pages.<connection>/<id>`, so a page moved into a category with `builder_configure_page` is updated in place and no second copy appears outside the section.
- With `category` on the remap, the page moves there, and its route changes: the builder answers a `route_changed` warning, and nothing redirects the old route.
- A remap keeps what the mapping does not set on the page: the icon, description, order and title when left out. A `title` that is sent wins, for the page's title and the table's caption alike. A new page with no `title`, or a blank one, takes the relation's name, humanized.
- A relation that loses its TableView (`tableView: false`) has its page removed wherever it was moved, after the repeat described below.

## Verifying a page

`page_verify` takes a `page` (a route as `list_pages` answers it, a concrete one for a route with parameters, or a page full id), or a list of up to ten. It signs the browser in through the same session handoff a password change uses, as the platform owner or, with `role`, as a member holding only that role. Each page is drawn at `desktop` (1440×900) and `mobile` (390×844) unless `viewports` names others.

The report holds, for each page:

- `failures`: one line per failed check. Read these first.
- `render`: each block the layout serves, present and drawn inside the page width, sideways scrolling and overlapping blocks, all read from the page's DOM.
- `data`: the state each table, chart and KPI reports: `ok`, `empty`, `error`, `loading`, or `needs_backend` in a preview. A table open on its board reports the board's cards: `loading` until its columns answer, then `ok` when it shows a card.
- `errors`: console errors, uncaught exceptions and failed requests of the browser. A request the dashboard makes while rendering on the server shows as the block's `error` state, not here.
- `interactions`: links answer, tabs select, and sorting and searching refetch or change the page. Each form on the page, and each one a `New`, `Add`, `Create` or `Edit` button opens, is submitted: it passes when it shows validation, or when it sends its write, on submit or on change. A form with no enabled submit control is first given a value in a text field. A form whose save no text field triggers is reported `not checked`.
- `permissions`: for each role of the workspace, whether its grants open the page, and what the browser saw signed in as a member holding only that role. A role that no member holds alone is `not_checked`.

With `mockup`, the page is compared with a page of `mockups/<name>/spec.json` drawn by the `/mockup` viewer: each mockup block is paired with the page block at the same layout path or drawing the same component. The viewer is owner-only, so it opens signed in as the platform owner, whatever `role` the page is checked as.

Every write the page tries while it is checked is held back, unless `submit` is `true`: then a form whose empty submit showed validation is filled with sample values and submitted, and its write goes through.

`page_verify` takes no screenshot, of the page or of the mockup. A screenshot would show the values of the page's rows, and a mockup block can read a live route, so the AI client could read them from the image. The first call downloads the headless Chromium `playwright-core` pins into Playwright's own cache, about 330 MB, once per machine; the backend log says so. `playwright-core` is an optional dependency of `@antelopejs/dms`, loaded only when the tool runs.

## Calls that wait for a repeat

An MCP client has no confirmation card. These calls answer what they would do and run nothing the first time:

- a deletion: `builder_delete_page`, `builder_delete_category`, `builder_delete_resource`, `builder_remove_field` and `builder_remove_query`;
- `builder_configure_project`, with the changes its dry run plans;
- `builder_set_connection_access`, with the change to `antelope.config.ts` it plans;
- `builder_map_resources`, when its preview finds a page to remove.

Show the answer to the person you work for. The same call, repeated unchanged within 10 minutes by the same MCP session, runs once. Each process the client starts from `.mcp.json` is one session, so another session's identical call waits again. A mapping whose pages to remove changed in between is a new call and waits again.

A client that asks the person itself tells the answer apart by its last text block, which is the JSON `{"code":"confirmation_required"}`. The prose before it can change wording, and the code does not. A call refused because its client sent no session carries no code, since repeating it never runs it. A confirmed call that then fails ends with `{"code":"confirmation_consumed"}` after the builder's error: the confirmation is spent, so the next identical call waits again. A call that fails before the gate, such as a refused preview, carries no code and holds nothing. Keep the `mcp__dms__builder_*` tools out of your client's allow list too, so the client asks before the repeat.

## Writes to an external database

An external database is read-only to the tools until the project allows changes to it. The access of each connection sits on the `dms-database` entry of `antelope.config.ts`, the one the Data browser of the Database module edits:

```ts fragment [antelope.config.ts]
"dms-database": {
  config: {
    externalConnections: {
      erp: { access: "read-write" },
    },
  },
},
```

`"read"` is the default when the entry is absent. Before each of these calls, the builder loads the project configuration with core's own `ConfigLoader` for the environment the project launched with, so it reads what `dms-database` receives: the entry, that environment's member of `environments`, `antelope.dms-database.json` and `envOverrides`, merged in core's order. A configuration that cannot be loaded counts as `"read"`, and the refusal says why. On a connection that does not resolve to `"read-write"`, these calls answer an error that names the connection, the place that keeps it read-only and how to allow changes, and write nothing:

- `builder_map_resources` with a `writable: true` resource that has a TableView, which would serve create, edit and delete routes on the table;
- `builder_add_block`, `builder_compose_page` and `builder_configure_block` for a `ResourceForm` in `new` or `edit` mode over a table mapped from that connection;
- `builder_add_block` and `builder_compose_page` for a `TableView` over a table mapped from that connection that still serves write routes. Map it again with `writable: false` first.

Mapping with `writable: false`, a `ResourceForm` in `view` mode and every `read` tool keep working. The builder reads the access on every call, so a change applies without a restart.

### What the agent sees of the access

`builder_analyse_database` and `builder_mapping` answer `access` beside `data`: what the configuration lets the dashboard do on the connection when the call runs, `"read"` or `"read-write"`, read the same way as the checks above. Each resource in their answer carries `writes`, what the database account may `insert`, `update` and `delete` in that relation, and the proposal's `database.writes` sums it up as `none`, `some` or `all`. On a `"read"` connection an agent proposes no add, edit or delete action and maps every relation `writable: false`.

```json
{ "ok": true, "data": [{ "ref": "erp/sales/orders", "resource": { "relation": "sales.orders", "writes": { "insert": true, "update": true, "delete": false } } }], "changes": [], "access": "read" }
```

### Allow writes once the person agrees

`builder_set_connection_access` changes a connection's access. Call it only after the person agreed in the conversation, since it changes what the dashboard can write to their database:

```json
{ "connection": "erp", "access": "read-write" }
```

It writes `config.externalConnections.<connection>.access` on the `dms-database` entry of `antelope.config.ts` with the same `ConfigureModule` step the Read & write switch of the Database module's Data browser sends. Its first call writes nothing and answers the planned change, as the other [calls that wait for a repeat](#calls-that-wait-for-a-repeat) do. The repeat writes it and answers `access`, what the configuration now gives the connection. The builder reads it on its next call, so `builder_map_resources` with `writable: true` works at once. The running backend applies it to the write routes once it restarts, which `ajs project dev` does on its own when `antelope.config.ts` changes.

It answers an error and writes nothing in these cases:

| Case | `error.code` | `error.detail` |
| --- | --- | --- |
| No catalog connection has that id | `not_found` | `no catalog connection "<id>" is declared: read database_connections for the ids the project declares` |
| The project has no `dms-database` module | `invalid_config` | ``the project has no dms-database module, whose `config.externalConnections` holds a connection's access: add it, then try again`` |
| `read-write` while the account may insert, update or delete rows in no relation | `invalid_config` | `refused to allow changes on connection "<id>": its database account may not insert, update or delete rows in any table, so the dashboard could change nothing. Ask the person to grant the account write privileges on the tables the dashboard should change, then try again.` |
| `read-write` while the catalog does not answer | `invalid_config` | `refused to allow changes on connection "<id>": the builder could not check what its database account may write, since its catalog answered: <reason>. Check that the database is reachable, then try again.` |

`"read"` is never checked, so lowering an access always works. A relation the account may not write stays read-only after the access is `"read-write"`: `builder_map_resources` maps it `writable: false` with a `relation_read_only` warning.

### Configuration steps never raise an access

`builder_configure_project` never raises an access. It refuses a step that sets `config.externalConnections.<id>.access` to `"read-write"` where the module's entry in `antelope.config.ts` does not already hold the literal `"read-write"` (an expression, a variable, a template or an environment that grants it does not count, since the step writes the entry every environment reads), to anything else but `"read"`, supplies it from a variable, or rebinds a variable `envOverrides` maps to it, whatever `mcp.access` is. The refusal names `builder_set_connection_access`. Keeping, lowering or removing an access works, so a step may restate the connections it does not change. A person also grants writes with the Read & write switch of the Database module's Data browser, or in the assistant's connect step: the `dms-database` route `PUT /api/database/connections/<id>/access` and the assistant's `POST /database/project` write through the builder interface, which leaves the access as asked.

### Connecting a database

A `builder_configure_project` batch that connects a database registers the connection with `dms-database` as `{ access: "read" }`. Before it runs, the agent asks the person whether the dashboard may only read that database or also change its rows. On read & write, it calls `builder_set_connection_access` once the restarted project lists the connection in `database_connections`, since the account's write privileges can be checked only then.

An agent never writes a database address either. A database connection runs only on a URL the person typed or confirmed, so `builder_configure_project` refuses a step that writes any value where a database driver's config takes a server or an account. A module is a driver when its id, a step's `source` or its entry in `antelope.config.ts` names a driver package, directly or through a local folder's `package.json`. A module whose entry or source the builder cannot read, or whose source is of another type such as `git`, counts as any driver. Members match whatever their case.

| Driver | Refused under `config` |
| --- | --- |
| `@antelopejs/postgres` | `url`, and `pool.connectionString`, which pg reads before the URL |
| `@antelopejs/mysql` | `url`, and `pool.host`, `pool.port`, `pool.socketPath`, `pool.user`, `pool.password`, `pool.password1` to `pool.password3` and `pool.passwordSha1`, which mysql2 reads before the URL |
| `@antelopejs/mongodb` | `url`, and under `options` the credentials (`auth`, `authMechanism`, `authMechanismProperties`, `authSource`), the client certificate (`tlsCertificateKeyFile`, `tlsCertificateKeyFilePassword`, `cert`, `key`, `pfx`, `passphrase`), the proxy (`proxyHost`, `proxyPort`, `proxyUsername`, `proxyPassword`), `srvServiceName` and `autoEncryption` |
| `@antelopejs/rethinkdb` | `url`, and `server`, `host`, `port`, `user` and `password` under `pool` and `connection`, plus `pool.servers` |

The refusal names the field to use instead: `env: { url: "<VARIABLE>" }`, which maps the variable that holds the URL. The person sets its value in the project's `.env` or in the assistant's connect step.

An agent never builds a block that sends the person's writes outside the page's own data API either: see [Requests a built block sends](/docs/ai-and-claude-code/block-requests).

## Safe mode

Safe mode is a tool scope, set with `mcp.access`. With `access: "safe"`, the server lists and runs only the `read` and `builder` tools: `tools/list` leaves out `builder_configure_project`, `builder_set_connection_access` and `builder_delete_resource`, and a call to any of them answers an error. The server enforces it, whatever the client's own permission settings allow. The default is `"full"`, which serves every tool.

A client can also ask for Safe mode for its own session, by launching the bridge with `--access=safe`:

```sh
node node_modules/.cache/dms/mcp-bridge.cjs --access=safe
```

The bridge sends the access it was started with on every message, in the `mcp-client-access` header. The session gets the stricter of that access and `mcp.access`: a bridge started with `--access=safe` gets Safe mode on a `"full"` project, and `--access=full` on a `"safe"` project still gets Safe mode. A client can narrow its access, never widen it. A bridge started without `--access`, or with a value other than `safe` or `full`, gets `mcp.access`.

## Configuration

| Key | Type | Default | Purpose |
| --- | --- | --- | --- |
| `mcp.enabled` | `boolean` | The runtime's development mode | Serves the route and writes the bridge files. `true` serves them in any mode. `false` turns them off in development too. |
| `mcp.access` | `"safe" \| "full"` | `"full"` | The tools a session may list and call. A bridge started with `--access=safe` narrows its own session to Safe mode. |
| `mcp.mcpJson` | `boolean` | `true` | Adds the `dms` server to `.mcp.json` when the entry is missing. `false` leaves the file alone. |
| `mcp.codexConfig` | `boolean` | `true` | Adds the `dms` server to `.codex/config.toml` when none is declared. `false` leaves the file alone. |
| `mcp.backendUrl` | `string` | `apiBaseUrl`, only when its host is loopback | The origin the bridge sends its requests and its credential to. Set it to `${@api.API_LOCAL_BASE_URL}`. A host that is not loopback is refused. |

Point the bridge at the backend on your machine:

```ts fragment [antelope.config.ts]
dms: {
  config: {
    mcp: { backendUrl: "${@api.API_LOCAL_BASE_URL}" },
  },
},
```

The other keys go beside it:

```ts fragment [antelope.config.ts]
dms: {
  config: {
    mcp: {
      backendUrl: "${@api.API_LOCAL_BASE_URL}",
      access: "safe",
      mcpJson: false,
      codexConfig: false,
    },
  },
},
```

A `mcp` value the DMS cannot read, such as `access: "Safe"`, turns the server off and logs why. The DMS reads the key once, at module construction, so restart the backend after you change it. To stop the DMS from writing `.mcp.json`, set `mcpJson: false` and delete the `dms` entry. While `mcpJson` is on, a deleted entry comes back on the next start. `codexConfig` does the same for `.codex/config.toml`.
