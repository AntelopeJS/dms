title: "Overview of mockups"
description: What an AntelopeJS DMS mockup is, how an agent drafts one, how you review it, and how it becomes real pages.
mode: explanation
---

A mockup is a draft of one or more DMS pages, written as a JSON file in your project. The dashboard draws it with the real DMS blocks over sample data, so what you review is what the DMS can build. An agent writes the mockup, you comment on it, and the agent builds the pages once you agree.

## A mockup goes from draft to built pages

::steps{level="3"}
### The agent drafts it

Ask the DMS AI assistant, or your coding agent with the `antelopejs` plugin, to mock up an app or a screen. The `antelopejs:dms-mockup` skill asks what the app is for, matches each need to a DMS block, and writes `mockups/<name>/spec.json` through the `mockup_write_spec` and `mockup_patch_spec` tools. A part no block can draw becomes a sketch, labelled **Custom**.

### You review it in the viewer

Open **Mockups** from the dashboard's header to see every mockup as a card. A mockup opens on its Overview, with every page side by side and arrows for the links between them. Click through the pages, edit blocks in place, and pin comments where you want changes. See [Viewer](/docs/ai-and-claude-code/mockups/viewer) and [Comments and review](/docs/ai-and-claude-code/mockups/comments).

### The agent applies your comments

**Resolve with AI** hands every open comment to the agent. It patches the spec and resolves each comment. Every write is a new version in **History**, so you can go back.

### The agent builds the pages

**Build it** asks the agent to build the real pages. The `antelopejs:dms-mockup-build` skill writes each page as TypeScript in your project, wires real data in place of the samples, and checks each page against the mockup with the `page_verify` tool. The card then reads **Built**, with a link to each page.
::

## A mockup draws only what the DMS can draw

The viewer renders each page with the same block renderer as the dashboard, from the block types registered when the spec is read. A block an installed module registers works like a built-in one. Options a block refuses, and links to pages the spec lacks, show as issues on the mockup. The build step therefore starts from blocks that exist, not from a picture to translate.

Sample data lives in the spec as fixtures. A fixture can also be generated, so the spec states a table's columns and not its rows. A page converted from a live page can switch between its samples and the real routes of your app. See [Nodes](/docs/ai-and-claude-code/mockups/nodes) and [Controller blocks](/docs/ai-and-claude-code/mockups/controller-blocks).

## Existing pages can become mockups

To change a page that already exists, ask the agent to turn it into a mockup. It calls `mockup_from_page`, which writes the page's blocks into a spec. After your review, `mockup_apply_to_page` writes the changes back into that page instead of creating a new one. See [Live page mockups](/docs/ai-and-claude-code/mockups/live-pages).

## Mockups are a development tool for the platform owner

- The DMS serves mockups only when the runtime runs in development mode, as under `ajs project dev` or `ajs project run`.
- Only the platform owner can open the Mockups page, edit a mockup and build it. A role holding the **Review mockups** permission opens the viewer read-only to comment: see [Let a client review](/docs/ai-and-claude-code/mockups/comments#let-a-client-review).
- Mockups are files in your project. The spec and its comments live in `mockups/<name>/`, which you can commit. The version history lives in `.antelope/mockup-history/<name>/`, which stays out of git when `.antelope` is in your `.gitignore`.
