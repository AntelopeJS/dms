The [MCP server](/docs/ai-and-claude-code/mcp-server) tools read the shape of a database the project connects to, map it into pages, and write to it only with the access the project grants.

## What the tools show of a connected database

The tools answer the shape of a connected database, never a value from its rows. See [Connected database values](/docs/ai-and-claude-code/connected-database-values).

## Mapping a database into menu sections

`builder_map_resources` writes one TableView page per relation, in the connection's category (`pages.<connection>`) unless the resource names another. Group the pages into sections by making the category first with `builder_create_category`, in the same `module` the tables are mapped into, then sending its id on each resource. Make it with `section: true` for a section of its own at the top of the sidebar, whose id is its name, such as `sales`:

```json
{
  "module": "shop-tables",
  "connection": "shop",
  "resources": [
    {
      "relation": "public.orders",
      "category": "pages.sales",
      "tableView": true,
      "writable": false,
      "fields": [{ "column": "reference" }, { "column": "total" }]
    }
  ]
}
```

- A new page is written inside the category. An id that is not a category, or a category another module declares, refuses that relation, naming it and the category, and writes none of its files. A module loads only its own sources, so a category made without the tables module's `module` cannot hold its pages.
- A relation mapped again updates its page where it is. The builder finds the page by the table it holds, the TableView named `table` bound to the relation's controller, not by its default route `pages.<connection>/<id>`, so a page moved into a category with `builder_configure_page` is updated in place and no second copy appears outside the section.
- With `category` on the remap, the page moves there, and its route changes: the builder answers a `route_changed` warning, and nothing redirects the old route.
- A remap keeps what the mapping does not set on the page: the icon, description, order and title when left out. A `title` that is sent wins, for the page's title and the table's caption alike. A new page with no `title`, or a blank one, takes the relation's name, humanized.
- A relation that loses its TableView (`tableView: false`) has its page removed wherever it was moved, after the repeat described below.

## Writes to an external database

An external database is read-only to the tools until the project allows changes to it. The access of each connection sits on the `dms-database` entry of `antelope.config.ts`, the one the Data browser of the Database module edits:

```ts fragment [antelope.config.ts]
"dms-database": {
  config: {
    externalConnections: {
      erp: { access: "read-write" },
    },
  },
},
```

`"read"` is the default when the entry is absent. Before each of these calls, the builder loads the project configuration with core's own `ConfigLoader` for the environment the project launched with, so it reads what `dms-database` receives: the entry, that environment's member of `environments`, `antelope.dms-database.json` and `envOverrides`, merged in core's order. A configuration that cannot be loaded counts as `"read"`, and the refusal says why. On a connection that does not resolve to `"read-write"`, these calls answer an error that names the connection, the place that keeps it read-only and how to allow changes, and write nothing:

- `builder_map_resources` with a `writable: true` resource that has a TableView, which would serve create, edit and delete routes on the table;
- `builder_add_block`, `builder_compose_page` and `builder_configure_block` for a `ResourceForm` in `new` or `edit` mode over a table mapped from that connection;
- `builder_add_block` and `builder_compose_page` for a `TableView` over a table mapped from that connection that still serves write routes. Map it again with `writable: false` first.

Mapping with `writable: false`, a `ResourceForm` in `view` mode and every `read` tool keep working. The builder reads the access on every call, so a change applies without a restart.

### What the agent sees of the access

`builder_analyse_database` and `builder_mapping` answer `access` beside `data`: what the configuration lets the dashboard do on the connection when the call runs, `"read"` or `"read-write"`, read the same way as the checks above. Each resource in their answer carries `writes`, what the database account may `insert`, `update` and `delete` in that relation, and the proposal's `database.writes` sums it up as `none`, `some` or `all`. On a `"read"` connection an agent proposes no add, edit or delete action and maps every relation `writable: false`.

```json
{ "ok": true, "data": [{ "ref": "erp/sales/orders", "resource": { "relation": "sales.orders", "writes": { "insert": true, "update": true, "delete": false } } }], "changes": [], "access": "read" }
```

### Allow writes once the person agrees

`builder_set_connection_access` changes a connection's access. Call it only after the person agreed in the conversation, since it changes what the dashboard can write to their database:

```json
{ "connection": "erp", "access": "read-write" }
```

It writes `config.externalConnections.<connection>.access` on the `dms-database` entry of `antelope.config.ts` with the same `ConfigureModule` step the Read & write switch of the Database module's Data browser sends. Its first call writes nothing and answers the planned change, as the other [calls that wait for a repeat](/docs/ai-and-claude-code/mcp-server#calls-that-wait-for-a-repeat) do. The repeat writes it and answers `access`, what the configuration now gives the connection. The builder reads it on its next call, so `builder_map_resources` with `writable: true` works at once. The running backend applies it to the write routes once it restarts, which `ajs project dev` does on its own when `antelope.config.ts` changes.

It answers an error and writes nothing in these cases:

| Case | `error.code` | `error.detail` |
| --- | --- | --- |
| No catalog connection has that id | `not_found` | `no catalog connection "<id>" is declared: read database_connections for the ids the project declares` |
| The project has no `dms-database` module | `invalid_config` | ``the project has no dms-database module, whose `config.externalConnections` holds a connection's access: add it, then try again`` |
| `read-write` while the account may insert, update or delete rows in no relation | `invalid_config` | `refused to allow changes on connection "<id>": its database account may not insert, update or delete rows in any table, so the dashboard could change nothing. Ask the person to grant the account write privileges on the tables the dashboard should change, then try again.` |
| `read-write` while the catalog does not answer | `invalid_config` | `refused to allow changes on connection "<id>": the builder could not check what its database account may write, since its catalog answered: <reason>. Check that the database is reachable, then try again.` |

`"read"` is never checked, so lowering an access always works. A relation the account may not write stays read-only after the access is `"read-write"`: `builder_map_resources` maps it `writable: false` with a `relation_read_only` warning.

### Configuration steps never raise an access

`builder_configure_project` never raises an access. It refuses a step that sets `config.externalConnections.<id>.access` to `"read-write"` where the module's entry in `antelope.config.ts` does not already hold the literal `"read-write"` (an expression, a variable, a template or an environment that grants it does not count, since the step writes the entry every environment reads), to anything else but `"read"`, supplies it from a variable, or rebinds a variable `envOverrides` maps to it, whatever `mcp.access` is. The refusal names `builder_set_connection_access`. Keeping, lowering or removing an access works, so a step may restate the connections it does not change. A person also grants writes with the Read & write switch of the Database module's Data browser, or in the assistant's connect step: the `dms-database` route `PUT /api/database/connections/<id>/access` and the assistant's `POST /database/project` write through the builder interface, which leaves the access as asked.

### Connecting a database

A `builder_configure_project` batch that connects a database registers the connection with `dms-database` as `{ access: "read" }`. Before it runs, the agent asks the person whether the dashboard may only read that database or also change its rows. On read & write, it calls `builder_set_connection_access` once the restarted project lists the connection in `database_connections`, since the account's write privileges can be checked only then.

An agent never writes a database address either. A database connection runs only on a URL the person typed or confirmed, so `builder_configure_project` refuses a step that writes any value where a database driver's config takes a server or an account. A module is a driver when its id, a step's `source` or its entry in `antelope.config.ts` names a driver package, directly or through a local folder's `package.json`. A module whose entry or source the builder cannot read, or whose source is of another type such as `git`, counts as any driver. Members match whatever their case.

| Driver | Refused under `config` |
| --- | --- |
| `@antelopejs/postgres` | `url`, and `pool.connectionString`, which pg reads before the URL |
| `@antelopejs/mysql` | `url`, and `pool.host`, `pool.port`, `pool.socketPath`, `pool.user`, `pool.password`, `pool.password1` to `pool.password3` and `pool.passwordSha1`, which mysql2 reads before the URL |
| `@antelopejs/mongodb` | `url`, and under `options` the credentials (`auth`, `authMechanism`, `authMechanismProperties`, `authSource`), the client certificate (`tlsCertificateKeyFile`, `tlsCertificateKeyFilePassword`, `cert`, `key`, `pfx`, `passphrase`), the proxy (`proxyHost`, `proxyPort`, `proxyUsername`, `proxyPassword`), `srvServiceName` and `autoEncryption` |
| `@antelopejs/rethinkdb` | `url`, and `server`, `host`, `port`, `user` and `password` under `pool` and `connection`, plus `pool.servers` |

The refusal names the field to use instead: `env: { url: "<VARIABLE>" }`, which maps the variable that holds the URL. The person sets its value in the project's `.env` or in the assistant's connect step.

An agent never builds a block that sends the person's writes outside the page's own data API either: see [Requests a built block sends](/docs/ai-and-claude-code/block-requests).
