A mockup is a JSON file that describes one or more DMS pages. The backend compiles it against the block types registered now, and `/mockup` draws each page with `DmsBlockPreview`, the renderer of the [block preview page](/docs/ai-and-claude-code/block-preview-page). A save shows in the open viewer in under a second, with no typecheck and no page reload. Because the mockup draws real blocks, it shows only what the DMS can draw.

## Availability

The DMS serves mockups only when the AntelopeJS runtime runs in development mode (`GetRuntimeInfo().dev`). `ajs project dev` and `ajs project run` start it in that mode. Neither `docsPreview: true` nor `DMS_DOCS_PREVIEW=1` turns mockups on.

The routes and the viewer serve the platform owner only. Every route answers `401` to a request with no session and `403` to any other signed-in user, the same answer as the Branding editor's routes. The viewer is owner-only. The Roles editor does not list it, and a role that holds its permission still cannot open it. The routes read and write the files of the project the backend runs in. The [MCP mockup tools](/docs/ai-and-claude-code/mcp-server) read those files directly, not through these routes.

## File layout

```text
<project root>/
  mockups/
    <name>/
      spec.json          the spec you write
      annotations.json   written by the DMS when a reviewer pins a comment
  .antelope/
    mockup-history/
      <name>/
        <n>.json         one version of the spec, written by the DMS: see Version history
```

The project root is the working directory of the backend process. `<name>` matches `^[a-z0-9][a-z0-9-]{0,63}$`. The DMS ignores a directory whose name does not match, and a directory without `spec.json`.

`@antelopejs/dms` ships two files under `node_modules/@antelopejs/dms/data/`:

- `mockup-spec.schema.json`, the JSON Schema of `spec.json` over the built-in block types.
- `mockup-example/spec.json`, a two-page example that compiles with no issue, and that `GET /api/mockup/example` answers.

## Spec

```json [mockups/order-desk/spec.json]
{
  "$schema": "../../node_modules/@antelopejs/dms/data/mockup-spec.schema.json",
  "version": 1,
  "title": "Order desk",
  "categories": [{ "id": "sales", "title": "Sales", "icon": "i-ph-storefront" }],
  "pages": [
    {
      "id": "orders",
      "title": "Orders",
      "category": "sales",
      "icon": "i-ph-shopping-cart",
      "description": "Every order, newest first",
      "headerActions": [{ "label": "New order", "icon": "i-ph-plus", "color": "primary" }],
      "options": { "theme": "light", "locale": "en", "padding": true },
      "fixtures": { "orders": [{ "_id": "o1", "customer": "Acme", "total": 120 }] },
      "tree": [{ "type": "KpiCard", "options": { "title": "Revenue", "staticValue": 48210 } }]
    }
  ]
}
```

| Field | Meaning |
| ----- | ------- |
| `$schema` | Optional. Points an editor at the JSON Schema. |
| `version` | Always `1`. |
| `title` | Optional. The title of the mockup. |
| `source` | Optional. Who wrote the mockup: `chat`, `claude-code` or `codex`. |
| `built` | Optional. Written by the build: `{ at, pages }`. Without it, the mockup is a draft. |
| `built.at` | When the build finished, an ISO 8601 date and time. |
| `built.pages` | 1 to 50 `{ path, title? }`. `path` starts with one `/`, not `//` or `/\`, and holds no whitespace or control character, 2048 characters at most. The path stands in for a missing title. |
| `data` | Optional. Where the mockup's data comes from: `{ connection, access? }`. See [Connection access](#connection-access). |
| `data.connection` | The external connection the app reads, by its id in `config.externalConnections` of the dms-database module, such as `crm`. |
| `data.access` | `read` or `read-write`, as `config.externalConnections.<id>.access` of dms-database: what the project lets the DMS do on the connection. Defaults to `read`, as in dms-database. |
| `categories` | Optional. The sections of the sidebar, as the categories of the dashboard's menu (`RootCategory`) group its pages, in the menu's order: up to 50 `{ id, title, icon? }`. `id` matches `^[a-z0-9][a-z0-9-]{0,63}$` and is unique among the categories; `icon` is an icon name such as `i-ph-storefront`. |
| `sidebar` | Optional. What the mockup adds to the dashboard's sidebar, in every page: `{ widgets }`. See [Sidebar widgets](#sidebar-widgets). |
| `pages` | 0 to 50 pages. An empty list creates the mockup first: add its pages later, such as with `mockup_patch_spec`. The whole file nests at most 100 levels of objects and arrays. |
| `pages[].id` | Matches `^[a-z0-9][a-z0-9-]{0,63}$`. Unique in the spec. |
| `pages[].title` | The title of the page: the display name of the live page, drawn as the title of its page header. |
| `pages[].category` | Optional. The `id` of the category the page is listed under. A page without one is in the default **Pages** section. An id no category has is an issue at the page's `category`. |
| `pages[].menu` | Optional. `false` leaves the page out of the sidebar, as a detail or form page the dashboard opens from another page. The viewer still lists it, marked hidden. Defaults to `true`. |
| `pages[].parent` | Optional. The `id` of the page this one is a sub-page of, such as a list's detail page. See [Sub-pages](#sub-pages). An id no page has, or parents that lead back to the page, is an issue at its `parent`. |
| `pages[].route` | Optional. A route parameter, `:` and a name such as `:id`: the page shows one row of its parent's rows. It needs a `parent`, else it is an issue at the page's `route`. |
| `pages[].icon` | Optional. The icon of the page (`icon` of the page's options), drawn in the badge of its page header and beside its entry in the viewer's sidebar, such as `i-ph-shopping-cart`. When it is absent, the header draws `i-ph-file`, and the sidebar a house for the first page and a file for the others. |
| `pages[].description` | Optional. The description of the page (`description` of the page's options), drawn under the title in its page header. |
| `pages[].headerActions` | Optional. The buttons right of the page header's title, in order: `{ label, icon?, color?, variant? }`. `color` is one of the dashboard's tones (`neutral`, `primary`, `secondary`, `success`, `warning`, `error`, `info`) and `variant` one of `solid`, `outline`, `soft`, `ghost` and `link`, as the `headerActions` of `DefaultLayout` take them. A button is outlined while its color is `neutral` or absent, and solid in any other color, as in the dashboard. What a button does (its `target`, its confirmation, its permission) is code: a mockup holds none, and the build step wires it. |
| `pages[].options.theme` | `light` or `dark`. |
| `pages[].options.locale` | A locale the dashboard knows, such as `fr-FR`. |
| `pages[].options.padding` | Pads the blocks off the edges of the frame. Defaults to `true`. |
| `pages[].fixtures` | Data the blocks of the page read. Each key matches `^[A-Za-z0-9_-]{1,64}$` and holds any JSON value, or a [`$generate`](#generated-fixtures) value the server turns into rows. |
| `pages[].livePage` | Set on a page converted from a live page, or by the build on each page it built: `{ ref, version }`, the page's builder ref and the version of its source file at the conversion or build. See [Edit a live page as a mockup](/docs/ai-and-claude-code/live-page-mockups). |
| `pages[].liveRoutes` | The live route of each fixture key, such as `{"sales":"/api/sales"}`: a `built.pages` path, where spaces may pad a token. See [Live routes](#live-routes). |
| `pages[].tree` | The blocks of the page, top to bottom. Absent or empty on a custom page. |
| `pages[].custom` | Optional. `true` draws the page as one sketch: see [Custom pages](#custom-pages). |
| `pages[].html`, `css`, `height`, `states` | A custom page's sketch. On any other page, each is an issue at its field. |

The envelope is strict: a key it does not list is an issue.

### Connection access

A mockup of an app over a client's database says which connection it reads, and the access the project gives the DMS on it:

```json
{
  "version": 1,
  "title": "CRM desk",
  "data": { "connection": "crm", "access": "read" },
  "pages": []
}
```

With `"access": "read"`, every option that writes rows is an issue at its pointer, as the builder refuses it on a read-only connection, and a write of the spec is refused like any other issue:

| Block | Option refused | Message |
| ----- | -------------- | ------- |
| `TableView` | `rowActions.add`, `edit`, `duplicate`, `delete`, `archive` or `restore` turned on (`true`, or a config not `isEnabled: false`) | `rowActions.edit writes rows, and the connection "crm" is read-only (data.access is "read"): leave it out, as a table over it only lists rows and opens their details` |
| `TableView` | `archiveMode: true` | `archiveMode writes rows, and the connection "crm" is read-only (data.access is "read"): leave it out, as a table over it only lists rows and opens their details` |
| `TableView` | `kanban.draggable: true` | `kanban.draggable writes rows, and the connection "crm" is read-only (data.access is "read"): leave it out, so the board's cards stay where they are` |
| `ResourceForm` | a `mode` other than `view` | `mode "edit" writes rows, and the connection "crm" is read-only (data.access is "read"): set mode to "view", so the form shows the row read-only` |

`rowActions.details`, an action written `false`, and a `ResourceForm` in `view` mode are allowed. With `"access": "read-write"`, or no `data`, nothing is restricted. A `data` without `access` reads `read`, as dms-database does.

## Nodes

A node is the tree format of `DmsBlockPreview`:

| Field | Meaning |
| ----- | ------- |
| `type` | A registered block type, such as `KpiCard`, or `sketch`. It wins over `componentName`. |
| `componentName` | The component a registered block type emits, such as `dms-kpi-card`. |
| `options` | The options the block's component receives. |
| `children` | The nested nodes. A container lists the block types it takes in `allowedChildren` (a `Grid` takes only `GridRow`); a block that is no container takes only the children its block options name, such as a `ChartCard`'s `chart`. |
| `id` | The id of a child under its parent, unique among its siblings. |
| `slot` | The slot of the parent the child renders in. |
| `colSpan` | The columns a child spans in a grid. |

For every block that takes no controller class, the options a component receives are its factory's options, with two exceptions:

- An option that holds a block, such as the `chart` of a `ChartCard`, is a child whose `id` is the option's name.
- A `Form` section either holds its own `fields`, as the `Form` factory takes them, or lists fields of `fields` by id in `fieldIds`, as the component receives them. The compiler hands the component the second shape: each section's own fields move after the form's `fields`, in order.

The compiler validates a block's options with `ValidateBlockOptions` against the block types registered when the spec is read. A block that an installed module registers is accepted like a built-in one. `GET /api/mockup/schema` describes the same set.

### Fixtures

A string option of the form `fixture:<key>`, at any depth, names a key of the page's `fixtures`. The compiler replaces it with `/api/mockup/<name>/pages/<page>/fixtures/<key>`, the route that answers that value.

```json
{
  "type": "ChartCard",
  "options": { "title": "Revenue", "fetchUrl": "fixture:revenue", "valueFormat": "currency", "currencyCode": "EUR" },
  "children": [{ "id": "chart", "type": "ChartArea", "options": { "xaxisType": "datetime" } }]
}
```

A key that the page does not hold is an issue at the option's pointer. The compiler still replaces the reference, and the block shows the error that a missing route gives it.

### Page links

A string option of the form `page:<id>`, at any depth of a block's options, links to the spec page of that id. A sketch links to a page with `<a href="page:<id>">`: see [Links to pages](#links-to-pages). It works wherever a block takes a URL or a route: a card's or a list item's `to`, a button's or a row action's `target.url`, a tab's `to`, a form's `backTo` or `redirectOnSuccess`. The compiler replaces it with `/mockup?name=<name>&page=<id>`, the viewer's URL of that page, and lists the page in the compiled page's `links`. A page the spec lacks is an issue at the option's pointer.

```json
{
  "type": "NavCardGrid",
  "options": {
    "items": [{ "title": "Orders", "icon": "i-ph-shopping-cart", "to": "page:orders" }]
  }
}
```

A link to a page with a [route](#sub-pages) passes it a row:

- From a `TableView`'s `rowActions`, the link passes the row's id, read at the table's `rowIdKey` (`_id` by default): `&record={{row._id}}`, which the table fills.
- From a page with a route to one of its own sub-pages with a route, the viewer opens the sub-page on the same row, as a detail page's link to its own edit page.
- Any other link passes none, and the page shows its sample row.

```json
{
  "type": "TableView",
  "options": {
    "fetchUrl": "fixture:orders",
    "columns": { "customer": { "type": "string" }, "total": { "type": "number" } },
    "rowClick": "single",
    "rowActions": {
      "custom": [
        { "label": "Open", "icon": "i-ph-arrow-right", "isDefault": true, "target": { "type": "page", "url": "page:order" } }
      ]
    }
  }
}
```

The build replaces each `page:<id>` with the route of the page it builds from that spec page, `/orders/{{row._id}}` for a row's link to a detail page.

### Sub-pages

A page with a `parent` is a sub-page of it, such as the detail page of a list, or the page of a custom form. Its blocks read the fixtures of its ancestors that it does not hold itself: a `fixture:<key>` option it lacks reads the nearest ancestor holding `key`.

A sub-page with a `route` shows one row of its ancestors' rows. On it, a `fixture:<key>` option naming an ancestor's array of rows reads one row: `/api/mockup/<name>/pages/<ancestor>/fixtures/<key>/record?id={{params.id}}`, the row whose `_id`, else `id`, is the route parameter. The viewer fills `{{params.id}}` with the row a link passed, else with the sample row, the first row of the first ancestor's rows the page reads. The compiled page carries it as `route.sample`.

```json
{
  "id": "order",
  "title": "Order",
  "menu": false,
  "parent": "orders",
  "route": ":id",
  "tree": [
    {
      "type": "ResourceForm",
      "options": {
        "mode": "view",
        "fetchUrl": "fixture:orders",
        "fields": [
          { "id": "customer", "label": "Customer", "type": "string" },
          { "id": "total", "label": "Total", "type": "number" }
        ]
      }
    }
  ]
}
```

The build registers a sub-page under its parent's route, `route` as its slug's parameter (`orders/:id`), and leaves a page with `menu: false` out of the menu.

### Generated fixtures

A fixture whose value is `{ "$generate": { "rows"?, "fields" } }` holds rows the server makes up, so a spec states a table's columns and not its data. Everything that reads a fixture sees the generated array: the fixture route, the rows route, a `TableView`, a `fixture:<key>` option and the fixture side of a page with `liveRoutes`.

```json
{
  "fixtures": {
    "customers": {
      "$generate": {
        "rows": 40,
        "fields": {
          "_id": "id",
          "name": "name",
          "email": "email",
          "company": "company",
          "city": "city",
          "since": "date",
          "active": "boolean",
          "orders": { "number": [0, 60] },
          "spent": { "money": [50, 9000] },
          "tier": ["free", "pro", "enterprise"]
        }
      }
    }
  }
}
```

| Part | Meaning |
| ---- | ------- |
| `rows` | How many rows, a whole number from 1 to 200. Defaults to 8. |
| `fields` | Required, at least one. Each key is a row field, written in the row in the order of `fields`. Each value is a kind. |

A kind is one of:

| Kind | Value |
| ---- | ----- |
| `"id"` | A unique text id: `r1`, `r2`, and on. Name the field `_id` for a table's `rowIdKey`. |
| `"name"` | A person's first and last name. |
| `"email"` | The email of the row's person, so a row with a `name` and an `email` agrees. |
| `"company"` | A company name. |
| `"city"` | A city. |
| `"text"` | A short sentence of business words. |
| `"date"` | An ISO 8601 date and time in the last 30 days, counted back from the start of today (UTC), so a view such as "This week" or a chart of the period has rows. |
| `"boolean"` | `true` or `false`. |
| `{ "number": [min, max] }` | A number from `min` to `max`: a whole number when both bounds are whole, otherwise rounded to two decimals. |
| `{ "money": [min, max] }` | An amount from `min` to `max`, to the cent. |
| `["a", "b"]` | One value of the non-empty array of strings for each row. |

The rows are the same on every read of the spec: a value comes from the mockup name, the page id, the fixture key, its field and its row alone, so adding or removing a field changes no other field, and the same fixture on another page differs. Only a `date` also reads the clock: it counts back from the start of today, so a day's reads agree and the next day moves every date of the fixture forward by a day. A date written in the spec, in a hand-written fixture or in a `$generate` of your own, stays as written. Nothing else is configurable. The `$generate` object is the whole fixture value; no other key sits beside it. A bad `$generate` is an issue at its own pointer, such as `/pages/0/fixtures/customers/$generate/fields/spent`, and the spec is refused as any envelope error is. A fixture that is no `$generate` value is served as written, and a `$generate` row never changes a hand-written fixture.

### Live routes

`liveRoutes` maps a fixture key to the route of the live app that answers the same data. A page that has it is compiled twice: once on its fixtures, as `tree`, and once with each key it maps read from its route instead, as `realTree`. A table's `fixture:<key>` then reads the route as is, without the `/rows` suffix, so the route must answer `{ results, total }` as a list route does. The viewer's **Real data** switch picks one of the two trees. The issues come from the fixture side only.

```json
{
  "id": "sales",
  "title": "Sales",
  "liveRoutes": { "api-sales": "/api/sales" },
  "fixtures": { "api-sales": null },
  "tree": [{ "id": "sales", "type": "ChartCard", "options": { "title": "Sales", "fetchUrl": "fixture:api-sales" } }]
}
```

With Real data off, the preview calls no live route. A `fixture:<key>` reads its fixture. Any other string in an option the preview requests or loads (a `*Url`, `url` or `location` option, an image `src`, an `*Endpoint`), at any depth and in any block, is replaced with a fixture route that answers an error, so the block shows its error state. The same option keeps its route in `realTree`.

The viewer and the mockup thumbnails also load the preview as `/dms-preview?fixtures=only`, which puts a Content Security Policy on its document: images, media and requests reach the mockup's routes, the dashboard's own (its realtime session, icons and system state) and its assets only. A fixture value that a cell turns into a request, such as an `image` cell holding a URL or a `file` cell holding a file key, is refused by the browser and never reaches the server. Switching Real data on loads the preview again without the policy.

### Controller blocks

`TableView` and `ResourceForm` take a controller class in code. A mockup builds them from fixtures:

- `TableView` takes the options of `TableView.fromSource`. `fetchUrl` is `fixture:<key>` and names an array of row objects. `columns` is keyed by row field, and each column takes `type`, a data type id such as `string`, `number`, `date`, `boolean` or `select`, and optionally `name`, `description`, `order`, `isVisible`, `filterable`, `sortable`, `cellWrap`, `size`, a [`display`](#column-displays) and a [`group`](#form-sections-and-groups). The compiler builds the table with the real `TableView.fromSource`, reading its rows from `/api/mockup/<name>/pages/<page>/fixtures/<key>/rows`. A table needs a `caption`, the title the real table shows above its rows: without one the real `TableView` moves its status tabs into the header and draws the views strip under them. A table with no caption, or a blank one, is an issue at its `options/caption` that reads `a table needs a caption: …`, listed in the viewer and refused on a write like any other issue, so the assistant adds it. A page linked to a live page (`livePage`) is left out, as its tables mirror that page's own.
- `ResourceForm` takes a serialized form: its `fields`, and a `fetchUrl` of the form `fixture:<key>` that names the record object. It has no `submitUrl`. The compiler validates it as a `Form`. Its `mode` is `new`, `edit` or `view`, as the real `ResourceForm` takes it: in `view` mode every field is drawn disabled, so the form shows the row read-only, as the real details view does.

`TableView.fromSource` builds a read-only table, with every built-in action off, archive and restore included. The compiler adds the forms a spec turns on, and archive mode, after it builds the table: see [Add, edit and details forms](#add-edit-and-details-forms) and [Archive mode](#archive-mode).

A table's `capabilities` default to `search`, `sort`, `paginate` and `filter`, all on. A table that writes its own `capabilities` keeps them as written: `TableView.fromSource` refuses tabs, quick filters and `queryParamFilters` unless that object sets `filter: true`. The rows route applies every parameter a source table sends. It reads each filter, `filter_<column>=<mode>:<value>`, with the compare modes of a data controller (`is`, `is_not`, `include`, `exclude`, `contains`, `not_contains`, `greater_than`, `less_than`, `greater_than_or_equal_to`, `less_than_or_equal_to`, `is_between`, `is_empty`, `is_not_empty`, `array_contains_string`), so tabs, quick filters, views, a `queryParamFilters` entry and a column's filter narrow the fixture's rows, and a row passes every filter, several on one column included. `is`, `is_not`, `include` and `exclude` take a comma-separated list, `is_between` its two bounds, a number or an ISO date each, and a list cell matches when one of its entries does. A filter of another mode keeps every row. `/rows/list` answers the same as `/rows`: it is where a kanban board reads its columns. Another block type that takes a controller class is an issue, and the preview draws it as a block that needs a backend.

#### Add, edit and details forms

A mockup table is read-only unless its spec writes `rowActions.add`, `rowActions.edit` or `rowActions.details`, each `true` or a row action config such as `{ "rule": { "field": "status", "equals": "draft" } }`. An action left out is off, though the real `TableView` reads an absent one as on. `formContainer` says where each form opens, as in the real `TableView`, whose types are `modal`, `drawer` and `page`:

- `{ "type": "modal", "size"?, "pages"? }`, the default, or `{ "type": "drawer", "direction"?, "pages"? }`. A drawer slides in from the bottom, or from the right with `"direction": "right"`, as the real `TableView` draws it. The add, edit and details forms are built by the real `Form` factory over the table's columns, the `rowIdKey` column left out, as the real `TableView` builds them over its controller. The edit and details forms read their row from `/api/mockup/<name>/pages/<page>/fixtures/<key>/record`. The add and edit forms save to `/api/mockup/<name>/pages/<page>/fixtures/<key>/rows` with the form's default `PUT`, which answers the row and keeps nothing: the form says it saved and closes, and the table's rows do not change. The details form saves nowhere and draws every field disabled: it shows the row read-only, the table's default details view. `pages.new`, `pages.edit` and `pages.details` give the forms' titles, `{ displayName?, description? }`.
- `{ "type": "page" }`. Each form turned on opens on a page of its own, as the real `TableView` does, in one of two ways:
  - **A generated page**, the default, for a long record or a long or sectioned form. Leave the form's `pages` entry out, or give it a `displayName` and a `description` alone. The real `TableView` registers a hidden sub-page of the table's page for it, holding the generated form, and the mockup draws that page: the same generated form over the table's columns as a modal draws, grouped by `@ColumnGroup`, read-only on the details page. The page has a Cancel back to the table, and saving closes it and goes back to the table without keeping the row, as a modal does. A `urlSlug` that is not `page:<id>` is the real table's URL for the page, which a mockup does not route: it is ignored. Write no spec page for it.
  - **A custom page**, which the module registers itself, for a form or a detail view no generated form draws. `pages.new`, `pages.edit` and `pages.details` each take `{ "urlSlug": "page:<id>", "customPage": true }`, and name a spec page. The edit and details pages show one row, so they need a `route`: the table passes them the row's id. A `customPage: true` without a `page:<id>` `urlSlug`, a `page:<id>` `urlSlug` without `customPage: true`, or an edit or details page without a route is an issue at its pointer.

  The two mix: each form of a table takes its own.

```json
{
  "type": "TableView",
  "options": {
    "fetchUrl": "fixture:orders",
    "columns": { "customer": { "name": "Customer", "type": "string" }, "total": { "name": "Total", "type": "number" } },
    "rowActions": { "add": true, "edit": true },
    "formContainer": { "type": "drawer", "direction": "right" }
  }
}
```

```json
{
  "pages": [
    {
      "id": "orders",
      "title": "Orders",
      "fixtures": { "orders": [{ "_id": "o1", "customer": "Acme", "total": 120 }] },
      "tree": [
        {
          "type": "TableView",
          "options": {
            "fetchUrl": "fixture:orders",
            "columns": { "customer": { "type": "string" }, "total": { "type": "number" } },
            "rowActions": { "add": true, "edit": true, "details": true },
            "formContainer": {
              "type": "page",
              "pages": {
                "new": { "urlSlug": "page:order-new", "customPage": true },
                "edit": { "urlSlug": "page:order-edit", "customPage": true },
                "details": { "urlSlug": "page:order", "customPage": true }
              }
            }
          }
        }
      ]
    },
    { "id": "order-new", "title": "New order", "menu": false, "parent": "orders", "tree": [] },
    { "id": "order-edit", "title": "Edit order", "menu": false, "parent": "orders", "route": ":id", "tree": [] },
    { "id": "order", "title": "Order", "menu": false, "parent": "orders", "route": ":id", "tree": [] }
  ]
}
```

The compiled table carries `formPages`, the viewer's URL of each page, `:id` standing for the row's id. The build replaces each `page:<id>` `urlSlug` with the slug of the page it builds, relative to the table's page (`new`, `:id/edit`, `:id`), keeps `customPage: true`, and wires the add and edit forms to the table's data controller.

A table whose forms open on generated pages needs no page beyond its own:

```json
{
  "type": "TableView",
  "options": {
    "fetchUrl": "fixture:orders",
    "columns": { "customer": { "type": "string" }, "total": { "type": "number" } },
    "rowActions": { "add": true, "edit": true, "details": true },
    "formContainer": {
      "type": "page",
      "pages": { "new": { "displayName": "New order", "description": "Take an order." } }
    }
  }
}
```

The compiler adds one page to the state for each generated form page, after the spec's pages: a sub-page of the table's page, out of the sidebar, titled by `pages.<kind>.displayName` and `description` or else "New entry", "Edit entry" and "Entry details", with the generated form as its tree. Its id is the table's page, the path of the table's node and the form (`orders.tree-0.edit`), so a page with several tables has pages for each, and it holds a `.` where no spec page id does. The edit and details pages are on the route `:id`, and show the first row of the table's fixture while no link names one. The compiled page carries `generated: true`: it has no spec page, so the viewer lets nothing on it be edited or commented, the Overview lays out the spec's pages alone and draws none of them, and the table's page lists none of them in its `links`, so no arrow reaches them.

Prefer the default details view, in a modal or a drawer, which needs no page of its own:

```json
{
  "type": "TableView",
  "options": {
    "caption": "Orders",
    "fetchUrl": "fixture:orders",
    "columns": { "customer": { "name": "Customer", "type": "string" }, "total": { "name": "Total", "type": "number" } },
    "rowActions": { "details": true },
    "formContainer": { "type": "drawer" }
  }
}
```

A details page earns its place only when it adds something to the row's fields, such as KPIs or related lists. On it, a `ResourceForm` shows the row read-only, so it is in `mode: "view"`; on an edit page, a `ResourceForm` changes the row, so it is not in `view` mode:

```json
{
  "id": "order",
  "title": "Order",
  "menu": false,
  "parent": "orders",
  "route": ":id",
  "tree": [
    { "type": "ResourceForm", "options": { "mode": "view", "fetchUrl": "fixture:orders", "fields": [{ "id": "customer", "label": "Customer", "type": "string" }] } }
  ]
}
```

A `ResourceForm` in the wrong mode is an issue at its `options/mode`, whether `mode` is written or not:

| Page | Mode refused | Message |
| ---- | ------------ | ------- |
| A table's `details` page | any but `view` | `this page is the details page of the table at <pointer>: set mode to "view", so the form is drawn read-only, as the table's own details are` |
| A table's `edit` page | `view` | `this page is the edit page of the table at <pointer>: set mode to "edit", so its fields can be changed` |

`<pointer>` is the spec pointer of the table whose `formContainer.pages` names the page.

#### Form sections and groups

A table's generated add, edit and details forms group their fields as the real `TableView` groups them from `@Column({ group })` and `@ColumnGroup(id, config)`. A column's `group` names its group, and the table's `columnGroups` gives each group its `{ label, description?, orientation?, order? }`, keyed by that id. A group's fields are gathered where its first column stands, and a group `columnGroups` does not declare is titled by its id. The real generated forms have no sections, so a table has none either.

```json
{
  "type": "TableView",
  "options": {
    "caption": "Customers",
    "fetchUrl": "fixture:customers",
    "columns": {
      "name": { "name": "Name", "type": "string", "order": 1 },
      "email": { "name": "Email", "type": "string", "order": 2, "group": "contact" },
      "phone": { "name": "Phone", "type": "string", "order": 3, "group": "contact" }
    },
    "columnGroups": { "contact": { "label": "Contact", "description": "How to reach them", "orientation": "horizontal" } },
    "rowActions": { "add": true, "edit": true, "details": true }
  }
}
```

A `ResourceForm` or a `Form` takes the real `Form`'s sections and groups. `sections` lists `{ id, label, description?, icon?, navGroup?, fields }`: each is a titled card holding its own fields and groups, a group being `{ id, label?, description?, orientation?, order?, fields }`. `sectionNav` says how the form lists its sections: `side` beside them, `jump` as chips above them, or `none`. A `ResourceForm` in `view` mode draws every field of every section and group disabled, so a details page shows its row read-only, card by card:

```json
{
  "type": "ResourceForm",
  "options": {
    "mode": "view",
    "fetchUrl": "fixture:customers",
    "sectionNav": "jump",
    "sections": [
      {
        "id": "general",
        "label": "General",
        "icon": "i-ph-identification-card",
        "fields": [
          { "id": "name", "label": "Name", "type": "string" },
          {
            "id": "contact",
            "label": "Contact",
            "fields": [
              { "id": "email", "label": "Email", "type": "string" },
              { "id": "phone", "label": "Phone", "type": "string" }
            ]
          }
        ]
      },
      { "id": "notes", "label": "Notes", "fields": [{ "id": "notes", "label": "Notes", "type": "string" }] }
    ]
  }
}
```

#### Archive mode

`"archiveMode": true` draws the table as the real `TableView` draws one in archive mode, `@ArchiveField` on its controller:

- a **Show archived** toggle above the rows, which lists the rows not archived, then the archived ones;
- **Archive** in the row menu of a row not archived, **Restore** in that of an archived one;
- **Edit**, when `rowActions.edit` is on, only on the rows not archived.

A row is archived when its `isArchived` field is `true`, the member `@ArchiveField` decorates in the DMS docs and playground. A fixture whose rows have no `isArchived` gets one made up: the last quarter of its rows, at least one and never all, are archived. `archivedCountLabel` is the caption's count while the archived rows show, `{count}` standing for their number.

Archive and restore are on in archive mode. `rowActions.archive` or `rowActions.restore` set to `false` turns one off, and a config object keeps its own rule beside the archive one. The rows route lists one side of the toggle, `showArchived=true` or `false`, and `/rows/archive` and `/rows/restore` answer that every row went and keep nothing, so the rows do not change.

```json
{
  "type": "TableView",
  "options": {
    "caption": "Orders",
    "fetchUrl": "fixture:orders",
    "columns": { "customer": { "name": "Customer", "type": "string" }, "total": { "name": "Total", "type": "number" } },
    "archiveMode": true,
    "archivedCountLabel": "{count} archived orders",
    "rowActions": { "edit": true },
    "formContainer": { "type": "drawer" }
  }
}
```

A table without `archiveMode` that turns `rowActions.archive` or `rowActions.restore` on is an issue at that action, `archive and restore need archiveMode: set "archiveMode": true`. The table is drawn without them, as the real `TableView` offers them only in archive mode.

#### Column displays

A column's `display` draws its cells in one of two shapes. The first is the display the builder proposes for a mapped column (`builder_analyse_database`) and writes from `fields[].display` (`builder_map_resources`), so a proposal goes into a spec as it is:

| `kind` | Column `type` | Meaning |
| ------ | ------------- | ------- |
| `badge` | `string` or `select` | `items` lists the column's values, each `{ value, label, tone }`, `tone` one of the dashboard's tones (`neutral`, `primary`, `secondary`, `success`, `warning`, `error`, `info`). The column becomes a `select` of those items, drawn as pills in their tone, and filtered by a list of them. |
| `price` | `number` or `price` | `currency` is optional, an ISO 4217 code such as `EUR`. The column becomes a `price` drawn as an amount. |

```json
{
  "status": {
    "type": "string",
    "filterable": true,
    "display": {
      "kind": "badge",
      "items": [
        { "value": "paid", "label": "Paid", "tone": "success" },
        { "value": "pending", "label": "Pending", "tone": "warning" },
        { "value": "refunded", "label": "Refunded", "tone": "error" }
      ]
    }
  },
  "total": { "type": "number", "display": { "kind": "price", "currency": "EUR" } }
}
```

A `select` column carries its values with their tones the same way: `{ "type": "select", "display": { "kind": "badge", "items": [...] } }`. The compiler checks a badge or a price as the builder does: a badge needs at least one item, each value once, each with a label and a tone of the dashboard, and a price an ISO 4217 code. A badge on a `date` column, say, is an issue at the column's `display`.

The second is a cell display of the TableView, `{ type, options? }`, as `display: new DefaultDisplays.IdentityDisplay(options)` serializes it in code. `type` is one of the DMS's own cell displays, `identity`, `pills`, `relative_date`, `indicator`, `status_pill`, `two_line`, `progress`, `sparkline`, `duration`, `bytes`, `string` and `mono`, and `options` the options of its class: an identity cell's avatar and secondary line, a two-line cell's `subField`, a status pill's `tones`.

```json
{
  "customer": {
    "type": "string",
    "display": { "type": "identity", "options": { "avatarField": "avatar", "subtitleField": "email" } }
  }
}
```

The column keeps its `type` for its filter. Another cell display id is an issue that lists the ones the DMS draws.

#### Board, groups, tabs and views

A mockup table also takes the options of the real `TableView` that `TableView.fromSource` lacks, in the shape `TableView` takes them, and `tabsFrom`, the builder's tabs:

| Option | Meaning |
| ------ | ------- |
| `kanban` | `{ groupByField, draggable?, columnMaxHeight? }`: the kanban board, a column of cards per value of `groupByField`, a column whose type is `select` (a badge), `boolean` or `status`. The board reads `/rows/list` with a filter per column. A card does not move: the board is drawn with `draggable` off, whatever the spec says. |
| `grouped` | `{ groupByField, by?, collapsible?, count? }`: the grid with a header row per group. `groupByField` is `sortable`; `by` is `value`, `day` or `week`, and `day` and `week` need a `date` column. |
| `tabsFrom` | `{ column }`: tabs read from a badge column, as the builder writes them from `tabs` of `builder_map_resources`: "All", then one tab per item of the badge, in its order and its tone, filtering on its value. The column is `filterable` and has a badge `display`. It writes the tabs, so it leaves `tabs` out. |
| `views` | `{ items, layout?, defaultView?, userViews? }`: the saved views. A view is `{ id, label, icon?, tone?, dot?, count?, filters?, search?, sort?, columns?, display?, density? }`, a filter `{ accessorKey, mode, value? }` on a `filterable` column, a sort `{ field, desc? }` on a `sortable` one, `display` a display the table offers. View ids are unique, and `defaultView` is one of them. A view holds no permission: that is code. |

A tab of `tabs` takes the keys of a `TableView` tab alone: `id`, `label`, `filter`, `icon`, `textColor`, `iconColor`, `to`, `permission`, `permissionId`, `countFrom` and `navBadge`. Another key is an issue at that key, where `TableView` would drop it: a `color` reads that `textColor` colours the tab's label and `iconColor` its icon.

The kanban board and the grouped display join `displays` as `TableView` serializes them, so `defaultDisplay`, `mobileDisplay` and a view's `display` may name them. A tab, a view and the board narrow the fixture's rows through the rows route's filters, and count them with it.

```json
{
  "type": "TableView",
  "options": {
    "fetchUrl": "fixture:orders",
    "labelKey": "customer",
    "columns": {
      "customer": { "type": "string", "sortable": true },
      "status": {
        "type": "string",
        "filterable": true,
        "sortable": true,
        "display": {
          "kind": "badge",
          "items": [
            { "value": "paid", "label": "Paid", "tone": "success" },
            { "value": "pending", "label": "Pending", "tone": "warning" }
          ]
        }
      },
      "total": { "type": "number", "sortable": true, "display": { "kind": "price", "currency": "EUR" } }
    },
    "tabsFrom": { "column": "status" },
    "kanban": { "groupByField": "status" },
    "grouped": { "groupByField": "status", "count": true },
    "views": {
      "items": [{ "id": "large", "label": "Large orders", "sort": [{ "field": "total", "desc": true }] }],
      "layout": "strip"
    }
  }
}
```

The builder's `tableOptions` of `builder_map_resources` hold the same settings under its own names: `kanban.groupBy`, `grouped.groupBy`, and a view filter's `column` and a sort's `column`, which a spec writes `groupByField`, `accessorKey` and `field`, as the page's `TableView` takes them.

### Sketches

A sketch draws static HTML and CSS of a part that no DMS block draws. The viewer renders it in a sandboxed `<iframe>` with the CSP `default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:` and a `<base href="about:srcdoc">`, so an `#anchor` scrolls inside the frame, and labels it **Custom**. The frame's `sandbox` is empty: no script runs, the frame has no origin, and it opens no form, popup or window. A sketch that [links to a page](#links-to-pages) gets `allow-top-navigation-by-user-activation` alone, never `allow-scripts` or `allow-same-origin`.

```json
{
  "type": "sketch",
  "options": {
    "html": "<ol class=\"steps\"><li>Ordered</li><li>Packed</li></ol>",
    "css": ".steps{display:flex;gap:12px}",
    "height": 160,
    "caption": "Delivery journey"
  }
}
```

| Option | Meaning |
| ------ | ------- |
| `html` | The markup, up to 524,288 characters. Required. |
| `css` | The style sheet, up to 524,288 characters. |
| `height` | The frame height in pixels, from 80 to 3,000. Defaults to 320. |
| `caption` | Up to 200 characters. |
| `states` | Named states drawn in place of `html`: see [Named states](#named-states). |

A sketch has no children. The compiler checks it as the frame will read it, and emits only the markup it checked; [Sketch check](/docs/ai-and-claude-code/sketch-check) lists what it refuses. A refused sketch is emitted with an empty `html` and no `css`, and each refusal is an issue. No JavaScript runs in a sketch: a `<script>`, an `on*` handler or a `javascript:` URL refuses it.

#### Links to pages

An `<a href="page:<id>">` in a sketch's `html` links to the spec page of that id, as a block's [page link](#page-links) does.

```json
{
  "type": "sketch",
  "options": {
    "html": "<p>3 orders wait.</p><a class=\"cta\" href=\"page:orders\">See the orders</a>",
    "css": ".cta{color:var(--sketch-accent)}"
  }
}
```

The compiler writes the link as `<a href="/mockup?name=<name>&page=<id>" target="_top" …>` and lists the page in the compiled page's `links`, so the Overview draws its arrow. When the sketch is on a page with a route and links to a sub-page of that page with a route too, as a detail page's link to its own edit page, the URL also passes the row on screen, `&record={{params.<param>}}`, which the preview fills. The preview draws the URL on the dashboard's origin, since the frame's `<base>` is `about:srcdoc`.

- A page the spec lacks is an issue at the sketch's `html`, and the link still opens the viewer, on its first page.
- Only an HTML `<a>` takes a page link. Any other `href` is refused as before: a site, a path, a viewer URL written by hand, a `page:` link whose id is not a page id, or a page link on an SVG `<a>`. So is a `target` the sketch writes itself.
- A click on the link in [Preview](#follow-a-link-and-preview) loads the viewer URL in the browser window: the viewer reloads on that page, and Preview, the frame width and the Real data switch start over.
- While editing, the frame's document takes no click, so a click on the sketch selects it, `Ctrl` + click (`⌘` + click) included: open Preview to follow a sketch's link. The sandbox runs no script that could tell the viewer which link is under the pointer.

The build replaces each `page:<id>` of a sketch with the route of the page it builds from that spec page, as it does for a block's link.

#### Named states

A sketch's `states` holds other markups of the same part, such as its empty, error or loading state, beside its default `html`:

```json
{
  "type": "sketch",
  "options": {
    "html": "<ol class=\"steps\"><li>Ordered</li><li>Packed</li></ol>",
    "css": ".steps{display:flex;gap:12px}",
    "states": {
      "empty": "<p>No delivery yet. <a href=\"page:orders\">Pick an order</a></p>",
      "error": "<p role=\"alert\">The carrier did not answer.</p>"
    }
  }
}
```

- A state's name is a lowercase letter, then lowercase letters, digits and `-`, 32 characters at most, and not `default`, which is the `html` itself. A sketch holds 8 states at most.
- Each state's markup is checked as `html` is, its page links included, and holds 524,288 characters at most. It is drawn with the sketch's `css`, `height` and `caption`. A refused state is emitted empty, with an issue at `/states/<name>`, and the other states still draw.
- The compiled sketch carries `states`, each name with its checked markup.

The inspector of a selected sketch with states shows a **State** picker: **Default**, then each name. The preview draws the state picked in place of the `html`. The pick lives in the viewer for as long as it is open, per page and per sketch, and never changes the spec. A comment pinned on the sketch while a state is drawn keeps that state as its `state`, and its card reads `On the <name> state`; see [Mockup annotations](/docs/ai-and-claude-code/mockup-annotations). The Overview and the thumbnails draw each sketch's `html`.

The build draws every state of a sketch in the custom component it makes: the default where the data is there, and each state where the page meets it.

### Custom pages

A page with `custom: true` is one whole-page sketch, drawn inside the real layout: the top bar, the sidebar and the page header stay the dashboard's own, fed by the page's `title`, `icon`, `description` and `headerActions`, and the sketch takes the place of the blocks. Use it for a page no block arrangement draws, such as a kanban of a custom shape or a landing page.

```json
{
  "id": "board",
  "title": "Board",
  "icon": "i-ph-kanban",
  "custom": true,
  "html": "<div class=\"lanes\"><section><h2>To do</h2><a href=\"page:card\">Fix the invoice</a></section></div>",
  "css": ".lanes{display:grid;grid-template-columns:repeat(3,1fr);gap:16px}",
  "height": 1200,
  "states": { "empty": "<p>No card yet.</p>" }
}
```

| Field | Meaning |
| ----- | ------- |
| `custom` | `true`. `false` or absent is a page of blocks. |
| `html` | Required. The page's markup, checked as a [sketch's](#sketches), [page links](#links-to-pages) included. |
| `css` | Optional. Its style sheet. |
| `height` | Optional. The frame height in pixels, from 80 to 3,000. Defaults to 800. |
| `states` | Optional. Its [named states](#named-states). |
| `tree` | Absent or `[]`. A block in it is an issue at `/pages/<i>/tree`. |

Each field is checked at the page's own pointer, such as `/pages/2/html` or `/pages/2/states/empty`. A custom page without `html` is an issue at its `html`, and an `html`, `css`, `height` or `states` on a page of blocks is an issue at that field.

The compiled page carries `custom: true`, and its `tree` is that one sketch, labelled **Custom** like any sketch. It has no spec node, so its `paths` are empty: a click on it while editing selects nothing and shows the page's inspector, which holds the **State** picker of a custom page with states, and a comment on it is a comment on the page, which keeps the state drawn. The catalog's blocks cannot be dropped on a custom page: the write is refused, as its `tree` holds no block.

The build does not copy the sketch. A custom page is built as a tree of DMS blocks, like every page, and a `CustomComponent` appears only for a part no block can draw, each with its `.meta()`. The mockup draws the whole page as one sketch only as a picture of the page: the sketch's links route to the pages the build makes, and each state is built where the page meets it.

### Sidebar widgets

`sidebar.widgets` sketches a widget of the dashboard's sidebar, such as a plan card or a help box, that no module provides yet. Each widget is a sketch drawn in the sidebar's widget area, below the dashboard's own widgets and above the menu, in every page of the mockup, in the viewer, in Preview and on the mockup's card.

```json
{
  "version": 1,
  "sidebar": {
    "widgets": [
      {
        "id": "plan",
        "title": "Your plan",
        "html": "<div class=\"plan\"><strong>Pro</strong><span>3 of 10 seats left</span></div>",
        "css": ".plan{display:flex;flex-direction:column;gap:4px;padding:10px;border-radius:var(--sketch-radius);background:var(--sketch-surface);color:var(--sketch-text)}",
        "height": 96
      },
      { "id": "help", "html": "<p>Need help? Write to support.</p>" }
    ]
  },
  "pages": []
}
```

| Field | Meaning |
| ----- | ------- |
| `widgets` | Up to 10 widgets, drawn in order. Required in `sidebar`. |
| `widgets[].id` | Matches `^[a-z0-9][a-z0-9-]{0,63}$`. Unique among the widgets: a second one is an issue at its `id`. |
| `widgets[].title` | Optional. The caption over the widget, up to 200 characters. |
| `widgets[].html` | The markup, up to 524,288 characters, under the [sketch](#sketches) rules. Required. |
| `widgets[].css` | Optional. The style sheet, up to 524,288 characters, under the sketch rules. |
| `widgets[].height` | Optional. The frame height in pixels, from 80 to 1,200. Defaults to 120. |

A widget is checked and drawn as a sketch is: the same check, the same sandboxed frame and the same **Custom** label. A refused widget is drawn empty, and each refusal is an issue at its `html` or `css`. The sidebar folded to its rail draws no widget. A widget is not a block: it cannot be selected, commented or edited in the viewer, so change it in `spec.json`.

## Compiled state

`GET /api/mockup/<name>` and the `state` event answer a `MockupState`:

```ts
interface PreviewNode {
  type?: string;
  componentName?: string;
  options?: Record<string, unknown>;
  children?: PreviewNode[];
  id?: string;
  slot?: string;
  colSpan?: number;
}

interface MockupState {
  name: string;
  title?: string;
  revision: number;
  categories?: Array<{ id: string; title: string; icon?: string }>;
  sidebar?: {
    widgets: Array<{ id: string; title?: string; html: string; css?: string; height: number }>;
  };
  pages: Array<{
    id: string;
    title: string;
    category?: string;
    menu?: false;
    custom?: true;
    parent?: string;
    route?: { param: string; sample?: string };
    links: string[];
    icon?: string;
    description?: string;
    headerActions?: Array<{ label: string; icon?: string; color?: string; variant?: string }>;
    options: { theme?: "light" | "dark"; locale?: string; padding?: boolean };
    tree: PreviewNode[];
    realTree?: PreviewNode[];
    livePage?: { ref: string };
    paths: Record<string, string>;
  }>;
  issues: Array<{ path: string; message: string }>;
}
```

| Field | Meaning |
| ----- | ------- |
| `revision` | Increases by one each time the backend reads `spec.json`. |
| `tree` | The page's nodes with fixture references replaced, controller blocks built and sketches checked. |
| `realTree` | `tree` with each key of `liveRoutes` read from its live route. Present only when the page has `liveRoutes`. Its layout paths are `tree`'s. |
| `categories` | The spec's categories, in order. Absent when the spec has none. |
| `sidebar` | The spec's sidebar widgets, in order, each checked as a sketch, `height` set to its default when the spec gives none. Absent when the spec has no widget. |
| `category`, `icon`, `description`, `headerActions`, `parent` | The spec page's fields of the same name, as written. |
| `menu` | `false` when the spec page sets it; absent otherwise. |
| `custom` | `true` on a [custom page](#custom-pages), whose `tree` is its one sketch; absent otherwise. |
| `route` | The spec page's route parameter, without its colon, and `sample`, the id of the row the page shows while no link names one. Absent for a page without a route. |
| `links` | The ids of the pages the page links to, through a `page:<id>` option or a table's form pages, in the spec's order. |
| `livePage` | The ref of the live page the spec page was converted from. |
| `paths` | The spec pointer of each node, keyed by the layout path `DmsBlockPreview` gives it: `block-<i>` for root `i`, then `<parent path>.<child id or index>`. |
| `issues` | Empty when the spec is valid. Each `path` is a JSON pointer into `spec.json`, such as `/pages/0/tree/1/children/0/options/title`. `""` names the whole file. |

Compilation is lenient. A node with invalid options, or with an unknown type, is still in `tree`, and its issues are listed. When `spec.json` is not valid JSON, or its envelope breaks the rules above, `issues` says why and `pages` keeps the last pages that compiled.

| ----- | ------ |
| `GET /api/mockup` | `{ results, total }`, one row per mockup, newest `spec.json` first. See [Listing](#listing). |
| `GET /api/mockup/schema` | The JSON Schema of the spec, built from the block types registered now. |
| `GET /api/mockup/example` | The spec of the shipped example mockup, as written: the file `mockup-example/spec.json`, with its `$generate` fixture. Copy it as the start of a spec. `example` is reserved: no mockup has that name. |
| `GET /api/mockup/schema/blocks` | `{ blocks }`: every registered block type, as `ListBlockTypes` describes it. |
| `GET /api/mockup/:name` | The `MockupState`. `404` when `spec.json` is missing. |
| `PATCH /api/mockup/:name` | Body `{ name?, title? }`, at least one. Renames the folder `mockups/<name>` to the new `name` and sets the spec's `title`, and answers `{ name }`. `400` for a name that is not a valid mockup name or is reserved, `404` when `spec.json` is missing, `409` when another mockup has the new name. |
| `POST /api/mockup/:name/duplicate` | Body `{ name? }`. Copies the folder as a draft and answers `{ name }`. Without `name`, the copy is `<name>-copy`, then `<name>-copy-2`, and so on. `400` for a name that is not valid or is reserved, `404` when `spec.json` is missing, `409` when another mockup has the name. |
| `DELETE /api/mockup/:name` | Deletes the folder `mockups/<name>`, its comments with it, and answers `{ name }`. `404` when `spec.json` is missing. |
| `GET /api/mockup/:name/events` | Server-sent events. See [Events](#events). `404` when `spec.json` is missing. |
| `GET /api/mockup/events/created` | Server-sent events, one for each mockup that did not exist before. See [Created mockups](#created-mockups). |
| `GET /api/mockup/:name/spec` | `{ spec, digest }`: `spec.json` as written, `fixture:` references included, and a digest of its text. |
| `PUT /api/mockup/:name/spec` | Body `{ spec, digest? }`. Checks the spec as `mockup_write_spec` does and answers `{ ok: true, digest }` or `{ ok: false, errors }`. `409` with the current `digest` when `digest` no longer matches the file. |
| `GET /api/mockup/:name/pages/:page/fixtures/:key` | The fixture value. |
| `GET /api/mockup/:name/pages/:page/fixtures/:key/rows` | `{ results, total }` over an array of row objects. `404` when the fixture is not one. |
| `GET /api/mockup/:name/pages/:page/fixtures/:key/record` | `?id=<id>`, with `&key=<field>` optional: the row whose `<field>`, else `_id`, else `id`, is `<id>`. `404` without `id`, or when no row has it. A sub-page with a route and a table's edit form read their row through it. |
| `GET /api/mockup/:name/pages/:page/fixtures/:key/rows/get` | The same row as the record route, where a data controller's `get` route stands: a table's details view in a modal or a drawer reads its row there, `?id=<id>&action=details`. |
| `PUT /api/mockup/:name/pages/:page/fixtures/:key/rows` | Where a table's add and edit forms save. Answers the row it was sent, merged into the row `?id=` and `&key=` name as on the record route when they name one, and keeps nothing. `400` when the body is not an object. |
| `GET /api/mockup/:name/annotations` | `{ annotations }`, each where its block or page is now. |
| `POST /api/mockup/:name/annotations` | Body `{ page, path?, offset, text }`. Anchors the note to the block at `path`, or to the page `page` without `path`, and answers it. `404` unless the spec has that page and node. `409` when `spec.json` does not parse or the block cannot be told apart. |
| `PATCH /api/mockup/:name/annotations/:id` | Body `{ status?, text?, place? }`. `place` is `{ page, path?, offset }` and moves the pin, anchored as a new note is. Answers the annotation. |
| `DELETE /api/mockup/:name/annotations/:id` | Removes the annotation. Answers `{ id }`. |
| `GET /api/mockup/:name/history` | `{ versions }`, newest first, each `{ seq, at, by, summary, comments }` without its spec. `comments` counts the notes pinned on that version, resolved ones included. See [Version history](#version-history). |
| `GET /api/mockup/:name/history/:seq` | `{ seq, at, by, summary, spec, state, annotations }`: that version's spec, its `MockupState` with fixture URLs that read the version's own fixtures, and the notes pinned on it, resolved ones included, each placed where its block or page is in that version's spec. `404` for a number with no version. |
| `POST /api/mockup/:name/history/:seq/restore` | Writes that version as the current spec, as `PUT /api/mockup/:name/spec` does, and answers `{ ok: true, digest }` or `{ ok: false, errors }`. |
| `GET /api/mockup/:name/history/:seq/pages/:page/fixtures/:key` | The fixture of that version, with a `/rows` variant, as the fixture routes above. |
| `POST /api/mockup/from-page` | Body `{ path }` or `{ pageRef }`, with `replace?` and `digest?`. Converts the page into a mockup, or opens the one it has. The AI calls it through `mockup_from_page`. See [Edit a live page as a mockup](/docs/ai-and-claude-code/live-page-mockups). `400` for a replace without `digest`, `404` for a page the builder does not know, `409` when `digest` no longer matches the file. |

The rows route reads these query parameters:

| Parameter | Meaning |
| --------- | ------- |
| `offset` | The first row to answer. Defaults to `0`. |
| `limit` | How many rows to answer. Every row from `offset` when absent. |
| `search` | Keeps the rows where a string, number or boolean value contains it, ignoring case. |
| `sortKey` | The row field to sort on. Numbers, and text that reads as a number such as `"1.25"`, sort by value first; then other text in reading order, ignoring case and accents; then any other value by its JSON text. Rows without the field come last in either direction. |
| `sortDirection` | `asc` or `desc`. Defaults to `asc`. |
| `filter_<field>` | `<mode>:<value>`: keeps the rows whose `<field>` passes. The key repeats once per filter on a field (a tab and the filters row), and a row must pass them all. The modes are `is` and `is_not` (a comma lists values: any of them, none of them), `greater_than`, `less_than`, `greater_than_or_equal_to` and `less_than_or_equal_to` (numbers, or dates read as ISO 8601), `is_between` (`<low>,<high>`), `is_empty`, `is_not_empty`, `include` and `exclude` (a value in a list field), `contains` and `not_contains` (ignoring case), and `array_contains_string`. A mode not listed keeps every row. |

A name, page id, fixture key or annotation id that does not match its pattern answers `404`, before the DMS builds any path from it. A mockup is named like a page id: lowercase letters, digits and dashes, 64 characters at most. `schema` and `example` are reserved, because the API answers on `/api/mockup/schema` and `/api/mockup/example` itself.

A duplicate has the files of the original but its `annotations.json`, and its spec loses `built`: the pages the original built are not the copy's, so the copy is a draft with no comments. Renaming and deleting never touch the pages a mockup built.

### Events

`GET /api/mockup/:name/events` opens a `text/event-stream`. While a stream is open, the DMS watches `mockups/<name>/` and reads a changed file once 40 ms pass without another change.

| Event | When | `data` |
| ----- | ---- | ------ |
| `state` | On connect, then after each change of `spec.json`. | The `MockupState` as JSON. |
| `annotations` | After each change of `annotations.json` or of `spec.json`, because a spec change moves where the notes' blocks are. | `{ annotations }` |

When `spec.json` is deleted, the next `state` keeps the last pages and has one issue that says the file is missing. When the module stops, the DMS ends every stream. The browser's `EventSource` reconnects once the backend is back.

### Created mockups

`GET /api/mockup/events/created` opens a `text/event-stream` that is not about one mockup. While a stream is open, the DMS reads `mockups/` every half second, and sends a `created` event for each name that had no `spec.json` and has one now.

| Event | When | `data` |
| ----- | ---- | ------ |
| `created` | A mockup whose spec did not exist when the stream opened, or when the directory was last read, is there. | `{ name, title? }`, `title` the spec's title when it has one |

The mockups there when the stream opens send nothing, and neither does an edit, a retitle or a rewrite of a mockup that exists. A mockup deleted and made again with the same name is sent again. The first frame of the stream comes once the mockups there are known, so a mockup made after it is always sent. The directory is read while the stream is open, so the first mockup of a project, made before `mockups/` exists, is sent too.

## Annotations

A reviewer pins a comment on a block or on a page from the viewer. [Mockup annotations](/docs/ai-and-claude-code/mockup-annotations) describes `annotations.json`, the routes, and how a note follows its block.

## Version history

Every write of `spec.json` is recorded as a version, so a mockup can go back. The versions live in `<project root>/.antelope/mockup-history/<name>/`, outside `mockups/` and so outside your git history. Add `.antelope` to `.gitignore` if the project does not ignore it yet. The last 50 versions of a mockup are kept; each new one prunes the oldest past that.

A version is `{ seq, at, by, summary, group?, spec }`:

- `seq` counts up from 1. A number is never reused.
- `by` says who wrote it: `ai` for `mockup_write_spec` and `mockup_patch_spec`, `you` for the viewer and for a restore, `disk` for a valid `spec.json` that changed outside both, such as an edit in your editor or a `git checkout`. The DMS notices a `disk` change when it next reads the mockup: while a viewer is open, at once; otherwise on the next request or the next write.
- `summary` is automatic, at page level: `Added Orders, Customers · Changed Overview · Removed Coupons`. The first version reads `Created with 3 pages`. A page is the same page by its `id`, and a list of more than three names ends in `and N more`. The summary is English whatever the viewer's language.
- Consecutive writes by the same author less than 2 minutes after the last one fold into one version: the newer spec replaces it and `at` moves. A build the AI writes page by page, or a burst of edits in the viewer, is one version. The summary then describes the change against the version before, not against the write it replaced. A restore never folds, and nothing folds into it.
- An AI write may carry a write group, kept as the version's `group`, and then folds by group instead of by time: writes of one group fold however far apart, and never with a write of another group or of none. The DMS assistant gives each of its replies a group, so a reply is one version, and a comment fix written 90 seconds after the build is a version of its own. AI writes without a group, such as those of Claude Code or Codex in a terminal, fold within the 2 minutes. The group is the `writeGroup` argument of `mockup_write_spec` and `mockup_patch_spec`: 1 to 128 letters, digits, `_` and `-`. The host sets it, as the assistant does for each reply, and the model leaves it out. A value that is not a valid group is ignored and the write goes on, without a group.

The write tools take an optional `summary` of up to 200 characters, which replaces the automatic one for that write.

A write that is refused leaves no version. A write that records nothing new, because the spec equals the newest version, leaves none either. Stamping a block id for a comment, or recording a build, changes the newest version in place when it held the spec as it was, so a comment does not add a version.

The viewer's **History** button opens the versions in the right panel. A version you pick is drawn read-only in the canvas, with its own page header and the top bar over it as [the dashboard draws them](#the-page-as-the-dashboard-draws-it), and with a bar that says `Viewing version N` and offers **Restore** and **Back to current**; Escape also goes back. Restore asks first, then writes that version through the normal write path: it becomes the current spec and a new version `Restored version N`, and the version it replaced stays in the list. Comments are not touched: each stays on the version it was pinned on. A comment whose block the restored spec lacks goes to the tray of comments without a block. While you preview, the viewer does not follow changes of the spec: it says `A newer version arrived`, and **Back to current** shows it. A version that no longer passes validation, for example because a block type was removed, cannot be restored: the answer lists the issues.

Comments belong to versions. A note is pinned on the version that is newest when it is placed, and a note resolved later is resolved on the version that is newest then: see [Mockup annotations](/docs/ai-and-claude-code/mockup-annotations#comments-belong-to-versions). Each row of the History list shows a chat icon and a count of the notes pinned on that version, resolved ones included, and no count when there are none. The preview of a version shows the pins placed on it, open or resolved, a resolved one drawn as a check, where their blocks are in that version. A pin of a past version opens a read-only card with its text and its state: `Open`, or `Resolved in version N`. In a preview you cannot place, move, edit, resolve or delete a pin. A note you delete leaves the preview and the count.

## Listing

`/mockups` shows each mockup as a card that opens `/mockup?name=<name>`, on the mockup's [Overview](#overview). It exists only in development, has no menu entry, and only the platform owner reaches it, from a header icon. Under its title it says what mockups are for: clickable drafts the AI writes before building your pages, to comment on and then build. It is a table view over `GET /api/mockup`, whose row is `{ name, title?, pages, openComments, source?, updatedAt, status }`, plus `builtAt` and `builtPages` when `status` is `built`.

A card shows:

- The whole first page, drawn by `/dms-preview` at desktop width on a 16:10 screen. It loads once its card scrolls into view.
- The title, or the name when the spec has none.
- A badge for the stage. **Draft** for a mockup never built, **2 of 5 pages built** when the build made fewer pages than the spec has, **Built** when it made them all, and **Out of sync** when a built page changed since.
- A badge with the open comments, when there are some.
- The page count, where it came from (the chat, Claude Code or Codex), and when `spec.json` last changed.
- For a built mockup, a link to each page it made.
- A **⋯** menu with **Open**, **Rename**, **Duplicate** and **Delete**. **Rename** edits the title the card shows and the name of the folder. **Delete** asks first, and says the pages already built stay.

The first card of the grid is **New mockup**. It hands the assistant a starter request, as described in [Hand a request to the assistant](#hand-a-request-to-the-assistant). With no mockup yet, the empty state shows the same button under its explanation.

Each entry of `builtPages` is `{ path, title, pageId?, changed }`. `pageId` is the spec page whose `livePage` is the page at `path`. `changed` is true when the builder's version of that page is no longer the one `livePage` records, so editing the page's source changes it and touching the file does not. A card with a changed page reads **Out of sync**, and each changed page offers **Update from page**: it converts that page again over its own spec page (`POST /api/mockup/from-page` with `mockup`), which clears that page alone. A built page with no linked spec page never reads as changed and offers no update.

### A new mockup opens by itself

The platform owner's dashboard follows the [created mockups stream](#created-mockups) from every page, in development, except `/dms-preview`: the Overview and the cards embed it once per page, and a stream each would hold every connection the browser opens to the host, six over HTTP/1.1, so the frames past the sixth would never load. A mockup created while the dashboard shows `/mockups` opens at once in its viewer, `/mockup?name=<name>`: the user usually clicked **New mockup**, which opens the assistant chat, and the assistant creates the mockup. Anywhere else the dashboard leaves the user where they are and shows a toast, `Mockup "<title>" created` (the folder name when the spec has no title), with an **Open** action that goes to the viewer. The page is read when the event arrives, so a user who left `/mockups` before the assistant created the mockup gets the toast and is not moved. Only a mockup that did not exist before counts: a rename of its title, an edit or a rewrite sends nothing. The texts are the `mockups.created.title` and `mockups.created.open` keys of the layout locales, in en-GB and fr-FR.

A row reads `spec.json` as far as it reads cleanly: a file that is not JSON lists as a draft of no pages, and an invalid `source` or `built` reads as absent. `openComments` counts the open annotations, `0` when `annotations.json` is missing or unreadable.

## Viewer

`/mockup` is a hidden, owner-only page that renders the `DmsMockupViewer` component with the bare preview layout.

| Query parameter | Meaning |
| --------------- | ------- |
| `name` | The mockup to show. Without it, the page lists the mockups. |
| `page` | The id of the page to show. Without it, the viewer shows the [Overview](#overview), the mockup's home. |
| `record` | The row a page with a route shows: the id a link from a row passed it. |
| `width` | `desktop` or `mobile`. |
| `data` | `real` or `sample`. Overrides the default of the Real data switch. |

The viewer opens the event stream, embeds `/dms-preview` in an iframe, and sends the current page's `tree` (or `realTree` with Real data on), `theme`, `locale` and `padding` in a `render` message on every `state` event. The `render` also carries the mockup's pages as `navigation`, which the preview draws as the dashboard's sidebar: picking a page there opens it, and below the dashboard's desktop width the sidebar folds behind a menu button. It carries the page's `header` too, `{ title, icon?, description?, actions? }` from the spec page's `title`, `icon`, `description` and `headerActions`, which the preview draws as the dashboard draws a page.

### Follow a link and Preview

A `page:<id>` link opens its page in the viewer. The page and its row are the URL's `?page=` and `?record=`: each page opened, from the Overview, a link or the sidebar, and each return to the Overview, is a new entry of the browser's history, so back and forward step through them. A page with a route is drawn with its parameter set to `record`, else to its sample row.

- **While editing.** A click selects, as before. `Ctrl` + click (`⌘` + click on a Mac) on a link of a block to a page of the mockup follows it. A link in a sketch does not: see [Links to pages](#links-to-pages).
- **Preview.** **▶ Preview** in the top bar, or `P`, hands every click to the page, as the dashboard runs it: links open their pages, rows open their row actions, buttons open their forms. Nothing is selected or commented meanwhile: the panels, the block toolbar, the Comment tool and the pins are off. `Esc`, pressed in the viewer or in the page while no menu or dialog of the page is open, or the toggle again, leaves Preview. Going back to the Overview leaves it too.

The preview frame never leaves `/dms-preview`. A visit to another page of the dashboard is cancelled, and a visit to a page of the mockup is handed to the viewer as a `navigate` message, `{ id, record? }`. The `render` message carries `params`, the route parameters the blocks fill `{{params.X}}` with.

### The page as the dashboard draws it

Above the blocks, the preview draws what the dashboard draws around a page, so the mockup looks like the page it becomes:

- **The top bar.** The dashboard's navbar: the sidebar toggle, the breadcrumb (home, then the page's title), the favorite star, and on the right the Mockups and Branding icons of a development dashboard, the quick actions and the notification bell. It is a copy with static data: none of it acts, a screen reader skips it, and no header action plugin runs. Below the dashboard's desktop width it holds the one button that works, the one that opens the sidebar.
- **The page header.** The dashboard's own `PageHeader` component, fed by the spec page's `title`, `icon`, `description` and `headerActions` instead of the page's layout. Its buttons look as the dashboard's header buttons do and do nothing. A page with no `icon` draws the dashboard's default one.

While the viewer edits, a click on the page header selects the page: the selection clears and the inspector shows the page's own settings, which include its icon, its description and its header buttons. The header is outlined under the pointer like a block is.

The page header and the top bar are not blocks: they have no layout path, and the preview's block layout leaves them out. A page declared with `hideHeader` in its layout is not mirrored: a mockup always draws the header.

The page is drawn as tall as the canvas shows at least, like a browser window: a short page keeps its sidebar and its background down to the bottom, and a longer page grows and the canvas scrolls. The viewer asks for this with a `min-height` message to the preview, at every frame width. The mockup thumbnails send none, so they stay as they were.

**← Mockups** at the top left goes back to `/mockups`. A click on the mockup's title, or Enter on it once focused, turns it into an input: Enter or a click away saves the spec's `title`, Escape puts it back, and an empty title is refused. The rename is one edit of the undo history. The folder name, which `?name=` holds, never changes. The left panel holds the block catalog, the page's layers and the pages; the right panel is the inspector. Each panel closes and opens from its button in the top bar, or with `[` for the left one and `]` for the right one, and the browser keeps that choice. With both closed, the page takes the full width. Selecting a block never reopens the inspector.

A developer changes the spec in place: a click selects a block, add one from the catalog by dragging it onto the page or by placing it, move, duplicate, delete and restyle blocks, edit a text by double-clicking it, and add, rename, reorder and remove pages. The inspector offers only an option's visual settings, from the groups `content`, `appearance`, `layout` and `features`. Each edit is written with `PUT /api/mockup/:name/spec` about 150 ms after the last one, with the digest the viewer last read or wrote. When another writer, such as `mockup_patch_spec`, changed the file in between, the write answers `409`: the viewer takes the file as it is now, starts its undo history over and says so. A note's stamp on the file keeps the editor's undo history: see [Mockup annotations](/docs/ai-and-claude-code/mockup-annotations#in-the-editor). The [keyboard shortcuts](#keyboard-shortcuts) undo, redo and edit the selected block.

### Sections

A spec's `categories` are the sidebar's sections, as a dashboard's menu groups its pages under its categories. The preview's sidebar and the **Pages** tab of the left panel list the pages under a header per section, in the order of `categories`, after the default **Pages** section, which holds the pages without a `category`. A mockup without categories lists its pages as before, under no header. The first page of the spec is the home page, which the sidebar marks with a house when it has no icon of its own.

Both lists edit the sections in place, and the preview's sidebar does so while the viewer edits the current version's page view:

- **New section** shows a name field. Enter or a click away adds the section at the end, its id made from its name (`Billing` is `billing`, then `billing-2`); Escape or an empty name adds nothing.
- A double-click on a section's title renames it in place.
- The ⋯ menu of a section offers **Rename**, **Icon**, which opens the same icon field as the page's inspector, and **Delete**. Deleting a section that holds pages asks first, and its pages move to the end of the default section.
- A page dragged onto a section, or between two of its pages, moves there; a section dragged above or below another moves in the menu. The arrows of a page in the left list move it within its section.

The preview's sidebar is the dashboard's own, and it lists the app's own menu too, dimmed and out of reach, then the mockup's sections. A mockup section is listed in the app's section of the same title, case and spaces aside: under one header, the app's entries come first, then the mockup's pages. The default section joins the app's own **Pages** section the same way. The header is the mockup's: renaming it renames the mockup's section, which then stands apart again, and the app's section is unchanged. A page converted from a live page (`livePage`) hides that page's own entry, so it shows once; the entry's sub-pages stay.

A page with `menu: false` is left out of the preview's sidebar. While it is open, the sidebar lights its nearest parent the sidebar lists. The **Pages** tab lists every page: a sub-page under its parent, depth first, indented, and a page with `menu: false` with an eye-slash mark. The arrows and drag reorder the top pages of a section; a sub-page moves with its parent.

Each change is an edit of the spec like any other: it is written with `PUT /api/mockup/:name/spec`, recorded in the history, and undone and redone with the rest. Moving a page or a section writes the spec's `pages` in the order the sections list them, so the page listed first is the spec's first page. The preview's sidebar posts each change to the viewer as a `section-edit` message, `{ kind, ... }` as `MockupSectionEdit` types it (`addCategory`, `updateCategory`, `removeCategory`, `moveCategory`, `movePageTo`), and the viewer writes it; the editing itself is `useMockupSectionEditing`, which any sidebar of the preview reuses.

### Keyboard shortcuts

`?` opens a sheet of every shortcut, grouped as below, and so does the keyboard button of the top bar. The top bar's buttons and the block toolbar's actions show their key in a tooltip. `Ctrl` reads `⌘` and `Alt` reads `⌥` on a Mac. A shortcut works while the focus is not in a text field, in text being edited in place, or in a dialog.

| Group | Keys | Action |
| ----- | ---- | ------ |
| Panels and help | `[` | Show or hide the edit panel. |
| Panels and help | `]` | Show or hide the inspector. |
| Panels and help | `?` | Show the shortcuts. |
| Editing | `↑` / `↓` | Select the previous or next block among its siblings. It stops at either end. |
| Editing | `Alt` + `↑` / `↓` | Move the selected block up or down within its parent. |
| Editing | `Ctrl` + `D` | Duplicate the selected block. The browser's bookmark shortcut does not fire. |
| Editing | `Delete` or `Backspace` | Delete the selected block. |
| Editing | `Enter` | Insert the block armed from the catalog right after the selected block. |
| Editing | `Esc` | Cancel the armed block, else the Comment tool, the pin being written or the open card, else clear the selection. In the Overview, cancel the Comment tool, the pin being written or the open card. |
| Comments | `C` | Arm or disarm the Comment tool. |
| History | `Ctrl` + `Z` | Undo. |
| History | `Ctrl` + `Shift` + `Z` or `Ctrl` + `Y` | Redo. |
| Overview | `Esc` | On a page, once none of the above takes it, close the page and go back to the [Overview](#overview) where it was. |
| Overview | `Shift` + `1` | Fit every page in view. It is the key that types `1`, whatever Shift types on it in the layout. |
| Preview | `P` | Turn [Preview](#follow-a-link-and-preview) on or off. |
| Preview | `Esc` | Leave Preview. |

`Esc` tries its meanings in the table's order, and an open menu, popover, tooltip or dialog takes it before any of them. In the overview only `?`, `Esc`, `Shift` + `1` and `C` work: the panel and editing keys, undo and redo do nothing there. In Preview only `?`, `P` and `Esc` work.

### Place a block

A click on a block of the catalog does not insert it. It arms the block: its name follows the pointer as a small chip, the page shows the same drop line a drag shows, and a click on the page drops the block there. One arming places one block. Escape disarms it before it does anything else. Drag keeps working.

While a tool is armed, a banner at the top of the canvas says what a click does and that `Esc` cancels: "Click to place a comment" for the Comment tool, "Click on the page to place <block>" for an armed block.

From the keyboard, Enter or Space on a focused catalog item arms it. With a block selected, Enter then inserts the armed block right after the selection and disarms it. The Comment tool and an armed block exclude each other: arming one disarms the other.

### Comments

Comments are pins on the page, always in view:

- **Comment** in the top bar, or `C`, arms the tool. The next click on the page drops a pin there and opens its text box, and the tool disarms. Escape disarms it, then closes the text box, then clears the selection. While the tool is armed the cursor is a comment bubble with a plus, over the page and its blocks alike, and a dashed outline shows where the pin would land: the block under the pointer, or the whole page outside every block. A pin being dragged shows the same outline.
- A pin dropped on a block is a note on the innermost block under it. A pin dropped outside every block is a note on the page as a whole. The pin keeps its spot as fractions of the block's box, or of the page, so it sits at the same place of the block on desktop and on mobile.
- The page header and the top bar are not blocks, so a pin dropped on them is a note on the page: its spot is a fraction of the whole page, header included.
- A pin is dragged at any time. Dropped on another block, it is a note on that block. Dropped outside every block, it is a note on the page.
- A click on a pin opens its card: edit the text, resolve or reopen the note, or delete it.
- A click anywhere outside the card closes it, a click on the page in the preview included, and a click on another pin opens that pin's card at once. A note's card closed this way keeps the text written in it and not saved for the next time it opens; **Close** and Escape let that text go. The card of a new pin closes on such a click only while it is empty: with text in it, it stays open and shakes, until **Comment** saves it or **Cancel** or Escape drops it.
- Only open pins show. A resolved pin leaves the page, and stays on the version it was pinned on: open **History** and pick that version to see it, with its state. See [Version history](#version-history).
- A note whose block or page was removed waits in the **Comments without a block** tray, in the corner of the canvas. Drag it onto the page to pin it there again.

While at least one comment is open, a bar at the bottom of the canvas reads "N open comments" and offers **Resolve with AI**, which hands every open comment of the mockup to the assistant. See [Hand a request to the assistant](#hand-a-request-to-the-assistant).

A mockup whose spec has no page yet shows "The AI is writing the mockup…". The pages appear as the AI writes them, since each save redraws the viewer.

The **Real data** switch shows when the page has `liveRoutes`. It is on by default for a page converted from a live page and off for any other; `?data=` and the developer's choice override that default. A mockup without live routes has no switch.

### Overview

The Overview is the mockup's home: a mockup opens on it, unless the URL names a page with `?page=`. It lays every page of the mockup side by side on one canvas, in the sidebar's order. Each page is a frame at the desktop width and at its full height, at least 800 pixels, under its icon, the one its sidebar entry shows, its title and the number of its open comments. Up to eight pages sit in one row; more wrap into rows of even length, so ten pages make two rows of five. A mockup with [sections](#sections) lays each section out in rows of its own, one below the other in the menu's order, under the section's icon and title; a section without pages takes no room. The overview opens with every page in view, and keeps them all in view while the long pages report their height, until you move.

A page opened from the Overview shows a large ✕ in the top right corner of the canvas, in a margin of its own beside the page. The ✕, or `Esc` once Preview, an open menu or popover, the comment, the armed block and the selection have each taken theirs, goes back to the Overview at the pan and zoom it had.

- Pan with the wheel or a trackpad, Space and a drag, a middle-button drag, or the arrow keys while the canvas has the focus (`Shift` pans further). Zoom around the pointer with `Ctrl` (`⌘` on a Mac) and the wheel, or a pinch. The control in the bottom right corner shows the zoom, zooms out and in around the middle, and fits every page in view, as `Shift` + `1` does. A move the control or the keyboard starts eases into place, unless motion is reduced.
- Hovering a frame outlines it and shows **Open**; a click picks it, outlined, with **Open** too. **Open**, a double-click on a frame, or Enter on a frame focused with `Tab` opens its page. A frame focused with `Tab` is panned into view.
- A sub-page is laid out right after its parent, its title naming the parent first (`Orders › Order`), and a page with `menu: false` carries an eye-slash mark.
- One arrow joins two pages when either [links](#page-links) to the other: solid, with a head at each end when they link both ways. A parent that does not link to its sub-page is joined to it by a dashed arrow. An arrow shows only while one of its two pages is hovered, or picked with a click or `Tab`; a click on the canvas drops the pick. The links button of the control in the bottom right corner shows them all. The arrows are laid out with the frames, in the frames' own pixels, so a pan or a zoom moves them with the canvas, and they keep their width on screen at any zoom.
- Comments work as on a page. Each frame draws its open pins. The Comment tool drops a pin on the innermost block under the click of whichever page it lands on, else on that page, at the same offsets. A pin dragged onto another frame moves to that page, and a click opens its card. A click on a frame or the canvas closes the card, while a pan, by any means, leaves it open. **Resolve with AI** hands the assistant every open comment, as on a page, without a page in view.
- Nothing is edited in the overview: the edit panel, the inspector, the block toolbar, undo and redo are off, and so are Real data and the frame width. Every page is drawn on its fixtures.
- While a [version](#version-history) is previewed, the overview lays out that version's pages and the pins pinned on it, read-only: the Comment tool does not arm.
- The frames near the view are drawn live by `/dms-preview`, as the page view is, at most ten at once. The iframes share the window's main thread, so they boot one at a time, the page nearest the middle first, and the canvas keeps answering meanwhile. Each iframe is then reused for the next page that comes into view rather than loaded again. While you pan or zoom, the frames drawn stay as they are, and they follow the view once it rests for a quarter of a second, so a gesture never waits on a page being drawn. A frame not drawn yet shows its page's icon, and its pins show once it is drawn.

### Hand a request to the assistant

Data wiring is never edited in the viewer. "Ask the AI to change it" on a sketch, "Build it", "Resolve with AI" and the Mockups page's "New mockup" card dispatch a cancelable `dms:assistant-prompt` event on `window` (`MOCKUP_ASSISTANT_PROMPT_EVENT`, detail `MockupAssistantPrompt`). The DMS assistant claims it with `preventDefault()`; when nobody does, the page shows the request to copy into another AI tool.

| `source` | Sent by | `prompt` | Other fields |
| -------- | ------- | -------- | ------------ |
| `custom-zone` | A sketch's "Ask the AI to change it" | A full sentence | `block` |
| `build` | "Build it" | The mockup's name | `target: { pageRef }` on a page converted from a live page; `title` |
| `resolve-comments` | "Resolve with AI" | The mockup's name | `page`: the id of the spec page in view, absent in the overview; `title` |
| `new-mockup` | The Mockups page's "New mockup" card | The start of a request in the user's language ("Draft a mockup of "), for the user to finish in a new conversation | none |

The assistant tells the viewer about the runs it makes for a mockup with two more events on `window`. Their names and the detail's type sit beside `MOCKUP_ASSISTANT_PROMPT_EVENT` in the `dms-ui` layer's `mockupAssistant` utilities, which the dashboard auto-imports:

| Event | Dispatched by | `detail` |
| ----- | ------------- | -------- |
| `dms:assistant-run` (`MOCKUP_ASSISTANT_RUN_EVENT`) | The assistant, when a build or a resolve run for a mockup starts, and again when it ends | `MockupAssistantRun`: `{ mockup, source, running }`, `mockup` the mockup's folder name, `source` `build` or `resolve-comments`, `running` true at the start and false at the end |
| `dms:assistant-run-query` (`MOCKUP_ASSISTANT_RUN_QUERY_EVENT`) | The viewer, once, when it opens | None. The assistant answers with a `dms:assistant-run` whose `running` is true for each run going on |

While a build of the open mockup runs, **Build it** reads **Building… ↗**; while its comments are being resolved, **Resolve with AI** reads **Resolving… ↗**. The arrow says that a click leads to the conversation: the click still dispatches `dms:assistant-prompt`, and the assistant opens the run's conversation. A run of another mockup changes nothing. Without the assistant no `dms:assistant-run` comes, and the labels stay as they are.

`title` is the mockup's title, sent only when it differs from the name: `prompt` stays the name, which is what names the mockup in the MCP tools. The copy names such a mockup by both, as in `"Shop admin" (shop-admin)`. On a page converted from a live page, the copy of a build says to build into that page instead of creating a new one. The copy of `resolve-comments` tells an AI to list the open annotations with `mockup_annotations`, apply each one with `mockup_patch_spec`, and resolve each one with `mockup_resolve_annotation`. Once a request went unclaimed, "Resolve with AI" reads **Copy the prompt**. An unclaimed `new-mockup` request shows its starter followed by an ellipsis, to copy and finish in another AI tool.

The viewer keeps room on its right for the dashboard's side panel, as the dashboard frame does, so the assistant's chat docks beside the mockup and shows the agent at work.

Deleting the whole `mockups/` directory while a viewer is open stops its updates; reload the viewer once the directory is back.

## Regenerate the schema

The shipped schema covers the built-in block types. Regenerate it after a change to a block's options:

```bash [Terminal]
pnpm --dir packages/dms mockup:schema
```

`pnpm --dir packages/dms mockup:schema:check` fails when the committed file is stale. CI runs it.
