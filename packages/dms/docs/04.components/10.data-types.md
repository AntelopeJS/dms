A **DataType** describes one piece of typed data: how it renders as an input, how it validates, and which filter operators apply. The same instance drives a `Form` field ([Forms](/docs/components/forms)), a `TableView` column ([Tables](/docs/components/tables)), and that column's filters. Declare the type once, and the field, the column and the filters agree.

A field's `type` is always a DataType **instance**, constructed with per-field options:

```ts fragment [src/pages/contact.ts]
import { DefaultDataTypes } from "@antelopejs/interface-dms/base/data-types";

{
  id: "quantity",
  label: "Quantity",
  type: new DefaultDataTypes.NumberType({ min: 0, max: 1000, step: 1 }),
}
```

The standard catalog lives in the `DefaultDataTypes` namespace, with `StatusType`, `DataType`, `DefaultDataCompareTypes`, `RegisterDataType`, and `RegisterDataCompareMode` exported alongside it.

## The built-in catalog

Each entry is registered with `@RegisterDataType("<id>")`. "Renders" names the `FormComponents.*` widget the type produces; "Compare modes" lists its filter operators (**default** in bold). Most types share one of four operator sets:

- **text**: **`contains`**, `is`, `is_not`, `not_contains`, `is_empty`, `is_not_empty`
- **numeric**: **`is`**, `is_not`, `greater_than`, `greater_than_or_equal_to`, `less_than`, `less_than_or_equal_to`, `is_empty`, `is_not_empty`
- **equality**: **`is`**, `is_not`, `is_empty`, `is_not_empty`
- **membership**: **`include`**, `exclude`

A `date` filter works in whole UTC days: a picked day is the whole day for `is` and `is_between`, `greater_than` keeps what comes after it (from the next day) and `less_than` what comes before it. A value with a time, such as a view's `{{now-7d}}`, is compared as that instant.

A multiple relation (`multiple: true`) stores a list of ids, so its filter asks whether the list includes the picked row (`include`, the default) or not (`exclude`), one row at a time.

A number's unit goes inside its field, after the value, with `suffix`, while the value stays a bare number. `NumberType({ min: 0, suffix: "$billing.days" })` reads "30 days", and the field stays as wide as the others. A `PriceType` takes a suffix too. It is written wherever the value shows: after the form field, and after the formatted number in table cells, expanded rows, cards and read-only fields. A text field shows the characters typed with `showCount: true`, out of `maxLength` when it has one ("4 / 60"): at the end of a single-line field, under a textarea.

```ts fragment
{ id: "graceDays", label: "Grace period", type: new DefaultDataTypes.NumberType({ min: 0, suffix: "$billing.days" }) },
{ id: "name", label: "Workspace name", type: new DefaultDataTypes.StringType({ maxLength: 60, showCount: true }) },
```

A short value does not need the whole row. A single-line number, percentage or text field takes `width: "compact"` to size itself for a few characters (11rem), and `width: "full"` to fill the row. Left out, the bounds decide: a number whose `min` / `max` fit in 6 digits (a percentage, by its 0 to 100), or a text whose `maxLength` is 16 or less, is compact; anything else fills the row. A number with no `max`, such as an estimate in hours or a quantity, is unbounded, so it needs `width: "compact"` to be compact. The compact width applies from the `sm` breakpoint up, in a page form and a drawer alike: on a phone every field keeps the full row.

```ts fragment
{ id: "estimateHours", label: "Estimate", type: new DefaultDataTypes.NumberType({ min: 0, step: 0.5, suffix: "h", width: "compact" }) },
{ id: "currency", label: "Currency", type: new DefaultDataTypes.StringType({ maxLength: 3 }) }, // compact by itself
```

The `display` options of `SelectType` and `BooleanType`, `StringType({ copyable })` and the `array`, `key_value`, `secret`, `code` and `tags` types are described with examples in [Field types](/docs/components/forms/field-types).

`RelationType`'s `keyMapping.avatar` accepts either a URL string or a stored image value (`{ key }` from an `ImageType` field on the related record, such as a DMS member's profile avatar); image keys are resolved to read URLs by the picker.

A relation picker can depend on another field of its form with `filterBy: { field, from }`: it lists only the related rows whose `field` equals the form's current value of `from`. A ticket's site among its customer's sites, a project's quote among its customer's quotes:

```ts fragment
@Column({
  name: "Site",
  type: new DefaultDataTypes.RelationType({
    dataApiController: SiteController,
    keyMapping: { label: "name", value: "_id" },
    filterBy: { field: "customer", from: "customer" },
  }),
})
site!: string;
```

The picker searches the related `select` route with the table filter syntax (`filter_customer=is:<id>`) and searches again when `from` changes; a pick made for the previous value is cleared, and going back to the value it was made with keeps it. The record's stored pair is kept as the form loads. While `from` is empty, every row is offered. `field` must be filterable on the related controller (`filterable: true` on its column, or `@Filter`), since the route ignores any other filter: a relation declaring an unfilterable `field` throws at registration. The picker narrows what is offered; a write rule that must hold (the site belongs to the customer) is still checked by the module's routes.

A `RelationType` field takes its value as the joined row (`{ _id, name }`) or as the plain id (`"u-5"`, or a list of ids when `multiple`). A form whose read answers ids shows each one's label and avatar all the same: the picker asks its target's `select` route for those rows alone (`?ids=u-5&idKey=_id`, `idKey` being `keyMapping.value`), so a route serving a standalone form need not join the related rows.

A list is the other way round: a table cell, a card and a kanban card draw the joined row and never read the ids themselves, so a route listing rows for them must join every relation it shows. The `Foreign` join a `RelationType` or `CascaderRelationType` column installs does it for the DMS `List` route; a custom `list` route has to apply it too, and a column declared `filterOnly` skips it, so its cells show the raw id. A filter chip names its ids by `?ids=`, like the form.

An id the `select` route does not answer reads "Not found", with the id in its tooltip, in the picker, a filter chip, a read-only list and a cascader cell. The id may belong to a deleted row or to a row out of the reader's reach, and the client cannot tell the two apart.

A `CascaderRelationType` cell and its picker's field show the path of the picked row ("Electronics / Audio / Speakers"), read by `?ids=` one level at a time: the picked rows, then their parents, until a root. That is as many requests as the tree is deep, whatever its size, on the route the picker already reads; the open picker still lists the route's rows to browse the tree.

## How a type is consumed

The same instance works as a form field type and a table column type; on a table it also supplies the column's filter operators. Table columns are declared with the `@Column({ … })` property decorator on the data-api controller class ([Data controller](/docs/components/data-controller)), not on the page:

```ts fragment
// Form field (on a page)
{ id: "email", label: "Email", type: new DefaultDataTypes.EmailType({ placeholder: "jane@example.com" }) }

// TableView column (on the data-api controller): the type drives the cell, the filter widget, and the operators
@Column({ name: "Unit Price", type: new DefaultDataTypes.PriceType(), filterable: true })
price!: number;
```

### Compare modes

A **compare mode** is one filter operator, such as the `is` in "status _is_ done". Each type declares the modes it supports and a default; the built-ins live in the `DefaultDataCompareTypes` namespace:

- **Equality**: `is`, `is_not`.
- **Ordering**: `greater_than`, `greater_than_or_equal_to`, `less_than`, `less_than_or_equal_to`, `is_between`. An empty value is neither before nor after a bound, so these leave it out: a deal with no last activity is not "less than 21 days ago". `is_empty` finds those rows.
- **Text**: `contains`, `not_contains`.
- **Sets**: `include`, `exclude`, `array_contains_string`. A row whose list is `null` or missing (an optional field saved empty) reads as an empty list: `include` and `array_contains_string` leave it out, `exclude` keeps it.
- **Emptiness**: `is_empty`, `is_not_empty`. These take no value: selecting the mode is the filter.

## Write a custom data type

The catalog is extensible: register your own type and it behaves like any built-in, as a form field, as a table column, and in that column's filters. A custom type has two halves. The backend class declares the type's validation, compare modes, and input widget; an optional frontend half formats its values for table cells and read views. The full contract, with annotated `status` and `rating` walkthroughs, is [Custom data types](/docs/extending-the-dashboard/custom-data-types).

## Permissions

Data types carry no permission logic of their own. Access is enforced on the page and the component, so gate a field's visibility with the permissions of the page that owns it (see [Auth & permissions](/docs/auth-and-tenancy/auth-and-permissions)).
