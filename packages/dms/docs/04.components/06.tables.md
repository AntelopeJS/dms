# Tables

A table is two pieces. A **`DataController`** declares the data shape and its operations — list, filter, sort, search, create/edit/delete, export, archive — once, with decorators; that whole backend side (route generators, field decorators, model wiring) is its own reference, [Data controller](/docs/components/data-controller). A **`TableView`** component points a page at that controller and renders the screen: toolbar, columns, forms, and pagination are wired for you, so a standard CRUD screen needs no Vue and no hand-written routes. For a static form or one-off list endpoint, use [Pages & components](/docs/building/pages-and-components) instead.

## What it renders

`TableView` produces a full table screen:

- **Toolbar** — the `caption` heading, a global **search** box (when `@Searchable` fields exist — it searches from 2 characters), a **filter** per `filterable` column, a **column-visibility** menu, an optional **tab strip** (`tabs`), a **display switcher** when more than one display is configured, an **Export** button (when the export routes are present), any `customButtons`, and an **Add** button (when the `add` action is enabled).
- **Columns** — one per `@Column`, headed by `name`; a `@Sortable` header toggles ascending/descending. Each cell renders through its `DataType` (a badge, date, thumbnail, relation chip), not raw text — see [Data types](/docs/components/data-types).
- **Rows** — one per record, keyed by `rowIdKey` (default `_id`). With `hasSelection` on, a leading checkbox column enables multi-select and bulk delete/archive/restore.
- **Row actions** — a per-row menu of the enabled actions (edit, details, duplicate, delete, copy link, archive/restore, plus `custom` entries), hidden or disabled per row by their `rule`.
- **Pagination** — a footer driven by the `list`/`count` routes.

Editing happens in a **form container** — drawer, modal, or page — built automatically from the controller's `@Column` fields. See [Forms](/docs/components/forms).

## Usage

Model the data first: declare the controller, its routes, and its field decorators as shown in [Data controller](/docs/components/data-controller) — this example reuses the `taskDataAPI` controller built there.

Pass the **controller class itself** (not an instance) to `TableView`. Columns come from the controller's `@Column` decorators — you do not redeclare them on the page.

```ts [src/pages/tasks.ts]
import {
  PageController,
  RegisterPage,
  pagesCategory,
} from "@antelopejs/interface-dms/page";
import { TableView } from "@antelopejs/interface-dms/base/table-view";
import { taskDataAPI } from "../data-api/tasks";

@RegisterPage()
export class TasksPage extends PageController("tasks", {
  displayName: "Tasks",
  icon: "i-ph-table",
  category: pagesCategory,
}) {
  static table = TableView(taskDataAPI, {
    caption: "Tasks",
    labelKey: "name", // names the row in form titles and breadcrumbs
    archiveMode: true, // requires an @ArchiveField on the controller
    formContainer: {
      type: "drawer",
      // The form titles, in a drawer, a modal or a page alike.
      pages: {
        new: { displayName: "New task", description: "Name it and assign people." },
        edit: { displayName: "Edit task" },
        details: { displayName: "Task details" },
      },
    },
    rowActions: {
      add: true,
      edit: true,
      details: true,
      hasSelection: true,
      delete: { isEnabled: true, rule: { field: "status", notEquals: "done" } },
    },
  });
}
```

## TableView options

::tip
A frontend layer can add **alternate displays** (kanban, cards, calendar…) beyond the built-in grid — see [TableView displays](/docs/extending-the-dashboard/table-view-displays) — and make table actions react to other components via [Component events](/docs/extending-the-dashboard/component-events).
::

`TableView(controller, options)`:

| Option                 | Type                                      | Default   | Purpose                                                                                                             |
| ---------------------- | ----------------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------- |
| `caption`              | `string`                                  | —         | Heading above the table.                                                                                            |
| `layout`               | `"full" \| "compact"`                      | `"full"`  | How much the table draws around its rows: the dashboard grid, or the compact list of a settings page (see [Layout](#layout)). |
| `searchPlaceholder`    | `string`                                  | —         | Placeholder of the search field (`$`-prefixed: i18n key).                                                           |
| `quickFilters`         | `TableViewQuickFilter[]`                  | —         | One-click dropdown filters in the toolbar over a column's values (see [Quick filters](#quick-filters)).            |
| `pageSize`             | `number`                                  | `10`      | Rows per page while the user picked none, 1 to 50 (registration throws above). A size other than 10, 25 and 50 joins them in this table's page size picker. |
| `pagination`           | `"pages" \| "loadMore" \| "infinite"`      | `"pages"` | How the rows go past the first page: a pager, a "Load more" button, or more rows as the footer scrolls into view (see [Pagination](#pagination)). |
| `density`              | `"default" \| "compact"`                  | `"default"` | Row density the table opens with (`compact`: 36px rows). The user picks another from the "Density" entry of the ⋯ menu, kept with the table's state. |
| `maxHeight`            | `string`                                  | —         | Caps the rows in a scroll area of their own (any CSS length, e.g. `"60vh"`), under a header that stays in view.     |
| `footer`               | `TableViewFooterOptions`                  | —         | Footer band: the row count (`$` key pluralized on `{ count }`, e.g. "7 members"), a hint, `summary` figures computed by the server and a `legend` (see [Footer](#footer)). |
| `emptyStates`          | `TableViewEmptyStates`                    | —         | What the empty body says when the table has no row yet, when its filters match nothing, or when the list failed (see [Empty states](#empty-states)). |
| `expandable`           | `TableViewExpandableOptions`              | —         | A caret column opens a detail band under each row, listing `fields` and/or rendering a `component` (see [Expandable rows](#expandable-rows)). |
| `rowIdKey`             | `string`                                  | `"_id"`   | Field used as row identity for actions and realtime.                                                                |
| `labelKey`             | `string`                                  | —         | Field naming a row: it follows the drawer/modal title ("Edit task · _Buy milk_") and ends the breadcrumb of the edit and details pages. |
| `rowActions`           | `TableViewRowActionOptions`               | —         | Which per-row actions to show and their rules (see [Row actions](#row-actions)).                                    |
| `customButtons`        | `CustomButton[]`                          | —         | Extra toolbar buttons with an `ActionTarget`.                                                                       |
| `formContainer`        | `{ type: "drawer" \| "modal" \| "page"; pages? }` | `page`    | Where the add/edit/details form opens, and its titles in `pages` (see [Form containers](#form-containers)).          |
| `archiveMode`          | `boolean`                                 | `false`   | Replace delete with archive/restore; requires an `@ArchiveField`.                                                   |
| `defaultFilters`       | `Array<{ accessorKey; value?; mode }>`    | —         | Filters pre-applied and visible when the table opens.                                                               |
| `defaultSort`          | `{ field; desc? }`                        | —         | Initial sort when the user has no saved preference.                                                                 |
| `queryParamFilters`    | `Record<string, { field; mode? }>`        | —         | Map URL **query** params to hidden filters (not shown, not persisted).                                              |
| `routeParamFilters`    | `Record<string, { field; mode? }>`        | —         | Map DMS **route** params (page-slug tokens like `:id`) to hidden filters — for detail pages scoped by a path param. |
| `strictRuleValidation` | `boolean`                                 | `false`   | When `true`, reject the whole request if any row fails a rule; when `false`, process only eligible rows.            |
| `tabs`                 | `TableViewTab[]`                          | —         | Tab strip above the table; each tab filters on one column (`filter`) or links to another page (`to`), never both. An implicit "all" tab is added automatically. |
| `realtime`             | `boolean`                                 | `true`    | Broadcast row mutations and presence to other viewers (opt-out).                                                    |
| `kanban`               | `KanbanOptions`                           | —         | Enable a kanban display; `groupByField` must be a non-multiple `SelectType`, `BooleanType`, or `StatusType` column. |
| `grouped`              | `GroupedOptions`                          | —         | Offer the `grouped` display: the grid's columns with a header row per group of rows (see [Grouped display](#grouped-display)). |
| `views`                | `TableViewViewsOptions`                   | —         | Named states of the whole table — filters, search, sort, columns, display, density — as tabs, a strip or a menu, opened from the URL, and saved by users for themselves (see [Views](#views)). |
| `card`                 | `{ fields?; component? }`                 | —         | The card the `kanban` and `cards` displays draw for each row (see [Cards](#cards)).                                 |
| `displays`             | `TableViewDisplayOption[]`                | —         | Additional custom displays beyond the built-in table (and kanban).                                                  |
| `defaultDisplay`       | `string`                                  | `"table"` | Display shown when the user has no preference. Supersedes the deprecated `defaultViewMode`.                         |
| `guards`               | `TableViewGuards`                         | —         | Server-side checks before mutating actions (see [Guards](#guards)).                                                 |
| `formSlots`            | `{ new?, edit?, view?: string }`          | —         | Component slot each generated form opens, so another module can extend it through `RegisterComponentSlot`. The values its fields submit reach the data routes only if the controller reads them — wrap the edit write with `TableViewRoutes.EditWith(baseRoute)`. |
| `bypassTenantAccessGate` | `boolean`                               | `false`   | Keep the table **readable** while a [tenant access gate](/docs/auth-and-tenancy/auth-and-permissions#tenant-access-gate) denies the tenant — for tables on recovery surfaces (invoices on a suspended tenant's billing page). Covers `view`, `list` and `select` only: every write, and `export` (which queues a job and delivers a file), still asserts the gate. Action permission checks apply on top. Latched controller-wide: once one `TableView()` registration of a controller declares it, a later registration without the flag cannot silently re-gate (or un-gate) the shared routes — so a table mounted on several pages shares the opening, and mounting it both ways is warned about. |

::note
`queryParamFilters` and `routeParamFilters` also seed form submit defaults: a form opened from a filtered view inherits the parent token (e.g. a `:projectId` route param flows into the new row's `projectId`), resolved at submit time and dropped if absent.
::

## Features

### Wrapping complex cells

The grid clips cell content to one line by default and inherits `white-space: nowrap` from the table container. Set `cellWrap: true` on a controller's `@Column` to let its default cell renderer wrap without a line limit. Other columns keep their existing layout.

```ts
@Column({
  name: "Access",
  type: new AccessSummaryType(),
  cellWrap: true,
})
```

Wrapping keeps secondary text such as scope hints visible without changing the data type, forms, or exports. Long unbroken text can break within the column. Rows grow to fit their content; column widths and pinning do not change.

`false` and omission both retain the theme default. A renderer's own `whitespace-nowrap`, fixed widths, or flex constraints still apply: use a wrapping or vertical container for a badge plus hint, and keep only the badge non-wrapping. This option does not create a tooltip or a disclosure control. Avoid hiding essential information inside a separately clamped child.

Standalone `TableColumn` definitions accept the same option. A custom `<column-id>-cell` slot replaces the default wrapper and owns its layout. `TableView` does not forward these slots. Alternate displays such as kanban are unaffected.

### Layout

`layout` decides how much a table draws around its rows. The default, `"full"`, is the dashboard grid: caption and count, a search button, filters, sort, refresh, the ⋯ table menu (columns, density, page size, export, import), column header menus and resizing, and a footer with the page size picker. `"compact"` is the list of a settings page: no caption (the page header names it, and the tabs move up into the header band), an always-open search field, quick filters, custom buttons, sortable headers, the row menu and a footer without the page size picker.

```ts [src/pages/members.ts]
static members = TableView(memberAPI, {
  layout: "compact",
  searchPlaceholder: "$page.members.search",
  quickFilters: [{ field: "roleIds", label: "$page.members.role" }],
  pageSize: 25,
  footer: { countLabel: "$page.members.count", hint: "$page.members.hint" },
});
```

Whatever the layout, a control shows only when it means something:

| Control         | Shown when                                                        |
| --------------- | ----------------------------------------------------------------- |
| Caption         | `caption` is set (without it, the tabs move up into the header).  |
| Search          | the controller declares `@Searchable` fields.                     |
| Filters         | a column is `filterable`.                                         |
| Export          | the caller holds the table's `export` action.                     |

A display's capabilities still apply on top (a kanban hides the tabs whatever the layout). Keyboard shortcuts, row actions, selection, presence, density and the `maxHeight` scroll area are unaffected.

### Quick filters

`quickFilters` draws one dropdown button per entry in the toolbar, listing the values of a `filterable` column: a select's items, a boolean's two labels, or the rows a relation points to (read from its `select` endpoint). Picking a value sets **the column's filter** — the very one the filters row edits — with the mode `array_contains_string` for a multiple select or relation, `is` otherwise, or the declared `mode` (`"is" | "is_not" | "include" | "exclude" | "array_contains_string"`); "All" (`allLabel`) clears it. Being a column filter, the value is kept with the table's state, counted as an active filter, shown as a chip in the filters row and cleared by "Reset filters". In the `compact` layout, which has no filters row, the button names the column and its value ("Role: Admin") next to a clear button. Registration throws for an unknown or non-filterable column.

### Link tabs

A tab can open another page instead of filtering (it then takes no `filter`) — sibling lists such as Members ↔ Invitations. Give it `to` (a page controller, whose URL and permission it follows, or a dashboard path with an optional `permission` id) and `countFrom` (a data controller, or its location) for its counter. A tab with the id `"all"` stands in for the implicit "all" tab, at its own position, with its own label and icon. `badge: true` publishes the tab's counter as the navigation badge of the page it stands for (the settings nav shows it):

```ts
tabs: [
  { id: "all", label: "$page.members.tabs.members", icon: "i-ph-users", badge: true },
  { id: "invites", label: "$page.members.tabs.invites", icon: "i-ph-envelope-simple",
    to: "/settings/user/members/invites", permission: "settings.user.invites",
    countFrom: "/api/tables/admin-invites" },
],
```

A link tab the caller may not open is left out when the layout is served; one whose list the caller may not read shows no counter.

### Cells drawn by a display

A column renders its cells through its data type's formatter. `display` on `@Column` draws the grid cells (and expanded-row fields) another way — forms, filters, validation and exports keep `type`, and the column keeps one label, its `name`. A display is a typed class, like a data type: its options are checked at compile time. The formatter receives the whole row, so a cell can compose sibling fields. `size` sets the column's default width in px (150 otherwise; room left is spread in proportion):

```ts
import { DefaultDisplays } from "@antelopejs/interface-dms/base/table-view";

@Column({
  name: "Member",
  type: new DefaultDataTypes.StringType(),
  size: 300,
  display: new DefaultDisplays.IdentityDisplay({
    avatarField: "avatar",
    subtitleField: "email",
    selfField: "userId",
  }),
})
declare name: string;
```

The DMS ships these displays (options in [Custom data types](/docs/extending-the-dashboard/custom-data-types#cell-data-types)): `IdentityDisplay` (avatar or icon tile, name, "You" tag, badges, secondary line), `PillsDisplay` (v2 role pills, or one filled pill such as an owner's crown), `RelativeDateDisplay` ("2 hr. ago", "Active now", "In 5 days", "Sep 27 · by Camille"), `IndicatorDisplay` (an on/off icon and word), `StatusPillDisplay` (a status pill toned per value, its cause under it), `ProgressDisplay` ("31 / 44" with a bar, failed items in red), `SparklineDisplay` (a series of numbers as a line), `DurationDisplay` ("910 ms", "4 min 12 s"), `BytesDisplay` ("1.4 MB") and `MonoDisplay` (an id in the mono font, with an optional copy button). The `status` type draws a v2 status pill.

A module declares its own display the same way: a class extending `ColumnDisplay<Options>`, registered with `@RegisterDisplay("<module>:<id>")` under the id of the frontend data type that draws it (`registerDataType`). Registration of the table throws for a display whose class was never registered.

```ts
@RegisterDisplay("automation:duration")
export class DurationDisplay extends ColumnDisplay<{ unit?: "s" | "ms" }> {}

@Column({ name: "Took", type: new DefaultDataTypes.NumberType(), display: new DurationDisplay({ unit: "ms" }) })
declare tookMs: number;
```

### Expandable rows

`expandable` adds a caret column in front of the content. Opening a row shows a detail band under it, on the muted surface: either the configured `fields` as a label/value list, or a registered frontend `component` that draws the whole band in their place. The option is a union, so giving both does not compile (and a schema-built option giving both, or neither, throws at registration).

```ts [src/pages/orders.ts]
static orders = TableView(orderDataAPI, {
  caption: "Orders",
  expandable: {
    // Column keys, or { key, label } to relabel one. Each value renders
    // through its column's data type, exactly like a grid cell.
    fields: [{ key: "shippingAddress", label: "Ship to" }, "carrier", "payment"],
    fieldsLabel: "Shipping & payment",
    defaultExpanded: "first", // "none" (default) | "first" | "all"
  },
});

static orderLines = TableView(orderLineAPI, {
  expandable: {
    // Resolved by name from the global frontend registry; draws the band.
    component: CustomComponent("OrderLinesDetail"),
    single: true, // opening a row closes the previous one
  },
});
```

| Option            | Type                                    | Default  | Purpose                                                                                                                                   |
| ----------------- | --------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `fields`          | `Array<string \| { key; label? }>`      | —        | Columns listed in the band (not with `component`). A field must name a declared `@Column` (registration throws otherwise) and be `@Listable` to carry a value.    |
| `fieldsLabel`     | `string`                                | —        | Eyebrow above the field list (`$`-prefixed: i18n key).                                                                                    |
| `component`       | `Component`                             | —        | Frontend component drawing the whole band (not with `fields`). It receives `row` (the listed row), `rowId` and `columns` (the column metadata), plus its own options. |
| `defaultExpanded` | `"none" \| "first" \| "all"`            | `"none"` | Rows open on arrival, and again whenever a new set is listed: page, page size, filter, search, sort, tab or archive view.                 |
| `single`          | `boolean`                               | `false`  | At most one row open at a time.                                                                                                           |

A field the grid should not show stays listed and takes `isVisible: false` on its `@Column`: it is then read off the row for the band only (the column manager can still show it). Data a component needs that is no column at all — order lines, a timeline — only has to be `@Listable` on the controller.

A refresh of the same set (the refresh button, a realtime update) keeps the rows the user opened, minus those no longer listed. The caret is a real button (`aria-expanded`, and `aria-controls` naming the band while it is open), so it works from the keyboard. It sits next to the selection checkbox and stays pinned with it, and the band spans the presence rail, the row actions and pinned columns; density, the `maxHeight` scroll area, archive mode and tabs apply as usual. Alternate displays (kanban, cards, custom displays) are unaffected.

### Filtering, search, and sorting

Filtering, search, and sorting need no page-side configuration — they come from the controller's decorators ([Data controller](/docs/components/data-controller)): a `filterable` column gets a filter offering its `DataType`'s operators, `@Searchable` fields feed the search box, and `@Sortable` columns get sortable headers.

While a search, a filter or a quick filter narrows the rows, the filters row and the "No results" empty state offer one clear action, named after what it clears ("Clear filters", "Clear search" or "Clear filters and search"). It drops the added filters, puts the `defaultFilters` back to their value, empties the search and the quick filters, and returns to page 1; sort, page size, tab, display, group-by and the archive view stay as they are. A chip's × removes that filter only.

What the page declares are **pre-applied filters**, in two forms. `defaultFilters` applies filters when the table opens, visible in the toolbar. `tabs` adds a tab strip where each tab applies its own filter, on one column; an implicit "all" tab is added automatically.

A tab pairs an `id` and a `label` (plus optional `icon`, `iconColor`, `textColor`) with its `filter`, on a single column: an `accessorKey`, a `mode`, and usually a `value` (several values of a list joined with commas). A tab filters **or** links (`to`, see [Link tabs](#link-tabs)): registration throws for a tab giving both. The `tabs` array below sits inside the `TableView(controller, { ... })` options object:

```ts [src/pages/tasks.ts]
tabs: [
  { id: "pending", label: "Pending", icon: "i-ph-clock",
    filter: { accessorKey: "status", value: "pending", mode: "is" } },
  { id: "high", label: "High priority", icon: "i-ph-fire", iconColor: "error",
    filter: { accessorKey: "priority", value: "high", mode: "is" } },
],
```

Each tab shows a row counter, and filter tabs with counters require the controller to mount `countBatch: TableViewRoutes.CountBatch` (`POST <location>/count/batch`); `TableView()` logs a warning at registration when a table declares `tabs` without it.

### Row actions

`rowActions` enables the per-row menu. Each built-in action takes a **boolean** or a `RowActionConfig` with optional `isEnabled`, `isVisible`, and `rule`:

| Action                | Needs route           | Effect                                                         |
| --------------------- | --------------------- | -------------------------------------------------------------- |
| `add`                 | `new`                 | Toolbar Add button (opens the new form).                       |
| `edit`                | `edit`                | Open the edit form.                                            |
| `details`             | `get`                 | Open the read-only view form.                                  |
| `duplicate`           | `new`                 | Open the new form pre-filled from the row (`?duplicate=<id>`). |
| `delete`              | `delete`              | Delete the row.                                                |
| `copyLink`            | `get`                 | Copy a deep link to the row.                                   |
| `archive` / `restore` | `archive` / `restore` | Soft-archive / restore (archive mode).                         |
| `hasSelection`        | —                     | Enable the selection checkbox column and bulk actions.         |
| `custom`              | —                     | Array of custom actions (below).                               |

A **rule** hides or disables the action per row by evaluating against the row's fields. Field operators are `equals`, `notEquals`, `in`, `notIn`; combine them with `and`, `or`, `not`:

```ts [src/pages/tasks.ts]
rowActions: {
  add: true,
  edit: { isEnabled: true, rule: { field: "status", notEquals: "completed" } },
  delete: {
    isEnabled: true,
    rule: {
      and: [
        { field: "status", notEquals: "completed" },
        { field: "priority", notEquals: "high" },
      ],
    },
  },
  hasSelection: true,
},
```

Rules are enforced **server-side** as well as in the UI:

- A delete/edit/archive/restore request for an ineligible row is filtered out.
- A non-strict edit whose single row is ineligible returns `403`.
- With `strictRuleValidation: true`, the whole request is rejected `400`.
- The rules are those of the controller's **writing** table view. A data controller has one: a `TableView` with at least one write action enabled (add, duplicate, edit, delete, archive or restore). Other pages may mount read-only table views over the same controller — every write action set to `false` — but a second writing one fails its page's registration at boot. To show the same data in two writing screens, derive a controller for the second one: see [Show the same data in two writing screens](/docs/components/derived-controller).

**Custom row actions** add menu entries that fire an `ActionTarget` rather than a built-in CRUD operation — the `custom` array below sits inside the `TableView`'s `rowActions`:

```ts [src/pages/tasks.ts]
custom: [
  {
    label: "Mark complete",
    icon: "i-ph-check-circle",
    target: { type: "api", url: "/api/task/complete", method: "POST",
              successMessage: "Task completed" },
    rule: { field: "done", equals: false },
  },
],
```

A custom row action can also take a `permission` (like a custom button below: stripped for a caller without it), a `color`, and — inline (`isVisible: true`) — a `variant` and `showLabel` to draw a labelled button ("Resend", "Revoke") rather than an icon. In the ⋯ menu, the row's own actions (details, edit, duplicate) come first, then the custom ones, then the destructive ones (delete, archive, restore) after a separator.

A built-in action's `RowActionConfig` can rename and re-icon it (`label`, `icon`: "Change roles" for `edit`); delete, archive and restore — the actions that run on a selection too — also take a `successMessage` toasted once they succeeded.

#### Bulk actions

`bulk: true` also offers a custom action on the selection bar (with `hasSelection`). It runs once for the selected rows: an `api`, `exportJob`, `page` or `external` target receives their ids as a repeated query parameter (`?ids=a&ids=b`), a `drawer` or `modal` component a `selection` prop (`{ ids, count }`), and a fixed confirmation's texts receive `{ count }` (a `{ from }` confirmation URL gets the ids too).

With `bulk: { allMatching: true }`, once the whole page is selected the bar offers "Select all N matching": the action is then sent `allMatching=true` with the table's current filters, search and archive view instead of ids (the export of the bar exports that whole query too, the built-in delete, archive and restore are not offered). The route finds the rows itself with `resolveBulkRowIds`, from inside a route of the table's data controller — it returns the selected ids, or every matching row read with the caller's `list` permission (at most `MAX_BULK_MATCHING_ROWS`, 10,000):

```ts
custom: [
  {
    label: "Re-run",
    icon: "i-ph-arrow-clockwise",
    bulk: { allMatching: true },
    confirm: { title: "$runs.rerun_title" },          // "Re-run {count} runs?"
    target: { type: "api", url: "/api/runs/rerun", successMessage: "$runs.rerun_done" },
  },
],

// on the data controller
@Post("rerun")
async rerun(@Context() ctx: RequestContext, @AuthUser() user: User) {
  const ids = await resolveBulkRowIds(this, ctx, user);
  // …restart them
  return { count: ids.length };
}
```

#### Row drawers

A custom action opening a `drawer` or a `modal` on a row hands its component a `navigation` prop, `{ index, total, hasPrev, hasNext, prev(), next() }`, over the rows the table shows; `prev()` and `next()` (and the J and K keys while it is open) show the neighbouring row in place, mounting the component anew. With `deepLink: true` the open row is kept in the URL (`?record=<id>`, `?<tableId>.record=<id>` on a page with several table views), so a link or a reload opens it again, even on a row the page does not list.

#### Confirmations

Every action — built-in or custom, whatever its target, and custom toolbar buttons — takes one `confirm` option, of one type, `ConfirmDialog`:

```ts
interface ConfirmDialog {
  title: string;
  description?: string;
  params?: Record<string, unknown>; // interpolated into the texts, besides the row's fields
  icon?: string;
  color?: ButtonColor;            // confirm button and header well
  confirmLabel?: string;
  cancelLabel?: string;
  impact?: { icon: string; label: string; count?: number | string }[];
  blocked?: boolean;              // explains why the action cannot run, with a close button
  confirmText?: string;           // type-to-confirm
  fields?: FormField[];           // values sent with the action's request
  component?: Component;          // escape hatch, drawn in the dialog's body
}

confirm?: ConfirmDialog | { from: string };
```

Texts are i18n keys (`$`) or literals; on a row action they receive the row's fields as parameters (`"Remove {name}?"`), and a numeric `params.count` pluralizes them. `{ from }` is a URL (`{id}` and the row's fields filled in) answering a `ConfirmDialog` — the confirmation the server words for that row, with its impact list, or a `blocked` explanation (the last owner of a workspace); build the answer with `serializeConfirmDialog(dialog)`. On delete, archive and restore it applies to one row: several rows at once keep the generic confirmation, which delete and archive always ask.

```ts
delete: { confirm: { from: "/settings/user/members/{id}/removal-confirm" } },
custom: [
  {
    label: "Refund",
    target: { type: "api", url: "/api/orders/{_id}/refund", body: { notify: true }, successMessage: "Refunded" },
    confirm: {
      title: "Refund {number}?",
      color: "warning",
      fields: [{ id: "reason", label: "Reason", type: new DefaultDataTypes.StringType(), required: true }],
    },
  },
],
```

The values of the dialog's `fields` are sent with the action's request: merged into an `api` target's `body` (the input winning), as the body of a delete, archive or restore. A request runs from inside the dialog: a refusal stays on screen, under its field when the server names one (a `{ field, message }` body or a validation issue), in the dialog's alert otherwise. Any other action (edit, a page target, a drawer…) runs once confirmed.

An `api` target may send a JSON `body` and copy a field of its response to the clipboard (`copy: "url"` for a share link).

A target can open a component in a drawer or a modal, navigate to an internal page or an external URL, run a quick action (`{ type: "quickAction", id }`), call an API endpoint, or run an async export job — each `ActionTarget` type and its fields are in [Actions & reactivity](/docs/building/actions-and-reactivity#action-targets). Custom toolbar buttons (`customButtons`) take the same target, plus a `variant` and a `color`.

A custom toolbar button can also declare a `permission`: either the id of one of the table's own actions (e.g. `"add"`) or an `Action` from another component (`otherTable.getAction("add")`). The button is stripped from the serialized options when the caller lacks the permission — same mechanism as the built-in actions. The route the button calls still needs its own guard (`@AuthUserWithPermission(...)`). Give it `placement: "header"` to draw it in the header of the page instead of the toolbar — the server adds it there, served as the table is (its permission and availability apply), and the table still runs it; the built-in add takes the same option (`rowActions: { add: { placement: "header" } }`). Give the button an `id` to expose it as a [quick action](/docs/building/navigation#quick-actions-the-command-palette) (`{ type: "button", page, button: "<id>" }`), which inherits this permission.

A custom toolbar button can also declare an `availability` resolver, called per request with `{ tenantId, user }` while the page layout is filtered. When it returns `{ reason }`, the button reaches the client disabled, with the reason (a string or a `$` i18n key) in its tooltip; a quick action pressing it shows the reason instead of opening the target. Returning `undefined` leaves it enabled, and a resolver that throws is logged and leaves it enabled too. It only shapes the UI: the operation behind the button must still refuse on its own.

### Archive mode

Set `archiveMode: true` **and** decorate a boolean field with `@ArchiveField()`; archive mode swaps delete for archive/restore.

- `TableView` throws at registration if `archiveMode` is set without an `@ArchiveField` on the controller.
- An `@ArchiveField` without `archiveMode` is accepted: it enables the archive filter on list without swapping the actions.
- Archive mode registers three permissions — `archive`, `restore`, `viewArchived`.

It also injects default rules so the right action shows per row: `edit`/`duplicate`/`archive` apply only when the archive field is **not** `true`; `restore`/`delete` apply only when it **is** `true`. Your own rule on any of these wins. These defaults are enforced server-side like any rule, and a row whose archive field was never written (created by a form that leaves it out) counts as active.

The `viewArchived` permission is enforced server-side: a client sending `showArchived=true` without it gets a hard **403**, not a silent empty list. Archive and restore are bulk PUT operations over selected `ids`.

### Kanban display

Setting `kanban` offers the built-in **kanban board** as an alternate display — cards grouped into columns by a field, with drag-and-drop between columns writing the group field back:

```ts [src/pages/tasks.ts]
static board = TableView(taskDataAPI, {
  caption: "Tasks",
  labelKey: "name",
  rowActions: { add: true, edit: true, delete: true },
  kanban: {
    groupByField: "status", // default grouping; users can switch to any eligible field
  },
  card: { fields: ["priority", "assignee"] },
  defaultDisplay: "kanban",
});
```

`KanbanOptions`:

| Option            | Type        | Default  | Purpose                                                                                                                                                                        |
| ----------------- | ----------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `groupByField`    | `string`    | required | The column cards group by. Must be a **non-multiple `SelectType`**, a `BooleanType`, or a `StatusType` column — anything else throws at registration.                          |
| `cardFields`      | `string[]`  | —        | **Deprecated** alias of the table view's `card.fields` (see [Cards](#cards)), removed in 0.5.                                                                                  |
| `cardComponent`   | `Component` | —        | **Deprecated** alias of the table view's `card.component`, removed in 0.5.                                                                                                      |
| `draggable`       | `boolean`   | `true`   | Allow dragging cards between columns to update the group field.                                                                                                                |
| `columnMaxHeight` | `string`    | `"60vh"` | Column height before the card list scrolls.                                                                                                                                    |

Kanban manages its own data (one query per column) and hides the filter tabs while active. Beyond kanban, a frontend layer can register entirely new displays — calendar, gallery, map — that inherit the whole toolbar: see [TableView displays](/docs/extending-the-dashboard/table-view-displays).

### Footer

`footer.summary` adds figures computed by the server over every row the table's filters, search and tab list — not only the page shown — after the row count: `{ label, field?, op: "sum" | "count", where?, format? }`. `where` is a row rule (the row actions' grammar) on the stored fields; a sum reads like its column's cells unless `format` (`Intl.NumberFormat` options) says otherwise. The controller mounts `summary: TableViewRoutes.Summary` (in `TableViewRoutes.All`); a table declaring summaries without it gets a registration warning. `footer.legend` names a select column whose items and colors the footer lists.

```ts
footer: {
  summary: [
    { label: "MRR", field: "mrr", op: "sum" },
    { label: "Past due", op: "count", where: { field: "status", equals: "past_due" } },
  ],
  legend: "status",
},
```

### Pagination

`pagination: "loadMore"` replaces the pager with a "Load more" button and `"infinite"` loads the next page when the footer scrolls into view; both show "20 of 128" and keep the rows loaded so far (a refresh or a realtime change re-reads them all), and a new filter, search, sort or tab starts over from one page. `pageSize` is the step.

### Empty states

`emptyStates` words the empty body in the module's terms: `firstRun` (no row yet; the add button stays), `filtered` (filters or search match nothing; "Clear search" / "Reset filters" stay) and `error` (the list failed; "Try again" stays). Each is `{ title, description?, icon?, actions?: BlockLinkAction[], component? }`; its texts are `$` i18n keys receiving `{ search }`, and `component` draws the whole state instead (it receives `state`, `search` and `refresh()`).

### Grouped display

`grouped` offers a display that keeps the grid's columns and draws a header row before each group of rows sharing a value of `groupByField` — a status, or, with `by: "day"` or `"week"`, the calendar day or week of a date ("Today · 29 Sept", "Week of 21 Sept"). The rows are listed sorted on that column (it must be `@Sortable()`), paged as usual, and a page starting inside a group repeats its header. `collapsible` folds a group from its header; `count` shows each group's row count, read from the controller's `countBatch` route. There are no aggregates.

```ts
grouped: { groupByField: "startedAt", by: "day", collapsible: true, count: true },
defaultDisplay: "grouped",
```

### Views

`views` declares named states of the table. A view sets everything at once — `filters` (on filterable columns), `search`, `sort`, `columns` (`visible`, `hidden`, `order`), `display` (a view may open the `grouped` or `kanban` display) and `density` — and what it leaves out falls back to the table's defaults. Views are drawn as tabs (`layout: "tabs"`, the default), a strip of pills above the status tabs (`"strip"`) or a menu in the toolbar (`"menu"`); `defaultView` opens on a first visit; `count: true` shows the view's row count; `permission` (a permission id) serves the view only to the callers holding it.

```ts
views: {
  layout: "strip",
  defaultView: "all",
  userViews: true,
  items: [
    { id: "all", label: "All runs", icon: "i-ph-squares-four" },
    { id: "failing", label: "Failing", tone: "error", count: true,
      filters: [{ accessorKey: "status", mode: "is", value: "failing" }] },
    { id: "mine", label: "Mine", count: true,
      filters: [{ accessorKey: "ownerId", mode: "is", value: "{{user.id}}" }] },
    { id: "timeline", label: "Timeline", display: "grouped" },
  ],
},
```

A filter value may hold tokens the server resolves on every request, so the rows and the counters follow the caller and the clock: `{{user.id}}`, `{{now}}`, `{{now-7d}}`, `{{now+14d}}`.

Changing the filters, search, sort, columns or density of the open view marks it modified, with **Reset** (back to the view) and, with `userViews: true`, **Save as new view**: a user's own views are kept with their table preferences, served to them only, and can be saved over or deleted. A view of the module is never overwritten, and opening another view and coming back opens it clean.

The URL opens a view or a tab: `?<tableId>.view=<id>` and `?<tableId>.tab=<id>`, where `tableId` is the table's key in its page; the short `?view=` / `?tab=` only when the page carries a single table view (with several, it is ignored, with a warning in development). A view the caller cannot open — another user's, or an unknown id — falls back to the default view, with a message. On the backend, `tableViewLink(page, tableId, { view, tab })` builds such a link (for a StatStrip item, a KPI card or a notification).

### Cards

The kanban board and the built-in `cards` display (offered with `displays: [{ id: "cards" }]`) draw one card per row, from one shared `card` option. Left out, a card shows the row's label (`labelKey`) and a few of its columns; `fields` picks those columns, each rendered by its column DataType, and `component` draws the whole card instead:

```ts [src/pages/tasks.ts]
static tasks = TableView(taskDataAPI, {
  labelKey: "name",
  kanban: { groupByField: "status" },
  displays: [{ id: "cards" }],
  card: { component: CustomComponent("TaskCard") }, // or { fields: ["priority", "assignee"] }
});
```

A card component (resolved by name from the global registry) receives the same props in both displays (`TableViewCardProps`): `row`, `rowId`, `columns`, `labelKey`, `actions` (the table's row actions, with `canEditRow(row)` / `canDeleteRow(row)`), `selected` and `select(value?)` for the row's selection, and `open()`, which does what a click on the row does in the grid. On the board it also receives `groupValue`, the value of the column it sits in. `card.fields` must name declared columns (registration throws otherwise).

### Form containers

`formContainer.type` controls where the add/edit/view form opens:

- **`page`** (default) — `TableView` auto-generates hidden sub-pages at `<page slug>/<key>/new`, `<page slug>/<key>/:id/edit` and `<page slug>/<key>/:id/view`, each gated by the matching permission. `<key>` is the key the table view is mounted under — `static invoices = TableView(...)` gives `.../invoices/new` — so several table views on one page, nested ones included, each get form pages of their own. A page entry of `formContainer.pages` (`new`/`edit`/`details`) can also set its `urlSlug`: a declared slug is relative to the page with **no key segment inserted**, which is full control over the URL; custom edit/details slugs **must** contain `:id`. Set `customPage: true` to skip auto-generation and register the page yourself. Two table views resolving to the same form URL fail the page's registration, naming both.
- **`drawer`** — slides in from the side.
- **`modal`** — opens centered; accepts a `size`.

Whatever the container, `formContainer.pages` titles the forms: each of `new`, `edit` and `details` takes a `displayName` and a `description` (`$`-prefixed: i18n keys). Left out, the forms read "New entry", "Edit entry" and "Entry details", a drawer or modal naming the `caption` in its description; the row's label (`labelKey`) follows the edit and details titles.

Whatever the container, the form behaves the same way with [unsaved changes](/docs/components/forms#unsaved-changes): its Save and Discard buttons show once a value changed, its footer sticks to the bottom of the page, drawer or modal when the form is longer than it, and closing the drawer or modal, leaving the page or going back in the browser with changes not saved asks first in a warning dialog. A clean form shows Cancel in their place, in the same spot: it closes the drawer or modal, or, on a form page, goes back to the list. Navigating to another page closes an open drawer or modal.

Forms are built from the controller's `@Column` fields, honoring `@Access`, `@Mandatory`, `readonlyBehavior`, and `@ColumnGroup`. See [Forms](/docs/components/forms).

### Export jobs

When the `ExportRoutes` are present, the Export button runs an **asynchronous job**, not a synchronous download: it exports the `@Exported` fields for the current filter/sort in the background, shows progress, and downloads the file on completion. Exports are **CSV** with **download** delivery — the only exporter and deliverer shipped.

- A job that exceeds its execution limit (10 minutes by default) is marked failed.
- Artifacts older than 24 hours are swept by a built-in cron.
- Jobs are private to the requesting user and tenant.

The engine behind this is reusable for your own exports — see [Backend services](/docs/building/backend-services#the-export-job-engine).

### Events & realtime

With `realtime` on (the default), the table broadcasts row mutations (`created` / `updated` / `deleted`) to other viewers — their tables refresh live — and tracks edit **presence**: opening a row's edit form acquires a row lock, and other viewers see who is editing (with a warning dialog before a concurrent edit). Set `realtime: false` to opt a table out.

The rendered table also emits component events — `TableViewEvents`: `ROW_CLICK`, `ROW_SELECT`, `ROW_ADD`, `ROW_EDIT`, `ROW_DELETE`, `FILTER_CHANGE`, `SORT_CHANGE`, `EXPORT` — that other components can react to through watch-actions ([Actions & reactivity](/docs/building/actions-and-reactivity#events-components-emit)). On the function side, `TableViewFunctions` ships one watchable id, `CUSTOM_PAGE_FORM_SUCCESS` (a `url`, optional `preserveQuery`): after a custom-page form succeeds, it navigates back to the table, restoring filters. `{{params.X}}` / `{{query.X}}` tokens in `url` are resolved against the current route first.

### Guards

`guards` runs a server-side check before a mutating action commits. `this` inside a guard is the **data controller instance**, so `@Model`-bound models are reachable. Throw with `assert(...)` from `@antelopejs/interface-api-util` to abort with an HTTP status and an i18n message key:

```ts [src/pages/tasks.ts]
import { assert } from "@antelopejs/interface-api-util";

guards: {
  edit: (ctx, { id, body, current }) => {
    assert(current.status !== "locked", 403, "$tasks.locked");
  },
  delete: (ctx, { ids }) => { /* … */ },
},
```

Guards exist for `edit`, `delete`, `archive`, `restore`, and `new`, each receiving the relevant ids/body (and, for `edit`, the `current` row).

A refusal that belongs to one field of the form (a name already taken, a value out of range) should say so: throw an `HTTPResult` whose body is `{ message, field }` — `field` being the field id — and the form shows the message under that field instead of a toast. `values` (optional) names the offending values of a list field (the invite form marks those addresses):

```ts [src/pages/tasks.ts]
import { HTTPResult } from "@antelopejs/interface-api";

guards: {
  new: async function (ctx, { body }) {
    if (await this.tasks.getByTitle(body.title)) {
      throw new HTTPResult(409, { message: "$tasks.title_taken", field: "title" });
    }
  },
},
```

The form reads the same way the zod issues `assertValidation` answers with (each issue's first path segment is its field) and the data API's `Missing mandatory fields: …` / `Invalid field type(s): …`. Anything else — a 403, a 429, a server error, a refusal naming no field the form shows — stays a toast.

## Permissions

Several table views may share one data controller (an overview and the screen that edits the rows), as long as only one of them writes: its data routes are shared, so each read action is guarded by the permission of **every** table view mounting it — a caller holding `list` on any of those tables may list, exactly what that table already exposes — and each write action by the writing table view's alone. A table view no page mounted carries no permission and is ignored. Two screens that both write need two controllers: see [Derived controllers](/docs/components/derived-controller).


Every table action registers its own permission, named `<componentPermissionId>.<actionId>`. The component permission id is the page's permission id (its full id, unless the page declares `permission.id`) followed by every field/child id in the table's position; each action appends its id — `list`, `select` (granted by default), `add`, `edit`, `view`, `delete`, `export`, plus `archive`/`restore`/`viewArchived` in archive mode. These same per-action permissions gate the row actions.

The table is **filtered per user**: it strips the forms and row actions the caller lacks before the page renders, and the matching routes reject unauthorized calls server-side. As a special case, if the `edit` action has no rule, the table force-disables `details` (the edit form already covers viewing). See [Auth & permissions](/docs/auth-and-tenancy/auth-and-permissions).
