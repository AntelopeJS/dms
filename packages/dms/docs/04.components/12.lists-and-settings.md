# Lists & settings

The blocks on this page cover what a settings screen or an overview is made of beyond charts and tables: a feed of recent events, a bar telling how much of a quota is used, and the titled sections whose rows hold a label, its help text and a control. Each is a builder you declare on a page like any other ([Pages & components](/docs/building/pages-and-components)); the playground shows all of them under **Blocks**.

```ts [src/pages/workspace.ts]
import {
  ActivityFeed,
  FieldRow,
  Meter,
  Section,
} from "@antelopejs/interface-dms/base";
```

## ActivityFeed

**What it renders.** A card with an eyebrow title and optional link buttons ("View all"), then one row per event: a tinted icon well, the title, dimmed details joined by "·", the time on the right and an accent dot for an unread event. Events are filed under day separators — "Today · Sep 29", "Yesterday · Sep 28", the weekday within the week, then the date — each row showing its time; with `groupByDay: false` the rows say how long ago instead. A skeleton shows while the first answer loads, an empty state when there is nothing, and an error state with a retry when the source fails.

```ts
static activity = ActivityFeed({
  title: "Activity",
  fetchUrl: "/api/activity",
  maxItems: 8,
  actions: [{ label: "View all", to: "/audit" }],
});
```

The source answers the entries newest first, as `{ items }` like every [list block](/docs/components/display-blocks#live-items); in the page editor it is picked in the data-source picker:

```ts
@Get("activity")
list() {
  return {
    items: [
      {
        icon: "i-ph-check-circle",
        tone: "success",
        title: "Order #10481 paid",
        meta: ["Globex Logistics", "€860.50", "Stripe"],
        date: "2026-09-29T09:18:00Z",
        to: "/orders/10481",
      },
    ],
  };
}
```

| Option           | Type                      | Default | Purpose                                                                     |
| ---------------- | ------------------------- | ------- | --------------------------------------------------------------------------- |
| `title`          | `string`                  | —       | Eyebrow title of the card head.                                             |
| `items`          | `ActivityFeedItem[]`      | —       | Entries shown when no source is set.                                        |
| `fetchUrl`       | `string`                  | —       | Route answering `{ items }`.                                                |
| `fetchUrlMethod` | `HttpMethod`              | `GET`   | Method of the fetch.                                                        |
| `groupByDay`     | `boolean`                 | `true`  | Day separators with times; off, relative times ("14 min ago").              |
| `maxItems`       | `number`                  | —       | Shows at most this many entries.                                            |
| `fillHeight`     | `boolean`                 | `false` | Fills its grid cell; the entries scroll inside (see below).                 |
| `skeletonCount`  | `number`                  | —       | Placeholder rows while loading. Optional. Defaults to `maxItems`, or 3.     |
| `actions`        | `BlockLinkAction[]`       | —       | Link buttons in the card head ("View all").                                 |
| `empty`          | `{ title, description? }` | —       | Empty state; the title defaults to "No activity yet".                       |
| `mono`           | `boolean`                 | `false` | Mono titles and details, for paths, queries and request logs.               |
| `card`           | `boolean`                 | `true`  | The card frame and its head; off, the bare list (inside a `Section`, say). |

Beside another card in a grid row, `fillHeight: true` leaves the row's height to that card: the feed stretches to it and its entries scroll under the fixed head, each day separator staying on top of its entries. Once the grid stacks its cells, the list takes its own height, scrolling past 24rem. The scroll area is focusable and named after the title, so the keyboard scrolls it too. The settings overview sets it on "Recent account activity", next to "Your account".

An entry (`ActivityFeedItem`) has a `title` and optionally an `icon`, a `tone` (`Tone`: `neutral`, `primary`, `secondary`, `success`, `warning`, `error`, `info`), `meta` (details), `date` (ISO, for the day and the time), `time` (literal text in place of the time), `unread` and `to` (makes the row a link). Titles and details are translated when they are `$`-prefixed i18n keys.

On the frontend each row is a `DmsActivityItem`, the feed preset of the generic `DmsListRow` (icon well or avatar, title, "·"-joined meta, trailing slot, unread and current states) that the settings pages also use for sessions and notifications.

## Meter

**What it renders.** An "x of y" bar (v2 `.c-meter`): the label, a dimmed hint and the value on one line, the bar under it, then an optional legend. One value fills the bar in its tone; `segments` stack several fills — members and pending invites in the seats meter — each with its legend label. `warnAt` and `errorAt` turn a single fill and the value text warning or error past a percentage of `max`.

```ts
static seats = Meter({
  label: "Seats",
  hint: "8 in use · 2 free",
  max: 10,
  segments: [
    { value: 6, label: "6 members" },
    { value: 2, tone: "soft", label: "2 pending invites" },
  ],
  legend: true,
  actions: [{ label: "Manage members", to: "/settings/members" }],
});
```

| Option               | Type                                           | Default    | Purpose                                                              |
| -------------------- | ---------------------------------------------- | ---------- | -------------------------------------------------------------------- |
| `label`              | `string`                                       | —          | Name of the measure.                                                 |
| `hint`               | `string`                                       | —          | Dimmed note after the label.                                         |
| `value`              | `number`                                       | `0`        | Filled amount; ignored when `segments` is set.                       |
| `max`                | `number`                                       | `100`      | Total the bar stands for.                                            |
| `segments`           | `MeterSegment[]`                               | —          | Stacked fills: `{ value, tone?, label? }`.                           |
| `legend`             | `boolean`                                      | `false`    | Shows the segment labels under the bar.                              |
| `format`             | `"fraction" \| "percent" \| "value" \| "none"` | `fraction` | Value text: `8 / 10`, `80%`, `8` or nothing.                         |
| `valueLabel`         | `string`                                       | —          | Replaces the formatted value text ("38.2 / 50 GB").                  |
| `tone`               | `MeterTone`                                    | `primary`  | Fill of a single value: a `Tone`, or `soft` (pending, reserved).     |
| `warnAt` / `errorAt` | `number`                                       | —          | Percent of `max` from which the fill turns warning / error.          |
| `size`               | `"xs" \| "sm" \| "md"`                         | `sm`       | Bar height: 4, 6 or 8 px.                                            |
| `fetchUrl`           | `string`                                       | —          | Route answering any of `{ value, max, segments, hint, valueLabel }`. |
| `card`               | `boolean`                                      | `false`    | Wraps the meter in a padded card.                                    |
| `actions`            | `BlockLinkAction[]`                            | —          | Link buttons under the bar, on the right.                            |

Figures that change per request — seats used, quota left — come from `fetchUrl`: a page layout is built once, when the page registers. A meter is one measure, not a list, so its route answers an object (any subset of those fields) rather than `{ items }`; the page editor picks it in the same data-source picker.

## Section and FieldRow

**What they render.** `Section` is the v2 settings block (`.st-block`): a 15px title and one line of description above a card. `FieldRow` is one row of that card (`.st-row`): a label with its help text and a control, set apart from the next row by a hairline. Together they compose a settings page from the backend, the way the core settings pages are drawn.

```ts
static plan = Section({
  title: "Plan & usage",
  description: "Seats, storage and API calls of the workspace.",
})
  .child(
    "seats",
    FieldRow({ label: "Seats", description: "Billed monthly.", layout: "form" })
      .child("meter", Meter({ max: 10, value: 8 })),
  )
  .child(
    "storage",
    FieldRow({ label: "Storage", layout: "form" })
      .child("meter", Meter({ value: 38.2, max: 50, valueLabel: "38.2 / 50 GB" })),
  );
```

| `Section` option | Type      | Purpose                                                                         |
| ---------------- | --------- | ------------------------------------------------------------------------------- |
| `title`          | `string`  | Heading above the card.                                                         |
| `description`    | `string`  | One line under the heading.                                                     |
| `danger`         | `boolean` | A block of destructive actions: red frame and title.                            |
| `card`           | `boolean` | The card frame around the children, `true` by default; off for a grid or a feed. |

| `FieldRow` option | Type                            | Default  | Purpose                                                                                       |
| ----------------- | ------------------------------- | -------- | --------------------------------------------------------------------------------------------- |
| `label`           | `string`                        | —        | Row label.                                                                                    |
| `description`     | `string`                        | —        | Help text under the label.                                                                    |
| `layout`          | `"inline" \| "form" \| "stack"` | `inline` | `inline`: compact control on the right. `form`: 240px label column. `stack`: label above.   |
| `required`        | `boolean`                       | `false`  | Red asterisk after the label.                                                                 |
| `disabled`        | `boolean`                       | `false`  | Dims the row.                                                                                 |

Both are containers. A field row holds one block that stands on its own — a meter, a banner, a status. Fields someone fills in and submits do not go in field rows: they belong to a [`Form`](/docs/components/forms), which owns their values, validation and submit, and which lays them out as section rows by itself (below). This keeps one way to declare a field.

The blocks render as `dms-activity-feed-block`, `dms-meter-block`, `dms-section-block` and `dms-field-row-block`. On the frontend the same pieces are the generic `DmsSection` (`:card="false"` drops the frame), `DmsFieldRow`, `DmsSaveBar`, `DmsSaveStatus` and `DmsInstantSaveBadge` components, usable in any custom page.

### A form in a section

A `Form` placed in a `Section` with its card drops its own card: its fields become the section's rows, with the 240px label column of a `form` field row. With the default `saveMode: "bar"` it saves through the sticky save bar (v2 `.st-savebar`): it offers Cancel while nothing changed when the form has somewhere to go back to (`backTo`), then, once a field differs from what the form loaded, names the changed fields and offers Discard and Save; saving brings Cancel back.

```ts
static profile = Section({ title: "Workspace profile" }).child(
  "form",
  Form({
    fetchUrl: "/api/workspace",
    submitUrl: "/api/workspace",
    fields: [
      { id: "name", label: "Name", type: new DefaultDataTypes.StringType(), required: true },
      { id: "description", label: "Description", type: new DefaultDataTypes.StringType({ textarea: true }) },
    ],
  }),
);
```

The bar works on a form outside a section too, in its own card (`saveMode: "footer"` puts the buttons in the form's footer instead); in a drawer or a modal the form keeps the container's footer. A record form's bar shows Cancel while nothing changed and Discard and Save once something did, at the same height, so switching never moves the content, and leaving the page with unsaved changes asks first (see [Unsaved changes](/docs/components/forms#unsaved-changes)). A custom page gets the same with `DmsSaveBar` plus `useUnsavedChanges`: without `cancellable` the bar hides while clean but keeps its place (the Profile and Roles settings pages).

### Instant save or a save bar

A settings page saves in one of two ways, never both:

- **A save bar.** Edits wait in a draft until the person presses Save in the sticky `DmsSaveBar` (or a `Form`, whose default `saveMode` is `"bar"`). The page header shows no save pill.
- **Instant save.** Each control writes as soon as it changes — a switch, a theme tile, a language picker. The page header shows the **Saved instantly** pill at its top right: the shared `DmsInstantSaveBadge`, the same pill with the same words on every such page, red while a save failed. A `DmsSaveStatus` stamp next to a control may still say which control just saved (*Saving*, *Saved*, or *Not saved* with a **Retry** button emitting `retry`), but it does not replace the header pill.

On the backend, a `Form` with `saveMode: "instant"` does all of it: each field saves on its own, shows its state, and the form puts the pill in the page header ([Saving a form](/docs/components/forms/saving#instant-save)). The DMS's Language & region page is such a form, with sections of its own.

A Vue page component (or the section that owns the instant-save controls) puts the pill in the header with `useInstantSaveHeader`, which renders it through `usePageHeaderActions`. Pass a getter of the page's save activity — `combineSaveStates` folds the state of each control into one (`saving` while any control writes, then `error` while any failed, then `saved`) — to make the pill's icon spin while a change is written, tick once it is, and turn red on a failure. Call it before the first `await` of the setup, so the pill is in the server-rendered header:

```ts
import { reactive } from "vue";
import type { SaveStatusState } from "#dms-ui/app/components/save-bar/SaveStatus.vue";
import {
  combineSaveStates,
  useInstantSaveHeader,
} from "#dms-layout/app/composables/layout/useInstantSaveHeader";

// one "idle" | "saving" | "saved" | "error" per control, set by its own save
const states = reactive<Record<string, SaveStatusState>>({ theme: "idle", density: "idle" });
useInstantSaveHeader(() => combineSaveStates(Object.values(states)));
```

In the DMS, Appearance, Language & region and Notifications are instant-save pages; Profile and the roles editor use a save bar; Security, Members and invitations act through explicit buttons and dialogs, and the OS switch of Keyboard shortcuts only changes the view, so none of them shows the pill.

## Permissions

These blocks follow the page's [Auth & permissions](/docs/auth-and-tenancy/auth-and-permissions) like any component: each child of a section or a field row has its own permission, and a child the user may not see is left out of the layout. The routes behind `fetchUrl` guard themselves.
