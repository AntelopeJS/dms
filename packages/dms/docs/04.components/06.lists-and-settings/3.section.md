# Section & field row

`Section` is the settings block: a title and one line of description above a card. `FieldRow` is one row of that card: a label with its help text and a control, set apart from the next row by a hairline. Together they compose a settings page from the backend, the way the core settings pages are drawn.

## FieldRow

::block-playground{type="FieldRow" height="140"}
---
options:
  label: Storage
  description: Files, images and exports.
  layout: form
children:
  - id: meter
    type: Meter
    options:
      value: 38.2
      max: 50
      valueLabel: 38.2 / 50 GB
---
::

::block-options{type="FieldRow"}
::

| `layout` | The row looks like |
| -------- | ------------------ |
| `inline` | A compact control on the right. The default. |
| `form`   | A 240px label column, the control beside it, once the row is 560px wide (its own width, not the window's); the label above the control when narrower. |
| `stack`  | The label above the control. |

## Usage

```ts [src/pages/workspace.ts]
import { FieldRow, Section } from "@antelopejs/interface-dms/base/section";
import { Meter } from "@antelopejs/interface-dms/base/meter";

static plan = Section({
  title: "$app.workspace.plan_title",
  description: "$app.workspace.plan_description",
})
  .child(
    "seats",
    FieldRow({ label: "$app.workspace.seats", layout: "form" })
      .child("meter", Meter({ fetchUrl: "/api/workspace/seats" })),
  )
  .child(
    "storage",
    FieldRow({ label: "$app.workspace.storage", layout: "form" })
      .child("meter", Meter({ fetchUrl: "/api/workspace/storage" })),
  );
```

A field row holds one block that stands on its own — a meter, a banner, a status. Fields someone fills in and submits do not go in field rows: they belong to a [`Form`](/docs/components/forms), which owns their values, validation and submit.

## A form in a section

A `Form` placed in a `Section` drops its own card: its fields become the section's rows, with the 240px label column of a `form` row. With the default `saveMode: "bar"`, it saves through the sticky save bar, which names the changed fields and offers Discard and Save.

```ts [src/pages/workspace.ts]
static profile = Section({ title: "$app.workspace.profile" }).child(
  "form",
  Form({
    fetchUrl: "/api/workspace",
    submitUrl: "/api/workspace",
    fields: [
      { id: "name", label: "$app.workspace.name", type: new DefaultDataTypes.StringType(), required: true },
      { id: "description", label: "$app.workspace.description", type: new DefaultDataTypes.StringType({ textarea: true }) },
    ],
  }),
);
```

## Instant save or a save bar

A settings page saves in one of two ways, never both:

- **A save bar.** Edits wait in a draft until the person presses Save in the sticky save bar — the default of a `Form`. The page header shows no save pill.
- **Instant save.** Each control writes as soon as it changes. The page header shows the **Saved instantly** pill, which reads *Saving* while a change is written and turns red with *Not saved* on a failure. A `Form` with `saveMode: "instant"` does all of it ([Saving a form](/docs/components/forms/saving#instant-save)).

A custom Vue page puts the same pill in the header with `useInstantSaveHeader`, fed by `combineSaveStates`:

```ts [app/pages/appearance.vue]
import { reactive } from "vue";
import type { SaveStatusState } from "#dms-ui/app/components/save-bar/SaveStatus.vue";
import {
  combineSaveStates,
  useInstantSaveHeader,
} from "#dms-layout/app/composables/layout/useInstantSaveHeader";

const states = reactive<Record<string, SaveStatusState>>({ theme: "idle", density: "idle" });
useInstantSaveHeader(() => combineSaveStates(Object.values(states)));
```

Call it before the first `await` of the setup, so the pill is in the server-rendered header. In the DMS, Appearance, Language & region and Notifications are instant-save pages; Profile and the roles editor use a save bar.

## Pitfalls

- `card: false` drops the section's frame, for a grid or a feed under a heading.
- On the frontend, the same pieces are `DmsSection`, `DmsFieldRow`, `DmsSaveBar`, `DmsSaveStatus` and `DmsInstantSaveBadge`, usable in any custom page.
- On the frontend, a stacked `DmsFieldRow` takes `fill`: the row and its control grow in their flex parent, for a control that fills it (`DmsInputCode fill`, see [A body that fills the drawer](/docs/frontend-composables/ui-toolkit#a-body-that-fills-the-drawer-and-its-footer)).
