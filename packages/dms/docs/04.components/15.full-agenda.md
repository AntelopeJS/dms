`FullAgenda` is a calendar block: the events of a module drawn by month, week, day, list or year, in columns per resource or on a timeline per resource, moved and resized by dragging, created by a click and edited in a details form. Its events come from a route of the module, not from a data controller, and its changes go back to another route, one at a time or together from a save bar.

Reach for it when time is what the user arranges: a team's meetings, room bookings, a store's shifts, a resource planning, leave over a year. A list of dated records read and edited one by one is a [table view](/docs/components/tables); a grid of values edited cell by cell is a [Matrix](/docs/components/matrix).

The preview draws events given in its options (`staticData`) and saves nothing. In the playground, the **Agenda** category holds an overview page that names the page showing each option, and eight agendas that read and save through routes: a team calendar, room bookings, a resource planning, a store schedule, a staff roster, leave over a year, a sales agenda in a boxed page, and agendas inside a grid column, a modal and a drawer.

## Usage

```ts fragment [src/pages/bookings.ts]
import { FullAgenda } from "@antelopejs/interface-dms/base/full-agenda";

static agenda = FullAgenda({
  title: "Room bookings",
  fetchUrl: "/api/bookings/events",
  saveUrl: "/api/bookings/save",
  resources: [
    { id: "room-a", label: "Room A" },
    { id: "room-b", label: "Room B" },
  ],
  views: [{ id: "rooms", type: "resources", label: "Rooms" }, "week", "list"],
  businessHours: [{ days: [1, 2, 3, 4, 5], start: "08:00", end: "19:00" }],
  create: { trigger: "click" },
  details: { container: "drawer" },
});
```

```ts fragment [src/api/bookings.ts]
import { Context, Controller, Get, JSONBody, Post, type RequestContext } from "@antelopejs/interface-api";
import type {
  AgendaData,
  AgendaSaveRequest,
  AgendaSaveResponse,
} from "@antelopejs/interface-dms/base/full-agenda-types";

export class BookingsController extends Controller("/api/bookings") {
  @Get("events")
  events(@Context() ctx: RequestContext): AgendaData {
    const from = ctx.url.searchParams.get("from");
    const to = ctx.url.searchParams.get("to");
    return { events: bookingsBetween(from, to) };
  }

  @Post("save")
  save(@JSONBody() body: AgendaSaveRequest): AgendaSaveResponse {
    return writeBookings(body.changes);
  }
}
```

Guard both routes as any other route of the module (`@AuthUserWithPermission(...)`): the agenda only draws what they answer and sends what the user did.

## Views

`views` lists what the view switcher offers, each a type or an object naming its `id`, `type`, `label` and its own settings:

- `day`, `week` and `days` (`duration` days, 3 by default) draw a time grid, a column per day, with the all-day row (`allDayRow`) above it and the current time (`nowIndicator`);
- `month` draws six weeks of day cells, events as chips, "+N more" past `maxEventsPerDay`;
- `year` draws twelve months, as a planner (a row per month, `yearLayout: "planner"`) or as twelve small months;
- `list` lists the events of `duration` days (30 by default) under their day;
- `resources` draws a column per resource (per resource and day over several days, `resourceLayout: "resourcesFirst"` or `"daysFirst"`); `resourcesAtOnce` shows at most that many at a time, picked in the sidebar's resource list;
- `timeline` draws a row per resource, time running left to right, by hour, by named slot (`scale: "slot"` with `slots`) or by day.

`initialView`, `initialDate`, `minDate` and `maxDate` set where the agenda opens and how far it goes; `weekStartsOn` and `hiddenDays` shape a week; `dayStart`, `dayEnd`, `slotMinutes`, `snapMinutes`, `hourHeight` and `scrollTime` shape the time grid; `businessHours`, on the agenda or on each resource, shade the closed hours. Every time is drawn in `timeZone` (the reader's zone by default): an agenda of a place keeps that place's hours wherever the reader is.

## Reading the events

`fetchUrl` answers `AgendaData`: the `events`, and optionally the `calendars`, `calendarGroups`, `resources`, `resourceGroups`, `backgrounds` (closed hours, holidays, highlights), the `unscheduled` items to plan, the agenda's `notices`, and `fieldOptions`, the choices of the form's selects by field id when they change with the data (the kinds of a booking and the length each presets). The block reads it again whenever the range changes, with `from` and `to` (the first and last day shown), `view`, `tz`, `q` (the search, once typing pauses), `calendars` (the calendars the legend shows, under `legend.serverFilter`) and `facet_<id>=a,b` per facet in use. `realtimeTopic` reads it again on each event of its topics, and `periodScope` follows a `PeriodSelector` of the page.

An event has an `id`, a `title`, a `start` (an ISO instant, or a day for an all-day event) and an `end`, and optionally its `calendarId`, `resourceIds`, `location`, `description`, `status` (`confirmed`, `tentative`, `cancelled`), `color`, `icon`, `avatar`, `badges`, `issues`, a `recurrence` (daily, weekly, monthly or yearly, with `interval`, `weekdays`, `until`, `count` and `exceptions`) and its own `data`. What the chip shows besides the title follows `eventContent`.

A few fields describe what every chip must show whatever its height: `mark` (the step a booking is at, an icon on a disc of its tone), a badge flagged `alert` (an alert about the event's subject, drawn as one icon in the tone of the strongest) or `pinned` (a state such as an overbooked slot), and `statusLabel`, the word the chip's accessible name gives a status (a no-show drawn as cancelled). `revision` is the version the route drew; the block sends it back with each change of the event, so the route decides on what the user saw. `changeableFrom` is the first day a change of a series may still alter.

`staticData` gives the events in the options instead, for an agenda without a route.

## Editing and saving

With `saveUrl` set, the agenda is editable: `dragMove` moves an event to another time, day or resource, `dragResize` stretches its end, `copyOnAltDrag` copies it, a click or a double click on empty time creates one (`create`), and `rangeSelect` with `selectAction` runs a target on a picked range. `constraints` (within business hours, minimum and maximum lengths, overlaps) and each event's `allowedResourceIds` are checked as the user drags, and a refused drop goes back with the reason.

`saveUrl` receives `AgendaSaveRequest`: the `changes` (each a `kind` of `create`, `update`, `move`, `resize`, `delete`, `schedule` or `unschedule`, the event's `id` or the new one's `tempId`, the `patch` of the fields it sets, the `previous` values, and on a recurring event the `occurrence` and the `scope` the user picked), `force` and `overwrite` when the user confirmed, the block's `conflicts` mode, and the range and view shown. A `null` in a patch clears that field.

- `saveMode: "immediate"` (default) writes each change at once, with an Undo for `undoSeconds`.
- `saveMode: "staged"` keeps the changes, draws them as not saved yet, and writes them together from a save bar or Ctrl+S; `review` lists them first.

The answer, `AgendaSaveResponse`, replaces the `events` it returns (a new one carrying the `tempId` it answers), drops the `removed` ones, and may answer new `unscheduled` items, `notices` or `backgrounds`. A change named in `errors` goes back with its `message`; an error that names a `field` is shown under that field of the form, which stays open on it, and `retryable: false` offers no Retry. `confirm` asks a question first: the user's yes sends the same changes again with `force`. Under `conflicts: "detect"` the route compares `previous` with what it holds and answers a `conflict` with the `current` event: the agenda offers Overwrite or Discard. `message` is a toast (`messageStays` keeps it until it is closed), and `refresh` makes the block read its range again.

A change to an occurrence of a recurring event asks which part it applies to (`recurringEdit: "ask"`), or applies to the occurrence or the series as `recurringEdit` says; `recurringTexts` gives that prompt its own words.

## The details

A click on an event opens its details in a `drawer`, a `modal` or a `popover` (`details.container`): its time, calendar, place, description and custom fields, its `eventActions`, Edit and Delete. `details.editDirectly` opens the form at once, and `eventAction` runs a target instead of the details. The open event is kept in the URL (`details.deepLink`), so a reload opens it again.

`fields` lists the form's fields: the built-in ones (`title`, `calendarId`, `resourceIds`, `allDay`, `start`, `end`, `location`, `description`) to order, relabel or hide them, and any other id as a field of the event's `data`, of a `kind` among `text`, `longText`, `number`, `boolean`, `date`, `datetime`, `time`, `select`, `tags`, `richText` and `relation`. A field may be `required`, `readOnly`, shown only `visibleWhen` another holds a value, and carry a `placeholder` and a `hint`.

- A `select` field marked `multiple` picks several options; the resources pick several unless `multiple: false`. An option naming `durationMinutes` ends a new timed event that long after its start.
- A `relation` field searches the records it points to as the user types: its `relation.searchUrl` answers `?q=<text>` with `{ items: [{ value, label, description? }] }` from `minChars` characters (2 by default), and `?id=<value>` with the record already chosen. The value kept is the item's `value`; the details read its name from the event's `data[labelField]` (`<field id>Label` by default).

`detailsTexts` gives the details their own words (the title of a new event, the question before a delete, the title of a refused change's toast, the agenda's word for its resources), for an agenda whose events are not meetings.

## Booking mode

`propose: { param, url }` opens a new event where a route says. When the page URL carries the query key `param` (a link from another page, or a toolbar action opening `?plan=next`), the agenda reads `url` with that key and its value and `tz`, goes to the day of the `AgendaProposal` it answers (`start`, `end`, `resourceIds`, `calendarId`, `title`, `data`, `message`) and opens the form of a new event there, prefilled, for the user to check and save. The key leaves the URL once read, so a reload books nothing twice.

## Resources and the sidebar

`resources` (and the route's `resources` and `resourceGroups`) are the columns and rows of the resource views; a resource may carry its own `businessHours`, be read-only (`editable: false`), and name the `calendarId` that usually works on it: with `create.defaultResource`, a new event placed on no resource starts on the first shown resource its calendar works on.

The `sidebar` holds the sections it lists (`miniCalendar`, `calendars`, `resources`, `unscheduled`, `notices`, `upcoming`, `tip`), on the left or the right. The resource list hides resources from the views (the resource filter), or picks those a view with `resourcesAtOnce` shows. `foldBelow` folds the sidebar under a container width; under `responsive.compactBelow` it becomes a sheet opened from the toolbar and the view becomes `responsive.compactView`. The `legend` toggles each calendar, counts its events, and with `serverFilter` asks the route for the calendars shown only. `unscheduled` lists items to plan, dragged onto a day, a slot or a resource, or planned from the keyboard at the first free time of the day shown. The `toolbar` holds the title, Today, the period arrows, the date picker, the view switcher, the search, the `facets`, Refresh, the `.ics` export, Print (`print`) and the `toolbarActions`.

`height` is a CSS length, or `"fill"`: the height left on a page that fills the window (`DefaultLayout({ fillHeight: true })`), or the body of a modal or drawer. An agenda with no `height` fills such a page and takes 44rem elsewhere.

## Keyboard

The shortcuts work while the focus is inside the agenda (`shortcuts`, on by default), never in a field:

| Key | What it does |
|---|---|
| T | Today |
| ← → | The previous or next period; on a focused event, the previous or next event |
| M, W, D, L, Y | The month, week, day, list or year view (the view named `week` first for W) |
| N | Opens the form of a new event on the day shown, at the next time it is open |
| Enter | Opens the focused event |
| Delete, Backspace | Deletes the focused event, after its confirmation |
| Shift + a letter | Runs the event action whose `shortcut` is that letter on the focused event |
| Alt + arrows | Moves the focused event by a snap step or a day |
| Alt + Shift + arrows | Stretches its end |
| Esc | Cancels a drag or a picked range |
| Ctrl + S, ⌘ + S | Writes the staged changes, after the review with `review` |

## Accessibility

Each view is a grid of named cells; in the month view the arrows move a single tab stop. Each chip is a button named by its title, time, calendar, mark, pinned states, alerts, status and save state, and carries a tooltip with the same words. A drag, a keyboard move and a save are announced in a live region, and a refused drop says why. The details are a dialog that returns the focus to the chip it came from; the sidebar's sheet is a dialog too. A status, a mark and an alert are named in words as well as drawn in colour.

## Printing

`toolbar.print` adds a Print button that prints the day shown, on an A4 landscape sheet, with its date and without the toolbar, the sidebar and the buttons. The sheet is set while an agenda is on screen, so another page prints on its own.

## Pitfalls

- The agenda trusts nothing it sends: check permissions, the times, the resources and `previous` (or `revision`) in the save route.
- Give every time with its offset, or a day for an all-day event: a time without an offset reads in the agenda's zone, which may not be the route's.
- Answer the events of the range asked, `from` to `to` inclusive, recurring ones by their series: the block expands the occurrences itself.
- A relation field's route answers by `q` and by `id`: without the second, a chosen record shows its id.
- Do not draw a calendar in a custom component for one of these screens: give the FullAgenda its routes instead.
