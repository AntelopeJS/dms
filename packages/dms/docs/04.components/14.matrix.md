# Matrix

`Matrix` is a grid whose cells are read and edited in place, spreadsheet style: the languages of each translation key, the sizes of an article by store, the shifts of a team by day, the fields of a collection's records. Its rows and columns come from a route of the module, not from a data controller, and its edits go back to another route, cell by cell or together from a save bar.

Reach for it where a module screen would otherwise hand-roll a grid. A list of records edited through a form is a [table view](/docs/components/tables); a table view's simple values edited in the grid are its [inline edit](/docs/components/tables/inline-edit).

In the playground, the **Matrix** category holds six pages: options, records, translations, stock, allocation and roster.

## Usage

```ts [src/pages/translations.ts]
import { Matrix } from "@antelopejs/interface-dms/base/matrix";

static translations = Matrix({
  title: "Translations",
  fetchUrl: "/api/translations/rows",
  saveUrl: "/api/translations/save",
  rowHeader: { label: "Key", width: 260 },
  saveMode: "immediate",
  conflicts: "detect",
  statusFilters: [
    { id: "missing", label: "Missing", tone: "warning" },
    { id: "complete", label: "Complete", tone: "success" },
  ],
  search: true,
  pagination: "infinite",
});
```


## Reading the rows

`fetchUrl` answers `MatrixData`: the `rows` (an `id`, a `label`, the `values` by column id, and per-cell `cells` state), optional `columns`, `groups`, the `counts` of each status filter, the choices of each facet, `targets` and a `footer` line. The grid reads it with `offset` and `limit` when paginated, `search`, `status`, `sort` and `direction`, `facet_<id>=a,b` per facet in use and `filter_<column>=<mode>:<value>` per column filter. `staticData` gives the rows in the options instead, for a grid without a route.

Columns come from the block's `columns`, from the response's, or both: the response wins for an id both declare and adds the ones it alone names (the languages of a workspace, the sizes of an article). Each column's `kind` picks its input — `text`, `longText`, `number`, `boolean`, `date`, `datetime`, `select`, `tags`, `json`, `code`, `richText`, `address` — the same DMS input as the matching field of a `Form`. An object is edited as JSON in the code editor.

A cell's state (`cells[columnId]`) carries a `tone`, a `hint` in its corner, `disabled` (hatched, outside the range), `readOnly`, `issues`, a `placeholder` (the base text, shown above the editor too) and the `previous` value drawn struck through.

## Editing

With `saveUrl` set, the grid is editable. A hovered editable cell is framed as the input it opens, and a click opens it with the keyboard in it; a switch toggles at once. The keyboard moves one focused cell with the arrows, Home / End and PageUp / PageDown; Enter or F2 edits it, Esc leaves the editor, Space opens the row's drawer, and `typeToEdit` starts editing with the character typed. `jumpToEmpty` adds N and Shift+N to reach the next or previous empty editable cell.

`json`, `code`, `richText` and `address` cells, and texts holding a line break or over 120 characters, are edited in a drawer holding that cell alone (`editIn: "auto"`); `editIn: "cell"` or `"panel"` forces either, on a column or on one cell.

## Saving

`saveUrl` receives `MatrixSaveRequest`: the `changes` (`rowId`, `columnId`, `value`, and `previous`, the value the edit started from), `force` when the user chose Overwrite, the block's `conflicts` mode and the grid's `query`, so the route can answer the counts of the filtered view.

- `saveMode: "immediate"` (default) writes each cell as it is left (Saving → Saved, Retry on failure).
- `saveMode: "staged"` keeps the edits, shows the old value struck through, and writes them together from a save bar; `review` lists them before → after first, and `undoSeconds` offers an Undo after the save.

The answer, `MatrixSaveResponse`, replaces the `rows` it returns; a change named in `errors` (with a `message`, on a cell or, without `columnId`, the whole row) or in `conflicts` stays in its cell with the message, and every other change counts as written. A non-2xx answer fails every change of the request. Under `conflicts: "detect"`, a route checks `previous` against the stored value and answers `{ rowId, columnId, current }` when it moved: the cell offers Overwrite (sent again with `force`) or Discard.

## Grouping, totals and targets

- `grouping` cuts the rows into groups under header rows: the group a row's `group` names (described by the response's `groups`), else its value in `groupByField`. Groups may fold (`collapsible`, `collapseAbove`), count their rows and carry `subtotals`.
- `totals: { rows, columns }` adds a Total column, a Total row, or both; `excludeFromTotals` leaves a column out.
- `targets` sets expected totals by row, column or overall: a total that differs turns red, and `blockSave` holds the save until each one matches.

## Actions on rows and cells

- `rowActions` fill the menu of a row's header (Override, Revert, Delete), each with an action target and an optional `visibleWhen` on the row's values.
- `rowPanel` adds a ⤢ button opening the whole row in a drawer, J and K stepping through the rows.
- `cellAction` runs on a click on a read-only cell (`{{row.id}}`, `{{row.column}}`, `{{row.value}}`).
- `fillActions` post the rows shown (and, with `selectable`, the checked ones) to a route answering `{ changes }`, applied as edits through the save mode.

## Pitfalls

- The grid trusts nothing it sends: check permissions, ranges and `previous` in the save route.
- A grouped grid's route lists the rows sorted on `groupByField`, so a group's rows follow each other.
- Do not draw a grid of inputs in a custom component for one of these screens: give the Matrix its route instead.
