A table is two pieces. A **`DataController`** declares the data shape and its operations (list, filter, sort, search, create, edit, delete, export, archive) once, with decorators. That whole backend side (route generators, field decorators, model wiring) is its own reference, [Data controller](/docs/components/data-controller). A **`TableView`** component points a page at that controller and renders the screen: toolbar, columns, forms, and pagination are wired for you, so a standard CRUD screen needs no Vue and no hand-written routes. For a static form or one-off list endpoint, use [Pages & components](/docs/building/pages-and-components) instead.

## What it renders

`TableView` produces a full table screen:

- **Toolbar.** The `caption` heading, a global **search** box (when `@Searchable` fields exist; it searches from 2 characters), a **filter** per `filterable` column, a **column-visibility** menu, an optional **tab strip** (`tabs`), a **display switcher** when more than one display is configured, an **Export** button (when the export routes are present), any `customButtons`, and an **Add** button (when the `add` action is enabled).
- **Columns.** One per `@Column`, headed by `name`; a `@Sortable` header toggles ascending/descending. Each cell renders through its `DataType` (a badge, date, thumbnail, relation chip), not raw text. See [Data types](/docs/components/data-types).
- **Rows.** One per record, keyed by `rowIdKey` (default `_id`). With `hasSelection` on, a leading checkbox column enables multi-select and bulk delete/archive/restore.
- **Row actions.** A per-row menu of the enabled actions (edit, details, duplicate, delete, copy link, archive/restore, plus `custom` entries), hidden or disabled per row by their `rule`.
- **Pagination.** A footer driven by the `list`/`count` routes.

Editing happens in a **form container** (a drawer, a modal or a page) built automatically from the controller's `@Column` fields. See [Forms](/docs/components/forms).

## Usage

Model the data first: declare the controller, its routes, and its field decorators as shown in [Data controller](/docs/components/data-controller). This example reuses the `taskDataAPI` controller built there.

Pass the **controller class itself** (not an instance) to `TableView`. Columns come from the controller's `@Column` decorators, so you do not redeclare them on the page.

```ts fragment [src/pages/tasks.ts]
import {
  PageController,
  RegisterPage,
  pagesCategory,
} from "@antelopejs/interface-dms/page";
import { TableView } from "@antelopejs/interface-dms/base/table-view";
import { taskDataAPI } from "../data-api/tasks";

@RegisterPage()
export class TasksPage extends PageController("tasks", {
  displayName: "Tasks",
  icon: "i-ph-table",
  category: pagesCategory,
}) {
  static table = TableView(taskDataAPI, {
    caption: "Tasks",
    labelKey: "name", // names the row in form titles and breadcrumbs
    archiveMode: true, // requires an @ArchiveField on the controller
    formContainer: {
      type: "drawer",
      // The form titles, in a drawer, a modal or a page alike.
      pages: {
        new: { displayName: "New task", description: "Name it and assign people." },
        edit: { displayName: "Edit task" },
        details: { displayName: "Task details" },
      },
    },
    rowActions: {
      add: true,
      edit: true,
      details: true,
      hasSelection: true,
      delete: { isEnabled: true, rule: { field: "status", notEquals: "done" } },
    },
  });
}
```

Covers `view`, `list` and `select` only: every write, and `export` (which queues a job and delivers a file), still asserts the gate. Action permission checks apply on top. Latched controller-wide: once one `TableView()` registration of a controller declares it, a later registration without the flag cannot silently re-gate (or un-gate) the shared routes. So a table mounted on several pages shares the opening, and mounting it both ways is warned about. |

::note
`queryParamFilters` and `routeParamFilters` also seed form submit defaults: a form opened from a filtered view inherits the parent token (e.g. a `:projectId` route param flows into the new row's `projectId`), resolved against the form's route and dropped if absent. A field of the form named by one of them starts with that value, so the picker of a mandatory parent relation shows the parent and the form submits without asking for it.
::

An active `queryParamFilters` filter counts as a filter: an empty table shows its `filtered` empty state (no clear action for a hidden filter, which the user cannot see; a `visible` one is removed from its chip, see below) rather than `firstRun`. When the URL changes a hidden filter's value, such as a link to `?status=open` on the same page, the table goes back to page 1, as for a visible filter (the page kept in the user's preferences is only restored under the hidden filter values it was reached with); a `loadMore` / `infinite` list starts over from one page.

A filter a link applies is invisible by default. `visible: true` shows it, while the URL carries its parameter, as a chip at the start of the filters row, named by `label` (a `$` key is translated) or else by its column's label, with its compare mode and value. Its × removes the parameter from the URL, which lists the rows again without it; the filter stays out of **Clear filters**, which clears what the user added. The chips live in the filters row, so they only show where that row can: a table with no `filterable` column, a `chrome` hiding the filters or a display without filters applies the filter without showing it.

```ts fragment
TableView(SuppressionsController, {
  queryParamFilters: {
    email: { field: "email", visible: true, label: "$mailing.suppressions.email" },
  },
});
```

## Features

The features are documented on their own pages:

- [Columns and displays](/docs/components/tables/columns-and-displays): cell wrapping, narrow screens, layout, expandable and pinned rows, the kanban display.
- [Filters and tabs](/docs/components/tables/filters-and-tabs): quick filters, link tabs, the filter builder, search and sorting.
- [Row actions](/docs/components/tables/row-actions): row actions, bulk actions, drawers, confirmations, archive mode and write guards.
- [Add and edit forms](/docs/components/tables/add-and-edit-forms): form containers, conditional fields and form watches.
- [Live pages and exports](/docs/components/tables/live-pages): events, realtime updates, live pages and export jobs.

The options below have a page of their own too.

### Footer

`footer` words the row count (`countLabel`), adds a `hint`, `summary` figures the server computes over every listed row (not only the page shown), and a `legend` of a select column's colors. Summaries need the controller's `summary: TableViewRoutes.Summary` route (in `TableViewRoutes.All`). See [Footer summaries](/docs/components/tables/footer-summaries).

### Pagination

`pagination: "loadMore"` replaces the pager with a "Load more" button and `"infinite"` loads the next page as the footer scrolls into view; `pageSize` (1 to 50) is the page or the step. See [Pagination](/docs/components/tables/pagination).

### Empty states

`emptyStates` words the empty body in the module's terms: `firstRun` (no row yet), `filtered` (the filters or search match nothing) and `error` (the list failed), each a title, a description, an icon and links, or a component drawing the whole state. The table keeps its own action in front. See [Empty states](/docs/components/tables/empty-states).

### Grouped display

`grouped` offers a display that keeps the grid's columns and draws a header row before each group of rows sharing a value of `groupByField`, or the same day or week of a date. See [Grouped display](/docs/components/tables/grouped-display).

### Views

`views` declares named states of the whole table (filters, search, sort, columns, display, density), drawn as tabs, a strip or a menu, opened from the URL (`?<tableId>.view=<id>`) and, with `userViews`, saved by users for themselves. Filter values may hold tokens the server resolves (`{{user.id}}`, `{{now-7d}}`). See [Views](/docs/components/tables/views).

### Sources

`TableView.fromSource({ columns, fetchUrl, capabilities })` lists the rows of a module's own route, answering `{ results, total }`, with no data controller: a read-only table with custom actions only. See [Source tables](/docs/components/tables/source-tables).

### Rows ordered by hand

`reorder: { field }` puts a drag handle in front of each grid row and on each card of the `cards` display; a move saves the new position of the rows it changed in `field`, a `@Sortable()`, writable `NumberType` column, through the edit route. See [Rows ordered by hand](/docs/components/tables/reorder).

### Cards

The kanban board and the built-in `cards` display (`displays: [{ id: "table" }, { id: "cards" }]`) draw one card per row from one shared `card` option: `fields` picks the columns shown, `component` draws the whole card (for instance with `DmsRecordCard`). See [Cards](/docs/components/tables/cards).

## Permissions

Several table views may share one data controller (an overview and the screen that edits the rows), as long as only one of them writes: its data routes are shared, so each read action is guarded by the permission of **every** table view mounting it, and each write action by the writing table view's alone. A caller holding `list` on any of those tables may list, which is what that table already exposes. A table view no page mounted carries no permission and is ignored. Two screens that both write need two controllers: see [Derived controllers](/docs/components/derived-controller).

Every table action registers its own permission, named `<componentPermissionId>.<actionId>`. The component permission id is the page's permission id (its full id, unless the page declares `permission.id`) followed by every field/child id in the table's position; each action appends its id: `list`, `select` (granted by default), `add`, `edit`, `view`, `delete`, `export`, plus `archive`/`restore`/`viewArchived` in archive mode. These same per-action permissions gate the row actions.

The table is **filtered per user**: it strips the forms and row actions the caller lacks before the page renders, and the matching routes reject unauthorized calls server-side. As a special case, if the `edit` action has no rule, the table force-disables `details` (the edit form already covers viewing). See [Auth & permissions](/docs/auth-and-tenancy/auth-and-permissions).
