# Cells edited in place

A price list, a stock count, a status flipped row after row: opening the edit form for one value is a detour. `inlineEdit` lets the grid edit those values where they are listed, each saved as soon as it is left.

```ts [src/pages/products.ts]
static products = TableView(productDataAPI, {
  labelKey: "name",
  inlineEdit: true, // or { columns: ["price", "stock", "active"] }
  rowActions: { add: true, edit: true, delete: true },
});
```

In the playground, open **Table view › Inline edit**: the first table keeps the default inputs, the second one draws every editable cell as its input.

## Which cells are edited

A cell is edited in place when its column:

- is listed in `columns` (left out, every column that can be),
- is in the edit form and writable there, and is not localized,
- takes a simple input: a text, email, phone or URL, a number, price or percentage, a switch or checkbox, a single select or segmented select, a single date, a time or a colour.

Any other column (a relation, rich text, code, files, images, a list, an address, key-values, tags) keeps its display and is edited through the edit form. A row the `edit` action's `rule` refuses keeps its display, and so does a field its `disabledWhen` makes read-only or its `visibleWhen` hides, evaluated on the listed row.

It works on the grid and on the `grouped` display; the board and the cards are left as they are. It needs the `edit` action: a caller without it gets the read-only grid. `TableView.fromSource` ignores it, having no edit route.

## How a value is saved

Enter or leaving the cell saves, Esc cancels. A pick in a select or a date picker saves, and a switch or a checkbox saves as it toggles, without opening anything. Each save is a partial edit of that field alone (`PUT <location>/edit?id=…`); an unchanged value sends nothing. A value the server refuses stays in its cell, marked invalid, with a toast saying why, until the user edits it again.

An inline edit sends the field without the edit form around it: what `forms.edit` declares on the form's builder (its watches setting another field) and the form's own submit defaults do not run. A rule the data must keep belongs to the column (`disabledWhen`, `visibleWhen`) or to a guard, which the edit route enforces either way.

## Inputs on hover, or always drawn

`inputs` says how an editable cell shows it is one:

| `inputs` | The cell at rest | Editing |
| --- | --- | --- |
| `"hover"` (default) | Its value, framed as its input while hovered. | A click opens the input with the keyboard in it. |
| `"always"` | The input itself. | Typed into at once. Tab saves the cell left, Enter saves and keeps the keyboard there, Esc puts the value back. A select opens on a click, the pick is the save. |

```ts [src/pages/stock.ts]
static stock = TableView(stockDataAPI, {
  inlineEdit: { columns: ["quantity", "location"], inputs: "always" },
  rowClick: "none",
  rowActions: { edit: true },
});
```

## The row click

A click on an editable cell is the cell's and does not open the row; a click anywhere else on the row still runs its [row click](/docs/components/tables/row-drawers#row-click). On a table whose every cell is an input, `rowClick: "none"` leaves the row to its actions: neither click opens it, and the row has no hover tint.

A data controller has one table view writing through it. To show the same rows edited in two tables, derive a second controller from the first (see [Derived controllers](/docs/components/derived-controller)).
