`Form` is the component builder for data-entry screens. You declare a list of **fields**, each labelled and typed by a `DataType` ([Data types](/docs/components/data-types)), plus where the form **loads** its values from and **submits** them to. The shared Inertia/Vue frontend turns that into rendered inputs, client-side validation, and the submit flow. You write no Vue.

Use a `Form` for create/edit screens, settings panels, and standalone data entry. For paginated, sortable, CRUD-backed lists whose add/edit forms are generated from a [Data controller](/docs/components/data-controller), use a `TableView` ([Tables](/docs/components/tables)) instead.

`Form` is a page component: assign the builder to a static field on a `PageController` (see [Pages & components](/docs/building/pages-and-components)). The field key becomes the component key and part of its permission id.

## What it renders

The frontend renders a titled card. From the top:

- An optional **title** and **description** header.
- The **fields**, each a labelled input chosen from its DataType (text box, select, date picker, file upload, rich text, …), with the field's `description` as helper text (none in a form where nothing can be changed, a record's details: there it would only tell how to fill a value shown read-only). A required field carries an asterisk after its label (a group's label when one of its fields is required), and a `* Required fields` legend closes the form; a disabled or hidden field is never marked. Invalid fields show an inline message and an error state.
- **Field groups**, whose members render together under a shared label, each keeping its own label above its control, laid out horizontally or vertically (`orientation`). A horizontal group sets its members side by side and wraps them onto the next line where the row is too narrow for each to keep a usable width (a modal, a drawer, a phone).
- **The layout follows the form's own width, not the window's.** A horizontal form (the default) sets each label in a 240px column beside its value once the row is 560px wide (a drawer from about 600px, a page card), and stacks the label above the value below that, whatever the screen: the same form reads well in a narrow drawer, a resized one and a full page. A group's fields sit side by side from the same width. **Wide fields** always take the row's full width under their label, read-only as editable, so a table of values never shares a drawer with a label column: rows of fields (`ArrayType`, the repeater), name and value pairs (`KeyValueType`), code (`CodeType`), rich text, several files or images (`multiple`), and a textarea taller than three `rows`. A group holding a wide field stacks too.
- The **save controls** at the bottom, as `saveMode` and `kind` set them ([Saving](#saving)). On submit the form validates against its schema; on success it shows `successMessage` (and optionally navigates via `redirectOnSuccess`), on failure `errorMessage`. A failure the server ties to a field (a zod issue, a `{ message, field }` body, see [Guards](/docs/components/tables/row-actions#guards)) shows under that field, marked invalid and focused, instead of the toast. A submit that went through but left something for the user to act on answers with a `warning` field (an i18n key or plain text) in its JSON response: the form then shows that warning instead of `successMessage`, and still redirects. A submit response carrying `notice: { title, description?, color?, params? }` adds a toast of its own, for a partial success such as "2 invitations sent, 1 address skipped" (`$` keys pluralized on a numeric `params.count`).

When `fetchUrl` is set the form first loads existing values and pre-fills the inputs (an edit form); without it the form starts empty (a create form). An edit form loads them again every time it opens, and its submit sends only the fields the user changed, so a value someone else saved in the meantime is not written back; a form that posts its loaded values as a new row (`submitUrlMethod: "POST"`, a duplicate) still sends them all.

## Usage

Assign the builder to a static field on the page.

```ts [src/pages/contact.ts]
import {
  PageController,
  RegisterPage,
  pagesCategory,
} from "@antelopejs/interface-dms/page";
import { Form } from "@antelopejs/interface-dms/base/form";
import { DefaultDataTypes } from "@antelopejs/interface-dms/base/data-types";
import { HttpMethod } from "@antelopejs/interface-dms/base/types";

@RegisterPage()
export class ContactPage extends PageController("contact", {
  displayName: "Contact",
  icon: "i-ph-note-pencil",
  category: pagesCategory,
}) {
  static form = Form({
    title: "Contact Us",
    description: "Send us a message and we'll get back to you",
    fields: [
      {
        id: "name",
        label: "Full Name",
        type: new DefaultDataTypes.StringType({ placeholder: "Jane Doe", maxLength: 100 }),
        required: true,
      },
      {
        id: "email",
        label: "Email",
        type: new DefaultDataTypes.EmailType({ placeholder: "jane@example.com" }),
        required: true,
      },
      {
        id: "message",
        label: "Message",
        type: new DefaultDataTypes.StringType({ textarea: true, rows: 6, maxLength: 1000 }),
      },
    ],
    submitUrl: "/api/contact",
    submitUrlMethod: HttpMethod.post,
    kind: "action", // sends something new each time: Reset and Submit, emptied after a submit
    successMessage: "Thanks — we'll be in touch.",
  });
}
```

The routes behind `submitUrl` (and `fetchUrl`) are normal API controllers. See [Pages & components](/docs/building/pages-and-components) for wiring. Return `_id`, never `id`, for created rows.

`Form(options)` takes a single options object (`FormProps`):

| Option              | Type                          | Default      | Purpose                                                                                |
| ------------------- | ----------------------------- | ------------ | -------------------------------------------------------------------------------------- |
| `fields`            | `(FormField \| FieldGroup)[]` | None         | Fields and field groups to render. See [Fields](#fields). Beside `sections`, they come first, outside any section. |
| `sections`          | `FormSection[]`               | None         | The fields split into titled cards on one page, saved together ([Sections](#sections)). |
| `sectionNav`        | `"side" \| "jump" \| "none"`  | `side` from 3 sections, else `none` | How a sectioned form lists its sections ([Sections](#sections)). |
| `title`             | `string`                      | None         | Heading above the fields (no heading is rendered when unset); the component's display name falls back to `"Form"`. |
| `description`       | `string`                      | None         | Sub-heading text under the title.                                                      |
| `fetchUrl`          | `string`                      | None         | URL to load existing values from (pre-fills the form). Omit for a create form.         |
| `fetchUrlMethod`    | `HttpMethod`                  | `GET`        | HTTP method for the fetch request.                                                     |
| `submitUrl`         | `string`                      | None         | URL the form submits to.                                                               |
| `submitUrlMethod`   | `HttpMethod`                  | `PUT`        | HTTP method for the submit request.                                                    |
| `submitLabel`       | `string`                      | None         | Label of the submit button (i18n key or literal). Defaults to the generic "Save changes". |
| `successMessage`    | `string`                      | None         | Toast shown after a successful submit.                                                 |
| `errorMessage`      | `string`                      | None         | Toast shown when a submit fails.                                                       |
| `saveMode`          | `"bar" \| "footer" \| "none" \| "instant"` | `"bar"` | How the form offers to save ([Saving](#saving)). |
| `kind`              | `"record" \| "create" \| "action"` | `"record"`   | What the form edits: a record keeps its values once saved; a create form makes a new row (its submit reads Create and shows from the start); an action (send, invite, run) empties after a submit ([Saving](#saving)). |
| `backTo`            | `string`                      | None         | Where Cancel leads a `record` form on a page opened directly (a link from outside the app, a bookmark); reached from another page of the app, Cancel goes back to it. Without either, the form offers no Cancel there. Table views set it on their form pages, to the list. |
| `labelKey`          | `string`                      | None         | Field of the loaded record whose value ends the page breadcrumb once the form has loaded. Table views fill it from their own `labelKey`. A custom component reads or sets the same label with [`usePageRecordLabel()`](/docs/frontend-composables/page-context#usepagerecordlabel). |
| `requiresRecord`    | `boolean`                     | `false`      | The form is about the record `fetchUrl` loads: while a route value that URL names is missing (no `?id=`), it shows "No entry selected" instead of its fields with their defaults. A `ResourceForm` in `edit` or `view` sets it. |
| `fieldsOrientation` | `"horizontal" \| "vertical"`  | None         | Overall layout direction of the field list.                                            |
| `redirectOnSuccess` | `string`                      | None         | Path to navigate to after a successful submit. Supports token substitution.            |
| `submitDefaults`    | `Record<string, unknown>`     | None         | Extra values merged into the submit payload. String values support token substitution. |

### Saving

`saveMode` picks the controls: `bar` (default, a sticky save bar while there are unsaved changes), `footer`, `none`, or `instant` (each changed field saves on its own). `kind` picks what the form edits: a `record` (default) keeps its values once saved, a `create` form makes a new row, an `action` (send, invite, run) empties after a submit. A form loaded from `fetchUrl` sends only the fields the user changed, a cleared one as `null` (`[]` for a list field). The modes, what a submit sends and the instant save are in [Saving a form](/docs/components/forms/saving).

### Unsaved changes

Every form tracks whether it holds unsaved changes, wherever it is rendered (a page, a drawer, a modal, a section). It is **dirty** while a field's value differs, by value, from the one it loaded (or its `defaultValue`, or what it last saved): typing a value then putting the original back makes it clean again, a successful submit makes the saved values the new starting point, and an empty, untouched create form is clean.

- **Save bar.** A `record` form's bar (or footer) shows in two states of the same height: **Cancel** while there is nothing to save (when it has somewhere to go back to), and an "Unsaved changes" mark with **Save** once there is, so switching never moves the fields. Beside Save, a form with somewhere to go back to keeps **Cancel**; one with nowhere to go back to offers **Discard**, which puts the values back and stays. A `create` form (`kind: "create"`, set on a table view's add form, the duplicate it opens and a relation's add form) makes a row: its submit, **Create** by default, shows from the start, so a duplicate saves as it opened, and neither the bar nor the fields list "changes", since all it holds is new. Cancel drops any change and leaves, in one click and without asking: it closes a drawer or modal; on a page it goes back to the page of the app the user came from, or to `backTo` (the list, for a table view's form page) when the page was opened directly. The bar sticks to the bottom of the visible area (the page, the drawer or the modal body) while the form runs past it, and sits right under the fields when they fit. On a page it floats over the form: hidden, it takes no space, and showing up moves nothing above it ([The save bar on a page](/docs/components/forms/saving#the-save-bar-on-a-page)).
- **Leave guard.** While a form is dirty, leaving it asks once, in a warning dialog ("Discard unsaved changes?", with "Keep editing" and "Discard changes"): closing its drawer or modal (X, Escape, a click outside, Cancel), navigating away (sidebar, breadcrumb, links, the browser's Back and Forward buttons), switching away from the tab panel it sits in, and reloading or closing the browser tab (the browser's own prompt). Nothing asks after a save, after Discard or Cancel, or when nothing changed, and a drawer closing because the page changed never asks twice.

Hand-built forms get the same behaviour from the `useFormDirty` and `useUnsavedChanges` composables (see [Utilities](/docs/frontend-composables/utilities#leave-guard)).

`submitUrl`, `redirectOnSuccess`, `backTo` and `submitDefaults` string values support **token substitution**, resolved against the form's route at submit time (the same tokens as every other option, see [Template tokens](/docs/building/pages-and-components#template-tokens)):

- `{{params.X}}`: a route path parameter. A route can repeat a parameter name (a table view's form page under a `:id` page resolves to `/workspaces/:id/invoiceTable/:id/edit`), and `X` is then its **last** occurrence; `{{params.X:n}}` reaches the n-th one, `{{params.id:1}}` being the id of the page above.
- `{{query.X}}`: a query-string parameter.
- `{{response.X}}`: (`redirectOnSuccess` only) a field of the submit's JSON response body, a dotted path reaching into it, e.g. `/items/{{response._id}}/edit` to redirect to a freshly created entity.

In a URL (`fetchUrl`, `submitUrl`, `redirectOnSuccess`) the `{{params.X}}` and `{{query.X}}` values are percent-encoded, so a value such as `GET /api/a?b=c` stays one parameter; `{{response.X}}` is written as answered, so a response may hand back a whole path, and `submitDefaults` values are written as they are.

`submitDefaults` entries whose tokens can't be resolved are dropped. This is how a page-rendered "new" form inherits context such as a parent id.

::note
`HttpMethod` is a string enum (`HttpMethod.get`, `HttpMethod.post`, `HttpMethod.put`, `HttpMethod.delete`, `HttpMethod.patch`, …). The options take the enum member or its string value (`"POST"`).
::

::warning
When `submitUrlMethod` is omitted, the frontend submits with `PUT`, so a creation form must set `submitUrlMethod: HttpMethod.post` explicitly.
::

## Fields

Each entry in `fields` is either a single **field** (`FormField`) or a **field group** (`FieldGroup`).

### Field

```ts fragment
{
  id: "email",                                   // payload key — required
  label: "Email Address",                        // visible label
  description: "We never share it",              // helper text under the label
  type: new DefaultDataTypes.EmailType({ ... }), // a DataType instance — required
  required: true,                                // marks the field and tightens validation
  defaultValue: "jane@example.com",              // initial value
  localized: true,                               // store one value per locale
  disabled: true,                                // render read-only
  inputComponent: FormComponents.InputText(),    // override the DataType's default input
}
```

| Property         | Type                      | Purpose                                                                           |
| ---------------- | ------------------------- | --------------------------------------------------------------------------------- |
| `id`             | `string`                  | The field's key in the payload. Required.                                         |
| `type`           | `DataType`                | The DataType instance driving the input, parsing, and validation. Required.       |
| `label`          | `string`                  | Field label. Use a `$`-prefixed i18n key in real modules.                         |
| `description`    | `string`                  | Helper text under the label.                                                      |
| `required`       | `boolean`                 | Marks the field required and tightens validation (see [Validation](/docs/components/forms/validation-and-watches#validation)). |
| `defaultValue`   | `DefaultValue`            | Initial value (`string \| number \| boolean \| Date \| null \| array`).           |
| `localized`      | `boolean`                 | Store the value as a per-locale record instead of a single scalar.                |
| `disabled`       | `boolean`                 | Render the input non-editable.                                                    |
| `readonly`       | `boolean \| FormFieldReadonly` | Show the value, not an input, optionally with a `badge` and a `link` ([Field notes](/docs/components/forms/field-notes)). |
| `hint`           | `string`                  | A grey help line under the control ([Field notes](/docs/components/forms/field-notes)). |
| `showEmptyOnCreate` | `boolean`              | Keep a read-only field on a create form while it holds nothing ([Field notes](/docs/components/forms/field-notes#read-only-values-readonly)). |
| `inputComponent` | `ComponentInfoSerialized` | Override the input the DataType would otherwise pick (see below).                 |
| `visibleWhen`    | `{ field, in }`           | Show the field only while `field` holds one of the values `in` lists (`null` for empty), from the moment the form opens: hidden, it is neither required nor sent. |
| `disabledWhen`   | `{ field, in }`           | Make the field read-only while the condition holds: its value is not sent. A table view's data routes enforce both ([Conditional fields](/docs/components/tables/add-and-edit-forms#conditional-fields)). |

The `type` is always a **DataType instance**: `StringType`, `EmailType`, `SelectType`, `DateType`, `FileType`, `RichTextType`, `AddressType`, and so on. Each carries its own options (placeholders, min/max, items, constraints) and supplies both the validation rule and the default input. See [Data types](/docs/components/data-types). Choice cards, segments, boolean cards, repeaters, key-value pairs, secrets, code and tags are in [Field types](/docs/components/forms/field-types).

### Field group

A group renders related fields together under a shared label:

```ts fragment
{
  id: "contactGroup",
  label: "Contact Information",
  description: "Your email and phone number",
  orientation: "vertical",   // or "horizontal"
  order: 1,                   // place among the groups giving an order
  fields: [
    { id: "email", type: new DefaultDataTypes.EmailType(), required: true },
    { id: "phone", type: new DefaultDataTypes.PhoneType() },
  ],
}
```

Grouped fields still submit as flat top-level keys (`email`, `phone`). The group only affects layout. The group's own `label` heads the cluster, and a member with a `label` keeps it above its control (with its own asterisk when required), so a group, a table's `@ColumnGroup` among them, can title a run of labelled fields. A member may omit `label` to show its control bare under the group's.

The groups giving an `order` trade the places they are declared at, lowest first (equal orders keep their declaration order); fields and groups without one keep their place.

### Field notes

Any field can carry notes under its control: a `hint` line, "Changed · was X" while a change waits for its save, "Module default: X · Use default" when it opts in (`offersDefault`) and holds something other than its `defaultValue`, and `readonly` (`true`, or with a `badge` and a `link`) for a value shown, not edited. See [Field notes](/docs/components/forms/field-notes).

### Linking to a field

A page opened on the anchor of a field (its id, as in `/settings#retentionDays`) brings that field into view and focuses it once the form is drawn, a loaded record included, and so does a change of the anchor while the page is open. A link inside the app needs nothing more: the browser's own jump does not happen there, the form's does. A form in a drawer or a modal follows no anchor. A section has its own anchor ([Form sections](/docs/components/forms/sections)).

## Features

Some features have a page of their own:

- [Custom inputs](/docs/components/forms/custom-inputs): an input component of your own for one field.
- [Validation and watches](/docs/components/forms/validation-and-watches): client and server validation, watches, and form modes.

### Sections

A long form splits its fields into `sections`, each `{ id, label, description?, icon?, fields }`: one card per section, on one page, saved by one submit. `sectionNav` (`side`, `jump` or `none`) lists them, each entry marked while its section holds unsaved changes or invalid fields, and the save bar names the changed sections. See [Form sections](/docs/components/forms/sections).

### Localized fields

Set `localized: true` to store one value per locale: the value becomes a record keyed by locale code (e.g. `{ en: "Title", fr: "Titre" }`) and the input renders a per-language editor. Set `fallbackLocale` to the language other languages fall back to: a table view fills it from the column's `@Localized({ fallbackLocale })`, and the form requires it whenever the field holds any language. This is for **content** translated per locale, not for the `$`-prefixed i18n **message keys** used for static labels ([Localization](/docs/building/localization)).

## Permissions

A `Form` is a page component: its permission id is the page's `fullId` (category chain + page id) joined with every field/child id in its position. For example, a `form` field on the page whose `fullId` is `pages.form.form-grouped` resolves to `pages.form.form-grouped.form`, while a form nested as `details` under `panel` resolves to `pages.form.form-grouped.panel.details`. That id is also what a watch's `requirePermission` references. Derivation rules, gating the backing routes, and registering standalone permissions are covered in [Auth & permissions](/docs/auth-and-tenancy/auth-and-permissions). A `Form` gates at the component level. It does not assign a permission per field.
