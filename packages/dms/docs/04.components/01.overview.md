The DMS ships a catalog of **blocks** you declare on the backend; the shared Vue frontend renders them. For a standard screen you write no Vue: you compose blocks, and the dashboard draws the result. Start with the group that fits your screen below. Many block pages include a **live preview** you can tweak, alongside usage examples, options, recipes and pitfalls.

::block-playground{type="KpiCard" height="200"}
---
options:
  title: Monthly recurring revenue
  icon: i-ph-chart-line-up
  valueFormat: currency
  currencyCode: EUR
  showDelta: true
  showSparkline: true
  compareLabel: vs last month
  staticValue: 92200
  staticDelta: 4.1
  staticSparkline: [78, 80, 83, 85, 84, 88, 90, 92]
---
::

New to the DMS? Read [Pages & components](/docs/building/pages-and-components) first to see how blocks attach to a page, then [Block fundamentals](/docs/components/block-fundamentals) for what every block shares.

## When nothing fits

[Custom component](/docs/components/custom-component) places a Vue component of your own on the page. Build only the block the catalog is missing, give it `.meta({ name, description, icon })`, and keep the rest of the page in DMS blocks so each part stays a permission of its own ([Best practices](/docs/ai-and-claude-code/best-practices)).

## How to read a block page

Use the examples first, then consult the options when you need a specific behavior. Pages with a playground follow this structure:

1. **What it is** — what it draws and when to reach for it.
2. **Live preview** — the real block, rendered by a DMS instance; change its options in the controls panel and copy the TypeScript.
3. **Usage** — the import and a minimal, real example, with the route that feeds it.
4. **Options** — the reference table generated from the block catalog.
5. **Recipes** and **pitfalls** — the patterns that work and the mistakes to avoid.
6. **Next steps** — where to go from there.

::note
When no preview instance answers, the preview falls back to a screenshot of the same block and the options table stays complete.

Some blocks need backend data or page context. Forms may show only their frame, tables may show a backend-required notice, and a live toggle needs a live page. Those pages explain the limitation and point to a screenshot or the running playground for the complete result.
::
