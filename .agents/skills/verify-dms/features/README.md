# Feature map

One file per feature. `covers:` lists the source globs it owns, `docs:` the pages a verdict judges, and `e2e/journeys/<feature>.mjs` its journeys. `dms-control map` checks that every user-facing file is covered and that every feature has its journeys and existing docs pages.

| Feature | What the user does | Journeys |
|---|---|---|
| [auth](auth.md) | Signing in and out, the sign-in redirect of protected pages, and password recovery by emailed code. The pages are `/auth`, `/auth/forgot`, `/auth/forgot-validation` and `/auth/recover`; the API is `/api/auth/*`. | login-form-persists, login-wrong-password, protected-page-redirects, logout-ends-session, forgot-password-resets, forgot-password-wrong-code, base-written-data-upgrade, switcher-lists-each-account-once, switcher-replaces-recreated-account, stored-account-refused-after-logout, session-lifecycle-refuses-replays |
| [block-preview](block-preview.md) | The public `/dms-preview` page renders a tree of registered blocks from `?state=` or from a postMessage, without the dashboard chrome. `GET /api/block-preview/types` lists the blocks it may draw. | preview-renders-state, preview-refuses-unknown-and-remote, preview-empty-and-unreadable, preview-postmessage-render, preview-renders-every-starter |
| [builder](builder.md) | The builder engine that lists and edits the pages, blocks, resources, queries and theme of the project's sources, reached through the builder tools of the MCP server. | builder-lists-and-reads-pages, builder-delete-waits-for-a-repeat, builder-refuses-an-unknown-page, builder-period-bound-series-and-comparison-card-answer-over-http, builder-survives-the-reload-its-write-triggers |
| [database-connect](database-connect.md) | Connecting an external database through the Builder's *Connect a database* form or `builder_configure_project`: the restart that follows installs the `builder-db-<name>-tables` module and the connection answers. | database-connect-restarts-under-watch, database-connect-corrects-a-url |
| [mcp-server](mcp-server.md) | The MCP server the DMS serves in development: a coding agent in the project reaches `POST /dms/mcp` through the stdio bridge `node_modules/.cache/dms/mcp-bridge.cjs`, which `.mcp.json` launches. | bridge-calls-a-read-tool, builder-refuses-a-form-posting-to-the-connect-check, page-verify-reports-a-page, page-verify-member-against-mockup, bridge-files-published |
| [mockups](mockups.md) | In development, `mockups/<name>/spec.json` is drawn live on `/mockup?name=<name>` and annotated there; `/api/mockup/*` serves its state stream, fixtures and annotations, to the platform owner only. Outside development none of it exists. | mockup-owner-only-in-dev, mockup-sample-reads-no-live-route, mockup-overview-labels-stay-in-their-frames |
| [module-pages](module-pages.md) | What a module's pages are made of: table views with their forms, row actions and search, record pages, realtime updates and uploads. The playground's Users table (`/table-view/table-view-users`, data API `/api/user`) stands for every table view. | table-create-record, form-required-fields, table-search-empty, table-edit-record, table-delete-record, realtime-row-reaches-other-tab, record-not-found |
| [modules-store](modules-store.md) | The installed modules page (`/modules`) and the module store (`/modules/store`, API `/dms/store/*`). Outside development the store is read-only: it lists the catalog but installs nothing. | installed-modules-open, modules-search-empty, store-read-only-outside-dev, store-open-in-dev, store-listing-owners-only |
| [onboarding](onboarding.md) | The first-run wizard at `/onboarding` creates the platform owner on an empty database; `GET /api/onboarding/informations` tells the frontend whether to show it, and `POST /api/onboarding/register` is what it calls. | wizard-creates-admin, wizard-refuses-weak-password, wizard-reads-the-setup-token-from-the-address |
| [settings-account](settings-account.md) | The signed-in person's own pages under Settings > Account, plus the Settings overview. Pages: `/settings` (overview), `/settings/user/profile`, `/settings/user/region` (Language & region), `/settings/user/security`, `/settings/user/notifications`, `/settings/user/appearance` and `/settings/user/shortcuts`. The page actions are under `/dms/pages/settings/user/<page>` (for example `security/password`, `security/sessions`, `region/preferences`, `notifications/preferences`). | profile-name-persists, profile-name-required, change-password-signs-out-other-devices, change-password-errors, change-email-confirms-with-code, change-email-errors, language-region-persists, time-format-persists, appearance-persists, notification-preferences-persist, notification-inbox-actions, sessions-sign-out, two-factor-email-enroll, export-my-data, delete-account-last-owner-refused, delete-account-member, settings-overview-and-search, shortcuts-layout-and-search |
| [settings-members](settings-members.md) | The people of the workspace and how they join: Settings > Workspace > Members lists them, Invite members sends invitation emails, Member invitations lists what is pending, and a link `/auth/signup?token=` turns an invitation into an account. The pages are `/settings/workspace/members` and `/settings/workspace/invites`; the data is `/api/tables/members` and `/api/tables/admin-invites`, and the page actions are under `/dms/pages/settings/workspace/members`. | invite-accept-lists-member, invite-validation-errors, invite-revoke-refuses-link, invite-resend-replaces-link, invite-edit-changes-roles, members-search-empty-state, remove-member-shows-impact, removed-member-lands-on-a-page, remove-last-owner-refused, make-owner-and-back, change-member-roles |
| [settings-roles](settings-roles.md) | What each role can see and do, and who holds it. Settings > Workspace > Roles is a list of roles beside an editor with the permission tree; the Owner entry is built in and locked. The page is `/settings/workspace/roles`, its actions are under `/dms/pages/settings/workspace/roles` (`create`, `:id`, `:id/duplicate`, `overview`, `editor-tree`, `preview`), and the stored roles are at `/api/tables/roles`. | roles-empty-state, create-role-persists, role-validation-errors, role-search-no-match, role-assigned-through-invitation, role-edit-changes-access, owner-only-page-not-grantable, role-preview-opens-tab, role-duplicate, role-delete-unused, role-delete-in-use-moves-members, role-editor-grants-only-held |
| [shell](shell.md) | The dashboard around every page: the sidebar and breadcrumb, the command palette, favorites, the notification bell and the error pages. It also owns the frontend server, the backend-to-frontend handshake and the notification and HTML render services the other features use. | sidebar-navigation, command-palette-navigates, command-palette-no-match, favorites-persist, email-renders-with-dms-layout, sign-in-notification, unknown-page-404, toast-burst-stays-stacked |
| [smoke](smoke.md) | The fixed journey every verdict runs, whatever the diff touches: a fresh platform onboards its administrator, the administrator signs in through the form, invites a member from Settings > Members, and the invitation is still there after a reload. | smoke |
| [table-view-saved-views](table-view-saved-views.md) | The views strip of a table view: named and saved views, and what the strip says as the user's filters, search and sort change the table the open view gave. The playground's *Views & grouped display* page (`/table-view/table-view-views`) stands for every table view. | table-view-strip-follows-filter-changes, table-view-hidden-column-survives-reload |
| [tenancy](tenancy.md) | Which workspace a request is bound to, who may enter it, and the tenant access gate. The playground runs one workspace, `default`, and demonstrates the gate on `/tenancy`. | suspended-workspace-gate, tenant-routes-refuse-visitors |

The smoke journey (onboard → login → invite a member → reload) runs on every verdict.

A flow that needs no `dms-control` journey can be a Playwright spec, `e2e/<feature>-<flow>.spec.ts`, run with `pnpm e2e <file>`. Its feature file describes it under Sub-features as `Spec e2e/<file>`; `dms-control map` reads journeys only and does not list specs.
