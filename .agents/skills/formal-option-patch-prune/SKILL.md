# Formal check: the binding prune after an option patch

`ConfigurePage`, `ConfigureBlock` and the page-draft save replace the value of an option in the author's page file (`displayName: "Board"` becomes `displayName: "Shop board"`). The old value may have read bindings the author wrote above the page: a constant, an enum, a class, a merged interface, an overloaded function, a name destructured from an object or an array. Once the value is gone, those bindings are unused, and a project compiled with `noUnusedLocals` refuses the save with `typecheck_failed`. So `applyPatch` records which locals the file reads before it writes, then drops each one that nothing reads after, and whatever only that local read (`pruningOrphans`, `local-bindings.ts`). A binding the author left unused before the patch is theirs and stays; a binding something else still reads stays.

Four pull requests each closed a gap in this prune, each found by the next one (dms#977, dms#990, dms#1001, dms#1004). Tests list the forms by hand (`option-patch-binding-forms.test.ts`), and no journey patches an option.

This check runs the real `applyPatch` of the engine, with no model of it, on modules generated by fast-check, and compares the result with the answer a plain graph of reads gives.

- `module-model.cts` builds a module from a recipe. It holds the reads as a graph: which names each binding reads, which the old option value reads, which the exports and the option's other members read. `survivors` computes the names the prune must leave from that graph alone, by the rule above.
- `properties.cts` draws recipes, runs `applyPatch` on an in-memory TypeScript project (ts-morph, the version the engine uses) and states the rules.
- `check.mjs` builds the two interface packages when their `dist` is missing, runs `properties.cts` with `tsx` and exits with its code. The runner shared with other fast-check targets is `.agents/formal/run-properties.cts`.

## Run it

From the repository root, with Node 24 and `pnpm install` done:

```sh
node .agents/skills/formal-option-patch-prune/check.mjs            # 300 modules for each rule
node .agents/skills/formal-option-patch-prune/check.mjs --full     # 5,000 modules for each rule
node .agents/skills/formal-option-patch-prune/check.mjs --verbose  # also print each finding's counterexample
node .agents/skills/formal-option-patch-prune/check.mjs --seed 7   # another run, same rules
```

A run starts from one fixed seed, so it reproduces. The CI configuration takes about 6 s and `--full` about 70 s, plus about 6 s the first time, when the script builds `packages/interface-dms` and `packages/interface-dms-builder` (`pnpm run checks:prepare`). It needs no database and no Java.

- Exit 0 means every rule that held still holds, and each finding still breaks.
- Exit 1 means a rule changed. `BROKEN` names a rule that held and now breaks, with its shrunk counterexample on the next line. `HOLDS` names a finding that no longer breaks.
- Exit 2 means the check could not run, or the arguments were wrong.

The lines that name a changed rule match `^(?:BROKEN|HOLDS) +(\w+)`. A rule that still holds prints as lowercase `holds`, and a recorded finding that still breaks prints as `finding`.

## When to run it

Run `--full` when a change touches a file in the coverage record below, or this folder. A changed rule exits 1. Explain it in the reply. CI runs the CI configuration on every push.

## The module and the patch

A recipe draws up to nine bindings from these kinds, each reading up to two earlier ones:

| Kind | Written as | Read in a value as |
| --- | --- | --- |
| `const` | `const c0 = "c0" + c1;` | `c0` |
| `enum` | `enum E0 { A = "A" }` | `E0.A` |
| `class` | `class K0 { static v = "K0" + c1; }` | `K0.v` |
| `merged` | two `interface S0` declarations | `({ row: "r", col: 1 } satisfies S0).row` |
| `overload` | two signatures and an implementation of `f0` | `f0("x")` |
| `object` | `const { d0x0, d0x1 } = { d0x0: "…" + c1, d0x1: "…" };` | `d0x0` |
| `arrayOfConst` | `const l0 = [...]; const [d0y0, d0y1] = l0;` | `d0y0` |
| `typedObject` | an interface, a value typed by it, `const { d0t0, d0t1 } = t0;` | `d0t0` |
| `arrayLiteral` | `const [d0z0, d0z1] = ["…" + c1, "…"];` | `d0z0` |

Then it draws the readers: `page.displayName` reads up to three names, or is the shorthand `displayName,` over a constant of that name; `page.title` reads up to two names and keeps reading them; `export const keep` reads up to three. It also draws two decoys: exported classes and interfaces whose members are spelled like each local (a member is not a read), and a function in the old value whose parameter is spelled like the first constant (a parameter is not a read). Each module is `export const page = { id, displayName, title }` below the bindings, and the patch is `applyPatch(page, { displayName: "Shop board" }, false, ctx)`, which is what `ConfigurePage` calls.

## The rules

| Rule | Plain sentence | Harm when it breaks | On main |
| --- | --- | --- | --- |
| `PatchTypechecksUnderNoUnusedLocals` | A module that typechecks under `noUnusedLocals` before the patch typechecks after it (no unused local, no missing name). | The save is refused with `typecheck_failed` for a binding the author never touches. | holds |
| `PatchRemovesExactlyTheOrphans` | The bindings left are those that something other than the old value reads, plus those that nothing read before: the author's. | A binding something reads is deleted and the file does not compile, or an unused one stays and the project refuses it. | holds |
| `PatchChangesNoOtherDeclaration` | Every statement that is not removed is written as before (a destructuring that loses a name loses it and its literal member only), and the option holds the new value. | The patch rewrites code the editor never touched. | holds |
| `PatchPrunesOrphanedArrayLiteralNames` | The first rule, on modules whose only destructurings are array patterns over a literal. | The save is refused for a name only the old value read. | finding F1 |

The first rule holds a module's unused locals out (a reader is added for each), the other two keep them. The text of a statement is compared with its whitespace folded and the commas that end an array pattern dropped, since `[a, ]` and `[a]` bind the same names.

## Findings on main

- **F1, a name of an array literal destructuring that only the old value read stays (`PatchPrunesOrphanedArrayLiteralNames`).** `isPrunableSingly` (local-bindings.ts:102) refuses to take one name out of a destructuring whose initializer is an array literal, since removing an element of the literal would shift the others. The name stays, unused, and a project with `noUnusedLocals` refuses the save. The shortest counterexample: `const [board, other] = ["Board", "Other"]; export const kept = other;` and a page whose `displayName` is `board`. Replayed on the real code with the integration harness of `packages/dms/TESTING.md` (a scratch test in the style of `option-patch-binding-forms.test.ts`, with `noUnusedLocals: true`): `ConfigurePage(PAGE, { displayName: "Shop board" })` answers `typecheck_failed` with `'board' is declared but its value is never read.`. The same destructuring over a constant (`const [board, other] = labels;`) is pruned, and `const { board, other } = { … }` is too. The fix is to leave a hole (`const [, other] = ["Board", "Other"];`), which keeps every position; it flips this finding to `HOLDS`: take the rule off `FINDINGS` in `properties.cts`, and move its row to the rules that hold.

## Real bug or modeling error

A counterexample is a recipe, printed as JSON. Rebuild its module with `buildModule` in `module-model.cts` (its `render` gives the text before and after), and replay the shortest one on the real code: write the module's statements above a page whose option reads the names, in a fixture with `noUnusedLocals: true`, as `option-patch-binding-forms.test.ts` does, and call `ConfigurePage`. A failure there is a real finding. A rule is wrong, not the code, when the generated module itself is rejected by TypeScript (the first rule throws `the generated module does not typecheck` then), or when the expected text of `render` does not match what a correct prune writes, for example a statement whose formatting `render` does not know.

## Changing the check

- For an intended change of the prune, edit the generators or `survivors` only where they no longer describe what the prune should do, and update the tables above. Never weaken a rule to make the check pass.
- A fixed finding leaves `FINDINGS` in `properties.cts` and keeps its row. A new finding goes into `FINDINGS` and into this file with its replay.
- A new binding form goes into `BINDING_KINDS` and `BUILDERS` of `module-model.cts`, with the text that writes it, how a value reads it, and which names its declaration reads.
- After you confirm that the check describes the code at a newer commit, move the sync commit forward. Do it only then.

## Scope and what is left out

A pass covers the modules the generators draw: at most nine bindings of the kinds above, each reading up to two earlier ones, with a patch that replaces `displayName` by a string. It is a sample of the space, not a proof, so run it with other seeds when a change is risky.

The check leaves out:

- imports. `pruneUnusedImports` runs, but no module imports anything, so named, default and namespace imports are covered by `page-option-shorthand.test.ts` only.
- the callers: `ConfigureBlock` (a patch of the options and the child metadata inside one `pruningOrphans`), the page-draft save and the category patch. Each calls the same `applyPatch` or `pruningOrphans`.
- options written as code the scanner cannot read, a patch that sets the value the file already reads (`optionsPatch` leaves it as written), a replacement value that reads bindings itself, and a patch that clears an option.
- a binding that the file exports, which is never pruned, and the page's own decorator: the module holds `export const page = { … }` in place of `@RegisterPage({ … })`, since `applyPatch` takes the object literal.
